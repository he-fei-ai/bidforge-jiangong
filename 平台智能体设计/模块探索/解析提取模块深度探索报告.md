## 1. 模块定位与边界

### 1.1 它做什么

解析提取模块的**唯一职责**是：把用户本地的任意受支持文档（Word / PDF / Excel / Markdown / 图片）转换成 **Markdown 文本**，交给下游的 AI 环节消费。

页面文案对此有明确定义（`DocumentAnalysisPage.tsx:255`）：

> 「当前步骤只负责把招标文件解析成 Markdown。下一步再基于这里的 Markdown 内容进行 AI 标书理解。」

**这是纯机械转换，不调用任何大模型**。除 MinerU 云端解析外，全部在本机完成。

### 1.2 它不做什么

| 容易被误认为属于本模块 | 实际归属 |
|---|---|
| 招标文件「解析项」提取（18 项、必选 6 项） | STEP 02 招标文件解析（`bidAnalysisTask.cjs`） |
| 目录生成 | STEP 03（`outlineGenerationTaskV2.cjs`） |
| 全局事实提取 | STEP 04（`globalFactsTaskV2.cjs`） |
| 正文生成 | STEP 05（`contentGenerationTask.cjs`） |
| Word / Excel 导出 | 导出模块（`exportService.cjs`） |
| 标书查重的元数据/指纹比对 | 查重模块（`duplicateCheckService.cjs`，**但它复用本模块做正文提取**） |

### 1.3 核心文件

| 文件 | 行数 | 角色 |
|---|---|---|
| `client/electron/services/fileService.cjs` | 801 | 模块主入口：provider 决策、MinerU 云端链路、图片资产化、业务导入入口 |
| `client/electron/services/doc2markdown/convert.mjs` | 1633 | 纯本地转换引擎（ESM），5 种格式分派 + 旧版 Word 三级后端回退 |
| `client/electron/services/documentParseErrors.cjs` | 49 | 错误归一：把 `office_backend_missing` 翻译成面向用户的可执行提示 |

`doc2markdown/` 目录下**只有 `convert.mjs` 一个文件**（无 index、无子模块、无测试）。

### 1.4 一个结构性事实：ESM 引擎挂在 CJS 主进程上

Electron Main 全部是 CommonJS（`*.cjs`），而转换引擎是 `.mjs`（ESM）。两者靠**动态 `import()` 桥接**：

```js
// fileService.cjs:120
const { convertPathToMarkdown } = await import('./doc2markdown/convert.mjs');
```

同样的手法在 `fileService.cjs:44`（`withLegacyWordDocxFile`）和 `duplicateCheckService.cjs:763`（用 `pathToFileURL` 构造绝对 URL 后再 `import`）各出现一次。

**这意味着**：`convert.mjs` 及其全部依赖（mammoth / cheerio / turndown / pdf-parse / pdfjs-dist / xlsx / chardet / iconv-lite）只有在**第一次真正解析文件时**才会被加载。冷启动不付出这部分成本，但首次上传文件会有一次明显的模块加载延迟。

## 2. 三种解析 Provider

### 2.1 定义

`fileService.cjs:10-14` 定义了三种 provider 及其中文标签（Renderer 侧 `DocumentAnalysisPage.tsx:8-12` 与 `SettingsPage.tsx:555-558` 各有一份**完全相同的副本**）：

| provider | 中文标签 | 是否需要 Token | 实现位置 |
|---|---|---|---|
| `local` | 本地解析 | 否 | `convert.mjs`（本机） |
| `mineru-accurate-api` | MinerU 精准解析 API | **是** | `fileService.cjs:203` → mineru.net v4 |
| `mineru-agent-api` | MinerU-Agent 轻量解析 API | 否（IP 限频） | `fileService.cjs:140` → mineru.net v1 |

默认值：`local`（`configStore.cjs:289-292`，`normalizeComponentsConfig` 也会兜底回 `local`）。

### 2.2 支持格式矩阵

代码中的三份后缀集合（`fileService.cjs:16-23`）：

```js
localSupportedExtensions        = .txt .md .markdown .docx .pdf .doc .wps .xls .xlsx
mineruAgentSupportedExtensions  = .pdf .doc .docx .ppt .pptx .png .jpg .jpeg .jp2 .webp .gif .bmp
mineruAccurateSupportedExtensions = 同上 + .html
```

对照表：

| 格式 | local | MinerU-Agent | MinerU-精准 | 说明 |
|---|---|---|---|---|
| `.txt` | ✅ | ✖ | ✖ | 仅本地，直接按 UTF-8 读取 |
| `.md` / `.markdown` | ✅ | ✖ | ✖ | 仅本地 |
| `.docx` | ✅ | ✅ | ✅ | mammoth 本地 / 云端 |
| `.doc` / `.wps` | ✅ | ✅ | ✅ | 本地需 Office 转换组件 |
| `.pdf` | ✅ | ✅ | ✅ | 本地双路表格识别 |
| `.xls` / `.xlsx` | ✅ | ✖ | ✖ | **云端 provider 下自动回退本地** |
| `.ppt` / `.pptx` | ✖ | ✅ | ✅ | 仅云端 |
| 图片（png/jpg/jpeg/jp2/webp/gif/bmp） | ✖ | ✅ | ✅ | 仅云端（走 OCR） |
| `.html` | ✖ | ✖ | ✅ | 仅精准解析 |

### 2.3 Provider 决策与回退逻辑（`resolveFileParser`，`:70`）

```js
function resolveFileParser(config, filePath) {
  const requestedProvider = config.components?.file_parser?.provider || 'local';
  const ext = path.extname(filePath).toLowerCase();
  const requestedSupported = getSupportedExtensions(requestedProvider).has(ext);
  if (requestedSupported) {
    return { provider: requestedProvider, requestedProvider, ext, supported: true, fallbackToLocal: false };
  }
  if (requestedProvider !== 'local' && localSupportedExtensions.has(ext)) {
    return { provider: 'local', requestedProvider, ext, supported: true, fallbackToLocal: true };
  }
  return { provider: requestedProvider, requestedProvider, ext, supported: false, fallbackToLocal: false };
}
```

三种结局：

1. **请求的 provider 支持该格式** → 直接用，`fallbackToLocal: false`
2. **请求的是云端、云端不支持、但本地支持** → **静默降级到本地**，`fallbackToLocal: true`（典型场景：选了 MinerU 精准解析，然后上传 `.xlsx`）
3. **谁都不支持** → `supported: false`，抛 `当前{标签}不支持该文件格式`

注意第 2 条：**降级是静默的**，用户只会看到提示语里多一句「当前格式已自动使用本地解析」。

### 2.4 文件选择器可选范围（`getSelectableExtensions`，`:63`）

```js
function getSelectableExtensions(provider) {
  if (provider === 'local') return localSupportedExtensions;
  return new Set([...getSupportedExtensions(provider), ...localSupportedExtensions]);
}
```

云端 provider 下，文件选择对话框同时列出云端 + 本地的全部后缀——这正是为了配合 §2.3 的自动降级。

**设置页文案与此一致**（`SettingsPage.tsx:576-600`）：
- 精准解析：「支持格式 pdf、doc、docx、ppt、pptx、图片、html；**xls/xlsx 自动本地解析**」
- 轻量解析：「支持格式 pdf、doc、docx、ppt、pptx、图片；**xls/xlsx 自动本地解析**」

### 3.2 `parseDocumentWithConfig` 主入口（`:521`）

这是整个模块的**唯一收敛点**，三个业务入口、知识库、查重全部经过它：

```js
async function parseDocumentWithConfig(app, filePath, config, options = {}) {
  const startedAt = Date.now();
  const parser = resolveFileParser(config, filePath);
  const developerLogger = createDeveloperLogger({ app, config, moduleName: 'file-parser', ... });
  developerLogger.write('file.parse.started', { file: await summarizeFileForLog(filePath), parser: ... });

  if (!parser.supported) { /* 写 file.parse.error 并抛错 */ }

  const provider = parser.provider;
  const preserveImages = options.preserveImages === true;
  const assets = preserveImages ? createAssetContext(app, options.assetScope || 'documents') : null;
  const parseOptions = { preserveImages, assets, imageResolver: createImageResolver(assets) };

  let markdown = '';
  try {
    if (provider === 'mineru-agent-api') {
      markdown = await parseWithMineruAgent(filePath, parseOptions);
    } else if (provider === 'mineru-accurate-api') {
      markdown = await parseWithMineruAccurate(filePath, config.components?.file_parser?.mineru_token || '', parseOptions);
    } else {
      markdown = await parseLocalDocument(filePath, parseOptions);
      markdown = preserveImages
        ? await rewriteMarkdownImages(markdown, assets, { localBaseDir: path.dirname(filePath) })
        : stripMarkdownImages(markdown);
    }
  } catch (error) {
    await deleteImportedImageAssets(assets).catch(() => undefined);
    developerLogger.write('file.parse.error', { duration_ms, parser, asset_count, error: compactLogError(error) });
    throw normalizeDocumentParseError(error, filePath);
  }

  const result = preserveImages ? markdown : stripMarkdownImages(markdown);
  developerLogger.write('file.parse.completed', { duration_ms, parser, asset_count, markdown_metrics: textMetrics(result) });
  return result;
}
```

三个可观测要点：

1. **`preserveImages` 决定一切**：为 `false` 时 `assets` 为 `null`，`imageResolver` 为 `null`，图片在转换阶段就被丢弃。
2. **图片清理只在失败路径**：成功时 `assets` 目录保留；失败时 `deleteImportedImageAssets` 递归删除。
3. **错误统一归一**：所有异常都过 `normalizeDocumentParseError(error, filePath)`。

### 3.3 `preserveImages` 的真实分布（重要）

| 调用方 | `preserveImages` | `assetScope` |
|---|---|---|
| `fileService.cjs:626` 技术方案-招标文件 | **false** | `technical-plan-{sha1(path)前12位}` |
| `fileService.cjs:716` 废标项检查 | **false** | `rejection-check-{role}-{sha1(path)前12位}` |
| `knowledgeBaseService.cjs:1219` 知识库 | **false** | `knowledge-{documentId}` |
| `duplicateCheckService.cjs:2320` 查重正文提取 | **true** | `duplicate-check-content-{fileId}` |

**结论：图片资产化管线并非死代码**，它被查重模块的「正文内容提取」使用。技术方案 / 废标项 / 知识库三个场景都会**主动剥离 Markdown 图片**。

## 4. 格式识别与分派（`convert.mjs`）

### 4.1 入口分派（`:100`）

```js
export async function convertPathToMarkdown(inputPath, options = {}) {
  const resolvedPath = path.resolve(inputPath);
  const includeImages = Boolean(options.includeImages);
  const imageResolver = typeof options.imageResolver === 'function' ? options.imageResolver : null;
  const format = await detectFileFormat(resolvedPath);

  if (format === 'markdown')    return convertMarkdownFile(resolvedPath, includeImages, imageResolver);
  if (format === 'docx')        return convertDocxFile(resolvedPath, includeImages, imageResolver);
  if (format === 'pdf')         return convertPdfFile(resolvedPath, includeImages, imageResolver);
  if (format === 'legacy_word') return convertLegacyWordFile(resolvedPath, includeImages, imageResolver);
  if (format === 'spreadsheet') return convertSpreadsheetFile(resolvedPath);

  throw new ConversionError('unsupported_format', '不支持的文件格式', { inputPath: resolvedPath, format });
}
```

### 4.2 魔数嗅探（`detectFileFormat`，`:128`）

**判定顺序严格固定**：先读文件头 8 字节，再按「魔数 → 后缀」的优先级依次判断。

```js
const PDF_HEADER           = Buffer.from('%PDF-');
const ZIP_LOCAL_FILE_HEADER = Buffer.from([0x50, 0x4b, 0x03, 0x04]);           // PK\x03\x04
const OLE_COMPOUND_HEADER   = Buffer.from([0xd0, 0xcf, 0x11, 0xe0, 0xa1, 0xb1, 0x1a, 0xe1]);
```

| 顺序 | 条件 | 返回 |
|---|---|---|
| 1 | 后缀 ∈ `.xls` `.xlsx` | `spreadsheet` |
| 2 | 头 = `%PDF-` | `pdf` |
| 3 | 头 = `PK\x03\x04` | `docx` |
| 4 | 头 = OLE 复合文档 | `legacy_word` |
| 5 | 后缀 ∈ `.md` `.markdown` | `markdown` |
| 6 | 后缀 = `.pdf` | `pdf` |
| 7 | 后缀 = `.docx` | `docx` |
| 8 | 后缀 ∈ `.doc` `.wps` | `legacy_word` |
| 9 | 其他 | `unknown` |

**设计意图**：让「后缀撒谎」的文件仍然能被正确识别——把 `.doc` 改名成 `.docx`（反之亦然）都能走对分支。

**注意顺序 1 的例外**：Excel 后缀**优先于魔数**。所以一个后缀是 `.xlsx` 但内容是 PDF 的文件，会被送去 `xlsx.readFile` 并失败，而不是被识别成 PDF。这是一个刻意的取舍（`.xls` 是 OLE 容器，与 `.doc` 头相同，若按魔数判断会误判成 Word）。

**后缀与魔数矛盾时的实际行为**：
- `.docx` 但头是 OLE → 顺序 4 命中 → `legacy_word`（正确）
- `.doc` 但头是 ZIP → 顺序 3 命中 → `docx`（正确）
- `.wps` 但头是 OLE → `legacy_word`

### 4.3 `.txt` 的特殊处理（不走 `convert.mjs`）

`fileService.cjs:113` 的 `parseLocalDocument` 在进入转换引擎前先拦截 `.txt`：

```js
async function parseLocalDocument(filePath, options = {}) {
  const ext = path.extname(filePath).toLowerCase();
  if (ext === '.txt') {
    return fs.readFile(filePath, 'utf-8');   // ← 直接读，不走 convert.mjs
  }
  const { convertPathToMarkdown } = await import('./doc2markdown/convert.mjs');
  return convertPathToMarkdown(filePath, {
    includeImages: options.preserveImages,
    imageResolver: options.imageResolver,
  });
}
```

这解释了为什么 `detectFileFormat` 里没有 `.txt` 分支——`.txt` 根本到不了那里。

## 5. 本地解析各格式实现

### 5.1 Markdown / 纯文本（`convertMarkdownFile`，`:176`）

```js
const raw = await readFile(inputPath);
const detected = chardet.detect(raw) || 'UTF-8';
let text = iconv.decode(raw, normalizeEncoding(detected));
text = text.replace(/^\uFEFF/, '');          // 去 BOM
text = normalizeNewlinesOnly(text);          // CRLF / CR → LF
if (includeImages) text = await inlineLocalMarkdownImages(text, path.dirname(inputPath), imageResolver);
else               text = stripMarkdownImages(text);
return ensureTrailingNewline(text.trimEnd());
```

**编码嗅探链路**：`chardet.detect()` 猜测编码 → `normalizeEncoding()` 归一 → `iconv-lite` 解码。

`normalizeEncoding`（`:467`）只做两件事：

```js
'utf-8' | 'utf8'                      → 'utf8'
'gb18030' | 'gbk' | 'gb2312'          → 'gb18030'
```

**注意**：`gbk` / `gb2312` 被**统一升级为 `gb18030`**，这是超集，能覆盖绝大多数简体中文文档，属于正确做法。

**本地图片内联**（`inlineLocalMarkdownImages`，`:1543`）：仅当 `includeImages` 为真时，把 Markdown 中的相对路径图片读出来转成 `yibiao-asset://` 或 `data:` URI。有**路径穿越防护**（`resolveLocalPath`，`:1585`）：

```js
if (path.isAbsolute(decodedTarget)) return null;         // 拒绝绝对路径
const relative = path.relative(resolvedBaseDir, candidate);
if (relative && (relative.startsWith('..') || path.isAbsolute(relative))) return null;  // 拒绝越界
return existsSync(candidate) ? candidate : null;
```

### 5.2 DOCX（`convertDocxFile`，`:478`）—— 三段式管线

```js
const result = await mammoth.convertToHtml(
  { path: inputPath },
  { convertImage: buildMammothImageConverter(includeImages, imageResolver) }
);
const html = cleanHtml(result.value, includeImages);
const { html: htmlWithoutTables, placeholders } = preserveTables(html);
let markdown = htmlToMarkdown(htmlWithoutTables);
markdown = restoreTables(markdown, placeholders);
return normalizeGeneratedMarkdown(includeImages ? markdown : stripMarkdownImages(markdown));
```

**第 1 段 — mammoth 转 HTML**（`buildMammothImageConverter`，`:490`）：
- `includeImages === false` → 返回 `{ src: '' }`，图片在源头就被清空
- 有 `imageResolver` → 读 buffer 交给 resolver 落盘，拿回 `yibiao-asset://` URL
- 无 resolver → 直接内联 `data:{contentType};base64,{base64}`

**第 2 段 — cheerio 清洗**（`cleanHtml`，`:507`）：
```js
$('a').each(...)  // 空锚点（无文本且无 img）直接删除；href 以 # 开头的锚点用内容替换自身
$('img').each(...) // src 为空的 img 删除
if (!includeImages) $('img').remove();
```

**第 3 段 — 表格占位 + turndown 转 Markdown**：
- `preserveTables`（`:546`）：把每个 `<table>` 抽出 HTML，原地替换为 `TABLEPLACEHOLDER0001`（4 位零填充）
- `htmlToMarkdown`（`:536`）：turndown + `gfm` 插件，配置 `bulletListMarker: '-'` / `codeBlockStyle: 'fenced'` / `headingStyle: 'atx'`
- `restoreTables`（`:557`）：把占位符换回 `\n\n{tableHtml}\n\n`

**为什么要绕这一圈**：turndown 对复杂表格（合并单元格、嵌套）转换质量不稳定，**保留原始 HTML 表格**能让下游 `MarkdownRenderer`（默认允许原始 HTML）渲染得更准确。这也是 `AGENTS.md` 里特别强调 `MarkdownRenderer` 默认允许原始 HTML 的原因之一。

### 5.3 PDF（`convertPdfFile`，`:565`）—— 双引擎并行 + 去重

```js
const buffer = await readFile(inputPath);
const parser = new PDFParse({ data: buffer });
try {
  const textResult      = await parser.getText({ parseHyperlinks: true });
  const tableResult     = await safePdfCall(() => parser.getTable());           // 引擎 A：pdf-parse
  const pdfJsTableResult= await safePdfCall(() => extractPdfJsTables(buffer));  // 引擎 B：pdfjs-dist 自研
  const imageResult     = includeImages ? await safePdfCall(() => parser.getImage()) : null;
  const markdown = await renderPdfMarkdown(textResult, tableResult, pdfJsTableResult, imageResult, includeImages, imageResolver);
  if (!hasInformativeText(markdown)) {
    throw new ConversionError('pdf_text_layer_missing', 'PDF 未检测到可选中文字层', { inputPath });
  }
  return normalizeGeneratedMarkdown(markdown);
} finally {
  await parser.destroy();
}
```

**`safePdfCall`（`:588`）** 是关键设计：三个表格/图片调用各自 `try/catch` 返回 `null`。**任一子引擎失败不影响整体解析**，只要文字层能提取出来就返回结果。

#### 引擎 A：pdf-parse `getTable()`
直接调用库能力，结果挂在 `tableResult.pages[i].tables`。

#### 引擎 B：pdfjs-dist 自研表格识别（`:596`）
完整实现了一条**基于矢量线条的表格重建流水线**：

1. **`extractPdfJsTables(buffer)`**（`:596`）：`getDocument({ disableWorker: true })` 逐页取 `getTextContent()` + `getOperatorList()`
2. **`normalizePdfJsTextItems`**（`:621`）：把文本项转成 `{ text, x, y, width, height, centerX, centerY }`，按 `y` 降序、`x` 升序排序，并用 `PDF_TEXT_DUPLICATE_TOLERANCE = 1` 去重（同文本同坐标的重复绘制）
3. **`extractPdfJsRectangles`**（`:658`）：遍历操作符列表，维护 CTM 矩阵栈（`save` / `restore` / `transform`），在 `constructPath` 时把路径点变换到设备坐标
4. **`multiplyPdfMatrix` / `transformPdfPoint`**（`:681` / `:692`）：标准 2D 仿射变换
5. **`extractPdfJsPathRectangles`**（`:699`）：把路径点集压成包围盒（只认 `moveTo(0)` / `lineTo(1)`，`closePath(3)` 跳过，其他操作符直接 `break`）
6. **`buildPdfJsTables`**（`:737`）：按几何特征分类线条
   - 水平线：`width >= PDF_GRID_MIN_LINE_LENGTH(12)` 且 `height <= PDF_POINT_TOLERANCE(2.5)`
   - 垂直线：`height >= 12` 且 `width <= 2.5`
7. **`buildPdfJsLineComponents`**（`:765`）：**并查集**把所有相交的横竖线聚成连通分量（`pdfJsLinesIntersect`，`:797`）
8. **`buildPdfJsTableFromComponent`**（`:819`）：对连通分量
   - `clusterPdfCoordinates`（`:860`）把相近坐标（≤2.5pt）合并成网格线坐标
   - 要求 `xCoordinates.length >= 2 && yCoordinates.length >= 2`
   - 要求 `宽 >= PDF_GRID_MIN_WIDTH(40)` 且 `高 >= PDF_GRID_MIN_HEIGHT(12)`
   - 逐格子筛文本项（按 `centerX`/`centerY` 落在格内 ±2.5pt）
   - 要求非空格子数 `>= 2`
9. **`renderPdfJsCellText`**（`:874`）：格内文本按 `PDF_TEXT_LINE_TOLERANCE = 3` 分行、行内按 x 拼接、多行用 `<br>` 连接、`|` 转义为 `\|`

**正文去重**（`removePdfTableDuplicateText`，`:951`）—— 这是本模块**最精巧的一段算法**。目的：PDF 文字层往往把表格内容又当成普通文本重复输出一遍，导致 Markdown 里同一张表出现两次。

逐行判断该行是否已被表格覆盖：

```js
function isPdfLineCoveredByTables(lineProbe, tableProbe) {
  if (lineProbe.length <= 2) return tableProbe.includes(lineProbe);   // 极短行：要求完全包含
  if (tableProbe.includes(lineProbe)) return true;                    // 完全包含即覆盖
  if (lineProbe.length < 8) return false;                             // 8 字以下不做分块
  const chunkSize = Math.min(12, Math.max(6, Math.floor(lineProbe.length / 2)));
  let covered = 0, total = 0;
  for (let index = 0; index < lineProbe.length; index += chunkSize) {
    const chunk = lineProbe.slice(index, index + chunkSize);
    if (chunk.length < 4) continue;
    total += 1;
    if (tableProbe.includes(chunk)) covered += 1;
  }
  return total > 0 && covered / total >= 0.75;                        // 75% 分块命中即判覆盖
}
```

还有一层**重复探测**：若直接判定未覆盖，再对行做 `collapseRepeatedPdfProbe`（`:1477`，即 `collapseRepeatedPdfChunks(text, 1, false)`）压缩连续重复片段后**再判一次**。这针对的是「同一段文字被 PDF 重复绘制两遍」的常见现象。

#### PDF 文本归一化

`normalizePdfPlainText`（`:1464`）：

`collapsePdfWhitespace`（`:1509`）：多空格压缩、**删掉中文字符之间的空格**、**删掉标点前的空格**（中英文标点各一套正则）。

`collapseRepeatedPdfText`（`:1471`）：`collapseRepeatedPdfChunks(text, 2, true)` + 两条正则
```js

/^([一二三四五六七八九十])\1(?=[.、．])/u                                     → '$1'   // 中文序号重复
```

`collapseRepeatedPdfChunks`（`:1481`）是一个**最长 4 轮的滑动窗口去重**：从 `minLength` 起逐长度扫描，发现相邻等长片段相同就删掉后半段并重新开始。`requireCjk` 参数控制是否要求片段含中文（用于避免误伤纯数字/英文）。

**结构**：

**单元格归一化**（`normalizeSpreadsheetCell`，`:284`）：去 NUL、按行压缩空白、**多行用 `<br>` 连接**、`|` 转义。

**日期格式化**（`formatSpreadsheetDate`，`:277`）：`YYYY-MM-DD`，若时分秒全为 0 则只输出日期。

1. `findSpreadsheetHeaderIndex`（`:368`）：扫描**前 20 行**，用「不同值个数」打分，取最高分；**分数需 ≥ 2**，否则认为没有表头（`-1`）
2. `findSpreadsheetHeaderStart`（`:382`）：从候选表头**向上最多再吃 2 行**（多行表头），条件是这些行的不同值数 ≥ 2 **且**非空格数 ≥ `max(3, ceil(表头列数 * 0.75))`
3. `buildSpreadsheetHeader`（`:421`）：多行表头**纵向拼接**为 `列A / 列B`（相邻相同值去重）
4. 无表头 → `buildGenericSpreadsheetHeader` 生成 `列1` `列2` …
5. 表头之前的内容 → 渲染为 `> 表格说明：{去重后的值用；连接}`

**分块渲染**（`renderSpreadsheetTables`，`:440`）：数据行每 `SPREADSHEET_TABLE_CHUNK_ROWS = 200` 行切一块，超过 1 块时插入 `### 表格分段 {i}/{n}` 标题并**重复表头**。这是为了避免超长表格撑爆下游 prompt / 渲染性能。

#### 统一回退骨架（`withLegacyWordDocxFile`，`:1064`）

```js
export async function withLegacyWordDocxFile(inputPath, callback) {
  const backends = await buildLegacyWordConversionBackends(inputPath);
  if (backends.length === 0) {
    throw new ConversionError('office_backend_missing', LIBREOFFICE_REQUIRED_MESSAGE, { inputPath, platform: process.platform });
  }
  const tempDir = await mkdtemp(path.join(os.tmpdir(), 'doc2md-node-'));
  const attempts = [];
  try {
    const legacyInput = path.join(tempDir, `${safeStem(inputPath)}${await getLegacyConversionSuffix(inputPath)}`);
    await copyFile(inputPath, legacyInput);                    // ← 先复制到临时目录
    for (const backend of backends) {
      await removeGeneratedDocxFiles(tempDir);                 // ← 每个后端前清理残留 docx
      const attempt = { backend: backend.label, type: backend.type };
      attempts.push(attempt);
      try {
        const docxPath = await backend.convert(legacyInput, tempDir);
        await assertGeneratedDocxFile(docxPath, backend.label, inputPath);
        attempt.success = true;
        return await callback(docxPath, tempDir);              // ← 成功后立即交回调用方
      } catch (error) {
        attempt.error = summarizeConversionError(error);
      }
    }
    throw createOfficeConversionFailedError(inputPath, attempts);
  } finally {
    await rm(tempDir, { recursive: true, force: true });       // ← 无条件清理临时目录
  }
}
```

**`getLegacyConversionSuffix`（`:1247`）有个精细处理**：
```js
const suffix = path.extname(inputPath).toLowerCase();

if (DOCX_SUFFIXES.has(suffix) && isOleCompoundHeader(header)) return '.doc';
return suffix || '.doc';
```
如果文件后缀是 `.docx` 但内容是 OLE（即实际是老 `.doc` 被改名），**复制到临时目录时会改回 `.doc` 后缀**——因为 Office COM 是按后缀选解析器的，后缀错了就打不开。

**`assertGeneratedDocxFile`（`:1206`）双重校验**：文件存在 **且** 头部是 `PK\x03\x04`。防的是「COM 报成功但产出的其实是空文件/HTML 错误页」这类情况。

**错误信息聚合**（`createOfficeConversionFailedError`，`:1222`）：

虽然技术方案链路用不到（`preserveImages: false`），但查重模块依赖它，且实现完整。

### 7.1 资产上下文（`createAssetContext`，`:340`）

```js
function createAssetContext(app, scope = 'documents') {
  if (!app?.getPath) return null;
  const safeScope = String(scope || 'documents').replace(/[^A-Za-z0-9._-]+/g, '_') || 'documents';
  const batchId = `${safeScope}-${Date.now()}-${crypto.randomUUID().slice(0, 8)}`;
  return {
    baseDir: path.join(getImportedImagesDir(app), batchId),
    urlPrefix: `yibiao-asset://imported-images/${encodeURIComponent(batchId)}`,
    index: 0,
  };
}
```

- 落盘位置：`userData/workspace/imported-images/{batchId}/`（`paths.cjs:123`）
- 访问协议：自定义 scheme `yibiao-asset://imported-images/{batchId}/{fileName}`
- `index` 自增，用于生成 `image-0001.png` 这样的顺序文件名

### 7.2 落盘（`saveImportedImage`，`:371`）

```js
const ext = imageExtensionFromMime(mime) || imageExtensionFromPath(sourceName) || '.png';
assets.index += 1;
const fileName = `image-${String(assets.index).padStart(4, '0')}${ext}`;
await fs.mkdir(assets.baseDir, { recursive: true });
await fs.writeFile(path.join(assets.baseDir, fileName), buffer);
return `${assets.urlPrefix}/${encodeURIComponent(fileName)}`;
```

**扩展名判定优先级**：MIME 类型 → 源文件名 → 兜底 `.png`。支持 jpg/png/gif/bmp/webp（`imageExtensionFromMime`，`:356`；`imageExtensionFromPath`，`:366` 会把 `.jpeg` 归一为 `.jpg`）。

### 7.3 图片来源解析（`resolveImageToAssetUrl`，`:435`）

按顺序尝试 5 类来源：

| 顺序 | 来源 | 条件 | 处理 |
|---|---|---|---|
| 1 | 已是资产 URL | `/^yibiao-asset:\/\//i` | 原样返回（幂等） |
| 2 | Data URL | `parseDataUrl` 匹配 `^data:([^;,]+);base64,(.+)$` | base64 解码落盘 |
| 3 | 远程 URL | `^https?://` 或提供 `context.baseUrl` | `loadRemoteImage` 下载（**10 秒超时**） |
| 4 | zip 内条目 | 提供 `context.zipEntries` | `findZipEntryImage` 查找 |
| 5 | 本地相对路径 | 提供 `context.localBaseDir` 且无协议前缀 | 读文件（**有路径穿越防护**） |

**远程图片防护**（`loadRemoteImage`，`:397`）：
```js
const controller = new AbortController();
const timeout = setTimeout(() => controller.abort(), remoteImageTimeoutMs);  // 10000ms
const response = await fetch(url, { signal: controller.signal });
if (!response.ok) return null;
const contentType = response.headers.get('content-type') || '';
if (contentType && !/^image\//i.test(contentType)) return null;   // 非图片直接丢弃
```

**zip 条目查找**（`findZipEntryImage`，`:411`）：先按「原路径」和「相对 markdown 所在目录的路径」两个候选精确匹配（统一小写、统一斜杠），失败再**按 basename 模糊匹配**。这覆盖了 zip 内目录层级与 Markdown 引用路径不一致的情况。

### 7.4 批量重写（`rewriteMarkdownImages`，`:490`）

```js
let result = await replaceMatchesAsync(String(markdown || ''), markdownImagePattern, async (match) => {
  const nextUrl = await resolveImageToAssetUrl(match.groups?.target || '', assets, context);
  const alt = match.groups?.alt || '';
  const title = match.groups?.title || '';
  return nextUrl ? `![${alt}](${nextUrl}${title})` : '';    // 解析失败 → 整段删除
});
result = await replaceMatchesAsync(result, htmlImageSrcPattern, async (match) => {
  const nextUrl = await resolveImageToAssetUrl(match.groups?.src || '', assets, context);
  return nextUrl ? `${match[1]}${nextUrl}${match[3]}` : '';
});
```

处理两种形态：Markdown `![alt](target)` 和 HTML `<img src="...">`。

**`replaceMatchesAsync`（`:505`）实现方式值得注意**：先 `matchAll` 收集全部匹配，再**逐段顺序重建字符串**（`parts.push(text.slice(lastIndex, index))` → `parts.push(await createReplacement(match))`）。这保证了**异步替换不会因为索引漂移而错位**——如果用 `String.replace` + 异步回调会很难保证顺序。

### 7.5 失败清理（`:559`）

```js

```
`deleteImportedImageAssets`（`:351`）递归删除 `assets.baseDir`。

**注意**：这只在**解析抛错**时触发。成功时资产目录会保留（供下游渲染使用）。查重模块另有 `deleteImportedImageBatches` 做整体清理。

### 8.1 归一函数（`documentParseErrors.cjs`）


### 8.2 二次包装（`fileService.cjs:127` `formatImportError`）

```js
function formatImportError(error, filePath) {
  const normalized = normalizeDocumentParseError(error, filePath);
  if (isLibreOfficeMissingError(normalized)) return normalized.message;   // ← 原文透出，不加前缀
  const rawMessage = formatDocumentParseError(normalized, filePath);
  if (/Can't find end of central directory|is this a zip file/i.test(rawMessage)) {
    return '文件解析失败：该文件不是有效的 DOCX 文档，请用 Word/WPS 另存为标准 DOCX 后重试';
  }
  return `文件解析失败：${rawMessage || '未知错误'}`;
}
```

两处特判：
1. **缺转换组件时不加「文件解析失败：」前缀** —— 因为那条消息本身就是完整可执行指引，加前缀会显得混乱
2. **ZIP 结构损坏时翻译成人话** —— mammoth 抛的 `Can't find end of central directory` / `is this a zip file` 对用户毫无意义，翻译成「不是有效的 DOCX，请另存为标准 DOCX」

### 8.3 Renderer 侧的组件缺失引导（`DocumentParseNoticeProvider.tsx`）

## 12. 风险点与「代码真实状态 ≠ 直觉」清单

### R1 · 三个业务入口的图片全部被剥离（设计如此，但容易误解）

`technical-plan` / `rejection-check` / `knowledge` 三处都显式传 `preserveImages: false`。虽然 `fileService.cjs` 里有完整的图片资产化管线（约 170 行），**技术方案用户永远看不到原文档里的图片**。

只有查重模块（`duplicateCheckService.cjs:2320`）传 `true`。

**影响**：如果未来希望技术方案正文生成时引用招标文件中的图片，需要改这三个调用点的 `preserveImages`，并同步考虑下游 Markdown 渲染与 Word 导出的图片处理。

### R2 · `stripMarkdownImages` 被重复执行

以本地 provider、`preserveImages: false` 为例，剥离动作发生**三次**：

1. `convert.mjs` 内部（`convertMarkdownFile` / `convertDocxFile` / `convertPdfFile` / `extractMarkdownFromZip` 各自调一次）
2. `parseDocumentWithConfig:556`（本地分支的 else 分支）
3. `parseDocumentWithConfig:568`（`const result = preserveImages ? markdown : stripMarkdownImages(markdown)`）

**是幂等的**（正则替换 + `\n{3,}` 压缩，第二次无变化），所以不产生 bug，但属于可清理的冗余。第 3 行是第 2 行的完全重复，**在本地 provider 分支下第 3 行纯属多余**。

### R3 · `result.fallbackToLocal` 永远为 `undefined`（真实缺陷）

`fileService.cjs` 的 `importTechnicalPlanDocument` / `importRejectionCheckDocument` 返回的是**逐文件的 `documents[].fallback_to_local`**，**没有顶层 `fallbackToLocal` 字段**。

但 `technicalPlanStore.cjs:2467` / `:2477` 却读顶层字段：

```js
// :2467
if (result.fallbackToLocal === true || mergedDocuments.some((item) => item.fallback_to_local)) {
  messageParts.push('当前格式已自动使用本地解析');
}
// :2477
fallbackToLocal: result.fallbackToLocal === true,     // ← 恒为 false
```

**后果**：
- `:2467` 的 OR 右侧挽救了用户可见提示，所以**用户不会感知到问题**
- `:2477` 传给 `saveTenderMarkdownAndState` 的 `fallbackToLocal` 恒为 `false`，导致 `:2629` 的兜底文案 `fallbackToLocal ? '文件解析完成，当前格式已自动使用本地解析' : '招标文件已导入'` 中**前者是死分支**（实际上 `message` 参数总是非空，兜底本来也不会走到）

**这是真实存在的字段名不一致缺陷**（snake_case 子项 vs camelCase 顶层），值得清理。

### R4 · `.txt` 不走编码嗅探，GBK 文本会乱码

`parseLocalDocument:116-118`：
```js
if (ext === '.txt') return fs.readFile(filePath, 'utf-8');
```

**硬编码 UTF-8**。而 `.md` 走 `convertMarkdownFile` 时是有 `chardet` + `iconv-lite` 完整链路的。

**后果**：GBK/GB18030 编码的中文 `.txt` 文件会解析成乱码，且**不会报错**（乱码字符串仍能通过 `hasInformativeText` 之类的检查——实际上 `.txt` 分支根本没做这个检查，直接返回）。

### R5 · `.txt` 内容不做有效性校验

`.txt` 分支直接 `return fs.readFile(...)`，**空文件会返回空字符串**，然后被 `importTechnicalPlanDocument:633` 的 `if (!fileContent)` 拦截并报「未提取到有效 Markdown 内容」。

但**全空白（只有空格/换行）的文件**会在 `.trim()` 后变成空串，同样被拦截——这一点是 OK 的。

### R6 · Excel 后缀优先于魔数

`detectFileFormat` 第一步就是 `if (SPREADSHEET_SUFFIXES.has(suffix)) return 'spreadsheet';`。所以**任何 `.xlsx` 后缀的文件都会送去 `xlsx.readFile`**，哪怕内容是 PDF。

**这是刻意取舍**：`.xls` 与 `.doc` 的 OLE 头完全相同（`D0 CF 11 E0...`），若按魔数判断会把 `.xls` 误判成 Word。代价是「后缀错误但内容正确的 Excel」会失败。

### R7 · 云端 provider 下的静默降级可能让用户困惑

用户选了「MinerU 精准解析 API」上传 `.xlsx`，实际走的是本地解析。提示语里有一句「当前格式已自动使用本地解析」，但**如果用户没注意到这句话**，会误以为 Excel 也走了云端。

设置页卡片里写了「xls/xlsx 自动本地解析」，但**上传页面（`DocumentAnalysisPage`）没有对应说明**。

### R8 · MinerU-Agent 的 `is_ocr: true` 是硬编码

```js
body: JSON.stringify({ file_name: fileName, language: 'ch', enable_table: true, is_ocr: true, enable_formula: true })
```

`is_ocr: true` 强制 OCR，**不可配置**。对于本来就是文字层的 PDF，OCR 会显著增加云端耗时。设置页把 MinerU-Agent 标为「解析质量：中」，与强制 OCR 有关。

### R9 · `remoteImageTimeoutMs = 10000` 对批量图片可能偏紧

查重模块 `preserveImages: true` 时，如果一份文档有几十张远程图片，每张最多等 10 秒。虽然并发（`Promise.all`）分摊了时间，但**单个慢图会直接丢弃**（`loadRemoteImage` 返回 `null` → `resolveImageToAssetUrl` 返回 `null` → 该图片整段被删除）。

**失败是静默的**，只写开发者日志。

### R10 · LibreOffice profile 目录泄漏风险

`runLibreOfficeConvert`（`:1391`）：
```js
const profileDir = await mkdtemp(path.join(os.tmpdir(), 'doc2md-lo-profile-'));
try { ... await runProcess(soffice, args, { timeoutMs: 180000 }); }
finally { await rm(profileDir, { recursive: true, force: true }); }
```

`finally` 保证了清理。但**如果 `runProcess` 超时被 `child.kill('SIGTERM')` 后 LibreOffice 仍有子进程持有 profile 目录**，Windows 上 `rm` 可能失败并抛出——这个异常会**覆盖掉原始的超时错误**，让用户看到文件占用错误而非超时错误。

### R11 · PowerShell 脚本每次转换都重新写盘

`runWindowsComOfficeConvert`（`:1180`）每次都 `writeFile(scriptPath, POWERSHELL_OFFICE_CONVERT_SCRIPT, 'utf8')`。内容是完全固定的常量。

**影响**：每次 `.doc` 转换多一次磁盘写入（约 1.5KB），可忽略。但 `-ExecutionPolicy Bypass` 意味着**脚本会临时落盘到 `os.tmpdir()`**——在受管控的企业环境里可能触发安全软件告警。

### R12 · `pollMineruAccurate` 的文件名匹配可能错配

```js
const item = items.find((candidate) => candidate.file_name === fileName) || items[0];
```

批量接口返回的是**整个 batch 的结果**。虽然当前每次只提交一个文件（`files: [{...}]`），但若 batch 里恰好有同名文件，`find` 会取到第一个匹配。有 `|| items[0]` 兜底，实际风险低。

### R13 · 无任何测试覆盖

`client/` 下的测试文件共 14 个，**没有一个覆盖 `fileService.cjs`、`convert.mjs` 或 `documentParseErrors.cjs`**。

现有测试清单：`aiService.outputTokenLimit` / `aiService.systemMessages` / `checkResultExportService` / `configStore.officialApi` / `contentIllustrationGeneration.html` / `knowledgeBaseStore.search` / `localImageRenderService` / `officialAccountService` / `officialInvoiceStore` / `outlineGenerationTaskV2` / `duplicateCheckIpc` / `rejectionCheckIpc` / `exportState`(×2)。

**`convert.mjs` 1633 行是纯函数密集的模块**（PDF 表格几何重建、去重算法、Excel 表头识别、编码归一），**是仓库里最适合做单元测试的部分**，却完全没有测试。`isPdfLineCoveredByTables` / `collapseRepeatedPdfChunks` / `hasSimilarPdfTable` / `findSpreadsheetHeaderIndex` 这些算法都有明确的输入输出，测试成本很低。

### R14 · `README`/文档未提及的隐性依赖

本地解析 `.doc` / `.wps` **必须**有 LibreOffice / WPS Office / Microsoft Word 之一。这是运行时才发现的外部依赖，安装包不会自带。

`LIBREOFFICE_REQUIRED_MESSAGE` 里的下载链接是 **`https://zh-tw.libreoffice.org/download/`（繁体中文站）**，而非简体中文站。

### R15 · `errors` 数组会重复「失败 N 份」

`fileService.cjs:655`：
```js
if (errors.length) messageParts.push(`失败 ${errors.length} 份`);
```

`technicalPlanStore.cjs:101-108` 的 `appendImportFailureParts` **又加一次**：
```js
messageParts.push(`失败 ${failed.length} 份`);
messageParts.push(failed.join('；'));
```

所以最终用户看到的提示是形如：`已解析 1 份招标文件，失败 1 份，失败 1 份；xxx.doc：文件解析失败：…`

**「失败 N 份」出现了两次**，且第二次后面跟着完整的错误列表。这是可确认的文案重复缺陷。

## 15. 总结

### 15.1 架构特征

1. **单一收敛点**：`parseDocumentWithConfig` 是全模块唯一入口，6 个业务场景全部经过它，便于统一日志、统一错误、统一图片策略。
2. **CJS/ESM 桥接**：转换引擎是 ESM（`convert.mjs`），靠动态 `import()` 从 CJS 主进程加载，实现**按需加载重依赖**。
3. **provider 抽象干净**：三种 provider 只暴露「后缀集合 + 一个 async 函数」，决策逻辑集中在 `resolveFileParser` 一个 20 行的函数里。
4. **本地转换深度定制**：不是简单调用库，而是针对中文招投标文档做了大量工程化处理——PDF 双引擎表格识别 + 三层去重、Excel 表头智能识别、DOCX 表格 HTML 保留、旧版 Word 三级后端回退。
5. **外部依赖兜底充分**：LibreOffice 命令查找覆盖 7 类候选路径 + macOS Spotlight；Windows COM 覆盖 WPS 三种 ProgID + Word；每个后端独立超时与错误聚合。

### 15.2 最值得关注的三件事

| 优先级 | 问题 | 位置 |
|---|---|---|
| **高** | `result.fallbackToLocal` 字段名不一致导致恒为 `undefined`，`saveTenderMarkdownAndState` 的 `fallbackToLocal` 参数失效 | `technicalPlanStore.cjs:2467,2477` |
| **高** | 「失败 N 份」在提示语中重复出现两次 | `fileService.cjs:655` + `technicalPlanStore.cjs:106` |
| **中** | `.txt` 硬编码 UTF-8 读取，GBK 中文文本静默乱码 | `fileService.cjs:117` |
| **中** | `convert.mjs` 1633 行零测试，且其中大量是纯函数算法 | 全模块 |
| **中** | `isLibreOfficeRequiredMessage` 依赖消息里的 `.wps` 字面量，文案改动会静默失效 | `DocumentParseNoticeProvider.tsx:13` |

### 15.3 一句话概括

**这是一个「本地优先、云端兜底、为中文招投标文档深度定制」的文档解析引擎**——本地链路用 mammoth / turndown / pdf-parse / pdfjs-dist / xlsx 覆盖 9 种格式，对 PDF 表格和 Excel 表头做了远超库默认能力的自研处理；云端用 MinerU 的两套 API（无 Token 轻量版 / 需 Token 精准版）兜住扫描件与 Office 系格式；旧版 `.doc/.wps` 靠 LibreOffice/WPS/Word 三级后端回退。代价是 **1633 行核心代码零测试**，以及若干字段名不一致与文案重复的小缺陷。
