## 1. 模块定位

全局事实是技术方案流程 **STEP 04**，位于「目录生成」之后、「正文生成」之前。

它解决的核心问题是：**超长标书分小节并发生成时，各章节会各自随机编造人名、工期、质保、型号、服务承诺，导致全文前后矛盾。**

做法是在写正文之前先把这些「全文必须统一的确定性事实」抽出来，形成一份轻量事实底稿：

- 生成阶段：从项目文件、项目概述、Step02 项目解析结果、目录、参考知识库、（扩写时）原方案中抽取；
- 使用阶段：正文编排时只给 AI 事实**标题**让其挑选，真正生成正文时只注入**被选中事实的完整内容**；
- 校验阶段：正文生成完成后，用全局事实做全文一致性审计与定点修复。

## 3. 数据模型与持久化

### 3.1 表结构（`sql/workspace_schema.sql:220`、migration v4）

```sql
CREATE TABLE IF NOT EXISTS technical_plan_global_fact_groups (
  group_id   TEXT PRIMARY KEY,
  title      TEXT NOT NULL,
  content    TEXT NOT NULL DEFAULT '',
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_technical_plan_global_fact_groups_order
  ON technical_plan_global_fact_groups(sort_order);
```

- 事实正文入 SQLite，是**权威存储**；不另建 JSON 缓存。
- 补全模式存在单例元数据表 `technical_plan_meta.global_facts_mode`（`TEXT NOT NULL DEFAULT 'fabricate'`，migration v22，目标结构 `user_version = 24`）。
- 读取按 `sort_order ASC, group_id ASC`（`technicalPlanStore.cjs:1563`）。
- 写入是「全删全插」：`replaceGlobalFacts()` 先 `DELETE` 再按数组下标写 `sort_order`（`:1572`）。

### 3.3 归一化规则

`normalizeGlobalFactGroups()`（`technicalPlanStore.cjs:1541`）：

1. `title`、`content` 去空白，**任一为空则丢弃该大项**；
2. `id` 由 `id / group_id / title` 归一化（小写、非 `[a-z0-9_-]` 转 `_`），冲突时追加 `_2`、`_3`；缺省回退 `fact_001`；
3. 保留 `updated_at`，缺失则取当前时间。

### 4.2 当前主流程：V2 Agent 版（`globalFactsTaskV2.cjs`）

```
startGlobalFactsGeneration
  │
  ├─ beforeStart: agentService.deletePersistentTask('technical-plan-global-facts')   // 丢弃旧会话
  ├─ 启动 patch: invalidatesContentGeneration=true, globalFacts=[], 清空正文任务/sections/plans/图片计划/runtime
  │
  ▼
runGlobalFactsTaskV2
  1. 读取 plan、归一化 mode（fabricate/omit/placeholder，默认 fabricate）
  2. 采集项目源：collectTenderSourceFiles()
       - 已选标段（bidSectionMode=multiple 且有 selectedSectionId）→ 只用工作副本 tender.md「当前专项方案范围」
       - 否则逐份读取 tenderFiles（多项目文件），都没有则退回工作副本
  3. 前置校验（失败直接抛错）
       - 无项目内容 → 「请先上传项目文件，再生成全局事实」

       - 扩写流程无原方案 → 「请先上传原方案，再生成全局事实」
  4. 读取参考知识库：referenceKnowledgeDocumentIds → knowledgeBaseService.readReferences()
       条目结构 { id: `${docId}::${itemId}`, title, resume, content }；读取失败仅记录日志并跳过
  5. 构造标段说明（bidSectionContextHint，仅工作副本/已选标段场景）
  6. 装配 Agent 工作区文件（files）
  7. 生成 Prompt（材料用途 + 工作原则 + 缺值写法 + 输出要求 + JSON 示例）
  8. agentService.runTask({ persistent_task: { mode:'create' }, output_file:'global-facts.json',
                            json_validation_schemas, max_retries:0, onActivity, onCheckpoint })
  9. 读回输出 → normalizeGlobalFactsResponse → validateGlobalFactsResponse
 10. checkpoint success(100%) + 写入 globalFacts + updatePersistentTask(success/completed)
```

**Agent 工作区文件清单**（`globalFactsTaskV2.cjs:338-380`）：

| 文件 | 内容 | 条件 |
|---|---|---|
| `项目文件/项目文件-当前专项方案范围.md` | `tender.md` 工作副本 | 已选标段 |
| `项目文件/项目文件-NN-<名称>.md` | 各项目源 Markdown（文件名做了非法字符替换、截断 80 字符） | 未选标段且有多份 |
| `项目概述.md` | `projectOverview`，缺省「未提供项目概述。」 | 总是 |
| `项目解析结果.md` | Step02 的**项目信息 / 甲方信息 / 交货和服务要求**（仅取 `status==='success'`） | 总是 |
| `技术方案目录.md` | 目录树（id + title + description，缩进表达层级） | 总是 |
| `标段说明.md` | 标段上下文提示 | 有标段提示时 |
| `参考知识库/条目-N.md` | 标题 + 简介 + 正文 | 选了知识库 |
| `原方案.md` | 原方案 Markdown | 已有方案扩写流程 |
| `材料说明.md` | 上述清单的用途说明（喂给 Agent 的「材料目录」） | 总是 |

**输出与校验**：

- 输出文件：`global-facts.json`；Prompt 明确要求「纯 JSON，不要 Markdown 代码块」。
- 预置 JSON Schema（`GLOBAL_FACTS_JSON_SCHEMA`）：根对象仅 `groups`，`minItems:1`，每项必填 `id/title/content`，`additionalProperties:false`；Agent 写完必须调用 `json-validation` 工具，只传 `{"file_path":"global-facts.json"}`。
- 程序侧二次校验：`validateGlobalFactsResponse()` 要求 `groups` 非空且每项 `id/title/content` 均非空，否则抛「全局事实第 N 项缺少 id、title 或 content」。
- `normalizeGlobalFactsResponse()` 兼容多种返回形态：数组、`{groups}`、`{facts}`、`{items}`、`{result:{...}}`；`content` 支持字符串 / 数组 / 对象，统一转成 `- **名称**：值` 形式的 Markdown bullet。

**进度节点**：`5 → 12（准备材料）→ 18（Agent 开始）→ 20（Agent 活动标题，截断 20 字）→ 95（完成）→ 100`。

**任务身份**：`primarySession: true`，持久任务 key `technical-plan-global-facts`，阶段 `global-facts`。

### 4.3 V1 模型调用流程（`globalFactsTask.cjs`，已不接线）

> **重要**：`runGlobalFactsTask` 在全仓已无调用者（`taskService` 只 require `runGlobalFactsTaskV2`）。该文件现以「工具模块」身份存活：V2 复用它的 `normalizeGlobalFactsResponse`、`validateGlobalFactsResponse`、`formatBidAnalysisFactsForPrompt`、`formatOutlineForPrompt`、`loadKnowledgeItems`、`normalizeGlobalFactsMode`、`normalizeReferenceDocumentIds`。但其 Prompt 与流程仍完整保留，是理解规则细节（尤其「必含工期/运维期/交货时间」「不得删项」）的最佳出处。

V1 的完整流水线：

```
① 项目文件分段提取 → ② 分批合并 → ③ 知识库分段 patch → ④ 原方案分段 patch（仅扩写）→ ⑤ 最终整理

| 阶段 | 进度 | 关键实现 |
|---|---|---|
| 分段 | 22→24 | `splitUserTextByContextLimit`，分段上限 = `context_length_limit × 0.8 − 固定消息长度`，下限 1000 字；默认 `context_length_limit=400000` |
| 分段提取 | 24→34 | 每段一次 `collectJson`，首段串行、其余 `Promise.allSettled` 并发，任一失败即整体失败 |
| 分段合并 | 44 | `mergeGroupResultsInBatches`：按上下文上限分批 → 并发合并 → 若轮次结果数未下降则再收敛一轮（多轮、多批） |
| 知识库补充 | 52/58/64/66 | `createKnowledgeItemSegments` 按条目打包成段 → 每段产出 `patches` → 分批合并 → `mergeGlobalFactPatches` 应用 |
| 原方案补充 | 70/77/84/86 | 同上（仅 `workflowKind === 'existing-plan-expansion'`） |
| 最终整理 | 90/92 | `finalizeGlobalFacts`：去重、要求句改写、保留工期类变量 |
| 完成 | 100 | checkpoint success + `globalFacts` |

Patch 合并语义（`mergeGlobalFactPatches`）：`append`（追加到末尾，默认）、`prepend`（置顶）、`replace`（整段替换）；按 `target_group_id` 或 `title` 命中已有大项，未命中则新增大项。

### 4.4 AI 调整流程（`globalFactsAdjustmentTask.cjs`）

```
前置校验：
  - requirement 非空                       → 「调整要求不能为空」
  - 已有 globalFacts                        → 「当前没有可调整的全局事实，请先完成全局事实设定」
  - hasPersistentTaskSession(global-facts)  → 「全局事实设定的 Agent 工作空间不存在，请重新生成后再使用 AI 调整」
执行：
  1. 把当前最新 globalFacts 覆盖写入工作区 global-facts.json（以用户在主界面手工改过的为准）
  2. updatePersistentTask(run_id = 当前任务 id, phase='global-facts-adjustment')
  3. agentService.runTask({ persistent_task: { mode: 'resume' }, ... })  // 复用同一 Session
  4. 读回 → 归一化 → 校验
  5. 取 assistant_text 作为总结（≤200 字，兜底「全局事实已按要求调整完成。」）

     stats.adjustment = { requirement, summary }

Prompt 强调：先读文件再改、与要求无关的项保持原样、保持完整 `groups` 结构、写回后必须过 `json-validation`。

## 5. 事实提取项目（选题规则）

全局事实**没有固定枚举清单**，选题由材料驱动，但代码里有非常明确的选题依据、强制项和排除项。下面把这些规则完整拆开。

### 5.1 事实的定义（什么算事实，什么不算）

`buildGlobalFactsSystemPrompt`（`globalFactsTask.cjs:50`）：

- 全局事实**不是**项目要求摘录、评分规则摘要或待办事项清单；
- 它是**技术方案正文中需要保持一致的确定性方案事实、响应设定、承诺口径或执行安排**；
- 资料给出明确事实时优先照录；
- 资料只给要求/约束/评价口径时，**不得原样摘录为要求句**，必须转写成「本方案已经采用/已经具备/统一承诺」的事实表达。

> 例：「项目人要求工期不超过 90 天」是要求；「本方案项目总工期为 90 个自然日」才是事实。

### 5.2 选题依据（这些信号出现就必须建项）

凡以下材料表明后续正文需要统一口径的事项，**都必须建项并写出 bullet，不得因为材料缺值而漏项**：

1. 项目要求（硬性要求、约束）；
2. 评分口径 / 技术评分信息；
3. 项目概述（`projectOverview`）；
4. 已生成技术方案目录（判断正文会反复用到哪些统一口径）；
5. 参考材料（知识库、原方案）；
6. Step02 解析结果：项目信息、甲方信息、交货和服务要求。

### 5.3 强制包含项

> **必须包含「工期、运维期、交货时间」中的至少一个相关变量。**

这是三个模式共同、也是唯一被硬编码的「必选题」。缺具体值时按模式写法填（见 §6），**不得省略该类变量、不得编造日期或周期**（fabricate 模式除外，它由项目语境补足）。

在 V2 的工作原则中，这条被表述为第 6 条：「必须包含工期、运维期或交货时间中的至少一个相关变量；缺具体值时按本任务给定的写法填写，不要省略该项」。

### 5.4 大项的确定来源（V2 明确分工）

V2 的 `buildWorkPrinciples()` 把「谁决定大项」说得很清楚：

1. **大项（id、title）由「项目文件 + 项目概述 + 项目解析结果 + 技术方案目录」确定**；多份项目文件要综合，不能因某一份没写就漏项；
2. **知识库只用于补充已有大项的 content，不得靠它新增大项**；
3. **原方案同理**；原方案与项目明确事实冲突时，原方案已落地的安排优先替换对应 bullet；
4. 材料较长时用检索定位，不能因为一次读不完就漏项。

（V1 的 patch 流程则允许知识库/原方案通过 `target_group_id` 或新 `title` 新增大项，并在合并时去重——两版在「能否新增大项」上口径不同，V2 更严格。）

### 5.5 明确排除的内容

不得输出为事实变量：

- 商务报价、资格材料；
- 分析过程、来源说明、风险提示；
- 正文草稿；
- 仍停留在要求层面的摘录、评分规则、资料清单、待办事项；
- 空泛、互相矛盾的表述（合并阶段删除）；
- 知识库中只是「通用要求、规范说明、写作建议、参考素材」的内容（除非能转成本项目统一采用的事实/安排/承诺口径/技术设定）。

### 5.6 已扩写流程的额外规则

- 原方案里已经写成专项方案方实际安排、既有承诺、统一配置、技术路线、服务口径、实施做法的内容，**优先补充进全局事实**；
- 原方案只是转述项目要求/评分规则/格式要求/资料提交要求的，不作为事实；
- 最终整理阶段明确：**原方案分段补充后的事实优先保留，不得弱化或删除原方案已有承诺**。

### 5.7 输出格式

```json
{
  "groups": [
    {
      "id": "project_team",
      "title": "项目角色变量",
      "content": "- 项目经理：张伟，负责总体协调。\n- 技术负责人：李明，负责方案设计和联调验收。"
    }
  ]
}
```

- `content` 是**短 bullet 列表**，每条应直接回答「后续正文遇到这个事项时统一写什么」；
- 全部使用简体中文；
- `id` 归一化：小写、非字母数字下划线连字符替换为 `_`，重复加 `_2` 后缀；
- V1/V2 都对多种返回形态做了容错归一化（数组 / `groups` / `facts` / `items` / `result` 包裹，content 为字符串/数组/对象）。

### 5.8 常见事实大项（来自 Prompt 示例与下游实践，非固定清单）

## 6. 三种事实补全模式（`GlobalFactsMode`）

| 值 | 页面名称 | 缺具体值时的写法 | 适用场景 |
|---|---|---|---|
| `fabricate` | 胡咧咧模式（默认） | 由 AI 按项目语境模拟生成合理、稳定、不冲突的具体值 | 成稿即可用、无需人工干预 |
| `omit` | 别招欠模式 | 保留该项，写成**不涉及**具体时间/地点/人员/业绩/证书/规格型号/工艺步骤/数量指标的正确笼统承诺，如「按项目文件对该岗位的要求配备」 | 不愿虚构，但希望正文完整可读 |
| `placeholder` | 放着我来模式 | 保留该项，值**逐字写成**【待填写】（不得写成「待定」「TBD」） | 需要人工二次确认后再生成正文 |

三者**选题范围完全相同**，差异只在「材料没给具体值时怎么填」。

共同硬规则（`buildGlobalFactsCompletenessRules`）：

1. 先按统一选题标准确定要输出哪些事实项，再按模式填值；
2. 参考材料已给出明确事实值时**照录**；
3. `omit` / `placeholder` 下**严禁虚拟、杜撰**任何未在参考材料中出现的具体事实；
4. `omit` 的笼统承诺和 `placeholder` 的【待填写】**都不是空泛内容**，合并与最终整理时不得因「不够具体」而删除；
5. 工期/运维期/交货时间类变量不得因为缺值而删项；
6. 已有方案扩写时，原方案已有事实必须提取。

模式存放：`technical_plan_meta.global_facts_mode`，默认 `fabricate`；页面通过 `saveGlobalFactsConfig({globalFactsMode})` 保存，「开始解析」会先保存当前弹窗选择再启动任务。

## 7. 下游如何消费全局事实

### 7.1 正文生成门禁（`contentGenerationTask.cjs:2925`）

```js
if (!globalFactsText || storedPlan.globalFactsTask?.status !== 'success') {
  throw new Error('请先完成全局事实设定，再生成正文');
}
```

### 7.2 编排阶段：只给标题

- `formatGlobalFactTitlesForPrompt()` 把所有大项 **title 去重后以 JSON 数组**给 AI；
- 编排结果 `plan.facts.titles` 经 `normalizeFactTitles(titles, allowedFactTitles)` **白名单过滤**，只允许使用已存在的大项标题；
- Prompt 明确：「编排时只能选择标题，不要输出具体变量内容」。

### 7.3 生成阶段：按标题取全文注入

- `resolveGlobalFactsByTitles()` → `formatSelectedGlobalFactsForPrompt()`，拼成 `## 标题\n内容` 注入当前小节；
- 系统提示硬约束（第 15、16 条）：
  - 提供了相关全局事实时**必须优先使用，不得前后矛盾**；
  - **未提供时不要主动编造**具体人员、周期、质保、品牌、型号等会影响全文一致性的承诺；
  - `omit` / `placeholder` 模式下追加「不得把【待填写】改成具体值，也不得为缺失项杜撰事实」。

### 7.4 生成后：全文一致性审计与定点修复

- `buildConsistencyAuditMessages()`：按目录分组把正文与 `globalFactsText` 一起交给 AI，只返回「冲突目录编号 + 冲突证据」；
- `buildConsistencyRepairMessages()`：返回精确 `old_text → new_text`（带 1-based 行号），不重写整章；
- `placeholder` 模式下明确：**【待填写】不是冲突**，不要求正文补成具体值。

### 7.5 其他复用点

- 单章节重新生成 / 中断恢复：`buildRestoredChapterContentMessages()` 同样注入选中事实；
- 原方案扩写还原：`buildOriginalMaterialRestoreMessages()` / Agent 版文件注入「Step04 全局事实变量标题清单」；
- 字数调整：`buildWordAdjustmentMessages()` 携带 `selectedFactsText`，避免调字数时改坏事实。

## 8. 失效与联动规则

| 触发 | 对全局事实的影响 | 对下游正文的影响 |
|---|---|---|
| 启动全局事实生成 | 清空 `globalFacts`、删除旧持久 Agent 会话 | `invalidateContentGeneration` → 清空正文任务/sections/plans/图片计划/runtime |
| AI 调整完成 | 覆盖写入新 `globalFacts` | 同上，全部清空 |
| 手工保存事实 | 全量替换 | 同上（事务内 `clearContentGenerationState()`：正文 content 置空、sections/plans/图片计划/runtime 删除） |
| 重新生成目录 | `globalFacts: []`、任务与调整任务置空 | 下游一并清空 |
| 切换标段 / 重导项目文件 / 换原方案 / 切工作流 | `DELETE FROM technical_plan_global_fact_groups` + `deleteGlobalFactsAgentTask()` | 目录、正文一并清空 |
| 目录被置空（`outlineData === null`） | 删除持久 Agent 会话 | 通知 Agent 工作区变更 |
| 清空/重置工作区 | 删除事实表 + 删除 Agent 工作区 | 全清，`global_facts_mode` 回到 `fabricate` |

任务互斥：`technical-plan` 组内互斥，全局事实生成/调整进行中，页面禁止保存、删除、改配置、重新解析（提示「全局事实设定任务正在运行，请等待任务结束后再…」）。

## 11. 观察与风险点

1. **V1 已成为死代码**：`globalFactsTask.cjs` 的 `runGlobalFactsTask`（1031 行里的主流程）没有任何调用者，仅其工具函数被 V2 复用。阅读与维护时容易误把 V1 的分段/多轮合并当成线上行为；若确认不再回滚 V1，建议删除主流程或加显式注释。
2. **V2 无自动重试**：`agentService.runTask` 传 `max_retries: 0`，Agent 一次失败即任务失败（页面提示「失败后不会自动重试，可点击重新解析」）。
3. **AI 调整强依赖持久会话**：工作区被清理/删除后会直接报「全局事实设定的 Agent 工作空间不存在，请重新生成后再使用 AI 调整」；而每次重新生成都会先 `deletePersistentTask`。
4. **任何事实变更都会清空全部正文**：这是刻意设计（保证正文不引用旧事实），但代价较大，尤其在已生成长正文后做小改。
5. **V1 与 V2 的「能否新增大项」口径不一致**：V1 的 patch 允许知识库/原方案新增大项；V2 明确限定它们只补充已有大项 content。若未来回滚或复用 V1，需要统一规则。
6. **测试覆盖**：全局事实没有独立的 `*.test.cjs`（仓库内只有 `outlineGenerationTaskV2.test.cjs`、`knowledgeBaseStore.search.test.cjs` 等），改动 V2 主要靠手工链路验证。
7. **【待填写】只做提示不做拦截**：`placeholder` 模式下用户仍可直接进入正文，仅会被定位到第一个占位大项。
