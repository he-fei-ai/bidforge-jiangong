## 1. 模块定位

导出是技术方案 / 可研报告的**最后一环**，把 SQLite 中 `outline_nodes.content` 里的 Markdown 正文，按用户配置的排版规则渲染成 `.docx`。它**不做任何 AI 调用**（除图片渲染外全是本地转换），是一个纯确定性的「渲染 + 落盘」模块。

模块实际包含**三条互相独立的链路**：

| 链路 | 产物 | 主文件 | 调用方 |
|---|---|---|---|
| ① Word 导出 | `.docx` | `exportService.cjs`（2472 行） | 技术方案首页、可研报告首页、导出格式页（导出测试） |
| ② Excel 导出 | `.xlsx` | `checkResultExportService.cjs`（459 行） | 废标检查、标书查重 |
| ③ 导出模板库 | — | `templateStore.cjs`（115 行） | 「我的模板 / 新建模板」页面 |

三条链路**除了共享 Electron 的 `dialog.showSaveDialog` 之外没有耦合**：模板库只存配置，Excel 导出用的是另一套 `xlsx` 依赖，二者都不经过 `exportService.cjs`。

## 2. Word 导出主流程

入口 `createExportService({ configStore }).exportWord(payload, onProgress)`（`exportService.cjs:2393`）：

```
1. countOutlineStats(outline)        统计叶子数 / Mermaid 图数
2. 校验 outline 非空                 否则 throw「没有可导出的目录内容」
3. reportProgress(2%)                「检测到 N 张 Mermaid 图…」
4. dialog.showSaveDialog             默认 downloads/{项目名}_{时间戳}.docx
   └─ 取消 → { success:false, canceled:true }
5. buildDocxResult(payload, { onProgress, warnings, developerLogger })
   ├─ 封面 / 编制说明
   ├─ addOutlineItems 递归          （转换进度 10% → 88%）
   ├─ 附表（可研）
   ├─ reportProgress(90%)
   ├─ 页面设置 / 页眉 / 页脚 / 页码 / 编号 / 段落样式
   └─ Packer.toBuffer(doc)
6. reportProgress(96%) → fs.writeFileSync → reportProgress(100%)
7. return { success:true, path, message, warnings }
```

### 2.1 进度模型

| 阶段 | 进度 | 来源 |
|---|---|---|
| 准备 | 2% | `exportWord` 起始 |
| 封面完成 | 10% | `buildDocxResult` |
| 内容转换中 | 10% + (已转换叶子 + 已转换 Mermaid) / (总叶子 + 总 Mermaid) × 78% | `reportConversionProgress` |
| 内容完成 | 90% | `buildDocxResult` |
| 写盘前 | 96% | `exportWord` |
| 完成 | 100% | `exportWord` |
| 取消 | 0%（`phase: 'canceled'`） | `exportWord` |
| 失败 | 100%（`phase: 'error'`） | `exportIpc.cjs` |

注意 `reportConversionProgress` 的分子是**叶子 + Mermaid 之和**，所以一张 Mermaid 图和一个小节在进度条上权重相同。

### 2.2 数据契约（payload）

```js
{
  requestId: 'export-<timestamp>-<random>',   // 进度事件路由用
  project_name: string,
  outline: OutlineItem[],                     // 权威正文在 item.content
  export_format: ExportFormatConfig | null,   // null 时全部走内置默认样式
  feasibility_options?: {                     // 存在即进入可研模式
    includeCover, includePreparationNotes, includeAppendixTables,
    securityLevel, preparationUnit, documentCode,
    project_info: { projectName, constructionUnit, industry, location,
                    constructionContent, constructionPeriodYears,
                    operationPeriodYears, totalInvestment, fundingSource }
  }
}
```

`base_dir` / `baseDir` 用于解析相对路径图片（通常不传，回退 `process.cwd()`）。

### 2.3 IPC 与进度回传

```js
// exportIpc.cjs
ipcMain.handle('export:word', async (event, payload = {}) => {
  const requestId = payload.requestId || payload.request_id;
  const donationPrompt = donationService.recordWordExport({ deferPrompt: true });
  const sendProgress = (progress) =>
    event.sender.send('export:word-progress', { requestId, ...progress });
  try {
    return await exportService.exportWord(payload, sendProgress);
  } catch (error) {
    sendProgress({ phase: 'error', progress: 100, message: error.message || '导出 Word 失败' });
    throw error;
  } finally {
    donationService.showPrompt(donationPrompt);
  }
});
```

三个细节：

- 进度事件带 `requestId`，Renderer 侧用 `if (event.requestId && event.requestId !== requestId) return;` 过滤，避免并发导出串台；
- **每次导出都会记一次捐赠计数**（`recordWordExport`），达到间隔后弹捐赠引导，且是在 `finally` 里弹 —— 即使导出失败也会弹；
- `export:open-file` 用 `shell.openPath` 打开导出的文件（Renderer 的「打开文件」按钮）。

## 3. 导出格式配置（ExportFormatConfig）

完整结构（`src/shared/types/exportFormat.ts:139`）：

interface ExportFormatConfig {

| 字段 | 默认 | 说明 |
|---|---|---|
| `paper_size` | `a4` | a4/a3/a5/b4/b5/letter/legal/16k 八种，mm 尺寸在 Main 与 Renderer **各存一份**（`PAPER_DIMENSIONS_MM` / `PAPER_DIMENSIONS`） |

| `first_page_different` | `false` | → `titlePage: true` |

| `footer_distance_cm` | 1.75 | |

| 页脚 | 默认**关闭** | |

> ⚠️ 页脚/页码有两处**语义相反的默认值**：`exportService.cjs` 里 `isFooterEnabled` / `isPageNumberEnabled` 的写法是 `!== false`（即未配置时默认**开启**），但 `DEFAULT_PAGE_SETUP` 里显式写了 `false`（默认**关闭**）。实际生效取决于传入的配置是否完整——走模板导出时模板里都有这两个字段，所以表现为「默认关闭」。

### 3.3 正文 / 表格 / 图片样式

**正文（BodyTextStyleConfig）**：字体（默认宋体）、字号（小四 = 24 half-pt）、对齐（左对齐）、段前段后、首行缩进 2 字符、行距 1.2 倍、`list_style`（disc）、`ordered_list_style`（decimal-dot）、`list_indent_chars`（2）。

**表格（TableStyleConfig）**：边框宽 1（`× 6 = 6` 作为 docx border size）、颜色 `#dcdff6`、单元格内边距 6pt、`full_width: true`（固定布局 + 列宽均分 9000 twips），表头/首列/正文三种单元格样式独立（字体、字号、对齐、文字色、背景色）。默认表头是黑体小四居中 + `#eef5ff` 底。

**图片（ImageStyleConfig）**：`max_width_percent: 90`、居中、图注宋体小五居中。图注识别靠**文本前缀**：段落文本匹配 `/^图[:：]/` 才用图注样式（`htmlNodeToDocxBlocks:1739`）。

## 4. 编号体系

### 4.1 标题编号（手动拼字符串）

`formatOutlineNumber(id, headingStyle)` 把 `1.2.3` 这样的节点 id 拆成数字数组，再套模板。支持占位符：

| 占位符 | 含义 | 例（id = `2.3.4`） |
|---|---|---|
| `{zh}` | 末级中文数字 | `四` |
| `{num}` | 末级阿拉伯数字 | `4` |
| `{tail}` | 三级起的部分（不足三级则取末级） | `3.4` |
| `{tail1}`…`{tail6}` | 从指定级开始的部分 | `{tail2}` = `3.4`，`{tail1}` = `2.3.4` |
| `{full}` | 完整编号 | `2.3.4` |
| `{circled}` | 带圈数字 ①-⑳ | `④` |
| `{alpha}` / `{ALPHA}` | 小写/大写字母（支持 26 进制进位） | `d` / `D` |
| `{roman}` / `{ROMAN}` | 小写/大写罗马（1-3999） | `iv` / `IV` |

拼完后 `shouldInsertSpaceAfterNumber` 判断是否需要补空格：结尾是 `、，。；：）)】]》〉` 时不补。

> ⚠️ **原生 Word 多级编号实际未启用**：`usesNativeHeadingNumbering(headingStyle)` 函数体是 `return false;`（`:1021`）。也就是说 `numbering_format: 'outline-decimal'` 分支、`context.usesHeadingNumbering`、`createHeadingNumberingConfig` 这整条链路**是死代码**——所有标题编号都是**拼进标题文本里的普通字符串**，不是 Word 的自动编号。后果：导出的 docx 在 Word 里**不会生成目录/导航窗格的可识别标题编号**，且编号不会随章节增删自动更新。

### 4.2 列表编号（Word 原生 numbering）

列表走的是另一套机制 —— **每个列表创建一个独立 numbering reference**（`technical-plan-numbering-1`、`-2`…），每个 reference 有 3 级：

```js
function createListReference(context, ordered) {
  if (!ordered && bodyStyle.list_style === 'none') return null;   // 无序且样式为「无」→ 不加编号，改用手动缩进
  const reference = `${NUMBERING_REFERENCE_PREFIX}-${++context.numberingIndex}`;
  context.numberingReferences.push({ reference, ordered, unorderedListStyle, orderedListStyle, listIndentChars, bodyRunFont, bodyRunSize });
  return reference;
}
```

- 无序标记 8 种：`disc •` / `circle ○` / `square ■` / `diamond ◆` / `dash –` / `check ✓` / `arrow ➢` / `sparkle ✧`，各有字体（Arial / Segoe UI Symbol）与 `sizeScale`；
- 有序 9 种：`decimal-dot`（1.）、`decimal-paren`（1））、`decimal-full-paren`（（1））、`chinese-dot`（一、）、`chinese-paren`（（一））、`lower-alpha`、`upper-alpha`、`lower-roman`、`upper-roman`；
- 缩进：`getListLevelIndent` = `left = 基础缩进 × (level+1)`，`hanging = min(left, 1 字符)`；
- 任务列表（`task-list-item` 或含 checkbox）**不加编号**，用 `getTaskListLevelIndent` 手动缩进，行首画 `☐ ` / `☑ `。

> ⚠️ **每个列表一个 reference**：一篇文档有 50 个列表就会生成 50 套 numbering config。这是为了每个列表独立从 1 开始计数，代价是 docx 的 numbering.xml 会显著膨胀。

## 5. Markdown → docx 转换管线

```
item.content (Markdown)
   ↓ normalizeMarkdownTablesForDocx
   ↓ normalizeMarkdownListMarkersForDocx
   ↓ renderMarkdownHtml({ allowRawHtml: true, enableGfm: true })
   ↓ cheerio.load(html, null, false)
   ↓ htmlNodesToDocxBlocks → htmlNodeToDocxBlocks（逐节点）
   ↓ Paragraph / Table / ImageRun / TextRun
```

### 5.1 表格预处理（模型输出的容错）

`normalizeMarkdownTablesForDocx` 专门修两类模型常见的坏表格：

1. **压缩表格行** `expandCompressedMarkdownTableRows`：模型把分隔行和后续数据行压成同一物理行时，按表头列数拆回 GFM 表格；
2. **同行多表格** `expandInlineMarkdownTableRows`：一行里塞了多行的表格文本时，用 `|\s+\|` → `|\n|` 拆开；
3. 表格前若上一行非空且不是表格行，补一个空行（否则 markdown-it 不会识别为表格）。

`normalizeMarkdownListMarkersForDocx` 把 `• ● ○ ◦ ▪ ▫ ■ □ ◆ ◇ ‣ ➢ ➤ ✓ ✔ ✧ – －` 这 15 种全角/特殊项目符号统一替换成 `- `，让 markdown-it 正确解析为列表。

### 5.2 markdown-it 配置

```js
new MarkdownIt(options.enableGfm ? 'default' : 'commonmark', {...})
  .use(cjkFriendly)                                          // 中文友好断行
  .use(taskLists, { enabled: true, label: true, labelAfter: true });
```

导出时固定传 `allowRawHtml: true, enableGfm: true`。

### 5.3 块级节点映射表

| HTML 标签 | docx 产物 | 备注 |
|---|---|---|
| `h1`-`h6` | 标题段落（`HeadingLevel`）+ 对应级别样式 | 级别由标签名解析，不是目录层级 |
| `table` | `docx.Table` | 见 §5.4 |
| `img` | 图片段落 | 见 §6 |

| `blockquote` | 左蓝框 + 浅灰底缩进段落 | 可研模式下若含 📸【插图指引】→ 转专用提示框 |
| `pre > code.language-mermaid` | **本地渲染 PNG** | 见 §6.2 |
| `pre`（其他） | Consolas 21 灰底段落 | 代码块不保留语法高亮 |
| `br` | 换行段落 | |
| `hr` | 居中的 `────────` 文本 | |
| `div/section/article` + 含块级子 | 递归子节点 | |

| 其他 | **记 warning 后递归子节点** | `addUnsupportedHtmlWarning`，同一标签只报一次 |

### 5.4 表格渲染

- 列数 = 各行 `colspan` 之和的最大值；
- `isHeader` 判定：第一行 **或** 单元格是 `th`；
- `isFirstColumn`：非表头且是第一列；
- 最后一个单元格的 `colspan` 自动补足到 `maxColumns`（补齐表格右侧缺口）；
- `full_width: true` → `TableLayoutType.FIXED` + 列宽均分（余数加给最后一列）；`false` → `AUTOFIT` 且不设列宽；
- 单元格内是**单段落**（`htmlInlineRuns` 展平），不支持单元格内多段落/嵌套表格。

## 6. 图片与 Mermaid（唯一的耗时与失败来源）

### 6.1 图片加载与缩放

`loadImage` 支持四种来源：

| 来源 | 处理 |
|---|---|
| `data:image/...;base64,...` | 直接 `Buffer.from(base64)`，类型从 MIME 推断 |
| `yibiao-asset://generated-images/...`、`yibiao-asset://imported-images/...` | `resolveAssetImagePath` 映射到 `getGeneratedImagesDir` / `getImportedImagesDir`，**带目录穿越防护**（`resolvedPath.startsWith(baseDir + sep)`） |
| `http(s)://` | `fetch`，失败抛「图片下载失败」 |
| 本地路径 / `file://` | 相对路径按 `context.baseDir` 解析，不存在返回 `null` |

失败重试：`loadImageWithRetry`，`REMOTE_IMAGE_RETRY_ATTEMPTS = 2` 次，间隔 `REMOTE_IMAGE_RETRY_DELAY_MS = 3000` ms。

缩放计算：

```
pixelDensity = URL 上 ?pixel-density= 参数（仅内部渲染产物，默认 1）
sourceWidth  = imageSize.width  / pixelDensity
sourceHeight = imageSize.height / pixelDensity
maxWidth     = 页面可用宽(px) × image.max_width_percent / 100
maxHeight    = 页面可用高(px) × 90%
ratio        = min(1, maxWidth/sourceWidth, maxHeight/sourceHeight)
```

页面可用宽/高由**纸张 mm → twips → /15 → px** 换算，减去左右/上下页边距。

**任何一步失败都不中断导出**：`imageRunFromNode` 的所有 catch 分支都返回一个**红色的 `[图片无法导出：…]` 文本 run** 并 `addWarning`。最终文案会提示「有 N 处图片未能插入，请打开文档核对」。

### 6.2 Mermaid 本地转图

`mermaidCodeToDocxBlocks` → `resolveMermaidImageForExport`：

```
1. getMermaidCacheEntry(app, code)      hash 命中？→ 直接用缓存 assetUrl
2. 未命中 → getLocalImageRenderService().renderMermaidToPng(code)
3. saveMermaidCacheImage(app, hash, buffer)   写回缓存（失败只记日志，不中断）
```

`renderMermaidToPng`（`localImageRenderService.cjs:686`）实现：

- 创建**离屏 BrowserWindow**，注入**本地** mermaid 脚本（`resolveMermaidBrowserScript()`，不依赖外网）；
- 视口先给 `680 × 1200` 让 SVG 按固有尺寸排版，再量内容包围盒；
- 轮询 `window.__yibiaoMermaidReady` / `__yibiaoMermaidError`（30 秒超时）；
- 按包围盒截图，宽度上限 `WORD_FRIENDLY_RENDER_WIDTH = 680`，**3 倍图**（`MERMAID_CAPTURE_SCALE = 3`）；
- 高度超过 `MAX_CAPTURE_SEGMENT_HEIGHT = 8192` 时分段截图再 `stitchPngVertically` 纵向拼接；
- 并发由 `components.mermaid_concurrency_limit` 控制（`clampConcurrency`，1-20，默认 5）；
- 尺寸小于 24×24 视为渲染失败。

缓存：`MERMAID_CACHE_VERSION = 5`，输出 PNG，主题 `default`，背景 `!white`，目录 `userData/workspace/generated-images/mermaid-cache/`。**`fullRegenerate` 时会 `clearMermaidCache()`**。

> ⚠️ 导出阶段**不校验 Mermaid 语法**：注释明确写「正文已有代码块则直接尝试本地渲染」。语法错误会在 30 秒超时后才暴露，是长文导出卡顿的常见原因。

### 6.3 像素密度（pixel-density）

HTML/Mermaid 转图时是 2-3 倍高清图，直接插入会显得过大。`getImagePixelDensity` 从 URL 的 `?pixel-density=` 参数读回倍数（仅对 `yibiao-asset://generated-images/mermaid-cache/` 和 `/technical-plan/illustrations/` 生效），把像素尺寸折算回设计尺寸，**版面按设计像素排、清晰度保留高清**。

## 7. 章节边框模式（heading_border）

这是导出模块最有特色的一项：**把整章内容装进一个 docx 表格**，做出「章节框」效果。

两种结构：

| 结构 | 表现 |
|---|---|
| `上下结构` | 表格单列：一级标题一个「标题行」（带底色 + 固定行高），其下所有内容一个「内容行」 |
| `左右结构`（`min_heading_left_enabled`） | 表格两列：**叶子**小节用「标题列 1800 tw + 内容列 7200 tw」并排 |
| 非叶子 | 无论哪种结构都用单列标题行（`columnSpan: 2`） |

行高按级别递减（`chapterHeadingRowStyle`）：L1 = 520、L2 = 430、L3 = 360、L4 = 320、L5 = 290、L6 = 270。

底色 6 级（`DEFAULT_HEADING_BORDER_CELL_COLORS`）：`#e0ecff → #e9f1ff → #f2f7ff → #f8fbff → #ffffff → #ffffff`。

⚠️ **Main 与 Renderer 的默认值不一致**：

| | Main（`exportService.cjs:48`） | Renderer（`exportFormat.ts:388`） |
|---|---|---|
| 默认 6 级底色 | `#e0ecff, #e9f1ff, #f2f7ff, #f8fbff, #ffffff, #ffffff` | `#eef5ff, #f3f7ff, #f8fbff, #fbfdff, #ffffff, #ffffff` |
| 默认边框色 | `#2174fd`（`getChapterFrameConfig` fallback） | `#cfd8ee` |

即 `export_format` 为 `null`（无模板）时，章节框颜色与页面预览**不一致**。走模板导出时不受影响。

其他细节：

- 章节框模式下，标题段落强制 `compact: true`（段前段后归零）、`manualNumbering: true`、`disablePageBreakBefore: true`；左右结构的叶子还强制 `omitNumbering: true`；
- 分页：`isLevel1PageBreakEnabled` 时，章节框**前**插入分页段落（因为框内不能分页）；
- 章节框只在 **level 1** 启用（`addOutlineItems:2077`），二级及以下仍是普通标题 + 正文。

## 15. 风险点与代码现状提示

1. **`usesNativeHeadingNumbering` 恒为 `false`，原生多级编号是死代码**。`createHeadingNumberingConfig`、`HEADING_NUMBERING_REFERENCE`、`context.usesHeadingNumbering` 这一整条链路不会被触发；标题编号是拼进文本的静态字符串，Word 里不会自动更新，也不会被「引用 → 目录」识别为编号。
2. **`exportService.cjs`（2472 行）零测试**。所有 Markdown/HTML → docx 的映射、表格修复、编号模板、图片缩放都没有自动化覆盖，改动只能靠「导出测试」人工核对。
3. **Main 与 Renderer 的默认值已分叉**：章节框 6 级底色（`exportService.cjs:48` vs `exportFormat.ts:388`）、边框色（`#2174fd` vs `#cfd8ee`）；纸张尺寸 mm 表也是两份（`PAPER_DIMENSIONS_MM` / `PAPER_DIMENSIONS`）。`export_format` 为 `null` 时预览与实际产出不一致。
4. **SQL 注释与实现不符**：`export_templates` 表注释称「尚未接入 Word 导出选择」，但实际导出强制走模板库。
5. **每个列表一个 numbering reference**：长文档会生成大量 numbering config，docx 体积与 Word 打开耗时都会上升。
6. **页脚/页码默认值语义不一致**：`isFooterEnabled`/`isPageNumberEnabled` 用 `!== false`（默认开），但 `DEFAULT_PAGE_SETUP` 写 `false`（默认关）；配置缺失时两层给出的结论相反。
7. **Mermaid 导出不预检语法**，语法错误要等 30 秒超时才暴露；长文多图时是主要卡顿源。缓存命中可缓解，但 `fullRegenerate` 会清空缓存。
8. **图片失败静默降级为红色文本**，只靠 `warnings` 提示。若用户忽略进度弹窗，导出的文档里会残留 `[图片无法导出：…]` 字样。
9. **表格单元格只支持单段落**，模型若在单元格里写多段会全部展平成一段。
10. **导出即累计捐赠次数，且在 `finally` 中弹窗** —— 导出失败也会触发捐赠引导（`exportIpc.cjs:20`）。
11. **图注识别靠文本前缀 `图:` / `图：`**，AI 生成的图注若不带前缀就不会应用图注样式。
12. **HTML 白名单之外的标签静默降级**：只报一次 warning，深层结构（如嵌套 div、figure）会被展平，复杂 HTML 配图（§正文生成模块的 html 类图片）在 Word 里可能与预览差异较大。
