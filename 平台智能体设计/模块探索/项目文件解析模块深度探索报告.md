## 1. 模块定位

解析模块是技术方案流程 **STEP 02**，位于「选择标书」之后、「目录生成」之前。它把整份招标文件一次性拆成 **18 个结构化解析项**并发提取，产出后续所有步骤共用的事实底座。

包含两个彼此独立但串联的任务：

| 任务类型 | 中文名 | step | 状态字段 | 说明 |
|---|---|---|---|---|
| `bid-section-extraction` | 多标段识别 | 2 | `bidSectionExtractionTask` | 可选前置：识别标段并让用户选择本次投标范围 |
| `bid-analysis` | 招标文件解析 | 2 | `bidAnalysisTask` | 主体：18 个解析项并发提取 |

两者都是 `group: 'technical-plan'`、`lockPolicy: 'group-exclusive'`，即技术方案组内互斥（解析时不能同时跑目录/全局事实/正文）。

## 2. 数据模型与持久化

### 2.1 解析项表

```sql
-- technical_plan_bid_items
item_id TEXT PRIMARY KEY,   -- 18 个解析项 id
label   TEXT,               -- 中文名
status  TEXT,               -- idle | running | success | error
content TEXT,               -- Markdown 或 JSON 字符串
error   TEXT,
sort_order INTEGER,         -- 按全量任务顺序排列
updated_at TEXT
```

- 写入是 `INSERT ... ON CONFLICT(item_id) DO UPDATE` 增量 upsert（`saveBidItems`）；
- `projectOverview` / `techRequirements` 另有「派生写」路径（`upsertDerivedBidItem`），因为 Main 会把它们同步成顶层字段随事件下发；
- 读取 `loadBidItems()` 返回 `Record<itemId, {id,label,status,content,error}>`。

### 2.2 meta 字段（`technical_plan_meta`）

| 字段 | 含义 |
|---|---|
| `bid_analysis_mode` | `key` / `full` / `custom` |
| `bid_analysis_selected_task_ids_json` | 实际选中的解析项 id 列表 |
| `bid_section_mode` | `single` / `multiple` |
| `bid_sections_json` | AI 识别出的标段数组 |
| `bid_section_extraction_status` / `_error` | `idle/running/success/error` 与错误信息 |
| `selected_section_id` / `selected_section_title` | 用户选择的本次投标范围 |

### 2.3 Renderer 类型

```ts
export type BidAnalysisMode = 'key' | 'full' | 'custom';
export type BidSectionMode = 'single' | 'multiple';
export type BidSectionExtractionStatus = 'idle' | 'running' | 'success' | 'error';

export interface BidAnalysisTaskState { id; label; status; content; error? }
export type BidAnalysisTasks = Record<string, BidAnalysisTaskState>;

export interface DetectedBidSection {
  id; index; unit; title; headLine; description;
  includeRanges?: BidSectionLineRange[];   // { startLine, endLine, reason }
  evidence?: string[];
}
```

### 2.4 存储形态差异

- **JSON 解析项**：`content` 存 JSON 字符串，页面用 `JsonResultTable` 解析成「中文标签 → 值」两列表格；空值统一显示「没有提及」。
- **Markdown 解析项**：`content` 存 Markdown，页面用 `MarkdownRenderer` 渲染并支持全屏查看。
- **整项缺失标记**：Markdown 项完全没内容时，模型被要求只返回 `未提取到`（`BID_ANALYSIS_MISSING_RESULT`）；页面与业务都用它区分「整项空」与「局部字段写没有提及」。

### 3.1 通用提取约束（`stableSystemPrompt`）

1. 严格基于给定上下文，除非任务明确允许，否则不得编造；
2. 已提取到内容但局部未提及时，明确写「没有提及」；
3. 只输出最终结果，不输出过程、提示语或客套话；
4. 始终使用简体中文。

JSON 项另有模板约束：只改 value、不改 key 与结构；没有的字段填「没有提及」。

### 4.2 按输出形态

- **Markdown 项（9 个）**：项目概述、技术评分要求、采购清单、响应文件要求、资格性审查、符合性检查、商务评分要求、无效标与废标项 → 页面渲染 Markdown。
  （计数：JSON 10 个 / Markdown 8 个——以 §3 表格的「输出」列为准。）

### 4.3 按解析范围模式（`BidAnalysisMode`）

| 模式 | 含义 | 选中项 |
|---|---|---|
| `key` | 只解析关键项（默认，省 Token） | 6 个必选项 |
| `full` | 完整解析 | 全部 18 项 |
| `custom` | 自定义 | 必选项 + 用户勾选的可选项 |

归一化规则（`normalizeBidAnalysisConfig`）：必选项**永远强制包含**，不可取消勾选；若勾选齐全量 → 自动判定为 `full`；若含任意可选项 → `custom`。配置变更后保存到 `bid_analysis_selected_task_ids_json`。

### 4.4 按是否存在缺失

- **整项缺失**：Markdown 项内容恰为 `未提取到` → 页面标记「未提取到」并提供「重新解析此项」；
- **技术评分项缺失**：`isMissingTechnicalScoreItems()` 额外判断 `## 技术评分项` 小节内容是否为「没有提及」→ 目录生成会要求走「无技术评分项模式」；
- **单项失败**：`status = 'error'`，条目显示错误原因，可单独重试。

## 5. 工作流程

### 5.1 前置：标段模式与多标段识别

```
① 页面点击「开始解析」
② Renderer 先调 window.yibiao.technicalPlan.checkBidSections()
     → Main: detectBidSections(原始招标 Markdown)（纯规则，不调模型）
     → 返回 { hasMultiple, totalDeclared }
     ├─ 选了 single 但检测为多标段 → 弹「疑似多标段，是否切换多标段」
     └─ 选了 multiple 但没检测到  → 弹「未检测到明确多标段，是否仍用 AI 识别」
③ 多标段 && 未选范围 → 启动 startBidSectionExtraction（若已识别过则直接开选择弹窗）
④ 用户在 BidSectionSelectorDialog 选标段
     → technicalPlan.selectBidSection(section)
     → buildSelectedSectionMarkdown()：从原始 Markdown 中剔除其他标段行，保留本标段行
       规则：只删除「属于其他标段且不属于本标段」的行；通用条款保留
     → 结果写回 tender.md（工作副本），并清空下游（目录、解析项、全局事实、正文）
⑤ 进入真正的解析
```

**规则检测（`bidSectionDetector.cjs`）**：
- 「共/划分为 N 个标段/标包/分包/标的/子项目」计数；N=1 → 单标段；N≥2 → 多标段；
- 否则用「一标段：」「第 1 标包：」「包 2：」等 16 种定义型正则去重计数；
- 否则用 `【1】【1-2】` 方括号编号行计数；
- 计数 ≥2 判定 `hasMultiple = true`；会排除「一、二标段」这类合并提及与文号行。

**AI 识别（`bidSectionExtractionTask.cjs`）**：
1. 读**原始**招标 Markdown（`readOriginalTenderMarkdown()`），给每行加 `L000001 | ` 行号；
2. 按上下文上限分段，逐段串行提取标段候选（严格 JSON：`sections[{id,index,unit,title,headLine,description,includeRanges[{startLine,endLine,reason}],evidence[]}]`）；
3. 多段时再调一次「合并」调用，合并同一标段、保留所有范围与证据；
4. 归一化：范围合法性校验（1 ≤ start ≤ end ≤ 总行数）、按 `unit:标题` 去重、范围去重排序、证据去重、按首行号重排 id；
5. 校验：少于 2 个标段直接失败「未识别到至少两个有效标段」；
6. 成功写 `bidSections` + `status=success`；失败写 `status=error` + 错误信息（**任务内部 catch，不抛给上层**）。

### 5.2 主流程：`runBidAnalysisTask`

```
① 归一化配置：normalizeBidAnalysisConfig(mode, selectedTaskIds) → { mode, taskIds }
② 读取招标内容：workspaceStore.readTenderMarkdown()
     （多标段时这是「当前投标范围」工作副本；单标段时是原文）
③ 前置校验（抛错即任务失败）
     - 内容为空 → 「请先上传招标文件，再开始解析」
     - bidSectionMode=multiple 且未成功识别/未选标段/标段失效 → 相应提示
④ 生成标段上下文提示 sectionHint（buildBidSectionContextHint）
⑤ 计算 fileSegments（按上下文上限预切分，供所有解析项复用）
⑥ 解析 payload：force_rerun（全量重跑）/ task_ids（只跑指定项）
     - forceRerun：先把所有选中项重置为 idle/空，并清空目录、全局事实、正文等下游，
       同时下发 projectOverview='' / techRequirements=''
     - 非 forceRerun 且非指定项：跳过已 success 的项（增量解析）
⑦ checkpoint running(0%) + 配置 patch
⑧ 执行：
     a. 先单独跑 projectOverview（提示词缓存预热）
     b. 成功且还有其他项 → 等 5 秒（PROMPT_CACHE_WARMUP_DELAY_MS）
     c. Promise.all 并发跑其余所有项（每项独立 try/catch，失败只标记该项 error）
⑨ 每项完成 → checkpointBidItem：写 bidAnalysisItem + bidAnalysisProgress + 任务进度
     projectOverview → 额外下发 projectOverview
     techRequirements → 额外下发 techRequirements
⑩ 结束判定 getMissingRequiredTasks()
     - 有必选项未 success 或内容为空 → 任务 error「必填解析项未完成：X、Y，请重新解析失败项。」
     - 否则 → 任务 success(100%)
```

**进度计算**：`doneProgress = 已完成（success/error）项数 / 选中项总数 × 100`（Store 侧 `calculateBidProgress` 逻辑相同）。

### 5.3 单项提取流程（含分段与汇总）

```
runBidAnalysisPromptTask(task)
  ├─ runBidAnalysisPromptTaskOnce()
  │    ├─ 若未预切分 → splitUserTextByContextLimit(fileContent, config)
  │    ├─ 单段 → 直接 runSingleBidAnalysisPromptTask()
  │    └─ 多段 → Promise.all 并发逐段提取，再 mergeSegmentedAiResults() 合并
  └─ 若结果是 Markdown 的「未提取到」→ 完整重跑一次（第二次结果原样保存）
```

单次调用的消息结构：

```
system: stableSystemPrompt（通用提取约束）
system: sectionHint（可选，标段上下文）
user  : 完整招标原文（或当前分段）+ 「后续任务基于本文件完成」
user  : 该解析项专属 Prompt（+ Markdown 项追加「整体无结果规则」）
```

JSON 项带 `response_format: { type: 'json_object' }`。

### 5.4 汇总机制（四处）

1. **分段结果汇总**：`mergeSegmentedAiResults()` 把所有分段的同一解析项结果合并。合并 Prompt 明确：某段写「没有提及/未提取到」只代表该片段，其他片段有有效信息则以有效信息为准；删除重复/空泛/冲突；不得新增或编造；全部无有效信息时遵守整体无结果规则；输出形态与原始任务一致。
2. **进度汇总**：任务进度 = 已完成项 / 选中项；页面显示 `doneCount/selectedTasks.length` 与进度条。
3. **结束汇总判定**：`getMissingRequiredTasks()` 检查 6 个必选项是否都 success 且内容非空，决定是否整体 error。
4. **下游汇总消费**：`formatBidAnalysisFactsForPrompt()` 把 **项目信息 + 甲方信息 + 交货和服务要求** 三项拼成「Step02 关键解析结果」Markdown，供全局事实设定与正文生成使用（只取 `status === 'success'` 的项）。

### 5.5 任务状态与重启恢复

- 运行时事件附带 `bidItem`（当前解析项）与 `technicalPlanPatch`（projectOverview/techRequirements 同步）；
- 重启恢复：
  - `bid-analysis` 残留 running/pausing → 转 `error`「上次招标文件解析未完成，请重新解析」，并把所有 still-running 的解析项标为 `error`；
  - `bid-section-extraction` 残留 → 转 `error`「上次多标段识别未完成，请重新识别」，同时写 `bidSectionExtractionStatus='error'`；
- 页面卸载不取消任务；重新挂载靠 Store 快照 + 活动任务回放。

## 6. 调用流程（全链路）

### 6.1 启动解析

```
BidAnalysisPage.startAnalysis()
  ├─ checkBidSections()                → technical-plan:check-bid-sections → detectBidSections()
  ├─ saveBidAnalysisConfig()           → technical-plan:save-bid-analysis-config
  ├─ startBidSectionExtraction()       → tasks:start-bid-section-extraction（多标段且未选范围时）
  └─ startBidAnalysis()                → tasks:start-bid-analysis
        → taskService.startBidAnalysis(payload)
        → runBidAnalysisTask({ aiService, workspaceStore, updateTask, checkpointTask, payload })
```

`startBidAnalysis` payload：

```ts
{ mode, selected_task_ids, task_ids?, force_rerun? }
```

- `task_ids`：只重跑指定项（页面「重新解析此项」）；
- `force_rerun`：**由页面自动判定**——未指定 task_ids 且选中项全部 success 时为 true（即「重新解析」按钮），此时清空下游。

## 7. 页面与交互汇总

**命令条**：`STEP 02 招标文件解析` + 配置 chip（单/多标段 · 解析模式 · N 项）+ 齿轮按钮 + 主按钮（开始解析 / 解析中 / 重新解析 / 重试失败项(N)）。

**左侧任务列表**：按 5 个分组展示选中解析项，每项显示中文名、字数（或描述）、状态（待解析/解析中/已完成/失败/未提取到）；顶部有可折叠进度条与提示语（含「正在优化提示词缓存」「关键项已解析完成…」「X未提取到有效内容，请重新解析该项」）。

**右侧阅读区**：
- JSON 项 → `JsonResultTable` 中文两列表格（约 60 个字段中文映射写在 `jsonFieldLabels`）；
- Markdown 项 → `MarkdownRenderer` + `MarkdownFullscreenViewer` 全屏；
- 操作：复制、失败/未提取到时「重新解析此项」。

**配置弹窗**：
- 投标范围：单标段 / 多标段（AI 识别）+ 识别/更换/选择标段按钮 + 当前标段 chip；
- 解析范围：只解析关键项（默认）/ 完整解析（更多 Token）两个预设；
- 关键项（6 项，勾选框禁用，标「必选」）与其他项（12 项，可勾选）；
- 操作：取消 / 保存配置 / 开始解析。

**其他交互**：
- 多标段识别成功且未选范围时自动弹出选择弹窗；

- 解析结果**只能逐项复制**，没有整体导出（Word/JSON）入口。

## 9. 失效与联动

| 触发 | 影响 |
|---|---|
| `force_rerun` 全量重解析 | 重置所有选中项为 idle；清空目录数据、全局事实、正文任务/sections/plans/图片计划/runtime；下发 `projectOverview=''`、`techRequirements=''` |

## 11. 观察与风险点

1. **解析项定义双份**：Main 与 Renderer 各维护一份 18 项定义，Prompt 细节已出现分叉（技术评分要求是否区分两类）。新增/修改解析项必须同时改两处，否则页面展示与实际执行不一致。
2. **Markdown 缺失才重跑一次，JSON 项不重跑**：`runBidAnalysisPromptTask` 只对 `output === 'markdown'` 的整项空结果重试一次；JSON 项解析失败只依赖 `aiService` 自身的重试。
3. **单项失败不熔断**：`Promise.all(runOneSafely)` 让每项独立成败，最终再靠必选项校验兜底；可选项失败容易被忽略。
4. **多标段识别内部吞异常**：失败只写 `status=error` 不抛出，若识别质量差（<2 标段）用户只能重试或改单标段。
5. **标段工作副本是「减法」**：`buildSelectedSectionMarkdown` 只删除明确属于其他标段的行，通用条款全部保留——跨标段共享内容不会被剔除，可能引入其他标段噪音。
6. **解析结果无整体导出**：只能逐项复制，缺少「导出解析汇总」能力。
7. **`force_rerun` 由页面隐式推断**：选中项全部 success 时点主按钮即全量重跑并清空下游，用户可能未预期「重新解析会清空目录/全局事实/正文」。
8. **无独立测试文件**：解析模块没有 `*.test.cjs`（仓库内只有 `outlineGenerationTaskV2.test.cjs`、`knowledgeBaseStore.search.test.cjs` 等），改动主要靠手工链路验证。
