## 1. 模块定位与边界

正文生成是技术方案六步工作流的 **STEP 05（`content-edit`）**，位于「全局事实设定」之后、「方案导出/扩写」之前。它把 Step03 产出的目录树中**标记为 `ai-generate` 的叶子小节**逐个写成正文，并在写完全文后做一串自动矫正（字数、一致性、表格、配图）。

任务定义（`electron/services/taskService.cjs:83`）：

```js
'content-generation': {
  label: '正文生成',
  group: 'technical-plan',
  groupLabel: '技术方案',
  step: 5,
  lockPolicy: 'group-exclusive',
  stateKey: 'technicalPlan',
  field: 'contentGenerationTask',
}
```

- **组内互斥**：与 `bid-analysis` / `outline-generation` / `outline-adjustment` / `global-facts-*` 互斥，同组同时只能跑一个。
- **全局事实暂停会锁死同组**：`assertTaskCanStart` 中只要 `technicalPlan.contentGenerationTask.status === 'paused'`，除 `content-generation + resume` 之外所有 `technical-plan` 组任务都抛错 —— 「正文生成已暂停，请先继续当前正文生成任务或重置技术方案后再启动新的任务。」

## 2. 前置依赖与启动校验

`runContentGenerationTask` 入口（`contentGenerationTask.cjs:2915`）按顺序做硬校验，任一不满足直接 `throw`：

| 顺序 | 校验 | 错误信息 |
|---|---|---|
| 1 | `outlineData.outline` 非空 | `请先生成目录，再生成正文` |
| 2 | `globalFactsText` 非空 **且** `globalFactsTask.status === 'success'` | `请先完成全局事实设定，再生成正文` |
| 3 | 扩写流程：`originalPlanFile` 存在 + `readOriginalPlanMarkdown` 可用 + 分段非空 | `请先上传原方案，再生成正文` / `原方案正文为空，无法执行已有方案扩写` |
| 4 | `resume` 时 `contentGenerationTask.status === 'paused'` | `没有可继续的已暂停正文生成任务` |
| 5 | 存在 `content_mode === 'ai-generate'` 的叶子 | `当前目录没有标记为“AI生成”的正文小节` |
| 6 | `retryContentCorrection` + `targetItemId` 不可同时 | `单小节重新生成不支持重试内容矫正` |
| 7 | `targetItemId` 能在叶子中找到 | `未找到要重新生成的正文小节` |
| 8 | `retryContentCorrection` 时所有叶子必须 success 或 ignored | `只有正文小节全部生成成功或已忽略后，才能重试内容矫正` |

额外一层在 `taskService.startContentGeneration`（`taskService.cjs:1466`）：

```js
if (!technicalPlan.outlineWordControlSnapshot) {
  throw new Error('当前目录没有字数控制生效快照，请重新生成目录');
}
```

即 **字数快照是启动正文生成的硬门槛**；快照由 Step03 目录生成成功时固化到 `technical_plan_meta.outline_word_control_snapshot_json`。

### 3.2 编排计划（content plan）结构

`CONTENT_PLAN_VERSION = 4`。落库结构：

```js
{
  plan_version: 4,
  plan: {
    writing_focus: '1-2 句话本节正文重点',
    knowledge: { item_ids: ['kb-xx', ...] },   // 只允许来自知识库轻量条目 id
    facts:     { titles: ['工期', ...] },      // 只允许来自全局事实分组标题
    table:     { needed: true, purpose: '...' },
    original_material: { restored, optimized, source_ids, source_titles,
                         source_hashes, restored_chars, restored_at, optimized_at }
  },
  table_requirement: 'none' | 'light' | 'moderate' | 'heavy',
  updated_at: ISO
}
```

复用规则 `isStoredContentPlanReusableForTableRequirement`：

- 有 `table_requirement` 记录 → 必须与本次 `tableRequirement` **完全相同**才复用；
- 无记录 → 只有本次为 `'none'` 才复用（历史数据视为「有表格」）。

`pruneContentGenerationPlans` 每次写回时做两件事：剔除已不在叶子集合中的节点、剔除版本不匹配或 `writing_focus` 为空的计划。

## 4. 主流程总览

完整阶段序列（`CONTENT_PHASE_LABELS`，`contentGenerationTask.cjs:2695`）与代码中的实际执行顺序：

```
                    ┌───────────────────────────────────────────┐
                    │ 前置校验：目录 / 全局事实 / 字数快照 / 叶子 │
                    └────────────────────┬──────────────────────┘
                                         ▼
 1 planning                 正文编排（逐叶子 JSON 决策）
                                         ▼
 2 restoring                原方案还原（仅扩写流程）
                                         ▼
 3 generating               正文生成（预热 + 并发 + Agent 兜底）
                                         ▼
 ── 决策点 ──  有未解决小节？ ── 是 ──▶ persistContentDecisionWait（任务 return，等用户）
                                         │ 否
                                         ▼
 4 section-word-adjusting   小节字数调整（strictSectionWords 时）
                                         ▼
 5 original-auditing        原方案覆盖检查（扩写 + 开关开启）
                                         ▼
 6 auditing                 全文一致性检查（默认开启）
                                         ▼
 7 table-cleaning           表格清理（仅 tableRequirement === 'none'）
                                         ▼
 8 final-section-word-adjusting  最终小节复核
                                         ▼
 9 total-word-adjusting     全文字数调整
                                         ▼
10 illustration-planning    全文图片编排（Agent）
                                         ▼
11 illustration-generating  全文图片生成
                                         ▼
   有效性检查（无有效可读内容 → status error） → phase: done
```

**单小节重新生成（`targetItemId`）走一条裁剪过的分支**：`original-auditing` → `auditing` → `table-cleaning` →（`strictSectionWords` 时）`section-word-adjusting`；**跳过** `final-section-word-adjusting`、`total-word-adjusting` 和全部配图阶段。且一致性审计在单节模式下被**强制降级为 `normal`**（`consistencyRepairMode = targetItemId ? 'normal' : requestedConsistencyRepairMode`）。

### 4.1 运行模式标志位

| payload 字段 | 含义 | 关键副作用 |
|---|---|---|
| `resume` | 继续已暂停任务 | 读 `previousState`，恢复 `contentRuntime` 与 `completed_stages` |
| `regenerate` | 全量重生成 | `fullRegenerate` 时清 Mermaid 缓存 + 清空目录 content |
| `targetItemId` | 单小节重新生成 | 走裁剪分支；成功后自动进入后续流程 |
| `requirement` | 单节重生成的额外要求 | 注入编排和生成 Prompt |
| `retryFailedSections` | 只重跑失败/未完成小节 | `tasksToRun = 未解决叶子`；**忽略 payload 里的 generationOptions，改用已存配置** |
| `continuePostProcessing` | 忽略未解决小节继续 | 先把未解决小节标为 `ignored`，`tasksToRun = []` |
| `retryContentCorrection` | 跳过生成，只跑矫正 | `tasksToRun = []`，所有成功小节加入 `touchedItemIds` |
| `rerunIllustrations` | 仅重新配图 | 清除旧配图后重新跑编排 + 生成 |
| `simulatePartialFailures` | 开发者模式随机失败 | 需 `developerModeEnabled` 且 `tasksToRun.length > 1`；随机选 `min(5, n-1, max(1, round(n*0.2)))` 个 |
| `generationOptions` | 本次配置 | 见 §11 |

派生标志：

```js
runOnlyIllustrationPlanning  = rerunIllustrations
                            || (resume && runtime.phase === 'illustration-planning')
                            || (retryContentCorrection && 上次 stats.phase === 'illustration-planning')
runOnlyIllustrationGeneration= (resume && runtime.phase === 'illustration-generating')
                            || (retryContentCorrection && 上次 stats.phase === 'illustration-generating')
runOnlyIllustrationStage     = 上面两者之一
regenerate = !resume && !retryContentCorrection && !rerunIllustrations
             && !retryFailedSections && !continuePostProcessing && payload.regenerate
```

`tasksToRun` 计算（`:3088`）：

```js
let tasksToRun = leaves.filter(({ item }) => {
  const section = sections[item.id];
  const content = section?.content || item.content || '';
  const originalState = getOriginalMaterialRuntimeState(item);
  return regenerate
    || (section?.status !== 'ignored'
        && (section?.status === 'error'
            || !String(content).trim()
            || originalState.needsOptimization
            || originalState.needsRestoreRepair));
});
```

即：**已有非空成功正文的小节默认跳过**（增量续跑），除非是 `regenerate`、状态为 `error`、内容为空、或原方案需要优化/修复还原。

### 5.1 编排决策的 5 个输出项

### 5.2 表格候选的全局择优

`table.needed` 只是**进入候选池**，不是最终一定生成。全局配额：

```js
maxTablesForRequirement(requirement, leafCount):
  none     → 0
  light    → floor(leafCount * 0.2)
  moderate → floor(leafCount * 0.4)
  heavy    → null   // 不限
```

`refreshRunLimits` 会扣掉本轮之外已保留的表格数。`pickDistributedTableTargets(plannedItems, limit)` 用**分段取中点**的方式在候选里分布式挑选，避免表格全挤在前面几节：

```js
for (let slot = 0; slot < limit; slot += 1) {
  const start = Math.floor((slot * n) / limit);
  const end   = Math.floor(((slot + 1) * n) / limit);
  const group = plannedItems.slice(start, Math.max(start + 1, end));
  selected.set(group[Math.floor(group.length / 2)].item.id, ...);
}
```

### 5.3 提示词缓存预热

`planAll` / 后续每个并发阶段都用同一套模式：**第一项串行执行 → `continueAfterPromptCacheWarmup` → 其余并发**，让首呼打通提示词缓存后再放量。

```js
const [warmupTarget, ...remainingTargets] = targets;
await handle(warmupTarget);
pauseIfRequested(...);
if (remainingTargets.length) {
  continueAfterPromptCacheWarmup(`…预热完成，开始并发处理剩余 ${remainingTargets.length} 项。`);
  await runItemsWithWorkerPool(remainingTargets, contentConcurrency, handle, isPauseRequested);
}
```

## 6. 阶段 2：restoring —— 原方案还原（仅扩写流程）

运行时状态由 `getOriginalMaterialRuntimeState(item)` 计算（`:3782`）：

| 字段 | 条件 | 后续处理 |
|---|---|---|
| `validRestored` | `restored && 所有 source_id 都能在原方案分段中找到 && 有正文` | 可作为覆盖审计对象 |
| `needsRestoreRepair` | `restored && !validRestored` | 重新进入还原 |
| `canRebuildRestoredContent` | `restored && 所有 source 有效 && 当前无正文` | **直接拼接分段重建，不调模型** |
| `needsOptimization` | `validRestored && !optimized` | 生成阶段走「还原扩写 Prompt」 |

`restoreOriginalMaterialsIfNeeded` 两条路：

1. **可直接重建** —— `buildOriginalMaterialFromSegments(segments)` 把分段内容拼起来，标记 `restored: true, optimized: false`；
2. **需要映射** —— 调 `buildOriginalMaterialRestoreMessages` 让模型输出每个小节对应的 `source_ids`，再落 `original_material`。

若映射提示词长度超过 `context_length_limit * AGENT_CONTEXT_THRESHOLD_RATIO`（默认 400000 × 0.7 = 280000），切换为 **Agent 文件模式**（把原方案分段写成 workspace 文件交给 Agent 处理）。

原方案分段最大长度 `ORIGINAL_PLAN_SEGMENT_MAX_CHARS = 6000`。

## 7. 阶段 3：generating —— 正文生成

### 7.1 `runOne` 主路径（`:4187`）

```

  ↓

  ↓

           : (regenerate || retryItemIds.has(id)) ? '' : previousContent
  ↓

  ↓

  : aiService 普通调用
  ↓
```

### 7.2 生成 Prompt 的硬约束（`buildChapterContentMessages`）

1. 专业准确、与章节标题描述一致；
2. 技术方案不是宣传报告，**朴实无华，不要假大空**；
3. 不用奇怪连接词，**避免"AI 味"**；
4. 围绕章节标题/描述/编排重点，**不发散**；
5. 表格：由 `contentPlan.table.needed` 决定，未编排表格时**严禁输出 Markdown/HTML 表格**；
6. **严禁输出 Mermaid / PlantUML / Graphviz / flowchart / sequenceDiagram 等图表代码块**——配图由系统另行处理；
7. 表格单元格内不用 `<br>`；
8. **严禁使用 Markdown 标题语法（#…######）**，分层只能用普通段落、无编号列表、表格或无编号加粗引导语（如 `**实施要点：**`）。

### 7.3 字数引导

`computeGenerationWordTarget`：

```js
if (!strictSectionWords) return 0;
if (!(maximumWords > 0) || !(leafCount > 0)) return 0;
const derived = Math.floor((maximumWords * 0.8) / leafCount);   // GENERATION_WORD_TARGET_RATIO = 0.8
return Math.max(sectionMinimumWords, derived);
```

注释说明动机：留出折扣缓冲，避免所有小节都顶着预设字数生成导致初稿总量**系统性超上限**。

`buildSectionWordRequirement` 区分强弱控：

- 强控：`目标约 X 字，硬性上限 Y 字，绝对不得超过上限；宁可略短也不要为凑字数扩写`
- 非强控：`建议 X 至 Y 字（目标约 X 字）…最终由全文字数流程统一调整`
- `preserveOriginalMaterial` 时追加：`字数要求不能覆盖保留原方案实质内容的要求`

### 7.4 并发与预热分组

```js
contentConcurrency = normalizeContentConcurrency(aiConfig.concurrency_limit)        // 默认 10
imageConcurrency   = normalizeImageConcurrency(aiConfig.image_model?.concurrency_limit) // 默认 2
```

预热键按 **还原/普通 × 表格/无表格** 四类分组（`getContentPromptWarmupKey`）：

```js
`${originalState.needsOptimization ? 'restored' : 'normal'}:${contentPlan?.table?.needed ? 'table' : 'plain'}`
```

### 7.5 Agent 统一封装 `runContentAgentTask`

所有 Agent 调用共用同一包装：

- `setInterval(abortAgentIfPauseRequested, 1000)` 每秒轮询暂停信号，命中即 `abort`；
- `runAgentTaskWithRecoveredOutput(..., timeout_ms: 30 分钟, max_retries: 1)`；
- 支持 `agentPartialOutput` 恢复（Agent 中断但已有部分输出时尝试抢救）；
- `validateOutput` 在落库前强校验，不通过即视为失败。

### 7.6 失败降级

`runOne` 的 catch 分支**保留已有有效正文**：若 `previousContent` 非空且状态不是 error，会保持成功态；只有完全无内容才标 `error`，错误信息写入 `sections[id].error`。开发者随机失败模式在此处 `throw new Error('开发者模式：随机模拟正文生成失败')`。

## 8. 决策点：未解决小节

生成结束后（`!runOnlyIllustrationStage && !targetItemId && !retryContentCorrection && !continuePostProcessing`）：

```js
const unresolvedContexts = leaves.filter(({ item }) => isUnresolvedContentSection(sections[item.id]));
if (unresolvedContexts.length) { persistContentDecisionWait(unresolvedContexts); return; }
```

`isUnresolvedContentSection(section)` = `status !== 'success' && status !== 'ignored'`。

`persistContentDecisionWait` 落库：`phase = 'generating'`、`awaiting_content_decision = true`，日志提示「请重试失败小节，或确认忽略后继续后续流程」，**任务正常 return（不是错误）**，前端弹决策卡片。

用户三个选项（ContentEditPage）：

| 操作 | payload | Main 行为 |
|---|---|---|
| 重试失败小节 | `retryFailedSections: true` | `tasksToRun = 未解决叶子`，本轮只跑这些 |
| 忽略并继续 | `continuePostProcessing: true` | 先把未解决小节标为 `ignored`，再跑后续全部阶段 |
| 重试内容矫正 | `retryContentCorrection: true` | 跳过生成，直接进一致性/字数/配图 |

## 9. 字数控制体系

### 9.1 字数快照

```js
normalizeOutlineWordControlSnapshot(value) → {
  enabled, minimumWords, maximumWords, sectionWords,
  strictSectionWords: sectionWords > 0 && Boolean(source.strictSectionWords),
  sectionMinimumWords: ceil(sectionWords * 0.8),
  sectionMaximumWords: floor(sectionWords * 1.2),
}
```

### 9.2 小节字数调整（阶段 4 / 阶段 8）

- 触发：`strictSectionWords === true`；
- 范围：`[ceil(S×0.8), floor(S×1.2)]`；
- 每个小节最多 `MAX_WORD_ADJUSTMENT_ROUNDS = 3` 轮；
- 粒度：`|current - S| / S > 0.2` 用 `paragraph`，否则 `sentence`；
- `adjustSectionToRange` 返回 `false` 表示 3 轮后仍越界 → 进入 `unresolved`；
- 阶段 8（`final-section-word-adjusting`）是矫正阶段改动正文后的**二次复核**，逻辑相同但 `stage = 'final-section'`。

### 9.3 全文字数调整（阶段 9）

`getTotalWordDirection`：低于 `minimumWords` → `expand`；高于 `maximumWords` → `shrink`；否则结束。

| 参数 | 值 | 说明 |
|---|---|---|
| `TOTAL_WORD_ADJUSTMENT_BATCH_SIZE` | 10 | 每轮最多选 10 个小节 |
| `MAX_WORD_ADJUSTMENT_ROUNDS` | 3 | **缩写**最多 3 轮（扩写无轮次上限） |
| `MAX_EXPANSION_NO_PROGRESS_ROUNDS` | 3 | 扩写连续 3 轮没涨字就停 |
| `TOTAL_WORD_SHRINK_SECTION_RATIO` | 0.25 | 强控下单节单次最多减 25% |
| `TOTAL_WORD_SHRINK_MIN_CAPACITY_RATIO` | 0.3 | 缩写时过滤「可缩空间 < 平均预算 30%」的小节 |
| `DEFAULT_SECTION_WORD_GUIDANCE` | 3000 | `sectionWords === 0` 时的内部指导值，**不是小节上限** |

**扩写预算分配**：先按「小节指导缺口」比例分配，余数按小数部分从大到小补 1；剩余额度再按均摊补齐（受 `capacity` 限制）。

**缩写预算分配**：`fairShare = ceil(剩余 / 剩余节数)`，单节受 `ratioCapacity`（25%）、`readableCapacity`（至少留 1 字）、强控下的 `sectionMinimumWords` 三重限制。

### 9.4 字数调整的硬校验（`requestWordAdjustment`）

模型返回后逐条拒绝：

```js
if (mode === 'expand' && nextWords <= currentWords) throw new Error('扩写后字数没有增加');
if (mode === 'shrink' && nextWords >= currentWords) throw new Error('缩写后字数没有减少');
if (Math.abs(nextWords - currentWords) > options.maximumChangeWords) throw ...;
if (Math.abs(nextWords - targetWords) >= Math.abs(currentWords - targetWords)) throw ...;
```

校验不通过 → 记录「全文字数调整未应用：{id}，{原因}」并计入 `total_adjustment_batch_failed`，**不会把正文改坏**。

### 9.5 收尾警告

任务结束时若仍有越界：

- 全文：`CONTENT_WORD_CONTROL_WARNING = '经多轮修复，字数仍未达预期，请您人工核对'`
- 单节：`SECTION_WORD_CONTROL_WARNING = '字数未达预期，请您人工核对'`

写入 `stats.word_control_warning` 并追加到日志。

## 10. 审计与矫正阶段

### 10.1 原方案覆盖检查（阶段 5，`original-auditing`）

**前置**：`isExpansionWorkflow && enableOriginalPlanCoverageAudit`。默认值：

```js
enableOriginalPlanCoverageAudit = isExpansionWorkflow
  && Boolean(generationOptions.enableOriginalPlanCoverageAudit ?? false);  // 默认关闭
originalPlanCoverageRepairMode  = isExpansionWorkflow && !targetItemId
  ? requestedMode : 'normal';   // 默认 'agent'
```

**normal 路**（逐节）：

- `buildOriginalCoverageAuditMessages` → 每个来源段返回 `covered` / `partial` / `missing` / `conflict`；
- `partial` + `missing` 进入修复队列，`repairOriginalCoverageSection` 最多 `ORIGINAL_COVERAGE_REPAIR_MAX_ATTEMPTS = 2` 次局部补写 patch；
- **`conflict` 不自动修**，日志明说「保留给一致性审计或人工核对」；
- 每次尝试若 `patch` 应用后正文无变化 → 记为失败并携带原因重试。

**agent 路**（全量）：

- 输入 `original-coverage-sources.md` + `technical-plan.md`；
- Agent 自行决定工作方式（可搜索/分段读/建索引/多轮编辑），5 步进度；
- 输出校验：`parseAgentSectionMarkdown` + `validateAgentConsistencySections`（未知小节 / 缺小节 / 把非空小节改成空 都抛错）；
- **失败不中断**：catch 里只记录「N 个小节需人工核对，任务将继续进入后续流程」。

### 10.2 全文一致性检查（阶段 6，`auditing`）

**默认开启**（`?? true`）。`consistencyRepairMode` 默认 `'agent'`，但**单小节模式强制 `'normal'`**。

**normal 路**：

1. `buildConsistencyAuditGroups`：按 `CONSISTENCY_AUDIT_GROUP_WORD_LIMIT = 300000` 字切组（超过就 2 组、3 组…直到每组不超限）；
2. 每组一次 `collectJsonResponse(buildConsistencyAuditMessages)`，只审计组内小节；
3. 冲突按 `section_id` 归并 → `repairConsistencySection` 局部 patch，最多 `CONSISTENCY_REPAIR_MAX_ATTEMPTS = 2` 次；
4. patch 必须**唯一定位**替换内容，否则报错「未能唯一定位替换内容」。

**agent 路**：

- 输入 `global-facts.md`（全局事实变量 + Step02 关键解析结果）+ `technical-plan.md`；
- 要求：保留章节编号/标题/HTML 注释标记/section id，不改结构，只改标记之间；
- 优先以 `global-facts.md` 为准；`globalFactsMode` 为 `placeholder` 时追加「不得把【待填写】改成具体值，也不得为缺失项杜撰事实」；
- 单节模式下 `writableIds = new Set([targetItemId])`——**只回写目标小节，其他小节的 Agent 修改被丢弃**；
- ⚠️ **失败会 `throw`**（与覆盖审计不同），注释写明「已保留原正文，未回退普通修复」，但异常会向上传播中断任务。

### 10.3 表格清理（阶段 7，`table-cleaning`）

**仅当 `tableRequirement === 'none'` 时执行**（把之前编排出来的表格转成普通文字）。

- `extractContentTableBlocks`：抽取 Markdown 表格（表头 + 分隔行 + 后续行）与 HTML `<table>`，**排除代码围栏区域**；
- `createTableCleanupBatches`：按 `TABLE_CLEANUP_BATCH_CHAR_LIMIT = 30000` 分批，每块附 `TABLE_CLEANUP_CONTEXT_CHARS = 600` 字上下文；
- 批次**倒序**处理（`batches.reverse()`），避免前面的替换打乱后面表格的字符偏移；
- 若模型返回的 `replacement_text` 里仍含表格（`containsContentTable`）→ 跳过该表格；
- 结果 `applyRangeEdits` 按字符区间替换，逐批落库。

### 10.4 有效性检查（收尾）

```js
if (countContentWords(content) > 0) { status = 'success'; continue; }
saveSection(item, { status: 'error', content, error: '正文最终结果没有有效可读内容' });
```

`taskStatusFor`：只要还有 `!success && !ignored` 的叶子 → 任务 `status = 'error'`；否则 `success`。

## 12. 全文配图

### 12.1 编排（阶段 10）

`runIllustrationPlanning` 开始前先 `stripGeneratedIllustrationsFromDocument` 清除旧配图，再 `clearIllustrationFiles()` / `clearUnreferencedGeneratedImages()`。

**可编排小节（eligible）判定**：叶子 && `content_mode === 'ai-generate'` && `sections[id].status === 'success'` && 有正文。

三类图片配置：

| kind | 默认上限 | allowed_types | 说明 |
|---|---|---|---|
| `html` | 10 | 用户自定义 `htmlImageTypes` | 配置允许的复杂图表；可跨同父连续多节 |
| `ai` | 6 | `engineering_diagram`（专业工程图示）、`realistic_photo`（专业实景图片） | 设备/现场/工程空间/实体部署等具象内容 |
| `mermaid` | 5 | `process`（流程图）、`hierarchy`（层级图）、`responsibility`（职责关系图） | 只用于简单流程、层级、职责关系 |

`limit <= 0` 会直接把该 kind 置为 `enabled: false`。

**Agent 输入**：`technical-plan.md`（带 `yibiao-section-start/end` 标记）、`outline-tree.json`、`illustration-config.json`。Prompt 有 13 条规则，关键几条：

- `limit` 是上限，绝不能超；
- `title` 是最终写入正文的完整图注，建议 4-15 字，禁止冗长；标准化后**不得重复**；
- `kind` 只能是 html/ai/mermaid，`image_type` 必须来自 `allowed_types`，且要求先读 `type_descriptions` 的中文含义再判断，**不得按英文单词猜测**；
- AI 与 Mermaid 每项只能引用一个叶子小节，`placement` 必须 `after`；
- HTML 可引用同父且顺序连续的多个叶子，说明类用 `before`、总结类用 `after`；
- 同一小节只允许编排一张图；冲突时优先级 **html > ai > mermaid**。

**`resolveIllustrationPlan` 的程序侧强校验**（Agent 输出不可全信）：

- 根对象只允许 `items`；每项只允许 6 个字段；
- `title` ≤ 20 字、不能以「图：」开头；`priority` 必须 1-5 整数；
- `section_ids` 非空不重复，且必须都是 eligible；
- 非 html 只能单节；单节 `placement` 必须 `after`；html 多节必须**同父 + 目录顺序连续**；
- 按 `kind` 顺序（html→ai→mermaid）+ priority 降序 + 目录顺序择优，占用小节互斥；
- 最终标题标准化去重，重复直接 `throw`；
- `item_id = sha256(item).slice(0, 24)`，`revision = sha256(planItems).slice(0, 24)`。

`ILLUSTRATION_PLAN_VERSION = 3`；生成阶段若 `plan_version !== 3` 直接抛「图片计划版本无效」。

### 12.2 生成（阶段 11）

三组并行：

```
Promise.allSettled([
  runTextGroup(),                                        // 文本组
  runItemsWithWorkerPool(aiExecutions, imageConcurrency, …)  // AI 生图组
])

runTextGroup = 
  runItemsWithWorkerPool(normalTextExecutions, contentConcurrency, …)  // mermaid + 短 html
  → 串行 agentHtmlExecutions                                          // 超长 html（> HTML_AGENT_THRESHOLD_CHARS）
```

- 恢复时把 `generation.status === 'running'` 的项重置为 `pending`；
- 单张失败 → `status: 'error'` + 写日志，**不中断其他图片**；
- 全部完成后 `applyGeneratedIllustrationsToDocument` 把图片按 `placement` 插回小节正文，`rebuildContentWordCounts()` 重算字数。

## 13. 暂停、断点续跑与崩溃恢复

### 13.1 暂停机制

```js
function pauseIfRequested(message) {
  if (!isPauseRequested()) return;
  persistPausedContentGeneration(message);
  throw createContentGenerationPausedError();   // CONTENT_GENERATION_PAUSED
}
```

`pauseIfRequested` 被插在**每一个阶段之间、每个批次之前、每个 Agent 调用前后**，粒度很细。

`persistPausedContentGeneration` 落库 `status: 'paused'` + `pause_requested: false` + 当前 `outlineData` / `sections` / `plans` / `runtime`。

顶层 catch 分三类：

| 错误 | 处理 |
|---|---|
| `isAiQueueScopePausedError` | 日志「未发起的 AI 请求已从队列丢弃」，落 paused，return |
| `isContentGenerationPausedError` | 落 paused（已在 pauseIfRequested 落过），return |
| 其他 | 写 `content.task.error` 并 `throw`（任务变 error） |

页面暂停时 `taskService` 还会调 `aiService.pauseQueueScope(control.queueScopeId)` 直接把排队中的 AI 请求丢弃。

### 13.2 断点续跑

`contentRuntime`（`normalizeContentGenerationRuntime`）持久化这些键：

```js
{ phase, target_item_id, regenerate_requirement, touched_item_ids,
  completed_stages: [...],
  word_adjustment_stage, word_adjustment_item_id, word_adjustment_round,
  word_adjustment_item_rounds, word_adjustment_completed_item_ids,
  word_adjustment_no_progress_rounds, word_adjustment_round_start_words,
  awaiting_content_decision, updated_at }
```

每个阶段完成后 `markStageCompleted(stage)` 写入 `completed_stages`；恢复时 `if (!completedStages.has('auditing'))` 跳过已完成阶段。字数调整还能精确到「第几轮、已完成哪些小节、每小节已跑几轮」。

### 13.3 应用关闭后的恢复

`taskService.recoverInterruptedContentGenerationTask`（`:953`）：

- 启动时发现 `contentGenerationTask.status` 仍是 active（running/pausing）；
- `normalizeInterruptedContentSections` 把 `running` 且无内容的小节规范化，把中断的 id 记入 `interruptedIds`；
- `inferContentGenerationPhase` 推断中断时的 phase；
- 改写为 `status: 'paused'`、追加日志「上次正文生成因应用关闭而暂停，可点击继续恢复」并广播。

## 17. 风险点与代码现状提示

1. **6758 行单文件且零测试**。`contentGenerationTask.cjs` 没有对应 `.test.cjs`；唯一相关测试是 `contentIllustrationGeneration.html.test.cjs`（HTML 图片渲染）。字数算法、patch 应用、Agent 回写均无自动化覆盖。
2. **两种 Agent 审计的失败语义不一致**。原方案覆盖 Agent 失败只记日志继续；一致性 Agent 失败会 `throw` 中断整个任务（尽管注释说「已保留原正文」）。这是一处容易踩的坑。
3. **扩写流程的原方案覆盖审计默认关闭**（`?? false`），且 `originalPlanCoverageRepairMode` 默认是 `agent` —— 即开启后默认走 Agent 全量改写，改动面比逐节 patch 大得多。
4. **一致性 Agent 在单节模式下只回写一个小节**：Agent 修改了全文，但 `applyAgentConsistencySections(..., writableIds)` 只落地目标小节，其余修改被静默丢弃（这是设计意图，但日志里没有显式提示）。
5. **强控小节字数 + 无全文上限**时 `computeGenerationWordTarget` 返回 0，生成阶段用的是 `sectionWords`，最终可能有相当比例小节需要靠 3 轮调整拉回，`word_control_warning` 会频繁出现。
6. **`tableRequirement: 'heavy'` 的 `maxTables` 为 `null`（不限）**，与 `light`/`moderate` 的比例约束不同；改为 heavy 后表格数量完全依赖模型克制。
7. **`progressFor` 只看小节落地状态**，后续 8 个矫正/配图阶段对主进度条没有贡献，用户在长文场景会看到进度条早早到 100% 后长时间停留在配图阶段（页面用 `progress_detail` 补偿显示）。
8. **提示词硬约束依赖模型自觉**：「严禁 Markdown 标题」「严禁 Mermaid」「不要 AI 味」等规则没有程序侧兜底（只有 `stripRepeatedChapterTitle` 处理重复的章节标题）。
9. **`retryFailedSections` / `continuePostProcessing` 会忽略 payload 中的 `generationOptions`**，用户在失败后调整配置再点重试，配置不会生效。
10. **`ILLUSTRATION_PLAN_VERSION` 强校验**：升级版本后旧计划直接抛「图片计划版本无效」，需要先清计划再重跑。

## 18. 一页速览

| 维度 | 结论 |
|---|---|
| 任务类型 | `content-generation`（step 5，group `technical-plan`，group-exclusive） |
| 主文件 | `electron/services/contentGenerationTask.cjs`（6758 行，无测试） |
| 前置 | 目录非空 + 全局事实 success + 字数快照存在 + 有 `ai-generate` 叶子 |
| 处理对象 | 目录树中 `content_mode === 'ai-generate'` 的**叶子** |
| 阶段数 | 11 个执行阶段 + 1 个决策点（`CONTENT_PHASE_LABELS` 12 项） |
| 核心链路 | 编排 →（还原）→ 生成 →【决策】→ 小节调字 → 覆盖检查 → 一致性 → 去表格 → 小节复核 → 全文调字 → 配图编排 → 配图生成 |
| 并发 | 文本 `concurrency_limit`（默认 10）、图片 `image_model.concurrency_limit`（默认 2） |

| 字数 | 小节 `[0.8S, 1.2S]`；生成目标 `max(0.8S, floor(0.8×max/叶子数))`；全文每轮 10 节，缩写 3 轮 / 单节 ≤25% |
| 主要风险 | 巨型单文件无测试；两类 Agent 审计失败语义不一致；进度条不反映后期阶段 |
