## 1. 模块定位

目录生成是技术方案流程 **STEP 03**，位于「项目文件解析」之后、「全局事实设定」之前。它把 Step02 的技术评分信息与响应文件要求，转成一棵**可直接用于专项方案文件、并区分每个叶子如何被处理**的目录树。

包含三个相关任务：

| 任务类型 | 中文名 | step | 状态字段 | 说明 |
|---|---|---|---|---|
| `outline-generation` | 目录生成 | 3 | `outlineGenerationTask` | 主流程：V2 Agent 多阶段生成 + 用户确认 |
| `outline-adjustment` | 目录AI调整 | 3 | `outlineAdjustmentTask` | 复用持久会话按自然语言调整 |
| （子任务）专项方案模版提取 | — | 3 | `stats.template_agent` | 仅开发者模式，独立普通 Session 并行 |

全部属于 `group: 'technical-plan'`、`lockPolicy: 'group-exclusive'`，与解析/全局事实/正文互斥。

## 2. 数据模型与持久化

### 2.1 目录树表

```sql
-- technical_plan_outline_nodes
node_id TEXT PRIMARY KEY,          -- 层级点号编号：1 / 2.1 / 2.1.1
parent_node_id TEXT,
sort_order INTEGER,
level INTEGER,
title TEXT, description TEXT,
content_mode TEXT,                 -- ai-generate | template-fill | point-to-point | other
content_mode_note TEXT,
source_requirement_id TEXT,        -- 对应评分项 R1/R2…
source_requirement_title TEXT,
knowledge_item_ids_json TEXT,
content TEXT,                      -- 正文（权威存储，STEP05 写入）
created_at TEXT, updated_at TEXT
```

- 保存是「upsert + 删除不在新集合中的节点」（`saveOutlineData`）；
- **正文 `content` 是权威**，不存在其他平行 JSON 缓存；
- `project_name` / `project_overview` 存在 `technical_plan_meta` 的 `outline_project_name` / `outline_project_overview`。

### 2.2 meta 字段

| 字段 | 含义 |
|---|---|
| `outline_mode` | `aligned` / `response-file` / `standalone-technical` |
| `outline_expansion_mode` | `ai-complement` / `original-only` |
| `outline_word_control_options_json` | 当前可编辑的字数配置 |
| `outline_word_control_snapshot_json` | 目录成功时**固化**的快照，正文生成只认快照 |

### 2.3 目录节点字段（生成协议）

| 字段 | 适用 | 说明 |
|---|---|---|
| `id` | 全部 | 层级点号，一级 `1/2`，二级 `2.1/2.2`，三级 `2.1.1`；程序统一 `renumberOutline` 重排 |
| `title` | 全部 | 纯标题，禁止章节编号与 Markdown 标记 |
| `description` | 全部 | 目录说明 |
| `attr` | 仅一级 | `通用` / `商务` / `资信` / `技术` / `其他` |
| `content_mode` | 仅叶子 | 四种内容处理方式（见 §4.2） |
| `content_mode_note` | 叶子且 `other` | 说明特殊处理原因 |
| `children` | 仅非叶子 | **至少 2 个**，禁止单子节点冗余层级 |
| `branch_id` | 内部字段 | Agent 工作流用的技术分支稳定标识，落库前被 `stripOutlineInternalFields()` 剥离 |

结构硬约束：最多 **6 级**；父节点不得有 `content_mode`，叶子不得有 `children`；id 必须与实际父子位置一致。

## 3. 生成配置（四类）

### 3.1 目录模式 `OutlineMode`

| 值 | 页面名称 | 行为 |
|---|---|---|
| `response-file` | 响应文件（默认） | 依据**响应文件要求.md** 生成一级目录（含商务/资信/技术等全部），再在技术分支下展开评分项 |
| `standalone-technical` | 技术文件独立成册 | 一级目录**直接对应技术评分大项**，`attr=技术`、`content_mode=ai-generate`；禁止「技术方案」「施工组织设计」等外层总目录，禁止商务/资信章节 |
| `aligned` | — | 已有方案扩写流程由页面**强制**使用（不暴露给用户） |

### 3.2 原方案目录使用方式 `OutlineExpansionMode`（仅已有方案扩写）

- `ai-complement`（AI 补充）：以技术评分信息为主，原方案辅助生成下级目录；
- `original-only`（仅原方案目录）：目录来源**仅限原方案.md**，不得依据其他资料或专业经验新增章节，也不得为凑字数拆分章节。此模式下知识库**不参与目录生成**（但仍用于后续全局事实与正文）。

### 3.3 字数控制 `OutlineWordControlOptions`

`minimumWords` / `maximumWords` / `sectionWords` / `strictSectionWords`。

目标叶子数计算（`deriveTargetLeafCount`）：

```
sectionWords 缺省取 3000
min>0 && max>0 → ceil( ((min+max)/2) / sectionWords )
仅 max>0      → floor(max / sectionWords) - 2
仅 min>0      → ceil(min / sectionWords) + 2
都没有        → null（由 Agent 自主决定）
```

独立成册时还要过 `enforceMinimumLeafTarget()`：目标不得低于「固定叶子数 + 技术分支数」；开启强控小节字数且 `maximumWords>0` 时，上限为 `floor(max / (sectionWords×0.8))`，若仍低于最小需求直接抛错提示用户调整配置。

### 3.4 参考知识库

`referenceKnowledgeDocumentIds` → `buildKnowledgeFiles()` 生成 `参考知识库/参考资料-N.md`（整篇 Markdown）。`originalOnly && noTechnicalScoreMode` 时不加载知识库。

## 4. 目录节点分类

### 4.1 属性分类 `attr`（仅一级目录）

`通用` / `商务` / `资信` / `技术` / `其他`。生成后默认只把 `attr=技术` 的一级目录勾选进「待扩展」选择列表。

### 4.2 内容处理模式分类 `content_mode`（仅叶子）

| 值 | 中文 | 含义 |
|---|---|---|
| `ai-generate` | AI生成 | 技术方案正文，由 STEP05 生成；字数目标统计的就是这类叶子 |
| `template-fill` | 模板填写 | 从项目文件提取后按模板填写的商务/资信材料 |
| `point-to-point` | 点对点应答表 | 需全部正文完成、Word 页码确定后回填 |
| `other` | 其他模式 | 特殊内容，须在 `content_mode_note` 说明原因 |

页面 `normalizeOutlineContentModes()` + `assertLeafContentModes()` 会校验每个叶子都填了合法模式。

### 4.3 结构分类

- 根节点（一级，带 `attr`）／中间节点（带 `children`，≥2 个）／叶子节点（带 `content_mode`）；
- 技术分支（带 `branch_id`）／非技术分支。

## 5. 工作流程（V2 主流程）

### 5.1 阶段总览

```
① 一级目录生成（initial-outline）        → outline.json
        ↓（任务挂起，等用户确认）
② 用户确认一级目录（OutlineSelectionDialog，可自动确认）
        ↓
③ 评分项结构化 + 目录规划（score-planning）['技术评分项' 存在时]
        → technical-score-groups.json + score-directory-plan.json
        ↓（用户 ask-user 确认映射与层级）
④ AI 生成叶子分配（leaf_allocation，仅多分支且设了字数目标）
        → leaf-allocation.json
        ↓
⑤ 子目录生成（children_generation）      → 覆盖写回 outline.json
        ↓（叶子数与目标不符时）
⑥ 叶子数量调整（leaf_adjustment，ask-user 三选一）
        ↓
⑦ 最终审核与修复（outline_review）       → outline-review.json
        ↓
落库 + 固化字数快照 + 清空下游
```

无技术评分项模式：`③→④` 整段跳过，直接从 ② 进入 ⑤（用 `createNoTechnicalScoreChildrenPrompt`），审核也换成 `createNoTechnicalScoreReviewPrompt`（只看重复目录与专业合理性，不查评分覆盖）。

### 5.2 Agent 工作区文件（7 个 JSON + 若干材料）

| 文件 | 阶段 | Schema | 内容 |
|---|---|---|---|
| `outline.json` | 全程 | `OUTLINE_JSON_SCHEMA` | 目录树（唯一业务产物） |
| `technical-score-groups.json` | ③ | `TECHNICAL_SCORE_GROUPS_SCHEMA` | `{groups:[{requirement_id:"R1",title,description,detail_points[]}]}` |
| `score-directory-plan.json` | ③ | `SCORE_DIRECTORY_PLAN_SCHEMA` | `{allow_root_changes,branches:[{branch_id,root_id,root_title,score_item_level,mappings[]}],extra_titles[]}` |
| `leaf-allocation.json` | ④ | `createLeafAllocationSchema()` | `{mode,target_ai_leaf_count,fixed_ai_leaf_count,allocatable_ai_leaf_count,allocations[]}` |
| `leaf-allocation-context.json` | ④ | 输入 | 程序算出的分支与可分配数量 |
| `outline-review-context.json` | ⑦ | 输入 | 程序算出的确定性检查结果 |
| `outline-review.json` | ⑦ | `OUTLINE_REVIEW_SCHEMA` | `{status,issues[],user_feedback,summary}` |

材料文件：`响应文件要求.md`、`技术评分信息.md`（非 standalone 时也在 ③ 阶段注入）、`项目概述.md`、`原方案.md`、`参考知识库/参考资料-N.md`。

**每次写文件后 Agent 必须调用 `json-validation`（只传 `file_path`），失败先改文件再校验**——这是所有阶段 Prompt 的统一收尾要求。

### 5.3 各阶段要点

**① 一级目录生成**（`createInitialPrompt`）
- 输入材料按模式组合：`originalOnly` 只给 `原方案.md`；无评分模式给 `响应文件要求.md + 项目概述.md [+ 原方案] + 知识库`；常规给 `响应文件要求.md [+ 技术评分信息.md] + 项目概述.md [+ 原方案]`；
- 只生成一级目录，不写 `children`；每个一级目录都填 `content_mode`；
- 产出后任务**挂起**：`updatePersistentTask(status='waiting-outline-selection', phase='outline-selection')`，并把候选写入 `stats.outline_selection`（默认勾选 `attr=技术`）。

**② 用户确认**（`taskControl.waitForOutlineSelection()`）
- 页面 `OutlineSelectionDialog` 让用户勾选待扩展的一级目录；
- `saveOutlineSelection({taskId, items, selectedIds})` 校验任务仍是同一个且未结束，写入 `confirmed:true`；
- 有自动确认服务（`autoConfirmationService`），用户一改草稿就 `suppressOutlineSelectionAutoConfirmation`；
- 确认结果只保留选中项并重新编号 → `lockedRoots`。

**③ 评分规划**（`createScorePlanningPrompt`）
- 从「技术评分信息.md」的**技术评分项**提取评分大项（R1、R2…），「技术评分要求」只能当评分标准/扣分规则，不得当评分项；
- 判断技术方案落在哪些分支、评分项应统一处于第几层（`score_item_level`，不预设二级）；
- **必须调用一次 ask-user** 让用户确认（无偏离时≤2 句话；有偏离时说明并给推荐方案 + 一个 `custom=true` 的「调整目录安排」选项）；
- 只有以下偏离需要用户批准：合并/拆分评分项、遗漏评分项节点、增加评分项中不存在的同级大项、改变目标层级、调整用户已确认的一级目录；
- `allow_root_changes` 默认 false（锁定一级目录）。

**④ 叶子分配**（`createLeafAllocationPrompt`，仅当设了字数目标且技术分支 >1）
- 按各分支的评分项数量、细项数量、复杂度分配 `allocatable_ai_leaf_count`；
- 所有 `leaf_count` 之和必须等于可分配数；覆盖全部 `branch_id`；
- 独立成册时 `leaf_count=1` 表示保留一级目录本身作叶子（不生成 children）。

**⑤ 子目录生成**（`createChildrenPrompt`）
- 以 `technical-score-groups.json` 为评分项权威清单、`score-directory-plan.json` 为位置权威规划；
- `branch_id` 是稳定标识，一级目录重排/改名/重编号都不能变；
- `target_title` 基本保持评分大项表述；`detail_points` 用于生成下级；
- 未纳入规划的一级目录保持原样，不得加子目录。

**⑥ 叶子数量调整**（`createLeafAdjustmentPrompt`，目标 ≠ 实际时）
- 固定三选项：`接受当前结果` / `允许 Agent 自行调整` / `自定义需求(custom)`；
- 只能调整 `ai-generate` 叶子的结构，**不得**把 `template-fill`/`point-to-point`/`other` 改成 `ai-generate` 来凑数；
- 接受或调整后记录 `leafWarning`（如「目标为 20，用户已确认最终保留当前 18 个」）。

**⑦ 最终审核**（`createOutlineReviewPrompt`）
- 程序先算 `outline-review-context.json`（确定性检查），Agent **直接采用不得重新统计**：
  - 叶子数量（目标 ±2 为可接受区间）+ 各 `content_mode` 分布；
  - 最大层级、父节点数、单子节点列表、非法叶子 content_mode；
  - 评分映射机械比对：缺失标题 / 多余标题 / 每个 requirement 的匹配情况；
- Agent 只负责语义部分：评分覆盖、近义重复、专业合理性；
- 四类问题 `category`：`leaf-count` / `score-coverage` / `duplicate-directory` / `professional-structure`；
- 只有「标题专业化」「不涉及评分映射节点的明显重复合并」可静默修复（`simple_fix`）；其余必须集中 ask-user 一次（2–5 个互斥选项，第一项推荐，含「保留当前目录」，另有一个 `custom=true` 的「调整修复方案」）；
- 四种 `status`：`passed` / `simple_fix` / `user_feedback` / `user_refuse`。

### 5.4 并行专项方案模版提取（仅开发者模式）

条件：`!standaloneTechnical && aiService.isDeveloperMode() && 项目 Word 原件存在`。

- 用 `ordinaryAgentService.forkPersistentTask(OUTLINE_AGENT_TASK_KEY → TEMPLATE_EXTRACTION_AGENT_TASK_KEY)` 分叉出独立普通 Session；
- 流程：`list-blocks` → 按一级目录 `extract-chapters` → `scan-template-fields` → 分类 fields/ignored → `apply-template-fields` 写入 `w:sdt`；
- 产出 `technical-plan/bid-template.docx` + `bid-template-fields.json`（`fill_by` 为 `ai`/`manual`，签字盖章手印一律 `manual`）；
- 两条分支用 `AbortSignal.any` 互相关联：**任一失败立刻取消另一条**；都成功才算完成；模版不完整则 `clearBidTemplate()` 并失败；
- 没有项目 Word 原件时返回 `{status:'skipped'}`，不影响目录生成。

### 5.5 完成落库

`checkpointTask(success)` 同时写入：

```
outlineData（已剥离 branch_id，带 project_overview）
outlineWordControlSnapshot = 本次生效的字数配置
contentGenerationTask: undefined
contentGenerationSections: {} / contentGenerationPlans: {}
contentGenerationRuntime: undefined / contentIllustrationPlan: undefined
bidTemplateExists = !standaloneTechnical && hasBidTemplate()
```

进度节点：`10 → 20(Agent 活动) → 30(等待确认) → 35 → 50 → 55 → 75 → 88 → 95 → 98 → 100`。

## 6. 汇总与校验机制

| 汇总点 | 实现 | 作用 |
|---|---|---|
| 叶子数量汇总 | `countAiLeaves()` / `countLeavesByMode()` | 只统计 `ai-generate`；按 4 种模式分类计数写进 `stats.outline.leaf_counts_by_mode` |
| 结构汇总 | `collectOutlineStructure()` | 最大层级、父节点数、单子节点、非法 content_mode |
| 评分映射汇总 | `collectScoreMappingCoverage()` | 按分支机械比对期望标题 vs 实际标题，产出 missing/unexpected/每个 R 的 matched |
| 审核上下文 | `buildOutlineReviewContext()` | 把上面三项 + 可接受区间打包成 `outline-review-context.json` 交给 Agent |
| 分支同步 | `synchronizeScoreDirectoryPlan()` | 目录重编号后回填 `root_id`/`root_title`，保证规划与最终目录一致 |
| 编号统一 | `renumberOutline()` / `buildFinalOutline()` | 强制层级点号编号与字段形态 |
| 内部字段清理 | `stripOutlineInternalFields()` | 落库前剥离 `branch_id` |
| 目标修正 | `enforceMinimumLeafTarget()` | 独立成册/强控字数时修正目标叶子数，必要时抛错 |

## 7. 调用流程（全链路）

```
OutlineEditPage
 ├─ technicalPlan.saveOutlineConfig()   → technical-plan:save-outline-config
 │     （知识库 ids、outlineMode、outlineExpansionMode、wordControlOptions）
 ├─ tasks.startOutlineGeneration()      → tasks:start-outline-generation
 │     → taskService.startOutlineGeneration(payload)
 │        · 归一化 outline_mode / outline_expansion_mode
 │        · 启动 patch 清空：outlineData=null、目录任务、全局事实、正文全部下游
 │        · beforeStart：删除 OUTLINE_AGENT_TASK_KEY 与 TEMPLATE_EXTRACTION_AGENT_TASK_KEY 持久任务、clearBidTemplate()
 │        · primarySession: true
 │     → runOutlineGenerationTaskV2()
 ├─ technicalPlan.saveOutlineSelection() → tasks:confirm-outline-selection （一级目录确认）
 ├─ tasks.suppressOutlineSelectionAutoConfirmation({taskId}) （用户改草稿时停自动确认）
 ├─ technicalPlan.saveOutline({outlineData, reason, idMap, affectedNodeIds}) → technical-plan:save-outline
 └─ tasks.startOutlineAdjustment({requirement}) → runOutlineAdjustmentTask
```

`startOutlineGeneration` payload：`{ outline_mode, outline_expansion_mode, word_control_options, reference_knowledge_document_ids, no_technical_score_mode, agent_resume? }`。

### 7.1 一级目录选择的挂起/恢复

- `taskControl.waitForOutlineSelection()` 返回 Promise，页面确认后 `resolve`；
- 重启恢复（`recoverInterruptedOutlineGenerationTask`）：只有**全部满足**才恢复等待——持久任务 `run_id` 一致、`status='waiting-outline-selection'`、`phase='outline-selection'`、`agent_connection='idle'`、有 `session_file`、Session 仍存在、`outline_selection.items` 非空且未 confirmed。此时用 `agent_resume:{phase:'outline-selection'}` + `restoreOutlineSelectionWaiter:true` 重新拉起任务；
- 否则标记持久任务 `interrupted`，任务转 error「上次目录生成未完成，请重新生成目录。」并清理模版。

## 8. 手工编辑与保存原因协议

`saveOutline({ outlineData, reason, idMap, affectedNodeIds })`，`reason` 决定失效范围：

| reason | 场景 | 行为 |
|---|---|---|
| `replace` | AI 调整完成、整体替换 | 清空**全部**旧正文；清空正文任务/sections/plans/图片计划/runtime；目录为空时清字数快照 |
| `edit` | 修改标题/描述/content_mode | 只清理受影响节点（`affectedNodeIds`）的正文 |
| `delete` | 删除节点 | 只清理受影响节点 |
| `add-root` / `add-child` | 新增节点 | 只清理受影响节点 |
| `sort` | 目录排序 | **保留**正文，按 `idMap` 重映射节点、正文状态、运行时和图片引用 |

- 非 `sort` 的变更都会使正文任务/runtime 与全文图片计划失效（`assertOutlineMutationAllowed()` 在正文 running/pausing/paused 时直接拒绝）；
- 页面保存前会 `renumberOutlineItemsWithIdMap()` 重新编号并生成 `idMap`；
- 保存后提示「目录项已更新，相关正文已清空」。

## 9. 目录 AI 调整（`outlineAdjustmentTask.cjs`）

```
前置：requirement 非空 / 已有 outlineData / hasPersistentTaskSession(OUTLINE_AGENT_TASK_KEY)
执行：把当前最新目录（含用户手工修改）覆盖写入 outline.json
     → updatePersistentTask(run_id=当前任务 id, phase='outline-adjustment')
     → agentService.runTask({ persistent_task:{mode:'resume'}, json_validation_schemas, max_retries:0 })
     → 读回 → buildFinalOutline → stripOutlineInternalFields
     → workspaceStore.saveOutline({ reason: 'replace' })   ← 清空全部正文
     → 返回 summary（assistant_text，≤200 字）
```

Prompt 强调：以文件为准而非记忆、与要求无关的保持原样、保持 `attr`/`id`/`content_mode` 规则、含糊时按专业惯例直接执行不要反复追问。

## 10. 页面与交互（`OutlineEditPage.tsx`）

- **生成区**：STEP 03 命令条 + 配置按钮 + 「生成目录 / 重新生成」；进度、日志、阶段提示；

## 11. 失效与联动

| 触发 | 影响 |
|---|---|
| 启动目录生成 | `outlineData=null`、清目录/全局事实/正文任务与结果；删除两个持久 Agent 任务、`clearBidTemplate()` |
| AI 调整完成 / `reason≠sort` 的手工保存 | 清空全部正文（或受影响节点正文）与图片计划 |
| `reason='sort'` | 保留正文并重映射 |
| 重新解析项目文件（`force_rerun`）、切换标段、重导项目文件、切工作流 | 目录与下游全清 |
| 目录生成成功 | 固化 `outlineWordControlSnapshot`，**后续只改当前字数配置不影响已生成目录**；清空正文侧状态 |
| 目录为空 | 清 `outline_word_control_snapshot_json` |
| 正文任务 running/pausing/paused | 禁止任何目录变更（`assertOutlineMutationAllowed`） |

## 13. 观察与风险点

1. **`max_retries: 0`**：目录生成与 AI 调整都无自动重试，Agent 一次失败即任务失败，只能重新生成（代价：清空下游）。
2. **强依赖持久 Session**：AI 调整与重启恢复都要求 `hasPersistentTaskSession`，工作区被清理后必须重新生成目录。
3. **字数目标只是「约」**：最终以 Agent 生成的叶子数为准，允许 ±2；用户接受差异时只写 `leafWarning`，不阻止进入下一步。
4. **`aligned` 模式实际是扩写流程专用**：页面只暴露两个选项，扩写流程强制 `aligned`；V2 主流程里只用 `standaloneTechnical` 布尔分支，`response-file` 与 `aligned` 在生成逻辑上无差异。
5. **模版提取只在开发者模式跑**：正式发布包不会生成 `bid-template.docx`；且两条并行分支任一失败会**互相取消**，模版不完整就整体失败。
6. **测试覆盖极薄**：`outlineGenerationTaskV2.test.cjs` 只覆盖「无评分模式 + 原方案来源限制 + 恢复路径」，评分规划、叶子分配、审核修复等核心阶段没有自动化测试。
7. **`branch_id` 是内部字段**：落库前剥离，但 Agent 若丢失 `branch_id` 会导致评分映射无法同步；`synchronizeScoreDirectoryPlan` 依赖它。
8. **审核由 Agent 自评**：虽然程序提供了确定性检查上下文，但「评分覆盖/重复/专业合理性」仍由模型判断，且 `confirmation_required` 的判定也交由模型。

```
   ↓

```
