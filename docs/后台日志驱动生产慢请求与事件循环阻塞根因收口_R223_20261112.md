## 三、根因定位（离线实测，非推断）

### 3.1 实验方法

R218 已加入「严重阻塞时采集在途任务栈」，但该代码随本轮工作树**尚未重启加载**，
生产日志窗口（11-07~11-11）中没有任何栈采样记录 ⇒ 只能从代码侧实测。

于是做**离线逐 checker 实测**：以生产库真实方案 `8d3594d4`（机电安装施工组织设计）
的 159 章 / 105,402 字直接构造 `PreflightContext`，对 `run_preflight` 的 8 个 checker
逐个计时（探针见 §六「可复用工具」）。

### 3.2 实测结果（修复前）

```
sections=159 facts=175 charts=4 total_chars=105402

=== individual checkers ===
  check_completeness                5.8 ms
  check_standards                  48.9 ms
  check_safety                      0.6 ms
  check_hazard_params               5.8 ms
  check_consistency               201.5 ms
  check_duplication            6420.3 ms   ← 占整轮 96%
  check_traceability                0.8 ms
  check_deliverability             32.1 ms
=== run_preflight (full) ===
  run_preflight              6685.6 ms
```

同时 `_collect_near_groups` 报告 **`pairwise=60086` 并触顶截断**
（`MAX_PAIRWISE_COMPARISONS = 60000`），日志中表现为
`跨章节段落搬运检测触顶截断… 结论可能不完整——部分搬运组可能漏报`。

### 3.3 根因链

```
用户动作「自动修复 / 总检 / 定位 / 暂存」
  → compliance._readiness_overview_compute → asyncio.to_thread(run_preflight)
      → check_duplication → find_cross_section_copies
          → _collect_near_groups：对每个句子取「共享 ≥ 2 个 bigram」的候选，
            再逐对调 sentences_near_match 做 Dice 精判   ← 60086 对 / 6.4s 纯 CPU
      ↓
  ① 单轮预检 ~6.7s 纯 CPU，持有 GIL → 事件循环被饿死 → loop lag 1.1~2.3s（常见）
  ② confirm 的链式重算分支对每个 (章节, 规则) 各重算**一整轮预检**
     → O(k) 放大：4 条 ≈ 27s ≈ 实测 confirm **29.7s**，同期 loop lag **29.15s**
  ③ 阻塞期间所有 HTTP 请求排队 → /sections 被拖到 6~10s、SSE 心跳变慢
  ④ 且 60000 对上限导致**触顶截断**，CON-06 结论不完整（漏报方向）
```

> **两级问题相互放大**：单轮 CPU 太重（①）是根因，请求内重复 N 次（②）是放大器。
> 只修其一，另一个仍在（修 ① 后 confirm 仍要 4×2s；只修 ② 则单轮 6.7s 的抖动仍在）。

### 3.4 该缺陷早已登记但从未落地

`docs/日志深度探索与十模块审计汇总_R107_20261018.md` §P2-6 / §161 行已登记：

> `preflight_engine 跨章节段落搬运检测触顶截断（pairwise=60121）` ×8 —— 结论可能不完整
> （漏报方向），既有告警自 R79 在案，**属容量参数问题（配置类）**；建议**提额或分桶比较**。

R107 之后至今（R108~R222）未落地。本轮把它落到代码级，且**不是简单提额**
（提额会按 O(n²) 线性放大 CPU），而是**从判据本身反导下界**，同时拿到
「更快 + 更完整 + 结论不变」三个结果。

## 五、问题分级与代码修复方案

### P1-A · `backend/app/services/duplicate_detection.py` · 跨章查重两两判定 6.4s + 触顶截断

**根因（代码级）**：`_collect_near_groups` 的候选生成阈值恒为常量
`_MIN_SHARED_BIGRAMS = 2`，且对同一对句子**双向各比一次**；精判入口
`sentences_near_match` 又在每次比较时**重跑 `build_skeleton_key` + `char_bigrams`**
（入参本就是同一函数产出的骨架串，纯重复劳动）。三者叠加 →
真实方案 60086 对精判、6.4s、触顶。

**修复（三项，均为「保结论不变」的精确剪枝 / 等价复用）**：

| # | 改动 | 依据 |
|---|---|---|
| ① | `_candidate_indices` 只保留**前向对**（`idx > self_idx`） | `flat` 按骨架键长度升序 ⇒ 候选满足 `|B| ≥ |A|`；判定对两入参完全对称、`claimed` 只认无序章节对 ⇒ 与旧结论逐字等价，省一半 |
| ② | `_collect_near_groups` 计算**真实交集** `shared = len(a_grams & b_grams)`，按分档双阈值反导下界 `max(⌈tier_cont·min(|A|,|B|)⌉, ⌈tier_dice·(|A|+|B|)/2⌉)` 跳过不可能命中的候选 | 真命中必须**同时**满足 `containment ≥ tier_cont` 与 `dice ≥ tier_dice`，二者共同蕴含该下界；用**真实交集**（非索引层低 DF 计数），故与 `_MAX_POSTING_LEN` 高 DF 剪枝正交，**不引入任何漏判** |
| ③ | 新增 `_near_match_from_grams`，直接复用 `_prepare_sections` 已算好的 bigram 集合算 Dice/containment | `build_skeleton_key` 对骨架串**幂等**（真实方案 2176 句 0 例不幂等，护栏锁定），结论逐字不变 |

> ⚠️ **本轮踩中的陷阱（已做成回归锁）**：首版把下界写成「`max(tier_cont,tier_dice) × 字符长度`」
> 并**下沉到索引层**。生产真实方案实测**漏判 7 对** —— 因为下界必须建立在 **bigram 集合基数**上
> （重复短语的去重 bigram 数远小于字符数），且索引层计数跳过高频 gram、只是真实交集的**下界**。
> 现有护栏 `test_r223_low_distinct_bigram_match_not_pruned` +
> `test_r223_tier_bound_not_pushed_into_index_layer` 双向钉死该教训。

### P1-B · `backend/app/routers/review_autofix.py` · `confirm` 请求内 O(k) 整轮重算

**根因（代码级）**：`_resolve_finding` 每次调用都执行**一整轮** `_readiness_overview_compute`；
`confirm` 的链式重算分支对每个 `(章节, 规则)` 各调一次（4 条 ≈ 27s ≈ 实测 29.726s）。
同循环体内还对每章各查一次 `_load_scheme` / `_build_facts`（与章节无关）。

**修复**：

| 改动 | 说明 |
|---|---|
| 抽出纯函数 `_finding_from_payload(payload, rule_id, section_id)` | 从**已算好**的 payload 取条，无 DB、无重算 |
| `_resolve_finding(..., *, payload=None)` | 新增**仅关键字**可选参数；缺省 `None` 时行为与旧实现**逐字一致**（自算一次），旧调用方零改动 |
| `confirm` 内新增惰性 `_ov_once()` / `_scheme_facts_once()` | 同一请求内**只算一次**总检 / 方案 / 事实；**惰性求值**保证最常见的纯前缀分支零额外开销 |
| 两处 `_resolve_finding` 调用改传 `payload=await _ov_once()` | 消除 O(k) 放大 |

**实测效果**：`confirm` 的链式重算路径由「k × ~6.7s」降为「1 × ~2.3s」。按生产实测 k=4 计，
**29.7s → ~2.3s（约 13×）**，同时消除该时段 29.15s 的事件循环阻塞来源之一。

### 既有护栏重锚 ×1（锁意图，强度不减）

`tests/test_review_autofix_no_persist_20261003.py::TestWiringParity::test_autofix_router_has_no_bare_compute_call`
原本断言「重算调用**恰好 3 处**」（锁实现）。R223 新增 1 处惰性调用点（**同样带 `persist=False`**）后计数变 4 → 红。
按本仓纪律「先问锁意图还是锁实现」重锚为「**每一处**重算调用都必须带 `persist=False`」
（`with_persist == call_sites` 且 `call_sites ≥ 3`）：意图保留、且对「有人新增裸调用」**判别力更强**。
