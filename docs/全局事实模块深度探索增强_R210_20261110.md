## 三、修复项清单（含代码依据）

### FIX-1（P1 · 后端）AI 调整预览不再独占项目级事实写锁

- **锚点**：`backend/app/routers/global_facts.py:158`（路由级 `dependencies=[Depends(_facts_write_guard_dependency)]`）、`:153-185`（依赖实现）、`:3808`（`adjust_facts`）、`:3943`（`if do_apply and ops:` 才是落库分支 ⇒ 预览**零写库**）；`backend/app/config.py:379`（`ai_adjust_timeout: int = 120`）；`backend/app/services/facts_write_guard.py:36`（`LOCK_WAIT_SECONDS = 20.0`）、`:119`（超时 → `FactsWriteConflict`）；`backend/app/routers/sse_handlers.py:7535`（SSE 提取落库**同一把锁**）
- **推理**：预览路径不写任何事实，却在整段 AI 调用（最长 120s）期间持有项目级独占写锁 + DB 租约 ⇒ ① 手工写入 20s 后转 409；② **SSE 事实提取落库抛 `FactsWriteConflict` ⇒ 整轮提取任务被判 failed**（配额白烧）；③ 文档重解析的 `_mark_project_facts_stale` 超时 fail-soft ⇒ **该标 stale 的事实没被标 stale**，正文继续用过时数据。
- **修法**：`_facts_write_guard_dependency` 对 `/adjust` **豁免前置锁**（读路径不加锁），改由端点在**真正落库阶段**（`if do_apply and ops:` 内）调用 `acquire_project_facts_write`，冲突时给出与依赖**逐字同构**的 409（`{"code": "facts_write_conflict", "message": ...}`），并在 `finally` 中释放。
- **关键函数**：`global_facts._facts_write_guard_dependency` / `global_facts.adjust_facts`

### FIX-4（P1/P2 · 前端）事实模块唯一错误文案出口

- **锚点**：后端 `global_facts.py:178`（`detail={"code": "facts_write_conflict", "message": ...}`，全仓唯一对象型 detail）；前端 `useFactsCrud.ts:26`（`e?.response?.data?.detail || ...` 按字符串消费）、`FactsTab.tsx:480`、`factsShared.ts:698`
- **推理**：FastAPI 把 dict 原样放进 `detail` ⇒ 响应体 `{"detail":{...}}`；前端把对象交给 `msg.error` ⇒ React 18 抛 "Objects are not valid as a React child" ⇒ **整条提示不出现**（用户体感「点了没反应」），退化形态 `[object Object]`。
- **修法**：新增 `factsShared.factErrorText(err, fallback)`（字符串 detail 原样 / 对象 detail 取 `message`→`code` / 顶层 `message` / axios `message` / 兜底），三处调用点统一改走该出口。

### FIX-6（P1 · 后端）跨条目冲突回写按条目身份定位

- **锚点**：`facts_cross_validators.py:918-941`（`_mark_cross_conflicts_on_items`：`by_name` 分组 + 只比 value）、`:899-904`（**同文件已加固**的「范围值兼容撤销」按条目身份撤销，注释明写「同名不同 key 的无关条目会被误撤销矛盾标记」）、`:104-110`（`_side()` 只带 name/value/source/confidence）
- **推理**：加固了「撤销」一处、漏了「回写」另一处 ⇒ 同族漏改。被误标的行命中注入门控排除条件（`has_conflict=0 AND is_resolved=1 AND is_simulated=0 AND is_stale=0`）⇒ **事实从正文/目录/导出凭空消失**，用户被迫裁决一个不存在的矛盾。
- **修法**：`_side()` 加法式补 `fact_key`；`_mark` 追加 key 一致性判定（两侧 key 均非空且不等 ⇒ 不连坐；key 缺失时退回旧 name+value 口径，向后兼容）。

### FIX-7（P2 · 后端）危大阈值参数取数

- **锚点**：`facts_classification.py:700-711`（`_extract_number_with_unit` 用 `search` ⇒ 取**第一个**数字）、`:752-804`（`extract_danger_params`，文档承诺「同一参数出现多个候选时取最大值（保守判定，避免低估危大级别）」）、`:801-803`（跨事实取最大）
- **实证**：`extract_danger_params([{'name':'基坑深度','value':'本工程共 3 层，基坑深度 12.5m'}])` 修复前 `{'depth': 3.0}`（层数！）→ 修复后 `{'depth': 12.5}`；`{'name':'支撑高度','value':'支撑高度 24m，分 2 层开挖'}` 修复前 `{'height': 2.0}` → 修复后 `{'height': 24.0}`。
- **修法**：新增 `_pick_param_number(value, unit, keywords)`：**关键词同句优先**（参数关键词之后、同一子句内的第一个数字）→ 兜底**同条事实内取最大**（与跨事实保守口径一致）；跨事实取最大与 `value_kind=='requirement'` 排除口径逐字不变。

### FIX-8（P2 · 后端）来源类别不被引句污染

- **锚点**：`facts_classification.py:590-611`（`classify_source_kind` 把 `source_ref` 整体拼进 blob）、`:564-575`（`SOURCE_KIND_RULES`，顺序即优先级：勘察 > 施工图 > 施工组织设计 > 手工 > 项目文件）
- **实证**：`classify_source_kind('招标文件.pdf', '[{"file":"招标文件.pdf","quote":"本工程含基坑支护及降水，另见施工图设计说明"}]')` 修复前 `'drawing'` → 修复后 `'bid_doc'`；`地勘报告.pdf` + 含「施工图」的引句修复前后均为 `'survey'`；非 JSON 字符串 `source_ref`（`'施工图设计说明'`）修复前后均为 `'drawing'`（向后兼容）。
- **修法**：新增 `_source_identity_text()`，结构化引用只取来源标识字段（file/source/doc_name/name/文档/文件名…），**丢弃 quote**；非 JSON 字符串仍按原文匹配。

### FIX-3（P2 · 后端）底稿待确认清单含「来源已过期」

- **锚点**：`services/dossier.py:105-114`（`collect_facts` 口径两档）、`facts_extractor.py:4088`（`_FACTS_INJECT_WHERE` 四档闸门）、`global_facts_docs.py:1283-1306`（`_mark_project_facts_stale` 批量置 stale）
- **推理**：`is_resolved=1 AND is_stale=1` 的事实**不进正文/导出**（注入门控）却**不进待确认清单**（旧口径）⇒ 底稿写「事实待确认 0 项」而正文实际少一条关键事实 —— 交付前复核**看不出**事实掉出交付物。

## 七、教训归档

1. **「只读路径持锁」是隐蔽的可用性缺陷**：写保护若挂在**路由级依赖**上，任何"其实不写库"的请求都会占锁；而本仓的锁是**项目级独占**（含 DB 租约），持锁 120s 的代价是同项目所有写路径被连带阻塞 —— 包括 AI 提取落库（直接导致整轮提取 failed）。**闸门要落在"真正写"的那一行**。
2. **错误体形状变化会静默吃掉提示**：后端把 `detail` 从字符串改成对象（此处为携带 `code` 语义），前端仍按字符串消费 ⇒ React 抛错 ⇒ 提示**根本不会出现**（而不是"显示难看"）。**跨端契约变更必须同步前端消费出口**，且前端应有唯一错误文案出口，而不是各处内联取 `detail`。
3. **同族加固必须 grep 全族**：本文件里「范围值兼容撤销」早已按条目身份加固（注释写明理由），而「跨条目冲突回写」仍按显示名分组 —— 同一文件、相邻函数、同一类缺陷，只有**一处**被修。
4. **保守口径必须在每个尺度上成立**：跨事实取最大（保守）、跨子句取首个（不保守）⇒ 整句 value 里的"3 层"顶掉"12.5m" ⇒ 危大判定**低估**。**安全方向的判定，取数策略必须逐尺度对齐**。
5. **轮询与用户操作必须分通道**：R208 修掉了"轮询打轮询"，注释里写好了修法（`skipAbortPrev`），但**代码从未落地** —— 注释承诺 ≠ 功能存在（与 R209 教训「声称已修 ≠ 已生效」同族）。
6. **组件副本的门禁口径必须成对锁**：FactsTab 与 UploadParseTab / DocumentParseList 是同一 UI 的两份实现，门禁维度一分叉就出现"上传中点全部重解析（新文件这轮不被解析）""解析中点删除（孤儿产物）"。本轮把 5 处维度对齐并加护栏。
7. **antd 两字按钮文案中间会插空格**（「取 消」「放 弃」）⇒ 测试里按文本找按钮必须先 `replace(/\s+/g, "")` 归一，否则永远找不到（本次实测踩到并当场修正）。
