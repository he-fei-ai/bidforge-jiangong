## 1. SSRF 防护（P0）

**改了什么**

- [config.py](file:///j:/编程/专项方案工具箱/backend/app/config.py)：新增开关
  `ai_allow_private_base_url: bool = False`（环境变量 `AI_ALLOW_PRIVATE_BASE_URL`）。
- [provider_factory.py](file:///j:/编程/专项方案工具箱/backend/app/services/ai/provider_factory.py)：在 `normalize_base_url` 中新增地址校验，辅助函数为
  `_ip_is_forbidden` / `_host_is_forbidden` / `_PRIVATE_HOSTNAMES`。
- [.env.example](file:///j:/编程/专项方案工具箱/backend/.env.example)：写入默认行为、风险与开启方法。

**判定规则（`_host_is_forbidden`）**

1. 主机名去空白、小写、去尾点；空值直接拒绝。
2. 命中 `localhost` / `localhost.localdomain` / `ip6-localhost` / `ip6-loopback` → 拒绝。
3. 字面 IP（IPv4/IPv6）用 `ipaddress` 判定，命中以下任一 → 拒绝：
   `is_private`（10/8、172.16/12、192.168/16、fc00::/7 等）、`is_loopback`（127/8、::1）、
   `is_link_local`（169.254/16，含云元数据 `169.254.169.254`、fe80::/10）、
   `is_unspecified`（0.0.0.0、::）、`is_reserved`、`is_multicast`。
4. 域名：先做 `socket.getaddrinfo`，**逐个解析结果**按第 3 条判定；任一落在受限网段即拒绝
   （防「域名解析到内网」绕过）。
5. 解析失败（DNS 不可达）：按「暂不拦截」处理并记 `debug` 日志 —— 这是有意的 **fail-open**，
   避免 DNS 抖动导致合法公网配置无法保存；真正访问时的 DNS 结果由网络出口策略兜底。

**为什么这样做**

- 保存/导入/探测是用户可控输入进入 `base_url` 的唯一入口，必须在写入前拦截，而不是等请求发出后才失败。
- 采用「解析所有 A/AAAA 记录、任一违规即拒」而非只取第一条，避免多记录里混入内网地址。

**TOCTOU 说明（重要，不能把 DNS 判定当唯一依赖）**

- 校验发生在**保存/探测时点**，运行期 `_build_provider` 不会重复解析；攻击者仍可能
  在「校验后、调用前」把域名改指向内网（DNS rebinding）。
- 因此本防护定位为**降低误配与低成本 SSRF**，不能替代网络层出站控制；生产仍应配合
  egress 防火墙 / 安全组禁止应用服务器访问内网与元数据网段。

**例外开关与兼容性**

- 默认 `false`：拒绝上述地址，**不静默放行**；错误信息明确提示
  `AI_ALLOW_PRIVATE_BASE_URL=true`，并说明适用于 Ollama / vLLM / LM Studio 等本机服务。
- 设为 `true`：跳过上述地址判定（仍保留协议/主机名合法性校验），供自建模型用户使用。
- 兼容性：**库中已保存的内网 Base URL 在运行期仍可继续调用**（运行期不走该校验）；
  但再次「保存 / 导入 / 测试连接 / 拉取模型」会被拒绝，需显式打开开关。这样既不破坏存量，
  又阻断新增风险面。

**如何验证**

`TestSsrfGuard`：8 类内网/回环/元数据地址被拒、公网字面 IP 通过、公网域名通过、
`getaddrinfo` 返回 `10.0.0.5` 时域名被拒、开关打开后放行、错误信息包含恢复指引。

**测试结果**：全部通过（含在新增文件的 30 passed 内）。

- [config.py](file:///j:/编程/专项方案工具箱/backend/app/routers/ai_config/config.py)：新增
  `PUT /ai/config/{id}/enabled`（`set_config_enabled`），写审计 `enable` / `disable`，主配置停用返回 400。
- 前端：状态列新增「启用/停用」`Switch`（主配置禁用），新增 `aiApi.setConfigEnabled` 与 `handleToggleEnabled`。

**为什么偏离字面「加 is_active 过滤」**

- `is_active=1` 是**全局唯一的「当前主配置」**标记，不是「参与调用」开关。若按 `is_active` 过滤降级链，
  结果只会在「当前主配置自己」的候选里筛选，降级链恒为空（历史上 BUG-F-02 的复现路径）。
- 正确语义需要第三个状态：`is_active`（谁在主导调用）、`priority`（顺序）、`enabled`（是否参与）。
  因此新增 `enabled` 列承载「停用但不删配置」的诉求；主配置由接口层禁止停用，避免语义自相矛盾。

**如何验证**：`TestFallbackEnabledFilter` 三条 —— `enabled=0` 不在 `_fallback_chain()`；
通过路由停用后不在链中；主配置停用返回 400。

## 6. BUG-06：空 `secret_key.key` 静默使用临时密钥

**改了什么**

- [crypto.py](file:///j:/编程/专项方案工具箱/backend/app/services/crypto.py)：
  - 空密钥文件分支改为 **WARNING + 删除空文件后走排他重建**（自动修复，不再静默）；
  - 落盘失败降级临时密钥的 `except` 由静默改为 WARNING，明确说明「重启后历史密文不可解」；
  - 新增 `ensure_master_key_ready()`：启动期触发密钥初始化并打印来源。
- [main.py](file:///j:/编程/专项方案工具箱/backend/app/main.py)：lifespan 鉴权检查之后调用上述自检，
  fail-soft（异常不阻断启动）；来源为 `temporary` 时给出明确 WARNING 与修复指引
  （检查 `FERNET_KEY` / data 目录写权限，修复后用「主密钥轮转」重新加密存量密文）。

**为什么**：临时密钥一旦被使用，重启后所有历史密文都将无法解密；必须在启动期就把问题暴露出来，

**如何验证**：`TestKeyRecovery` 覆盖密钥来源与迁移；启动自检在 `test_api_contract` 的 lifespan 中执行（子集回归通过）。
