## 4. 仍未处置的条目

### P2-3 围栏闭合标记在预算截断后丢失

- **现状**：`_repair_closing_fence` 只存在于 `govern_text` 的两条路径（`prompt_material_guard.py:233`、`:263`）。目录生成/审核/补齐/调整链路走的是 `_apply_prompt_context_budget`（`_sse_outline_review.py:154`），该路径直接调用 `allocate_context_budget`，不会补回 `MATERIAL_CLOSE`。
- **为什么现在不做**：只在 `prompt_injection_defense` 与 `prompt_context_budget` **同时开启**时才可能触发；两个开关默认关闭，现有生产行为不受影响。且改法需要跨越 `prompt_governance` 与 `prompt_material_guard` 两个模块的依赖方向（当前 `prompt_governance` 不反向依赖 `prompt_material_guard`，直接调用会引入循环），属于结构性改动。
- **要做才能做**：把"闭合修复"下沉到 `prompt_governance`（或在 `_apply_prompt_context_budget_report` 内做一次 `MATERIAL_OPEN` 计数配对检查），并补一条"两开关同时开启"的用例，断言每段 `MATERIAL_OPEN` 都配平 `MATERIAL_CLOSE`。

### P2-4 `serialize_bounded_json_array` 只裁首条

- **现状**：`prompt_governance.py:960/965` 仍是 `items[0]` 单点判断。首条不超预算、后续某条超大时，超大条目走"整条省略"，而不是"裁到 allowance"。
- **为什么现在不做**：该函数在超预算时会在返回结构里写入 `truncation`（省略条目数/字符数/原因），模型与调用方都能看到"有内容被省略"，不属于静默丢失；且真实触发条件是"首条很小、后续某条极大"，在本项目目录/事实数据形态下概率低。
- **要做才能做**：把 `clip_item` 的适用条件从"仅首条"改为"任一单条自身超 allowance"；注意这会改变已锁定的"未超预算逐字节不变"基线，需要同步更新 `test_prompt_json_budget_20261107.py`。

### P3-1 启动扫描无超时

- **现状**：`main.py:338` 裸 `await run_startup_scan()`；`scan_section_links` 内部 `SELECT id, scheme_id, parent_id FROM sections` 全表读取后整体分类，无时间预算。
- **为什么现在不做**：异常会登记 `failed` 并放行启动（fail-soft 已具备），最坏后果是"启动慢"，不是"启动失败"；`sections` 是单库单表，按项目规模（每方案几十到几百章节）耗时在秒级以内。
- **要做才能做**：给 `run_startup_scan` 套 `asyncio.wait_for`，超时即登记 `failed`（`reason=startup_scan_timeout`）并继续启动；先在真实体量库上量一次耗时，确定阈值。

### P3-2 跨方案父链接检测不到
