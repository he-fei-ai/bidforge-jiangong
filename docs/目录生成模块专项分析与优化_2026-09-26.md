## 3. 本轮修复项（均有代码依据 + 回归测试）

工作区已存在一批**未完成**的接线改动（把 `renumber_section_body_subheadings`
接到两条正文落库路径）。审查发现 3 个缺陷，其中 2 个是接线本身的错误。

### F1 · 编号规范化早于结构重排（编号错位）

- **位置**：`sections.py::update_section`
- **问题**：规范化被放在 `fields` UPDATE **之前**。若同一次请求既改 `parent_id`
  又改正文（如「把第 3 章挂到第 1 章下并补充正文」），规范化读到的是**移动前**的
  `outline_json.id`，随后 `renumber_sections_after_reorder` 又把编号改成新位置
  → 正文子标题永远停留在旧编号，与目录树、导出成稿**永久错位**。
- **修复**：改为「先 `UPDATE` → 再 `renumber_sections_after_reorder` → 最后规范化」，
  按**最终**编号折算。字数/字状态在规范化后同步重算。
- **测试**：`test_move_and_edit_content_uses_new_numbering`

### F2 · 配置开关形同虚设

- **位置**：`config.content_subheading_renumber`（默认 `True`，文档承诺
  「设为 False 回退旧行为」）；`sections.py` / `sse_handlers.py`
- **问题**：探查实证 —— 两处调用点**都没有读取该开关**
  （`inspect.getsource` 校验 `"content_subheading_renumber" in src → False`）。
  用户/运维设 `CONTENT_SUBHEADING_RENUMBER=false` 完全无效。
- **修复**：新增唯一实现 `numbering.normalize_section_content_subheadings()`，
  内部读取开关 + 降级兜底；两条落库路径收口调用，杜绝再次各写一份样板而漂移。
- **测试**：`test_switch_off_keeps_original` / `test_switch_on_normalizes` /
  `test_sse_path_honours_switch`

### F3 · 生成标准报告与落库正文不同源

- **位置**：`sse_handlers._persist_section`
- **问题**：规范化在锁内、且在 `standard_report()` **之后**执行 → 报告按
  「AI 原始编号正文」计算，落库正文却是「规范化后」，两者不是同一份文本
  （正文编号 token 会进入 `extract_number_tokens` 的数值抽取），
  用户按报告看到的证据在落库正文里找不到。
- **附带问题**：规范化要 2 次 DB 往返却放在全局 `_db_write_lock` **内**，
  与本函数 P1-3「锁内只保留最小事务」的设计结论冲突（5 章并发时排队等同一把锁，
  实际并发退化为串行）。
- **修复**：移出锁、移到 `standard_report` 之前。
- **验证**：`inspect.getsource` 断言 `standard_report` 索引 > 规范化索引已反转。

### F4 · 过度失效一致性扫描缓存（回归护栏）

- **位置**：`sections.py::update_section`
- **问题**：我最初把 `_content_renorm_pending` 计入
  `invalidate_consistency_scan_cache` 条件，被既有测试
  `test_content_only_keeps_cache` 拦下（`assert 0 == 1`）。
- **结论**：编号规范化改的仍是 `content` 字段本身 → `content_hash` 已自动失效，
  无需整方案清空。已回退并补注释说明**为何不可**计入。

## 4. 探查结论（未改动，现状正确）

以下为逐项核验后**确认无缺陷**的部分，记录以免后续重复排查：

- **目录树构建**：`_build_tree` 默认不拉 `content` 大字段；子节点按 `sort_order`
  排序；孤儿节点（parent 不存在）自动升为 root，不丢数据。
- **多级编号同步**：删除/新建/拖拽/结构 PATCH 四处入口均调用
  `renumber_sections_after_reorder`，且 `level` 列与 `outline_json.level` 同步回写。
- **竞态守卫**：`outline_generation_in_progress` 覆盖 save-outline / apply-and-save /
  create / update / delete / reorder 共 8 处；只拦 `running/paused`，终态残留不误拦。
- **分步生成状态**：`_advance_outline_phase` 为阶段切换唯一入口，EMA 校准只在切换点
  写入（避免进度条回退）；`_outline_push_value` 走 `_monotonic_progress` 不可回退护栏。
- **断线恢复**：`_partial_holder` 提升到闭包外，`finally` 写 checkpoint；
  `_build_partial_preview` 深拷贝 + 全树规范化，预览与收尾结构逐节点一致。
- **幂等性**：`renumber_section_body_subheadings` 对纯文本/井号/先深后浅/代码围栏
  场景二次运行均零改动（实测验证）。
- **降级命名空间**：`body_subheading_demote_with_children` 使有 DB 子章节的正文
  子标题走 `1）/ a、` 命名空间，与子章节 `X.X` 完全隔离。
- **空数据/超长/编码**：`_validate_outline` 区分「缺 children」与「children=None」；
  节点上限 500（修复轮放宽）；全链路 UTF-8。

## 6. 第二轮修复（2026-09-26 续）：AI 调整目录导致正文丢失

### BUG-5（严重）· `__original_id` 在前后端传递链上被丢弃

**症状**：用户用「AI 自然语言调整目录」改一两个章节标题，确认保存后，
**该方案所有章节已生成的正文全部丢失**（不可恢复）。

**根因（缺陷链，三环叠加，任一环单独存在即造成数据丢失）**：

1. **后端** `sections._save_outline_to_db._preserve_original_ids` 无条件执行
   `node["__original_id"] = node.get("id", "")`
   —— 把 `/adjust-outline` 回传的真实 DB 主键**冲掉**，退化为用 renumber
   覆写后的**展示编号**（`"1"` / `"1.1"`）当主键。
2. **前端** `outlineToTreeNode` 只取 `n.id` 作 key，**不读** `__original_id`
   → key 变成 `"1"`/`"2"`：既非 DB 主键，也不带 `local_`/`upload_` 前缀。
3. **前端** `treeToOutline` 也不回传 `__original_id`。

三者叠加 → `is_new` 判定全为 `True` → 整表重建 → 已生成正文被级联 DELETE。

**实测证据**：`TestAdjustThenSavePreservesContent` 在修复前 3 个用例失败
（正文被清成 `''`），修复后 11 passed。

**修复**：
- 后端：仅在 `__original_id` **缺失**时才用 `id` 兜底（不覆盖已有值）；
- 前端：`outlineToTreeNode` 优先取 `__original_id` 作 key 并透传；
  `treeToOutline` 原样回传；`TreeNode` 类型新增 `__original_id?`。

### BUG-6（由 BUG-5 的测试暴露）· 纯数字编号被当作章节主键

**症状**：AI 新增的章（无 `__original_id`），其 `id` 是 renumber 产物 `"3"`。
前端 `outlineToTreeNode` 把它当 key →
① `isUnsavedLocalKey("3")` = **false** → 前端认为「已落库」，
顶部橙色「未保存」Tag 与左侧 Alert 都不显示；
② 提交给后端时 `id="3"` 匹配不到任何 section → 整表重建 → 正文丢失。

**修复**：引入 `_PURE_NUMERIC_ID_RE = /^\d+(?:\.\d+)*$/`，
`key` 判定改为三档优先级：
1. `__original_id`（真实主键）；
2. **纯数字 id → 一律回落 `upload_` 临时键**（绝不当主键）；
3. 非纯数字 `n.id`（如识别结果的 `"n1"`、UUID）→ 原样使用。

**向后兼容**：无 `__original_id` 的旧路径行为完全不变
（`test_id_only_submit_backward_compatible`）。

## 7. 关于「services → routers 反向依赖」的处置结论

**问题**：`numbering.renumber_section_body_subheadings` 运行时
`from app.routers.export import (...)`，形成 services → routers 反向依赖。

  `numbering.py` 的**函数级 import** 显式规避（模块级 import 会形成循环）。

## 9. 第四轮修复（2026-09-26 续）：清理过时测试与并发闸门口径

### 并发闸门「文档与实现不符」

- **现象**：`test_content_order_concurrency` 与 `test_task_control_semantics`
  两个用例都断言「guarded_gen 内不得持有 `async with _run_semaphore`，
  并发闸门已由 `_WINDOW` 窗口调度器接管」。
- **实测**：代码里既无 `_WINDOW`、也无 `_pending` / `_launch_next`，
  现行实现是**「每任务独立信号量 + FIFO 放行」**
  （`asyncio.Semaphore(effective_concurrency)`，协程按 `leaves` 目录序创建，
  信号量对等待者 FIFO 放行 → 启动顺序 = 目录 DFS 序；`as_completed`
  只影响完成顺序，不影响启动顺序）。
- **结论**：测试断言的是一套**从未落地（或已回退）**的方案；
  而 `sse_handlers` 里那段「并发闸门（严格按用户档位…）」的文档字符串
  也照抄了同一套说法，属**注释与实现不符**。
- **处理**：两边都按**现行实现**校准 —— 实现侧补注释说明真实口径与回退历史，
  测试侧改为锁定真正的不变量（容量取用户档位、闸门在 `wait_resume` 之后、
  禁用全局自适应信号量、`as_completed` 回收）。

### 自身引入的问题（自查修正）

新写的 `test_content_constants_track_settings_changes` 最初用
`importlib.reload(sse_handlers)` 验证「改 settings 后常量跟着变」，
实测会**重建模块级单例**（信号量 / 熔断器 / 配置缓存），

### 11.8 BUG-15（根因级 · 基础设施）· 已关闭连接被当活连接复用

- **触发面**：不是目录模块独有，但**正是全量套件长期红着的 8 个用例的根因**
  （`test_perf_content_pipeline` 4 例 + `test_reasoning_effort_passthrough` 4 例），
  单跑 100% 通过、全量跑必红 → 任何模块都无法可靠做全量验证。
- **根因**（`app/db.py`）：
  1. aiosqlite 的 `Connection._conn` 是 **property**，连接关闭后访问即抛
     `ValueError("no active connection")`（即日志里那条 cryptic 错误的原文）；
  2. `_probe_conn` / `_read_probe` 只把 `disk I/O error` 判为坏连接，
     **已关闭连接**抛的异常落在"非 IO 类异常 → 视为可用"分支被放行；
  3. `get_conn` 只认自定义 `_poisoned` 标记，30s 健康检查 TTL 让死连接在窗口内原样发出；
  4. `_release_pool_conn` / `_release_read_conn` 会把**已关闭的连接放回池**。
- **实证**：
  ```
  旧 _probe_conn(已关闭连接) = True   ← 把死连接当好连接放行
  新 _probe_conn(已关闭连接) = False
  ```
- **修复**：新增 `_is_dead_conn()`（只读 `_connection`/`_running` 属性，**绝不碰
  `_conn` property**）与 `_is_closed_conn_error()`；在 `get_conn`（TTL 短路**之前**）、
  两个探针、写池/读池的 acquire + release、`close_db()`（幂等化）全部接入。
- **测试**：`backend/tests/test_db_dead_connection_20260926.py`（15 例，含
  "判定函数不得触发 `_conn` property"反例自检）。
