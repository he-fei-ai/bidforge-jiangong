# 全局事实「要求 vs 事实口径」字段（value_kind）落地报告 · R80

> 日期：2026-10-15 ｜ 前置：R77《参考软件全局事实机制全流程报告与引入方案》§11.3 P2-3 递延项正式落地
> 原则：零新增依赖；迁移仅「幂等补列」（沿用 chapter/fact_attr 四维标注既有惯例）；历史存量不回填；全部接口契约**加法式**；''（未区分）行读侧行为与引入前**逐字一致**。

---

## 1. 背景与问题定性

R77 引入易标全局事实机制时登记 P2-3：「要求 vs 事实类型字段，需数据迁移，递延」。语义源自任务书原始定义：

- **要求**（requirement）：招标人/规范提出的约束原文 ——「招标人要求工期不超过 90 天」；
- **事实**（fact）：本方案的采用值/承诺 ——「本方案项目总工期为 90 天」。

提取提示词早有「要求 → 事实（响应设定转写）」纪律（`prompts/analysis.py`），但**无字段承载转写成败**：当 AI 无法安全转写（验收标准、规范编号、监测报警值限值等以要求形态存在的条目）而保留要求原文时，下游注入与正文无法区分「这是本方案既定值」还是「这是需要响应的要求」——正文可能把要求口径当本方案口径直接抄写。

## 2. 方案定稿

### 2.1 字段与值域

| 值 | 语义 | 来源 |
|---|---|---|
| `''` | 未区分（历史行/手工行缺省）——读侧按 fact 处理，**行为零变化** | 表默认值 |
| `fact` | 本方案口径：文档明示实值，或已按要求转写为承诺值 | 提取默认 |
| `requirement` | 招标/规范要求原文口径（无法安全转写而保留） | AI 显式标注 / 手工指定 |

非法值（AI 幻觉、客户端脏值）经 `normalize_value_kind` 归一为 `''`，绝不抛错阻断提取（`facts_extractor.py::normalize_value_kind`，单一事实源，解析/落库/手工三处共用）。

### 2.2 迁移（最小 DDL）

- `schema_sql.py`：`global_facts` 建表语句加列 `value_kind TEXT DEFAULT ''`；
- `db.py::_migrate`：幂等补列清单登记 `("global_facts", "value_kind", "TEXT DEFAULT ''")`——旧库启动时自动补列，无需人工迁移、无需清库。

## 6. 遗留与后续建议

1. **数据字典双口径**：requirement 行进入 `build_global_data_dictionary` 时宜标注口径或与 fact 行分别建键（需评估 `iter_consistency_values` 改造面）。
2. **审计豁免**：一致性审计对「要求值 vs 本方案采用值」差异应判合规而非冲突（如要求≤90 天、本方案 85 天）——需在 `consistency_scanner` 冲突判定中引入 value_kind。
3. **前端编辑入口**：事实编辑弹窗可加口径下拉（fact/requirement），当前仅徽标展示。
4. **运维**：需重启后端（`facts_extractor`/`facts_builder`/`global_facts`/`schemes`/`prompts` 常驻）；前端需重建；**无需清库**（启动时自动补列）。
