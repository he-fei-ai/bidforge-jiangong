## 1. 扫描方法

### 1.1 「硬截断」的 AST 判定口径

硬截断指「用一个字符上限直接切掉尾部，且没有任何账目/标记」。统一按 AST 判定，不靠正则匹配源码字符串：

```python
# 判定：Subscript，且 slice 是 Slice(lower=None, step=None, upper=整型常量)
x[:30000]        # 命中
x[:max_chars]    # 全仓口径命中（upper 是名为 max_chars 的变量）
x[:600]          # 命中（是否保留由白名单决定）
x[:N]            # 命中
```

**不命中**的形态（属已知盲区，见 §6）：

```python
x[a:N]           # 有下界
x[::N]           # 有步长
x[:n - 1]        # upper 是 BinOp，不是整型常量/简单变量
x[:len(y)]       # upper 是调用表达式
```

### 1.2 两套扫描器

**A. 全仓口径（本文的原始盘点与现状对照都用它）**

- 范围：`backend/app/**/*.py` 全部模块。
- 计数单位：**每个 AST 切片节点算一处**（同一行出现两次就算两处；不按源码行去重）。
- 纳入条件：`upper` 是整型常量且 `N >= 200`，**或** `upper` 是变量名 `max_chars`（原始基线 6 处、HEAD 4 处；其默认上限可能低于 200，但属于「参数化文本裁剪」，仍纳入）。
- 为什么设 200 字阈值：小于 200 的多是 SSE 预览、错误消息、文件头采样，不属于「文本量级」截断。用这组条件在原始基线上重跑，零留痕数正好复现历史记录的 77；因此把它固定为本文件的复现口径。阈值以下**不代表安全**，只表示不在本清单量级内（见 §6）。

**B. 进模型请求棘轮口径**（仓库内已有测试，`backend/tests/test_prompt_truncation_ratchet_20261107.py`）

只扫「会进模型请求」的源码位置，任何 N 都算（包括 `[:20]` 这类小上限）：

- `render(...)` / `get_prompt(...)` 的实参（`_SINK_FUNCS = {"render", "get_prompt"}`）；
- 赋值/注解赋值**目标变量名**含 `prompt`、`messages`、`instruction`（大小写不敏感）时的右值；
- 切片若落在留痕包装实参内，豁免：`_LEDGER_WRAPPERS = {clip_text_notice, serialize_bounded_json_array, govern_text}`；
- 出现 `clip_text(...)` 直接判红（`_FORBIDDEN_CALLS = {"clip_text"}`）；
- `clip_text_logged(...)` 只允许两个登记作用域（§4）；
- 白名单 `_IRRELEVANT_LIMITS` 2 条（§4）；
- 去重键：`(相对路径, 作用域名, 切片源码段)`，同一处只报一次。

两套口径互补：A 覆盖全仓「文本量级」截断，B 覆盖模型请求路径上「任意量级」的裸切。

### 1.3 「留痕裁剪」与「裸切」怎么区分

满足以下任一条件即判为**留痕**（不是裸切）：

1. 切片位于留痕包装的实参内：`clip_text`、`clip_text_logged`、`clip_text_notice`、`clip_text_notice_report`、`serialize_bounded_json_array`、`govern_text`（这些函数自己写日志/指标/标记）；
2. 同一处切片前后 **±5 行**内出现账目调用：`logger.*`、`logging.*`、`log.*`、`record_token_budget_truncated`、`record_clip_ledger_failure`、`record_truncation`、`_record_context_degraded`、`ai_text_truncated`、`print(...)`。

不满足任一条件 → 记为**零留痕 / 裸切**。

注意：零留痕不等于「一定有害」。它只说明「此处丢字是静默的，运维无法从日志/指标/响应里知道丢了多少」。§3.2 逐条给出为什么不改。

### 2.3 最危险的两处：把已序列化 JSON 按字符数切开

这两处不是「切一段文本」，而是**切一段 JSON 源码**——超长时模型收到的不是「少了点内容」，而是**语法非法的 JSON**（括号/引号/逗号被截断），既无法解析，又可能被模型当作「输入到此结束」而漏掉整章或整条事实，且没有任何说明。

| 位置（修复前） | 原始形态 | 后果 |
|---|---|---|
| `routers/sections.py:1889` | `current_outline=current_outline_text[:30000]` | 目录调整提示词里的章节 JSON 被切成半截 |
| `routers/global_facts.py:3811` | `current_facts=json.dumps(_facts_for_adjust_prompt(rows), ensure_ascii=False)[:30000]` | 事实调整提示词里的全局事实 JSON 被切成半截 |

`29c5960` 的改法：改为统一的**结构化预算器** `prompt_governance.serialize_bounded_json_array`（`prompt_governance.py:899`）：

- 未超预算：返回 `json.dumps(items, ensure_ascii=False)`，**与原实现逐字节一致**；
- 超预算：主体仍是合法 JSON `{field: [...保留的完整条目...], "truncation": {...}}`，只在**条目边界**省略；
- `truncation` 显式给出 `kept_items` / `omitted_items` / `omitted_chars` / `reason` / `note`（「被省略条目不在输入中，禁止臆造其内容」）。

现状落点：

- `sections.py:1913` `_outline_adjust_current_text(...)` → `:1920` 调 `serialize_bounded_json_array`；调用点 `sections.py:2007`。
- `global_facts.py:3672` `_facts_adjust_current_text(...)` → `:3679` 调 `serialize_bounded_json_array`；调用点 `global_facts.py:3880`。
- 两处 `[:30000]` 在 HEAD 已不存在（全仓扫描确认）。

## 5. 三个裁剪原语的边界

实现均在 `backend/app/services/prompt_material_guard.py`（HEAD 行号）：

| 维度 | `clip_text`（:267） | `clip_text_logged`（:325） | `clip_text_notice`（:423）/ `clip_text_notice_report`（:387） |
|---|---|---|---|
| 返回值 | `str` | `str` | `str` / `(str, dict \| None)` |
| 未超限/`limit<=0` | 原样返回（逐字节一致） | 原样返回 | 原样返回；report 返回 `(原文, None)` |
| 切点 | 纯 `text[:limit]` | 纯 `text[:limit]` | `_clip_cut_point`（:306）：按 `\n\n`→`\n`→`。！？；`→`. ! ? ;`→`，, `→空格优先级找切点；切点距上限不足 60%（`_CLIP_BOUNDARY_MIN_RATIO`）则退化为硬切 |
| 是否插标记 | **否** | **否** | **是**：`\n\n[……{label}已截断：原文 N 字，此处保留前 K 字，已省略 M 字]` |
| 记账 | `logger.warning` + `record_token_budget_truncated(label)` | `logger.warning` + `record_token_budget_truncated(label)`；指标失败 → `_record_ledger_failure("truncation_counter")` 计入 `clip_ledger_failures` | `logger.warning` + `record_token_budget_truncated(label)`；report 额外回传 `{from, to, omitted, limit}` |
| fail-soft | 是（两处 `except Exception` + `# noqa: BLE001`） | 日志不兜底（logging 不冒泡）；指标兜底但**失败可观测** | 是（日志/指标均 fail-soft） |
| 允许用途 | **全 app 禁止**（`_FORBIDDEN_CALLS`） | 仅 2 个内部判定作用域（§4.3） | 模型可见路径的默认选择 |
| 现状 | 0 调用 | 2 调用 | 全仓多处 |

关键区别与理由：

1. **`clip_text` vs `clip_text_notice`**：差别只在「模型是否知道被截断」。`clip_text` 写日志但模型看到的是半截文本；`clip_text_notice` 追加说明，模型知道「原文 N 字、保留前 K 字」。所以棘轮禁前者、允许后者。
2. **`clip_text_logged` 为什么绝不能插标记**：它的两个调用点都是「拿这段文本做正则/关键词判定」。标记文本会混进匹配输入，改变命中结果——例如危大分类、工期规则、类目兜底。插标记会把「截断静默」换成「判定错」，更糟。因此它只允许逐字节返回 `text[:limit]`，账目只落日志/指标。
3. **`clip_text_notice_report` 与 `clip_text_notice`**：同一实现。`notice` 是薄包装取 `[0]`，输出逐字节不变；`report` 额外给调用方 `{from,to,omitted,limit}`，用于响应里加法式回传 `instruction_truncated`。未超限时 `report` 返回 `(原文, None)`，调用方可据此判断「是否真的截断过」。
4. **6000 字物理上限**：`INSTRUCTION_PROMPT_MAX_CHARS = 6000`（:384），用于「调整要求」这类任务本体。它在预算器**之前**执行（物理兜底与 `prompt_context_budget` 开关无关：开关默认 0 时预算器直通，粘贴整篇文档会直接 502）。6000 的推导：编辑对象 JSON 上限 30000 字 + system 模板约 3000 字，按 1.5 字/token 保守折算约 22k tokens；32k 窗口扣输出预留 4k → 指令约 9k 字，再留 3k 余量。
5. **`serialize_bounded_json_array` 不是文本原语**：它保证输出始终可被 `json.loads`，只在条目边界省略，并用 `truncation` 说明省略了多少。文本原语无法保证 JSON 合法，所以 JSON 场景必须用它。

## 6. 诚实边界

1. **静态 AST 判定的盲区**。只认 `x[:整型常量]` 与 `x[:max_chars]`。以下写法会漏：
   - 经中间变量多次传递后再切片（`y = prepare(x); y[:N]`，`prepare` 里做了什么静态看不见）；
   - `x[:n - 1]`、`x[:len(y)]`、`x[a:N]`、`x[::N]`；
   - 运行期拼接：f-string、模板变量在 `render` 内部生成后才超长；
   - 非切片截断：`text.partition(...)`、`rsplit(...)[0]`、`json.loads` 后按条数丢弃等。
2. **棘轮的范围盲区**。棘轮只扫「`render`/`get_prompt` 实参」与「名字含 prompt/messages/instruction 的赋值右值」。`return "\n".join(lines)[:max_chars]`（`content_data_contract.py:760`）和 `sib = ...[ :400]`（`outline_title_fix.py:116`）都不在其扫描面内，是本次**全仓口径**才捕获的残留（§3.2 #26 / #34）。棘轮绿不等于全仓零裸切。
3. **200 字阈值是量级口径，不是安全线**。本清单不含 `[:20]`、`[:24]`、`[:200]` 以下的截断；小上限若落在模型路径上，由棘轮单独管；落在非模型路径，则由 §3.2 的 E/P/S/Q 分类解释。
4. **「留痕」是 ±5 行启发式**。可能把不相干的日志算作留痕（低估零留痕），也可能把账目写在远处而误判为零留痕（高估）。77 与 39 这两个数字应理解为「按本口径可复核的计数」，不是绝对真值。历史 106 与本次 107 的 1 处差即由此类边界噪声造成（§2.4）。
5. **本次未跑全量回归**。只跑了棘轮 8 条（8 passed）。默认配置 `prompt_context_budget=0` 时预算器直通，既有全量回归只证明**关闭态不变**；开启态（预算器真正分配）的行为由定向用例覆盖，不在本次扫描证明范围内。
6. **两处 JSON 修复的运行期验证**在 `backend/tests/test_prompt_json_budget_20261107.py`，本次未重跑；本文只核对了源码落点与「`[:30000]` 已不存在」。
7. **本文是只读产物**。扫描未修改任何源码，未 `git add` / `commit` / 改 ref / 推送。
