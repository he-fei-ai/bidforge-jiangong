## 1. BUG-1 · OMML `m:boxPr` 非法子元素（P1，最高优先）

**改了什么**

`backend/app/services/docx_math.py` → `_dangling_placeholder_omml()`

- 删除非法元素 `<m:alignment m:val="center"/>` 与整棵 `<m:border>…</m:border>`
  （含 `borderHide/borderTop/Bot/Left/Right`）；
- 对齐改用 schema 合法元素 **`<m:aln m:val="1"/>`**；
- 虚线边框改由 **`<m:ctrlPr><w:rPr><w:bdr w:val="dashed" w:sz="4" w:space="0" w:color="auto"/></w:rPr></m:ctrlPr>`** 承载；
- 最终子元素顺序为 schema 要求的 `opEmu → noBreak → diff → brk → aln → ctrlPr`。

**为什么**

OMML `CT_BoxPr` 的合法子元素集只有上述 6 个且有序。Word 对公式校验偏宽松，但 **WPS 会直接把该公式部件判为损坏**（公式不渲染，严重时整篇提示文档损坏）——这正是用户最关切的“打不开/公式坏”类风险中确定性最高的一条。

**如何验证**

1. 新增 `tests/test_docx_math.py::test_dangling_placeholder_omml_schema_legal`：
   `latex_to_omml("N =")` → lxml 解析 → 断言 `boxPr` 子元素**恰好等于**
   `["opEmu","noBreak","diff","brk","aln","ctrlPr"]`；并用 python-docx 的
   `parse_xml` 再解析一次（导出链路的真实入口）。
2. `test_dangling_placeholder_display_variant_legal`：`oMathPara` 形态同样合法。
3. `test_non_dangling_formula_has_no_placeholder_box`：`\frac{a}{b}`、`N_{Qk}`、
   `\sum` 等**普通公式不含 `<m:box>`** —— 保证“除悬空运算符情形外产物不变”。
4. 综合样本体检（§6）：`omml_boxpr_count=1`、`omml_illegal_boxpr=[]`、`待填` 仍在。

**测试结果**：`tests/test_docx_math.py` 18 passed（原 15 + 新增 3）。

**等价性说明**：改动只落在 `_dangling_placeholder_omml()` 这一条分支；该函数仅在
`_DANGLING_OP_RE` 命中（公式以 `=`/`≤`/`≥`/`<`/`>`/`≈`/`le`/`geq?`/`leq?`/`ne`
结尾）时被调用，其余公式走原解析路径，**逐字节不变**（由上述第 3 条断言守护）。

**改了什么**

## 3. BUG-5 · sections 非严格读 + 无空章拦截（P1）

**改了什么**

`backend/app/routers/export.py` → `_prepare_export()`

- `:3249` 章节读改为 `_db_fetch_all(..., strict=True)`；读失败 → `DBReadError` → **HTTP 503**
  （“章节数据读取失败（数据库连接异常），请稍后重试”）。
- `:3326` 图表登记同样 `strict=True` → 503（旧实现降级为空集会让图表静默消失却仍按成功入缓存）。
- 零章节/全部空章：**明确降级并留痕**，不拦死导出：

## 7. RISK-175-01 · 预渲染与写侧排序口径不一致

**改了什么**

`export.py:185` 新增唯一排序实现 `_compute_doc_order_rank(roots, children_map)`：
同级按 `_section_sort_key` 排序 + **深度优先**，得到文档真实渲染顺序的 rank。

- `:2296` 写侧 `_build_docx_sync` 删除内嵌 `_rank_order`，改用该函数；
- `:3489` 预渲染 `_prepare_export_render` 删除 `enumerate(sections)`（SQL 扁平序），
  改用 `plan["roots"]/children_map` 调同一函数。

**为什么**

写侧借图时按文档顺序选“排在自己之前、最近的同类图”；预渲染段按 SQL 扁平序
建索引，两者在存在父子章节时**顺序不同** → 兜底借图可能借到错误来源，
表现为“图表插到了错误章节/顺序错位”。

**对既有产物顺序的影响**

- **全为根章节（绝大多数方案）**：扁平序 == DFS 序，产物**逐字节不变**；
- **含父子层级**：仅当某章标记了图表但本章无登记、需要跨章兜底借图时，
  借图来源由“SQL 序前一章”改为“**文档序前一章**”（即修正后的正确顺序），
  图表插入位置随之修正；图号仍按章节自增，不受影响；
- `unique_codes` 的渲染调度顺序可能变化，只影响渲染先后，不影响产物内容。

**如何验证**

- `test_doc_order_rank_uses_dfs_document_order`：`a→a1→b` 而非扁平 `a,b,a1`；
- `test_prerender_and_writer_share_same_order_rank`：同一输入两次结果一致，
  且与扁平序确实不同（防测试自证）。

**测试结果**：2 passed。
