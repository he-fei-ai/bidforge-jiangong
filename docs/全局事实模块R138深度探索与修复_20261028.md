## 三、架构与现状分析（结论均带代码依据）

1. **抽取**：`facts_extractor.py`（3,455 行）分段 → 并发 AI 提取 → `facts_builder` 合并去重（`normalize_key` 单一出口）→ `facts_cross_validators` 交叉校验 → `facts_enrich` 补单位/证据类型 → `facts_patches` 补丁。
2. **分类**：`facts_classification.py`（956 行）22 类事实类型 × 九大章节四维（chapter / fact_attr / source_kind / is_shared，建办质〔2018〕31号）。**分类是派生输入**：`chapter` 由 `category` + 正文关键词派生（`_rederive_dimension_columns`）。
3. **保存**：写路径三条（建档 / 行级更新 / 分组重建），必须共享同一套 `_apply_item_updates` 条目级口径，否则出现「同一份数据两条路径结论不同」。
4. **一致性**：门控不变式 + `has_conflict` 清空 + `is_simulated` 回解 + `fact_key` 重归一化。
5. **更新机制**：`update_fact` 按 `multi_line`（≥1 非空行以列表符开头）分流为「行级更新」与「分组重建」——**分流判据本身就是本轮 D1/D6/D2 三处缺陷的温床**。
6. **容错**：写路径 R13 判空齐备；**读路径与缓存失效路径此前为空**（D4）。
7. **前端**：`SchemeWorkbenchPage.tsx`（`factsApi.create/update/updateItem/resolve/delete`）零改动即可消费本轮所有变化（新键为**追加**）。
8. **测试**：后端 42 个事实相关测试文件；前端 8 个 `facts*` 用例文件 + `types/facts.ts` 类型契约。

## 五、修复项清单（文件 · 关键函数 · 修法 · 依据）

> 全部改动集中在 `backend/app/routers/global_facts.py`（+111 行 / 3,020 → 3,131 行）与两处测试文件。**零新增配置项、零 DDL、零迁移。**

### D1 · 分类变更必须重派生（`update_fact`，行级分支）

```python
_content_structured = ("content" in fields and _looks_like_fact_line(_content_field))
_structured = bool(fields) and (
    "title" in fields or "category" in fields or _content_structured)
...
if "category" in fields:
    iu["category"] = _normalize_fact_category(fields.get("category"))
```

- **旧行为**：`category` 不在结构化判定里 ⇒ 只传分类时落到裸 `UPDATE`，① 不过 `_normalize_fact_category`（可写入 `bogus`，`CATEGORY_TO_CHAPTER` 查不到 ⇒ 事实从章节视图与覆盖率统计中**静默消失**）；② 不重派生 `chapter/fact_attr`。
- **新行为**：与 `_apply_item_updates` / 分组重建**同口径**（分类走白名单 + 派生列重算）。空串归一 `other`。

### D6 · 未被条目口径消费的字段必须单独落库（`update_fact`，leftover 机制）

```python
leftover = {k: v for k, v in fields.items()
            if k not in ("title", "category")
            and not (k == "content" and _content_structured)}
if len(iu) > 1 or leftover:
    n, _sid = await _apply_item_updates(db, [iu] if len(iu) > 1 else [], commit=False)
    if leftover:
        _sets = ", ".join(f"{k}=?" for k in leftover)
        _lcur = await db.execute(
            f"UPDATE global_facts SET {_sets}, updated_at=datetime('now','localtime') WHERE id=?",
            (*leftover.values(), fact_id))
        _assert_fact_write_applied(_lcur, f"更新事实字段 fact_id={fact_id}")
    await db.commit()
```

- **旧行为**：`title` 在 ⇒ `_structured=True`；非结构化 `content` 不进 `iu`；`len(iu) > 1` 命中即 `return`，用户正文被 `_apply_item_updates` 的「改名同步 content」**覆盖回旧值**，接口仍回 `ok=true`。
- **新行为**：leftover 与条目级更新**同一事务**（`commit=False` 统一提交，失败整体回滚）。

### D2 · 分组标题五级兜底（分组重建段）

```python
_old_gtitle = (grow.get("group_title") or "").strip()
_old_cat_default = CATEGORY_TITLES.get((grow.get("category") or "").strip(), "")
if title.strip():
    group_title = title.strip()
elif _old_gtitle and _old_gtitle != _old_cat_default:      # ← 用户自定义名优先保留
    group_title = _old_gtitle
else:
    group_title = (CATEGORY_TITLES.get(category, "") or _old_gtitle or "其他事实")
```

- 保留旧行为：旧名**恰是**分类默认名时，改分类后仍跟随新分类（有护栏 C2 反向锁）。

### D3 · 空条目过滤 + 空载荷 400 + 可观测计数（`_build_create_fact_rows` / `create_fact`）

- `_build_create_fact_rows` 返回类型改为 `tuple[list[tuple], int]`（`rows_buf, skipped_blank`）；结构化分支跳过 `name`/`value` 皆空的条目；旧版单条分支跳过「空名 + 空值」。
- `create_fact`：`if not rows_buf: raise HTTPException(400, "事实内容不能为空")`，并 `except HTTPException: rollback; raise`（**不留半截写入**）。
- 响应**加法式**追加 `inserted` / `skipped_invalid`（既有 `id` / `ok` 保留）。

### D4 · 读 / 缓存失效路径 R13 判空（新增 helper + 10 处接入）

```python
def _require_fact_read_cursor(cur, what: str):
    """R13 判空守卫（读 / 缓存失效路径）：游标为 None 时回 503，不裸抛 AttributeError。"""
    if cur is None:
        logger.error("事实读路径游标为空（R13）· 操作=%s · 数据库暂不可用", what)
        raise HTTPException(status_code=503, detail="数据库暂不可用，请稍后重试")
    return cur
```

接入点（10 处）：`_validate_fact_scope:468`、`_assert_fact_in_scheme_scope:515`、`_invalidate_fact_scope_cache:553`、`_load_fact_rows:635`、`list_facts:717`、`update_fact` 首查 `:1738`、分组旧行 `:1853`、`resolve_fact:2089`、`adjust_facts:2827`、`delete_fact:3013`。
其中 `_invalidate_fact_scope_cache` **在写已 commit 之后**执行 —— 旧实现此处裸抛会把「已成功写入」变成 500，用户重试造成重复写。

### D7 · 去除既有用例的真实网络依赖（测试加固，不改生产代码）

`tests/test_facts_derivation_closeout_r54_20261008.py::test_response_contract_is_additive` 以 `apply=False` 调用 `adjust_facts`，**必然**走「AI 生成计划」分支；本机 `settings.agnes_api_key` 长度 51、`ai_adjust_timeout=120` ⇒ 每次运行都在打真实网络 + 真实 LLM：

- 网络抖动 → `502 事实调整失败`；
- LLM 偶发编造 `fact_id` → `ignored` 非空。

两者都会让「纯结构断言」红掉（实测：**簇内跑红、单跑绿**）。修法：**只钉住「AI 返回了什么」这一个外部不确定源**，原断言（既有键在位 / `applied is None` / `ignored` 为空 / DB 未被改）一律不动：

```python

    return {"operations": []}, {}
monkeypatch.setattr(gf, "collect_json_response", _fake_collect_json_response)
```

## 十、判据教训归档（供后续轮次复用）

1. **「分类是派生输入」**：任何只改派生输入的 PATCH 必须**重派生**，且「行级更新」与「分组重建」两条写路径必须**对称** —— D1 正是两条路径不对称的产物。判据：改完必须有一条护栏断**读路径**（`list_facts` 的 item），只断 DB 列是不够的。
2. **「字段被新口径消费」之前先问：不被消费的字段去哪了？** D6 的 `title` 一进来就把整条 `fields` 判为结构化，非结构化 `content` 既不在 `iu` 也不在 `UPDATE` ⇒ 静默丢失。凡「按字段子集分流」必须显式列 `leftover` 并同事务落库。
3. **`ok=true` 不代表事情发生了**：D3 与 D6 都是「接口回成功、数据没落/落错」。护栏要断**落库后的读回值**，不是断响应码。
4. **兜底要能兜住「旧值与默认值相同」**：D2 若只写 `CATEGORY_TITLES.get(category)`，自定义名必然被覆盖；五级兜底里 `_old_gtitle != _old_cat_default` 这一条是「区分用户命名与系统默认名」的唯一判据。
5. **R13 判空只覆盖写路径是不够的**：D4 的 10 处里，`_invalidate_fact_scope_cache` 位于 **commit 之后** —— 裸抛 `AttributeError` 会把「已写入成功」变成 500，重试造成重复写。凡「写在前面、副作用在后面」的函数，副作用段必须独立判空。
6. **回显值必须与实际一致**：D5 的 `pagination.offset` 原样回显一个**未被使用**的参数，比不回显更坏（调用方以为翻页成功）。
7. **「簇内红、单跑绿」先查外部依赖，不要先怀疑并发争抢**：本轮 D7 的取证顺序是「看用例有没有 stub AI」→「看 `settings.agnes_api_key` 是否非空」→「看 traceback 是否落在 `chat_with_fallback`」，三步即定性为真实网络依赖。R137 教训⑨ 的反例（资源型不确定）与本条互为补充。
8. **fixture 漏关 aiosqlite 连接 ⇒ pytest「跑完不退出」**：症状是**摘要行已打印、EXIT 不返回**，A/B 脚本的 `subprocess.run` 因此永久阻塞。判据：单跑该文件若也不返回即为泄漏；修法与 `conftest.db_conn` 同口径 —— teardown `await conn.close()`。
9. **磁盘损坏会以「坏 `.pyc`」的形式延迟爆发**：症状是收集期 `ValueError: bad marshal data (unknown type code)` + `EXIT=2`。取证不要靠猜：`PYTHONPYCACHEPREFIX` 指向全新目录即可**零删除**验证「是不是字节码缓存坏了」。
10. **变异脚本必须按文件真实行尾匹配**：`global_facts.py` 为 CRLF，脚本按 `\n` 写锚点 → `M1 原文命中 0 次`。凡「多行锚点 + 落盘改写」的脚本，读入后先 `replace("\r\n", "\n")` 归一，写出前再还原，并把「命中次数 != 1 即中止」作为硬断言（本轮因此没有写坏一行）。
