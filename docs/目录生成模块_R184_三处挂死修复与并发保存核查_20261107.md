## 二、并发保存同一方案：实测结论

### 2.1 方法与边界

- 用 `sqlite3.backup` 把生产库复制到 `%TEMP%`，所有写入只落副本；
- 副本内先清空该 scheme 的 `export_cache` 行，避免 `invalidate_export_cache` 删到真实 `_exports` 产物；
- 两条独立 aiosqlite 连接（WAL、`busy_timeout=15000`、`foreign_keys=ON`），`asyncio.Barrier(2)` 对齐起跑，`asyncio.gather` 并发调 `_save_outline_to_db`；
- 3 个场景 × 12 轮 = 36 次并发保存。

### 2.2 有没有按 `scheme_id` 的作用域锁

**没有。** 全库仅有：

- `db.py` 的全局 `_db_lock`（连接层，非按方案）；
- 导出缓存 `_EXPORT_BUILD_LOCKS`（按格式/方案/指纹，与保存无关）；
- `compliance._OVERVIEW_LOCKS`、`sse_handlers._db_write_lock`、`facts_write_guard`（各自领域）。

`_save_outline_to_db` 自身不持有任何按 `scheme_id` 的锁；`SELECT existing_rows` 走 autocommit，DML 才隐式开事务，构成典型的「读-算-写」竞态窗口。

### 2.3 实测结果

36 次并发调用 **0 次异常**（没有 `database is locked`，`busy_timeout` 足够），但出现两类脏结果：

| 场景 | 轮次 | 实际结果 |
|---|---|---|
| S1：A 在 P 下新增 / B 删除 P | 12 | 12/12 丢更新：B 整体覆盖，A 新增的章节被 B 的级联删除一并删掉；A 返回 182 行，最终库 181 行 |
| S2：A/B 同时把同一旧章节当新节点插入 | 12 | **12/12 产生重复行**：同一 `(title, level, parent_id)` 出现 2 条（各自生成新主键） |
| S3：A 删 X / B 删 Y | 12 | 12/12 两次删除都生效（并集）：两边各返回 181 行，最终库 180 行，均不等于任一调用方的预期 |

孤儿（`parent_id` 非空但不在本方案 id 集）在 12 轮 S1 中**未观测到**；但路径成立：A 已插入子节点、B 的读快照早于 A 的插入时，B 删除父节点而不知新子节点 → 子行成为孤儿。本轮时序下 B 的读发生在 A 提交之后，故表现为「A 的写入被整体删除」。这不改变结论：可并发、会产脏。

补充：`invalidate_export_cache` 在命中缓存行时会内部 `commit()`，因此「只有 L1606 一次 commit」并非严格成立；生产上若该方案有导出缓存，事务边界会提前，竞态窗口进一步变化。

### 2.4 触发条件与脏行形态

触发条件：

1. 两个请求（或多 worker）并发保存**同一 `scheme_id`**；
2. 两次保存的目录树有差异（新增/删除/重命名/移动任一）；
3. 两次 `SELECT existing_rows` 都发生在对方提交之前（`_save_outline_to_db` 前段的多个 await 足以造成）。

脏行形态（按实测）：

- **重复行**：同一逻辑章节两条不同主键，`(title, level, parent_id)` 相同；
- **丢更新**：后提交者整体覆盖，先提交者新增的章节消失；
- **并集删除**：双方各自只想删一章，最终两章都没了；
- **孤儿**（理论路径，本轮未命中）：新子行的 `parent_id` 指向已被另一次保存删除的父行。

### 2.5 最小修法取舍

| 方案 | 改法 | 优点 | 代价/风险 |
|---|---|---|---|
| **按 `scheme_id` 加锁** | `asyncio.Lock` 字典按 scheme 串行 | 改动最小、不动 schema | 只在单进程内有效；多 worker 部署仍会并发 |
| **版本号乐观锁** | `sections`/`schemes` 加版本列，保存时 CAS | 跨进程、可检测冲突并让用户重试 | 需改 schema + 所有写路径；冲突时用户要重试 |
| **唯一约束** | 对 `(scheme_id, parent_id, sort_order)` 或标题建唯一索引 | DB 层兜底 | 无法表达「重排后同一逻辑节点」，且只能防重复行，防不了丢更新/孤儿 |

**推荐**：在 `_save_outline_to_db` 的读之前执行 `BEGIN IMMEDIATE`（SQLite 写锁前移），把「读-算-写」整体串行化。它不改 schema、跨进程有效、只影响保存频率（低），`busy_timeout=15000` 已能吸收等待。若确认部署为单进程，也可先用按 `scheme_id` 的 `asyncio.Lock`（更细粒度、等待更短）。二者择一即可，不建议同时上。

本轮**已实现**该修复（`d7be620`，最小修法：读之前 `BEGIN IMMEDIATE`）：不改 schema、跨进程有效、只影响保存频率（低），`busy_timeout=15000` 已能吸收等待。若确认部署为单进程，按 `scheme_id` 的 `asyncio.Lock` 是更细粒度的备选；二者择一，未同时上。

### 2.6 修复落地与验收（`d7be620`）

事务边界（改后）：

- **位置**：`_save_outline_to_db` 在占位标题自动重写（最后一个 AI 调用）之后、`SELECT scheme_project_id` / `SELECT existing_rows` 之前执行 `BEGIN IMMEDIATE`。上方 AI 调用期间不得持锁。
- **常规路径**：`BEGIN IMMEDIATE` 立即取得 RESERVED 写锁 → 读旧快照、组装、UPDATE/INSERT/级联 DELETE、renormalize、一致性扫描缓存 DELETE 全在同一事务 → 唯一一次 `db.commit()` 提交并释放锁；异常时由连接池归还前 `rollback()` 释放。
- **例外路径**：调用方已有未提交写事务（`create_scheme` 先 `INSERT schemes` 再套用目录库）时跳过 BEGIN（否则 SQLite 报 `cannot start a transaction within a transaction`）；该事务首个写语句已持 RESERVED，串行语义等价，末尾提交范围与旧行为相同。
- **中途 commit 确实会提前放锁**：`invalidate_export_cache` 命中 `export_cache` 行时内部 `await db.commit()`（`facts_extractor._delete_cache_once`），会把未提交的整表重建提前提交并释放 `BEGIN IMMEDIATE` 锁 → "单次提交"不成立。已把该调用移到最终 commit **之后**（独立短事务，幂等 DELETE，失败只告警）。一致性扫描缓存失效（`invalidate_consistency_scan_cache`）不内部 commit，留在事务内。
- 空目录分支为 `count → DELETE → commit`，无读-组装环节，其导出缓存失效本就在 commit 之后，未改。

验收（`backend/tests/test_outline_save_concurrency_r184_20261107.py`，两连接同库并发，每轮埋一条 `export_cache` 行）：

- S1/S2/S3 各 12 轮全绿：S1 恒 2 行且 0 孤儿；S2 同名子节点恒 1 行；S3 恒 2 行（后到者保留的那个子节点，旧实现只剩根 = 并集删除）；两侧均返回 `ok`。
- 变异：删掉 `BEGIN IMMEDIATE` 后同一用例 **3 failed / 1 passed**（S1 孤儿 `parent_id='p'` 不存在；S2 第 1 轮同名子节点 2 个；S3 第 1 轮只剩根）；还原后 **4 passed**。
- 串行路径不变：真实库（5 schemes / 578 sections）`VACUUM INTO` 两份，HEAD 版 vs 工作区版逐方案串行保存，稳定字段+返回值规范化 JSON 双侧 **1,354,331 字节**，sha256 均为 `4b3584bbb6cfdaca2402baeaa494b0246a47e3934ef84e3145a837091db9d0d2`（IDENTICAL）。
- 既有回归：`test_adjust_outline.py` + `test_dataflow_risk_fixes.py` 20 passed；ruff 全过。

## 四、启动扫描（方案 B）落地

实现：`backend/app/services/outline_integrity.py`

- `classify_section_links(rows)` 纯函数：三类互斥计数（自父只计 `SELF_PARENT`，不计入 `CYCLE_NODE`；父行缺失只计 `ORPHAN`）；

- 日志：完成且全 0 打 INFO；任一非零打 WARNING 并带每类前 3 个节点 id；失败打 ERROR。

- 异常：关闭连接后扫描 → `status=failed`、`counts=None`、`error` 非空。
