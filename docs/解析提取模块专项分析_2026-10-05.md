## 三、架构现状分析

### 3.1 上传（`global_facts.upload_documents`）
- **流式落盘** + 逐文件校验，命中异常 `rollback` 并清理已落盘文件（不留孤儿）。
- **三重配额**（均可配置，经 `GET /api/v1/system/upload-limits` 下发）：
  - 单文件 `upload_max_bytes`（默认 30MB）
  - 累计体积 `upload_max_total_bytes`（默认 200MB）
  - 文件数 `upload_max_files_per_request`（默认 20）
- **R13 合规**：`cur/ins_cur/del_cur/hash_cur` 全部判空；配额触顶 `break` 后其余登记进 `quota_files`（不再静默丢文件名）。

### 3.2 格式识别（`file_parser`）
- 扩展名白名单 + 文件头签名校验 `signature_valid`，防"改名伪装"；ZIP/OLE 守卫防解压炸弹。

### 3.3 内容解析
- 主分流 `parse_file_content_ex(content, fname) -> (text, diag)`；`diag` 含 `file_type/text_len/truncated/warnings/page_count`。
- CSV/Excel 边读边截断（`MAX_CSV_ROWS` / `MAX_EXCEL_ROWS`），输出 Markdown 表格，超限 `_note_truncation`。
- `_parse_excel`：xlsx 走 `openpyxl(read_only, data_only)` 且 `finally: wb.close()`（Windows 句柄）；xls 走 `xlrd`。

### 3.4 信息保存与分类
- 唯一落库点 `_persist_parse_result`（返回 `bool`，`None` 时不 commit、返回 `False`，上层归入 failed）。
- 分类单一事实源 `services/doc_categories.py`：`DOC_CATEGORIES`(9) / `OTHER_CATEGORY` / `AUTO_CLASSIFY_RULES` / `EXTRACT_PRIORITY`；前端 `DocumentParseList.CATEGORY_COLOR_MAP` 保留副本 + 兜底。

### 3.5 错误处理
- `ParseError → 400`；空文本 `<10` 字 → `failed`；落库失败 → `failed`；读路径判空 → `503`（可重试）。
- 批量解析逐文档 try/except 隔离（单份失败不阻断整批），并统一落 `parse_status`。

### 3.6 工作流 / 路由
- 顶层 6 Tab：`import / outline / facts / content / review / export`（`utils/workflowDerived.ts`）。
- `import` = 1 顶层 Tab + 2 内嵌子 Tab（`docs` 文档解析 / `extract` 项目提取）。
- `NEXT_TAB/PREV_TAB` 提供 Tab 间导航；`pickInitialTab` 按文档/解析状态智能定位。

### 3.7 AI 调用
- 解析结果 → `/api/v1/bid-analysis` 结构化提取；合并多份资料时按 `EXTRACT_PRIORITY` 排序读取。

### 3.8 数据链与存储
- 四层落盘由 `store.ALL_LAYERS` 管理；解析成功后 `_ingest_parsed_doc` 落解析层 + 分块（失败不阻断批量）。

### 3.9 容错 / 缓存 / 并发 / 日志 / 配置
- **并发**：`_doc_parse_guard(doc_id)` 逐文档串行锁；`max_concurrency=5` / `image_max_concurrency=2`。
- **缓存**：force 解析与删除均调用 `_mark_project_facts_stale` + `_invalidate_project_export_caches`（无缓存未失效）。
- **日志**：`set_context(trace_id, project_id, scheme_id)` 埋点，批量解析可串联。
- **配置**：`app/config.py` L47-50（三个上传上限）；R13 约定见 `AGENTS.md §5.5`。

### 3.10 测试方式
- 后端 pytest：`conftest.py` 内存库 fixture + autouse 隔离；解析相关套件 ~900+ 用例。
- 前端 vitest + @testing-library/react：组件级/Tab 级交互测试（`UploadParseTab`、`DocumentParseList`、`ParseResultCategoryPanel`、`ImportSubTabBar`、`SchemeWorkbenchPage` 等）。
- 跨语言护栏：pytest 读前端源码断言接线（`test_import_parse_closeout_20261005.py`、`test_upload_format_contract.py`）。

## 五、修复项 / 优化项清单（含代码方案）

### D1 修复：上传拒绝文案按后端下发的实际生效上限渲染

**文件**：`frontend/src/utils/workflowDerived.ts`；**关键函数**：`summarizeUploadResult`、`buildUploadNotice`

- 新增 `export type UploadLimitHints = { maxBytes?; maxTotalBytes?; maxFiles? }`。
- 新增私有辅助 `formatMbText(bytes, fallbackMb)` / `normalizeFileCount(value, fallback)`。
- `summarizeUploadResult(data, limits?)`：`oversize` → `${maxBytesText}`、`too_many` → `单次 ${maxFilesText} 个上限`、`quota_exceeded` → `累计体积超过 ${maxTotalText} 上限`。
- `buildUploadNotice(data, limits?)` 透传。
- **向后兼容**：`limits` 为可选；不传时逐字回落历史文案（30MB / 200MB / 20），旧调用方与旧单测零改动。

**接线**：`SchemeWorkbenchPage.tsx`
- 新增状态 `maxUploadFiles`，在上传配额下发 effect（`/system/upload-limits`）中读取 `max_files_per_request`。
- `handleUploadDocuments` 调用 `buildUploadNotice(data, { maxBytes: maxUploadBytes, maxTotalBytes: maxUploadTotalBytes, maxFiles: maxUploadFiles })`。

### D2 补齐：单次文件数预检（与后端 `files[:N]` 同序）

**文件**：`frontend/src/utils/uploadAccept.ts`；**关键函数**：`splitByUploadFileCount`（新增）、`MAX_UPLOAD_FILES_FALLBACK`（新增，默认 20）

```ts
export function splitByUploadFileCount(files: File[], maxFiles = MAX_UPLOAD_FILES_FALLBACK)
  : { accepted: File[]; held: File[] }
```
- 语义：**保留前 N 个**（对齐后端 `global_facts.upload_documents` 的 `files[:N]` + `too_many`），其余 `held`；非法/非正数上限回落兜底 20（不得等价于"无上限"）。
- **接线**：`handleUploadDocuments` 在「累计体积预检」之后、`setUploadingFacts(true)` 之前调用，命中即 `msg.warning` 并仅上传 `accepted`。
- 与既有两项预检构成完整三段：**单文件体积 → 累计体积 → 文件数**。
