## 二、修复项清单（3 项）

### FIX-1（P3）· L-1：Agent 分支统计接线（「准备中 · 0/0」全程失真）

**根因**：`outline_agent_enabled=True` 时，SSE agent 分支对 progress 事件只合并 `last_p`，`_prog` 的 `phase` 恒为出厂值 `"prepare"`、`nodes` 恒 0 ⇒ `_snapshot_outline_stats` 对每个事件与心跳附带 `phase_label="准备中"`、`done=0/total=0`、ETA 恒 None。前端统计面板全程「准备中 · 0/0」。（R154 裁定「留痕维持」的依据是「先修无消费者」——但消费面在 R135 接线时已通：前端消费 stats，只是数据源恒空；且 R149 FIX-E/F 已确立 agent-gated 前置修复先例。）

**修法（三段，全加法式）**：
1. `outline_agent_flow`：`run_outline_agent`（包装层）与 `_run_outline_agent_impl` 新增 `stage_ref: dict | None = None`；`_emit_activity` / `_report` 两个回调入口实时同步 `state["stage"]` 进 `stage_ref`（回调每阶段内高频触发，至多滞后一拍）。
2. `outline_agent_flow.outline_agent_event_stream`：创建 `stage_ref` 传入 runner；三个 progress 构造器（`_report_progress`/`_emit_activity`/`_emit_event`）给事件携带 `"workflow_stage": str(stage_ref.get("stage") or "")`。
3. `sse_handlers`：新增模块级 `_AGENT_STAGE_TO_PHASE`（6 个 Agent 工作流阶段 → `_OUTLINE_PHASE_MODEL` 的 draft/level1/sublevels/review）+ 纯函数 `_enrich_agent_progress_event(ev, prog, partial_holder)`（last_p 单调合并 + 阶段映射 + `_count_nodes(partial_holder["outline"])` 实时节点数 + stats 合并），agent 分支改调纯函数。

**语义边界**：Agent 单链无「章节」维度，`done/total` 保持 0/0（与一次性直出同口径，前端据此隐藏章节计数——这是**正确值**而非缺陷）；本轮修的是错误的 phase 标签与恒 0 的 nodes。未知阶段不映射（保留原值）、非 progress 事件原样返回、计数失败 fail-soft 保持原值。

**护栏**（A 组 5 例）：映射双向完备（`set(_AGENT_STAGE_TO_PHASE) == set(_OUTLINE_FLOW_STAGES)` 且值 ⊆ 阶段模型）、last_p 单调、阶段映射+节点计数+phase_label 行为、未知阶段/非 progress 透传、三段接线静态锚（impl 两处同步 / wrapper 转发 / stream 三构造器 / 分支调用）。

### FIX-2（P3）· L-9-D3：`accept_agent_outline` 剥标题内嵌编号（剥空保留原文）

**根因**：Agent 链接受产物只 `str(...).strip()`；stage_prompts 虽明令「title 不得含编号」但**无程序侧强制**——模型违反时「第一章 工程概况」一路进 completed 事件 / 工作区 outline.json / 审核上下文（前端保存前预览出现「1 第一章 工程概况」双重编号形态，审核语义基于脏标题）。legacy 链每条产出路都过 `normalize_outline`（renumber tree 档剥编号），落库最终收敛——本轮收口的是**中间态契约不对称**（与落库同一唯一实现 `strip_outline_numbering_tree`）。

**修法**：`visit` 内标题剥编号（树档）+ **剥空保留原文**（标题本身即编号「第一章」时不丢内容，R85 BUG-D 口径）；身份契约（未知 ID 拒收/重复拒收/已知沿用）零改动。

**护栏**（B 组 4 例）：递归剥净+身份/编号分配不回归、纯编号标题保留、普通标题恒等、身份红线反向锚。

### FIX-3（P3）· L-3-tail：upload save-as-outline 补终态 checkpoint 清理（R154 平行入口回扫）

**根因**：R154 的 L-3 修法接线在 `_save_outline_to_db`（save-outline / apply-and-save 的共同落库出口）；`upload_outline.save_as_outline` 是**第三条整表重建路径**（自建 DELETE/INSERT，R137-O L-4 已记载其独立实现）——旧树同样会在刷新重挂时以「待确认成果」复活（`_attach_checkpoint_result` 回传旧 outline_result，用户确认即用陈旧树覆盖刚保存的目录）。R150 教训②「同族修复必须回扫所有平行入口」的直接应用（与 R149 FIX-J rename_map 同型）。

**修法**：`await db.commit()` 之后接线 `_clear_outline_checkpoints_for_scheme(db, scheme_id)`（advisory 语义，失败不阻断保存）+ 响应加法式 `cleared_checkpoints`（>0 才下发，与 save-outline 同名同语义）。只清终态：运行中任务的 partial checkpoint 是断线重挂唯一恢复源，绝不清（R154 既有语义复用）。

**护栏**（C 组 2 例）：行为级（completed 的 outline_result 清空 / running partial 保留 / 非 outline_result kind 不动 / 响应 cleared_checkpoints=1）+ 接线静态锚。

## 七、判据教训归档

1. **「遗留收口」指令的第一步是逐项核对现状而非按清单动手**——R153/R154 与本轮仅隔一天收口了 9 项中的 7 项；本轮真正的增量只有 3 项。静态信任自己上轮写的遗留清单 = 给并行会话重复记账（R145 教训⑤「预存失败是动态的」的遗留版）。
2. **同族修复回扫平行入口（第四次命中）**——R154 的 checkpoint 清理接在 `_save_outline_to_db`，upload 第三条整表重建路径漏掉（与本轮 R149 FIX-J rename_map 完全同型）。修族清单：save-outline / apply-and-save / **save-as-outline**。
3. **「先修无消费者」的裁定要复查消费面是否真的不存在**——R154 对 L-1 的留痕依据是「Agent 先修无消费者」，但消费面（前端 stats 消费 SSE stats）在 R135 接线时已通，缺的是数据源。区别「无消费者」与「消费者在饿着」。
4. **统计面板的 0/0 有两种语义**——「无章节维度」（一次性直出/Agent 单链，正确）与「计数器没接」（缺陷）。本轮只修后者；修前先确认哪个是真。
5. **间接层必须同步事件契约**（R149 教训⑨的 SSE 版）——flow 内部加 `stage_ref` 通道时，stream 的三个事件构造器都要携带新键，漏一个就会出现「活动事件有阶段、报告事件没有」的半残映射。
