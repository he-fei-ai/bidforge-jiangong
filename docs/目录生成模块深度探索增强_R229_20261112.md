## 三、缺陷定稿与修复

### F1 · P2 · 匹配器第三份独立副本（「同族漏改」反模式复发）

`services/outline_matcher.py`（R209 抽出的单一事实源，`sections._save_outline_to_db` 与
`outline_library.apply_library_and_save` 已迁移）之外的**第三份**——
`routers/upload_outline.save_as_outline` 仍自持一份完整内联匹配器：

```
existing_by_title / existing_by_parent_level / existing_by_level / existing_by_path
+ consumed 集合 + _take_from(bucket, expected_nt)  + cur_path = path_parts + (mnt,)
```

且两份副本已**实质分叉**（匹配身份口径不同）：

| 维度 | `outline_matcher.take(title=…)` | `upload_outline` 内联版 |
|---|---|---|
| 匹配身份 | 调用方传入的 `title`（`sections` 侧传**清洗后** title） | `mnt = pre_nt_index.get(...) or nt`（**自动外科式改写前原标题**） |

这正是 AGENTS「同一判据多份副本」的最高频反模式：任一侧改判据、另一侧必然漂移，
而 `_take_from` 的「跨桶已消费」判定又依赖 `consumed` 全局集合——两处实现各自演进
时，「同标题多父级正文张冠李戴」类缺陷会在一侧修、另一侧漏。

**修复（行为逐字保持，非行为变更）**：
1. `outline_matcher.OutlineMatcher.take()` 新增可选形参 `match_title`：匹配身份
   **优先**用 `normalize_outline_title(match_title if match_title else title)`，
   缺省（None/空串）回退 `title` —— 既有两个调用方（`sections`/`outline_library`）
   不传 `match_title`，逐字不变。
2. `upload_outline.save_as_outline` 删除内联三层索引 + `existing_by_*` + `consumed` +
   `_take_from`，改调 `build_outline_matcher(existing_rows)`，匹配调用点传
   `match_title=mnt`（把「改写前标题匹配身份」语义下沉为单一事实源），展示/落库
   标题仍用改写后 `title`（二者解耦，「改标题」不再等于「丢正文」——R101 遗留①
   的语义被集中锁死，不再散落在路由层）。
3. `_old_title_path`（跨路径匹配日志用）保留，改走 `normalize_outline_title` 单一归一口径。

**等价性核对（逐点）**：
- `normalize_outline_title`（`_WS_RE.sub("")` + `.strip()`）≡ 旧 `_norm_title`
  （`_re.sub(r"\s+","").strip()`），首尾空白处理一致。
- `path_titles + (mnt,)` ≡ 旧 `cur_path`（都是「祖先归一标题 + 本节点匹配身份」）。
- 桶优先级（标题路径→同父同层→同层→全局同名）与「归一化标题相等才认领」判据完全一致。
- 85 例 upload-outline 行为测试（`test_upload_outline_interaction` 等）全绿，证明匹配
  结果与收敛前逐字一致。

### F2 · P0（阻断级 · 非目录面但阻断本轮验证）在途文件缺 `import logging`

`app/services/ai/providers/omp_provider.py`（本轮 R229 在途未跟踪文件）第 45 行
`logger = logging.getLogger("ai_provider.omp")` 使用了 `logging` 却**从未 import**，
导致 `provider_factory` 导入链 `NameError`，**全部目录簇测试收集期 4 报错**。补
`import logging`（与既有 provider 同形态），恢复测试可运行。

### F3 · P2 · AI 调整目录口缺编号 fail-closed 闸门（遗留①收口 · 同族漏改第三处）

`adjust_outline`（`sections.py:2438`）是目录四个写路径中**唯一**漏接
`validate_outline_numbering` 的口子 —— `save_outline`/`save_as_outline`/
`normalize_outline_for_library` 都在落库口判红，唯独 AI 调整口没有。
`normalize_outline` 内部 `renumber_outline` 失败会被 try/except 吞掉（仅留 ERROR 日志）
后返回「已裁剪但未编号」树，旧实现直接以 `ok:True` 把脏树交前端「待确认」：
前端展示双重编号、用户确认后 save_outline 才被拦（体验割裂），且脚本直连 API 时
无人拦截。

**修复（加法式 · fail-closed · 本端点不落库零数据风险）**：在 `adjust_outline` 的
`normalize_outline` 之后补 `validate_outline_numbering(normalized)`（与 R187 落库口
**同一判据单一事实源**），不合法时 400 拒绝；编号正常时（问题列表为空）逐字不变。
虽该端点当前前端零调用（死端点），但补齐后：① 脚本/旧版前端直连 API 时脏编号不再
静默放行；② 四个写路径的编号闸门收敛到同一 `validate_outline_numbering`，
「同族漏改」反模式在目录面上闭合（与 F1 的匹配器第三份副本收敛同主题）。
3 条新护栏（判红 400 / 判绿放行 / 源码棘轮锁闸门走单一源且判据置于 `ok:True` 之前）
入 `test_adjust_outline.py`。
