## 2. L-1 · 知识库素材进入「整案稳定段」→ Prompt Cache 命中归零（**P1 · 重构**）

### 2.1 根因（代码级实证）

| 事实 | 位置 |
|---|---|
| `knowledge_text` 由调用方**按本章过滤** | `sse_handlers.py:3282-3291` `_knowledge_text_for(leaf)` → `_filter_knowledge_rows(knowledge_rows, leaf)` ⇒ **逐章不同** |
| 但它被放进**整案稳定段**（①段） | `content_runtime.py::build_chapter_layered_messages` —— `stable += "…【项目知识库素材】…"` |
| 稳定段的**定义**就是「逐章逐字相同」 | 同函数文档：「①整案稳定上下文：同一方案下**所有章节逐字相同**」 |
| 显式 cache 断点落在稳定段末尾 | 分层设计的目的即「把可复用块变成前缀断点」 |

**后果**：段内任一字节不同 ⇒
- **显式断点**（`cache_control` 落在稳定段末尾）：**整块**判不命中 ⇒ 整案上下文（项目概述 / 施工内容 / 全局事实 / 生成标准块）**每章全价重算**；
- **自动前缀缓存**：只能命中到分叉点，稳定段后半截同样失效。

**为什么既有护栏没抓到**：`test_prompt_prefix_stability_r57` 的 `test_stable_prefix_identical_across_sibling_chapters` 断言 `msgs_a[:-1] == msgs_b[:-1]`，但它给两个叶子**喂了同一份** `knowledge_text` ⇒ 缺陷在纯函数层**不可观测**（生产侧逐章过滤后才暴露）。

### 2.2 修法（最小改动 + 保住 R57 契约）

`content_runtime.py::build_chapter_layered_messages`：
- **移出**：①稳定段不再拼接知识库块；
- **移入**：③任务差异段**段首**（它本就是逐章量）；
- **为什么是段首而非段尾**：R57 护栏 `test_stable_blocks_come_before_task_differences` 定向锁「`idx_knowledge < idx_section`（知识库素材必须排在【当前章节编号】之前）」⇒ 置于段首可**逐字不动**该契约；置于段尾会把它改红。

### 2.3 治理侧无副作用（逐条核过）

| 环节 | 结论 |
|---|---|
| 围栏 / 注入扫描 | `sse_handlers:4919-4928` **按每条 user 消息**施加 `_guard_external_material`；「项目知识库素材」仍是 `MATERIAL_LABELS` 成员 ⇒ 照常围栏/扫描 |
| 切片预算 | `_apply_prompt_context_budget(txt)` 亦按消息施加；知识库段优先级 **3**（素材档）⇒ 预算不足时先于任务本体（优先级 1）被削减，**与移段前同档同序** |
| 续写轮 | `user_content` 由 `messages` 拼接而来（`sse_handlers:4931`）⇒ 与消息同步，顺序变更自动传导 |
| 平铺路径 | `build_chapter_user_content`（`content_stable_prefix_enabled=False` 时）**逐字不动**（该路径无前缀复用收益，改它只会平白增加回归面） |

### 2.4 新增护栏（R206，4 条）

`test_stable_segment_identical_when_knowledge_differs`（**喂不同知识库** → `msgs[:-1]` 仍逐字节相同 —— 这条正面覆盖 R57 原护栏的盲区）、`test_knowledge_block_not_in_stable_message`、`test_knowledge_precedes_current_section`、`test_stable_segment_no_longer_contains_knowledge`。

## 3. L-12 · WAL 模式下跨进程提示词变更长期不可见（**P2 · 重构**）

### 3.1 根因

旧判据（`_cache.py::_get_prompt_cache`）：

```python
if _db_newer_than_cache(current) and _needs_reload_by_watermark(current):
```

—— **mtime 是前置门禁**，表级水印只是「第二道闸」。而 SQLite **WAL 模式**下跨进程写入落在 `-wal` 文件，**主库文件内容与 mtime 都不变**（只在 checkpoint 时改写）⇒ 前置门禁恒 False ⇒ 水印那第二道闸**永远走不到** ⇒ 外部进程 / 脚本 / 迁移工具写入的提示词在本服务进程内**长期不可见**（前端已保存却不生效，且无任何告警）。

### 3.2 修法（水印为权威，mtime 降级为粗判兜底）

新增 `_cache.py::_needs_reload_wal_aware(db_path)`：

| 情形 | 判据 |
|---|---|
| **有水印基线** | 以水印为权威（`_needs_reload_by_watermark`，内含 1s 节流）：水印变了 / 探测失败 ⇒ 重载；未变 / 节流窗口内 ⇒ 不重载。「他表写入 bump 了库 mtime」仍**不触发**全量重载（R108 原意保留 —— 探针判定水印未变时会把 mtime 推到当前值，消化掉这次 bump） |
| **无水印基线**（极旧库缺 `updated_at`、库文件尚不存在） | 退回 mtime 粗判 ⇒ R179「库文件后创建即重载」与旧行为**逐字不变** |

### 3.3 既有 R108 护栏逐条兼容（**未改任何断言**）

| R108 用例 | 新实现下的走向 |
|---|---|
| `test_other_table_bump_no_reload` | 水印未变 ⇒ 探针返回 False ⇒ 不重载 ✓ |
| `test_real_change_reloads` | 水印变更 ⇒ 重载，新内容可见 ✓ |
| `test_no_watermark_falls_back_legacy` | 无水印基线 ⇒ mtime 粗判 ⇒ 重载 ✓ |
| `test_probe_throttle` | 节流窗口内不重载；窗口放开后重载 ✓ |

### 3.4 A/B 反向验证（`tools/_r206_ab.py`，已执行并清理）

同一 WAL 场景、同一份数据，运行时把门禁换回旧实现：

```
[A/B] WAL 场景（mtime_unchanged=True）
  旧门禁（mtime 前置）→ 跨进程写入可见? False   （期望 False = bug 复现）
  新门禁（水印权威）  → 跨进程写入可见? True    （期望 True  = 修复生效）
[A/B] PASS（2/2 命中预期）
```

## 4. L-14 · `prompt_audit_logs` 无版本号（**P3 · DDL**）

### 4.1 语义定义

`version` = **全局单调递增的提示词变更序号**（事务内自增）。

**根因**：`created_at` 仅**秒级**精度 ⇒ 同秒内多次变更的先后**不可判定**；既有排序 `created_at DESC, rowid DESC` 只能靠 rowid 兜底，而 rowid 在 `VACUUM` / 重建表后会变，跨进程也不保证与写入顺序一致。

### 4.2 DDL（增量 · 幂等 · 可回退）

| 对象 | 变更 | 位置 |
|---|---|---|
| `prompt_audit_logs.version` | `INTEGER NOT NULL DEFAULT 0` | `schema_sql.py`（新库 DDL）+ `db.py::_migrate` 补列清单（旧库 `ALTER TABLE`，`PRAGMA table_info` 先探、缺表跳过） |
| `prompt_audit_sequence` | 单行序列表（`id=1 CHECK(id=1)` / `seq`）+ `INSERT OR IGNORE` 种子行 | `schema_sql.py` + `db.py::_migrate` 兜底建表 |
| `idx_prompt_audit_key_version` | `(prompt_key, version)` 覆盖索引（改按 version 排序后原 `(key, created_at)` 索引不再覆盖排序） | `db.py::_migrate` |

### 4.3 写入 / 读取

- **写入**（`audit_service.py::record_prompt_audit` —— 全仓**唯一**写入口，两条 INSERT 都在其内）：`_next_prompt_audit_version(db)` 在**同一事务**内 `UPDATE ... SET seq = seq + 1` 取号 ⇒ 事务回滚则序号一并回滚（**不留空洞**）；并发写由 SQLite 写锁串行化 ⇒ 序号唯一。
  **刻意不用 `MAX(version)+1`**：两个并发事务会读到同一个 MAX 并各自写入相同序号 —— 而序号重复正是本项要消灭的问题。
- **逐级降级**（旧库缺列不丢审计）：INSERT 先带 `version`+`snapshot_json` → 失败摘 `version` 重试 → 再失败摘 `snapshot_json` 重试 → 仍失败才抛（终态与旧实现一致）。
- **读取**（`list_prompt_audit_logs`）：`ORDER BY version DESC, created_at DESC, rowid DESC`；旧库缺 `version` 列 ⇒ 整条查询降级为旧排序（**不 500**）；`item["version"]` 恒存在（缺失归一为 0）。

### 4.4 向后兼容

| 面 | 结论 |
|---|---|
| 历史行 | `version = 0`（DEFAULT）⇒ 其相对顺序仍由 `created_at`/`rowid` 决定 ⇒ **逐字不变** |
| 新旧行混排 | 新行 `version ≥ 1` ⇒ 排在旧行之前（正确：更新的变更在前） |
| 既有测试写法 | 既有测试用 `ORDER BY rowid DESC LIMIT 1` 取「最新一行」⇒ 序号与插入顺序一致 ⇒ 取到同一行 ✓（`test_prompt_rollback_governance` 18 处审计断言、`test_prompt_cache_db_path::TestPromptGovernance` 均不受影响） |
| 直接 INSERT 无 version 列的旧测试 | `DEFAULT 0` ⇒ 不报错 ✓ |
| 前端契约 | `PromptAuditLog.version?: number`（**可选**，纯加法）⇒ `tsc` EXIT 0，零前端行为改动 |

⚠️ **甄别记录（重要陷阱）**：`git diff --stat` 对 `prompt.ts` 报 **190 行改动（98 增 92 删）**，而我实际只加了 **6 行**。根因**不是**行尾漂移，而是**既有仓库状态**：该文件（及 `aiConfig.ts`）在仓库里被提交成 **CRLF**，而 `core.autocrlf=true` + `text` 属性会让 git 对**已修改**文件做 clean 转换（CRLF→LF）后与 CRLF blob 逐行比对 ⇒ **任何**编辑都被放大成整文件 diff（未修改文件走 stat 缓存跳过内容比较，故看不出来）。用 `git diff --ignore-cr-at-eol --numstat` 量化后真实改动为：

```

```

⇒ **本轮零行尾损伤、零 BOM 损伤**（先前一次「HEAD 有 BOM」的判断是 PowerShell 管道重编码的假象，以 subprocess 直读为准）。**教训**：量化真实改动量必须用 `--ignore-cr-at-eol`；字节体检必须用 subprocess 直读字节（`git show | python` 会被宿主管道重编码，结论不可信）。
