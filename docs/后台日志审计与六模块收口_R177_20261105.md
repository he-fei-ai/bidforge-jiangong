## 〇、先纠偏：三条必须先知道的事实（否则结论会错）

### 1. 日志混入了本地 E2E 脚本流量，不是生产

`logs/backend.log` 里 2011 条 `httpx:` 行中 **253 条（12.6%）** 的 host 是 `http://testserver/`
（`httpx.ASGITransport` 默认 base_url）—— 来自 `backend/legacy_scripts/_e2e_r149.py`、
`_e2e_r153_fullchain.py` 等脚本，**与服务端访问日志交织**。

被这条事实**证伪**的两条原始假设（详见 §五）：

| 原假设 | 裁决 |
|---|---|
| 「8 次 `save-as-outline` 400 与『正文被清除』是同一请求的因果链」 | ❌ 两条日志分属**不同端点**（400 在 `/upload-outline/{id}/save-as-outline`，正文清除在 `/schemes/{id}/sections/save-outline` 且 HTTP 200）；400 实为 14 行 = 7 对 |
| 「270 条 JSON 修复空转 = 90 个对象白烧 AI」 | ❌ 全部来自 E2E 打桩（`_fake_chat` 故意返回散文，无 JSON），真实调用 135 次而非 90 |

**取证纪律**：凡判定「生产故障」，必须先用 `httpx:` 行 host 过滤掉 `testserver` 流量。

### 2. `system_logs` / observability 子系统**不在当前 master**

`backend/app/services/observability/` 在当前工作树与 HEAD 均**不存在**；全仓仅
`feature/r126-r129-omml-degradation` 分支含该模块（`observability.py` blob `fb268402`，453 行）。

→ 日志里的 **286 条 `database disk image is malformed` + 51 条 `database is locked`
（system_logs 写入失败）+ 8 条批量写失败**来自 **r126 分支线的构建**，不是 master。
master 的 `schema_sql.py` 无 `system_logs` 表、无 `idx_system_logs_trace`。

→ 结论：**现象 1/4 在 master 上无法原样复现**，但其底层放大器（全局单写连接无写互斥、
`synchronous=NORMAL`、探活即写）在 master 上**原封不动存在**。

### 3. 12 次 `Cannot operate on a closed database.` 全部是本地脚本

12/12 的上下文行都是 `http://testserver/` —— E2E 脚本收尾 `close_db()` 时，
未 await 的 fire-and-forget 观测写任务仍打到已关闭连接。**生产侧 0 条**。

## 五、本轮修复（4 项，均为加法式/零契约破坏）

### FIX-1 · `task_registry.finish_task` 根修（P1，F-1）

**根因**（file:line 级）：
- `task_registry.py`（修前）：终态落库 `await retry_db_op(...)` 是函数**第一个 await**；
  `except Exception` **捕获不到** `CancelledError`（BaseException）→ 直接穿出函数。
- 内存态清理 `_tasks.pop(task_id, None)` 的 `finally` 只挂在**「广播」那层 try** 上
  → 落库被取消时**整段清理被跳过** → `_tasks` 永久残留。
  这与该函数 docstring 自称的 G12-5「内存态清理必须**无条件**执行」直接相悖。

**修法**（两处同修）：
1. 终态落库包 `asyncio.shield(...)`：外层被取消只中断**等待**，内层写仍在后台完成
   → DB 里任务不再永远停在 running（前端 `pollTaskUntilTerminal` 是它唯一等待的信号）。
2. 把 `_tasks.pop` + `_ab.notify()` 提到**外层 finally**，覆盖函数全体；
   并把「内存态标终态 + 停后台子任务」抽成同步函数 `_mark_task_terminal_in_memory`，
   让「落库被取消」路径也能必达（取消时先标终态再原样上抛，**不吞掉取消语义**）。

### FIX-2 · `sse_handlers` 三处断线兜底 `finish_task` 加 shield（P1，F-1）

`bid_analysis.py:1348` 早在 2026-09-23 就落了同一范式（`asyncio.shield(finish_task(...))` + 捕获

## 七、教训归档

1. **日志取证必须先分流生产与测试流量**。本仓 `logs/backend.log` 混入了 legacy E2E 脚本的
   `http://testserver/` 流量（2011 条 httpx 行中 253 条），导致「8 次 400 + 正文被清除」
   与「270 条 JSON 修复空转」两条**假生产故障**。判据：看相邻 `httpx:` 行的 host。
2. **审计结论必须与代码基线对齐**：`observability/system_logs` 子系统**不在 master**，
   只在 `feature/r126-r129-omml-degradation` 分支线 —— 286 条 `database disk image is malformed`
   属该分支构建产物，不是当前基线的故障。
3. **「同一 trace 内相邻出现」不等于因果**：400 与「正文被清除」分属不同端点、不同 trace。
4. **异常安全的真实边界是 BaseException**：`except Exception` 捕获不到 `CancelledError`，
   而 SSE 收尾链恰好全在 `finally` 里 —— 「finally 里的第一个 await 抛 CancelledError」
   会把该 `finally` 之后的全部清理（包括挂在更深层 try 上的 `finally`）一起跳过。
   本仓已有正确范式（`bid_analysis.py:1348`），只是另三条链漏改 ⇒ **同类实现必须做全仓横向对齐**。
5. **A/B 变异脚本的还原逻辑必须先判并发**。本轮首版脚本在还原写入被 Windows 占用打断时
   抛 `Errno 22`，导致**变异体残留在生产文件里**（M1 的 shield 被摘除，护栏立刻红）。
   教训：① 还原前先比对「当前内容 == 我写下的变异体」，不等则判定并发写入并放弃还原；
   ② 还原写入必须带重试；③ 变异前必须留**独立于脚本进程**的字节快照。
   （R106 已有同类教训：A/B 后严禁对未提交文件 `git checkout --`。）
6. **并发会话会改热文件**。本轮审计期间，另一并行会话正在改写 `config.py` 与 `provider_factory.py`
   （对冲放大 / 429 Retry-After / 推理预算），`provider_factory.py` 的 SHA 在会话期间多次变化。
   处置：① 变异前后都做 SHA 快照与并发检测；② 还原冲突时**不覆盖**他人改动；
   ③ 交付前必须**逐一复验 4 项修复仍在位**（本轮据此发现并修复了 FIX-1 的残留）。
