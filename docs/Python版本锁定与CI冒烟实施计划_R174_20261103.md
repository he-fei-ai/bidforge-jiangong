### 1.2 决策点：锚定哪个版本

#### 方案 A：以 CI 3.12 为准（降级）

| 维度 | 内容 |
|---|---|
| 锚定值 | `3.12`（本机另装 CPython 3.12.x 作为生产解释器） |
| 需改文件 | `backend/.python-version`（3.14→3.12）；本机安装 3.12 并处理 [start_all.bat:84](file:///J:/编程/专项方案工具箱/start_all.bat#L84) 探测顺序（Python314 在列表首位，**装了 3.12 仍会先命中 3.14**，需设 `PYTHON_EXE` 环境变量或卸载 3.14 或调整列表顺序）；CI 不动 |
| 对 pin 的影响 | 6 处偏差全部按 pin 降级实装（见 §1.3）；且本机 3.14.4 上实装的 fastapi 0.139 / httpx 0.28.1 等需在 3.12 环境重新安装 pin 版本 |
| 对 CI 的影响 | 零改动（CI 已是 3.12） |
| 风险 | ① 运行时降级：3.14.4 → 3.12，R169 全量基线作废，须在 3.12 上重建全量基线（本仓 pytest 收集量 9000+，成本高）；② `import app.main` 与全部 9241 项收集量（2026-11-03 勾稽口径，出处：R174 前置批次 memory 勾稽）仅在 3.14 实证过，3.12 存在未知兼容面（如 PyMuPDF 1.27.2.3 / numpy 2.4.6 在 3.12 的 wheel 组合未实测）；③ 本机生产解释器切换有窗口期 |
| 回滚 | `git revert` `.python-version` 提交 + 本机恢复 3.14 解释器（`PYTHON_EXE` 指回即可，零代码回滚面） |

#### 方案 B：以实装 3.14 为准（**推荐**）

| 维度 | 内容 |
|---|---|
| 锚定值 | `3.14`（生产 = 本机 = CI 三口径合一） |
| 需改文件 | 仅 [ci.yml](file:///J:/编程/专项方案工具箱/.github/workflows/ci.yml) 两处 `python-version: "3.12"` → `"3.14"`（L21、L99）+ 6 处 pin 收敛（requirements.txt / requirements-dev.txt）；`.python-version` 已是 3.14 不动 |
| 对 pin 的影响 | 5 处 pin 升到实装值，1 处（cryptography）反向处理（见 §1.3 特判） |
| 对 CI 的影响 | backend job / smoke job 换解释器；所有 pin 包在 3.14 的 wheel 可得性已被本机实证（同版本 wheel 已装且 `import app.main` 通过），ubuntu manylinux wheel 供给面一致，风险低 |
| 风险 | ① ruff 0.6.9→0.16.2 新规则可能令 CI `ruff check .` 红（缓解：CI working-directory=backend 是单目录扫描，仓库已知结论「ruff 0.16.2 整仓扫描有 Annotation range panic bug，单独目录扫描不触发」——单目录口径安全，但新 lint 规则命中存量代码需先跑 `ruff check .` 预评估）；② CI 上 pytest 9.1.0 + pytest-asyncio 1.4.0 组合：本机已实证兼容（27 项定向回归全过 + 全量在 9.1.0 环境跑过 R169 基线） |
| 回滚 | `git revert` ci.yml + requirements 两个提交，CI 立即回到 3.12 口径；本机零回滚面 |

**推荐理由**：3.14.4 是唯一同时满足「依赖全装 + `import app.main` 通过 + 全量回归基线（R169）」的运行时；3.12 只是 CI 的声明值，从未在本机实证。方案 B 使「本机 = CI = 文档」三口径合一，偏差处理量最小（改 3 个文件），且不触碰生产环境。

#### 方案 C：双线兼容（声明范围 + CI 矩阵）

| 维度 | 内容 |
|---|---|
| 锚定值 | `requires-python = ">=3.12,<3.15"`（收紧上界）+ CI matrix `[3.12, 3.14]` |
| 需改文件 | pyproject.toml（加上界）、ci.yml（backend job 改 matrix strategy）、6 处 pin 必须取**两版本交集可装版本**（先收敛偏差再谈矩阵） |
| 对 pin 的影响 | 最大：每个 pin 都要在 3.12 与 3.14 双环境验证，cryptography 等 C 扩展包需双 wheel 口径核对 |
| 对 CI 的影响 | backend job 时长近似翻倍（matrix 并行但配额消耗翻倍） |
| 风险 / 代价 | 长期维护两个 minor 的验证负担；对**应用**（非库）而言双线兼容收益低——本仓交付物是自用平台，不是被外部引用的包 |
| 适用前提 | 仅当未来需要「客户机器只有 3.12」的部署形态时再启用 |

**结论**：本仓是应用不是库，推荐方案 B；方案 C 的 `requires-python` 上界收紧（`<3.15`）可作为 B 的可选加固项一并做（一行改动，防 3.15 破坏性变更静默进入）。

### 2.3 转阻断路线

**判据（明确、可数，替换 ci.yml:82-85 注释中的既有表述）**：

1. **观察期起点**：smoke-windows job 首次进入 default 分支的 run。
2. **转阻断条件（满足任一）**：
   - **连续 10 次 run 最终结论为 pass**（「最终结论」含 fail 后手动 re-run 成功的情形——re-run 成功记 flaky 不记 pass，避免把不稳定洗成稳定）；
   - 或 smoke 捕获过 **≥1 个 Windows 特有真实缺陷**（判定标准：ubuntu job 绿而 smoke 红，且根因定位为平台差异而非环境偶发）并已修复。
3. **观察期内记录方式**：每次 run 在本文档附录表登记：日期 / run id / 结论（pass·fail·flaky）/ 失败原因分类（`env-flaky` = runner 资源或网络；`code-defect` = 真实缺陷）。连续 10 次的计数器**只被 `env-flaky` 重置，不被 `code-defect` 重置**（后者触发第 2 条直接转阻断）。
4. **转阻断后偶发失败处理**：
   - 第一响应：re-run failed jobs 一次（当前探测已是 60 次循环，偶发失败多源于 runner 冷启动慢于 60s，可将循环上限随转阻断一并升到 120s）；
   - **同一步骤连续 3 次记 `env-flaky`** → 不再重试，改为修步骤本身（加预热/调超时），重试不是长期方案；
   - `code-defect` 直接走缺陷修复流程，冒烟红灯合理拦截。

**落地方式**：转阻断 = 删除 [ci.yml:89](file:///J:/编程/专项方案工具箱/.github/workflows/ci.yml#L89) 的 `continue-on-error: true` 一行 + 同步改写 L82-85 注释为已生效判据，单文件单提交。
