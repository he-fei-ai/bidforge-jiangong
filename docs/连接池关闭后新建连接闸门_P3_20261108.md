# 连接池关闭后新建连接闸门（P3）方案（2026-11-08）

适用范围：`app/db.py` 的全局连接、写池（`write_tx_conn`）、读池（`read_db`）与
`close_db()` / `init_db()`；以及 `app/main.py` 的 `lifespan.shutdown()`。

## 状态

**仅方案，未实现。** 2026-11-08 评估结论：本轮不做（理由见「为什么现在不做」），
窗口一（读池回退取锁被取消，`4e6dea0`）、窗口二（`close_db` 关闭连接 await 被
取消，`cf33a32`）已修完，本项留档，避免下次从头评估。

## 问题

`close_db()` 之后、`init_db()` 之前，任何再发起的 DB 操作都会**静默重建连接**：

- `get_conn()`：`_conn is None` ⇒ `aiosqlite.connect()` 新建全局连接；
- `_acquire_pool_conn()` / `_acquire_read_conn()`：两条池已被摘空且 `*_total == 0`
  ⇒ 满足获取闸门，直接新建连接。

已经关闭的池因此“复活”。其中 `get_conn()` 新建的全局连接**再没有任何人关闭**
（`close_db` 已经跑过）⇒ 留下一条永久非守护 `_connection_worker_thread`，
进程退出被拖住；池连接则会在归还时被 `_release_*`（`tracked=False`）关掉，
属于短暂复活，但同样在关闭窗口内多起线程。

## 影响面（实测）

### 生产路径

- `close_db()` 只有两处调用点：`app/main.py` 的 `lifespan.shutdown()`（关闭段
  **最后一步**，之前已停审计 flush、Provider 状态、回收循环并执行
  `task_registry.shutdown_inflight()`），以及 `init_db()` 失败时的清理
  （`app/db.py`）。
- uvicorn 在进入 `lifespan.shutdown()` 之前已停止接收连接并取消剩余请求任务
  （上限 30s，见 [服务关闭运维契约_20261107.md](服务关闭运维契约_20261107.md)）。
- 结论：**正常关闭路径上，关闭之后没有任何 DB 访问**。这也解释了为什么本项只被
  归为 P3 —— 它既不产生计数漂移也不漏线程，只是在“不该还能连”的语义上留了口子。

### 残余可达路径（闸门真正要拦的）

1. 越过 3s 收尾预算、仍在跑的散兵任务；
2. 未被 `task_registry._detached_tasks` 跟踪的后台写（新增游离任务若忘记登记）；
3. 未来任何“关闭后再醒一次”的代码（定时器、心跳、延迟 flush）；
4. 关闭后误入的健康检查 / 运维脚本调用。

### 测试面的代价（决定“现在不做”的关键）

- `close_db()` 目前同时被当成**测试重置原语**：48 个测试文件、79 处调用。
- 至少两条上一轮的护栏依赖“关闭后再取连接”：
  - `tests/test_db_close_inflight_pool_20261107.py`（L30、L58：`await db.close_db()`
    之后直接 `_acquire_pool_conn()` / `_acquire_read_conn()`，用于验证借出连接
    未回池）；
  - `tests/test_db_startup_failure_cleanup_20261107.py`（L32→L43：`close_db()`
    之后 `get_conn()`，期待启动期 `setup boom` 原样上抛）。
- 硬闸门会让这两条变红，必须同时改其“重置”语义（补 `init_db()` 或显式清标志）。
  这属于关闭语义变更，不是顺手补丁。

## 为什么现在不做

1. 正常关闭路径已无 DB 访问（见上），收益是纯防御性的；
2. 代价是跨 48 个测试文件的既有“重置”用法 + 两条上轮护栏的语义调整，
   而收益在本轮无任何可观测的计数漂移 / 线程泄漏；
3. 闸门若不配“唤醒等待者”，会把“漏线程”换成“永久睡死”——必须与窗口一那套
   `_schedule_*_wakeup` 一起做，工作量不是一行 `if`。

## 要做时怎么一次性做（单次提交）

1. **标志**：模块级 `_db_closed: bool = False`；在 `close_db()` **同步段最开头**
   （摘池之前）置位；在 `init_db()` 入口（`_self_heal_corrupt_wal()` 之后、
   `get_conn()` 之前）清除。
2. **错误类型**：`class DatabaseClosedError(RuntimeError)`，文案
   `"数据库连接池已关闭（服务正在关闭），拒绝新建连接"`。不要复用
   `RuntimeError` 裸抛，避免被“可重试/降级”分支误吞。
3. **闸门点**（一律在**取锁/等待之前**抛出，避免把请求排进永远不醒的队列）：
   - `get_conn()`（`async with _db_lock` 之前）；
   - `_acquire_pool_conn()`、`_acquire_read_conn()`（容量判断之前）。
4. **唤醒等待者**：`close_db()` 第二阶段用 `_schedule_write_pool_wakeup` /
   `_schedule_read_pool_wakeup`（窗口一的取消安全写法）通知两条 `Condition`，
   让已在 `wait()` 的获取者醒来即撞闸门。
5. **调用方语义**：路由/SSE 处已是 `except Exception` 转错误事件，无需改动；
   后台任务侧按“关闭后一律失败”记录，不做重试（`is_retryable_db_error` 不命中）。
6. **测试**：新增 `tests/test_db_closed_gate_20261108.py`——
   修复前红：`close_db()` 后 `get_conn()` / `_acquire_pool_conn()` /
   `_acquire_read_conn()` 均能新建连接，且线程数 +1（留一条 `_conn is None`
   但线程残留的判据）；修复后绿：三处均抛 `DatabaseClosedError`，无线程新增，
   计数守恒不破。再 `init_db()` 后必须恢复可写（标志复位）。
7. **同步修改**：上述两条护栏的“重置”改为 `await db.init_db()` 之后再取连接
   （或显式清 `_db_closed`），**不放松任何断言**。

验收口径：`init_db() → close_db() → 三处入口均抛 DatabaseClosedError（无线程新增）
→ init_db() 后恢复可写`；`test_db_shutdown_inflight_20261107.py` 的
“终态先于 close_db 写入、不依赖关闭后重建连接”必须继续绿。
