## 一、开篇结论

**最关键机制缺陷**：方案/项目删除与运行中任务的生命周期**完全脱钩**（BUG-B）。`delete_scheme`/`delete_project` 直接删 `task_registry` 行，但对内存 `_tasks` 中仍在跑的目录/正文/事实生成任务**不做任何取消**——AI 配额继续白烧直至自然结束，章节继续写入已删方案的孤儿行，任务凭空消失且 DB 无终态痕迹。这是四条主链中唯一「设计意图（每任务必有终态收口）与实际路径（删除路径绕过全部收口）」结构性不符的点。

**最该优先修的 3 个 BUG**：
1. **BUG-B**：删方案/项目不取消内存运行任务（资源浪费 + 孤儿数据 + 任务失踪）；
2. **BUG-A**：`delete_scheme` 只清 `*.docx` 导出文件，漏 `*.pdf` 与 `*.tmp.docx`（project 级已修、scheme 级漏改，磁盘永久泄漏）；
3. **BUG-C**：续写去重 `_dedup_continuation` 对「整体重复」与「>300 字单段重复」失效，重复正文可进成稿（探针实测复现）。

**会不会导致用户看到错误内容/数据丢失**：
- 会看到**错误内容**：BUG-C 的残余重复会真实拼进章节正文并落库导出（实测 3200 字重复拼接）。
- 「改了内容但导出旧缓存」类缺陷：经对 `_content_fingerprint` 全部 14 维逐一核对（_export_cache.py:80-198），sections 全字段（id/parent/sort/level/title/content）、charts、facts、附录、config 白名单、fe 像素、renderer 版本均在指纹内，`_prepare_export` 读取的 config 键（export.py:3604-3636）与指纹白名单 `_EXPORT_CONFIG_KEYS` 逐一比对**无缺漏**，未发现失效缺口。
- 数据丢失：删除路径的级联清理（R101/项目删除加固后）覆盖面完整，未见误删；未发现「保存成功但内容丢失」路径。

## 三、状态机与并发

**任务状态合法取值**：`running / paused / completed / stopped / failed`（task_registry.status；`error` 仅作为 SSE 事件名不落 status）。
- **写方**：`register_task`（INSERT running / 旧任务→failed）、`_write_task_terminal_db`（终态只允许从 running/paused 迁移，:268-283，防终态互覆）、`set_task_status`（控制指令，同样有 running/paused 守卫 + 返回 bool 区分真假停止，:386-410）。
- **读方**：`GET /sse/task/{id}`（内存优先）、sections 409 守卫、reap_orphan_tasks。
- **终态可被回写？** 否——两处 UPDATE 都带 `WHERE status IN ('running','paused')`。register_task 的「替换旧任务→failed」与晚到 finish_task 的竞态已被该守卫阻断（注释与实现一致，亲验 :271-277）。
- **两流程同时写同一任务？** 同型任务被 `_register_lock` + 防僵尸 SELECT+INSERT 原子化阻断；跨类型被锁内 conflict_types 判定阻断（F5 收口，亲验 :100-121）。
- **连接池闭合性**：`get_db` finally 回滚+归还（db.py:1374-1392）；`write_tx_conn` 捕获 BaseException 回滚后归还（:1395-1419）；读写池剔除路径（poisoned/dead/探活失败）均先扣 `_pool_total` 再 close 并 notify（:1344-1371 / :1522-1547）——**异常与取消下借用/归还/剔除闭合，未发现泄漏路径**。
- **SSE 订阅者释放**：`broadcast()` 已降级 no-op、`_subscribers` 字典已删（task_registry.py:595-607），不存在队列泄漏面；SSE 走生成器 yield 直出 + on_end 同步回调，无消费者滞留。

## 四、确定 BUG 清单

### BUG-A ｜ P2 ｜ delete_scheme 漏清 PDF/tmp 导出文件（磁盘永久泄漏）
- **触发条件**：删除任一方案，且该方案曾导出 PDF（或 DOCX 原子替换失败留下 .tmp.docx）。
- **后果**：PDF 产物永久孤儿。`_gc_orphan_exports` 只在同方案再次导出时触发，方案已删 → 永不回收。
- **证据**：
  - [schemes.py:234](file:///j:/编程/专项方案工具箱/backend/app/routers/schemes.py#L234) `for f in EXPORTS_DIR.glob(f"{scheme_id}_*.docx"):` —— 只有 docx；
  - 同源修复在项目级**已做**：[projects.py:228-231](file:///j:/编程/专项方案工具箱/backend/app/routers/projects.py#L228-L231) `for ext in ("docx", "pdf")`（2026-10-03 修复注释），**scheme 级漏改**；
  - PDF 产物命名确证：[export.py:4542](file:///j:/编程/专项方案工具箱/backend/app/routers/export.py#L4542) `out_path = EXPORTS_DIR / f"{scheme_id}_...{pdf_content_hash[:8]}.pdf"`、tmp：`:4556`。
- **建议修法**：schemes.py:234 改为与 projects.py:228 相同的 `for ext in ("docx", "pdf")` 双循环（一行级改动，零风险）。

### BUG-B ｜ P2 ｜ 删方案/项目不取消内存运行任务（生命周期脱钩）
- **触发条件**：目录/正文/事实生成任务运行中，用户删除该方案（或整个项目）。
- **后果**：
  1. 生成任务跑至自然结束，AI 配额/时长全部白烧；
  2. `_persist_section` 继续向已删方案的 section 写、目录完成时整表重建 sections → **孤儿行**（scheme_id 指向已删方案，永不清理）；
  3. `update_progress`/`finish_task`/checkpoint 的 UPDATE 全部命中 0 行（task_registry 行已被 projects.py:96 / schemes.py:207 删除），DB 无终态、无痕迹；
  4. 用户侧新注册任务时防僵尸 SELECT 查不到旧任务 → 旧任务完全游离于所有互斥/回收机制之外。
- **证据**：
  - [schemes.py:190](file:///j:/编程/专项方案工具箱/backend/app/routers/schemes.py#L190) 注释自认：「运行中任务的后续写库会被各处 try/except 安全吞掉」——行为是接受的，但代价（配额+孤儿行）未记账；
  - schemes.py / projects.py 全文 **无 `request_control` 调用**（grep 0 命中）；而同类场景 register_task:89-91 已有现成范式 `for old_id in stale: request_control(old_id, "stop")`。
- **建议修法**：delete_scheme/commit 前遍历内存 `_tasks`，对 `scheme_id` 匹配的 running/paused 任务 `request_control(tid, "stop")`（约 5 行，与 register_task 同款）；项目级按 scheme_ids 集合同理。

### BUG-C ｜ P3（质量）｜ 续写去重对「整体重复」复活、对「>300 字单段重复」漏删
- **触发条件**：弱模型续写时整段/超 300 字重抄前文。
- **后果**：重复正文拼进章节落库 → 用户成稿出现成段重复（该函数注释自述要修的正是这个症状）。
- **证据（探针实测，脚本已删）**：
  - 探针1：`cont = prev[-200:]`（整段重复）→ `_dedup_continuation` 返回与输入完全相等（`out == dup.strip()` 为 True）。根因 [sse_utils.py:145](file:///j:/编程/专项方案工具箱/backend/app/routers/sse_utils.py#L145) `return b or cont.strip()`——全剥空后**复活完整重复**，违背函数自身契约；
  - 调用点 [sse_handlers.py:3786](file:///j:/编程/专项方案工具箱/backend/app/routers/sse_handlers.py#L3786) `cleaned not in result[-3000:]` 二次守卫把 ≤3000 字窗口内的常见场景拦住（故降级 P3）；
  - 探针2：前文 12000 字单段、续写重抄末尾 3500 字 → 字符级探针上限 300（sse_utils.py:132 `max_probe = min(300, len(b))`）只剥 300 字，输出 3200 字；调用点守卫 `3200 not in prev[-3000:]` 判真 → **拼接 3200 字重复**（实测输出）。
- **建议修法**：`return b or cont.strip()` 改为 `return b`（调用点 :3788 已有空串分支安全兜底，只多一条「已丢弃」日志）；字符级探针上限 300 → 按需提高或改用后缀数组式最长对齐（改动小收益大的是前者）。

2. **内存 `_tasks`**：finish_task finally 无条件 pop（G12-5，task_registry.py:359-363）；mark_stream_ended 宽限回收兜底；唯一例外是 BUG-B（删除路径绕过）。
3. **子任务**：register_child_task 显式 bool + done_callback discard（:572-590）；finish_task 非 completed 取消全部 child（:348-351）。
4. **连接池**：借用/归还/剔除闭合（见 §三）；唯一热点是 S-1 锁内 IO。
5. **导出磁盘**：5 份保留 + 孤儿 GC + inflight 豁免 + tmp 600s TTL，闭合；BUG-A 是删除路径的缺口。

## 八、性能热点

1. S-1（锁内 IO 探针/建连）——J 盘劣化场景下全站 DB 借用排队，与 R165 取证的「后端连接超时」症状同源，建议建连/探针移出条件锁（中改动）。
2. `_content_fingerprint` 每次导出全量读 sections+charts+facts——导出本就是重操作，且保证了缓存正确性，**不建议动**。
3. 续写链路 `_dedup_continuation` 字符级 `for n in range(...)` O(300×n)——可忽略。
4. `reap_orphan_tasks` 每 5 分钟全表扫 task_registry——小表，可忽略。
