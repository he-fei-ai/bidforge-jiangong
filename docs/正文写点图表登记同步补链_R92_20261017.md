## 1. 问题与根因

**报障症状**：导出成稿里图表位置显示红字「[图 X-Y … — 渲染失败]」。

**双根因**（上一会话诊断）：
- 根因 A（环境）：本机零可用 Mermaid 渲染后端 + `allow_pil_fallback` 默认 False —— 属部署/配置面，不在本轮代码修复范围。
- **根因 B（代码，本轮修复对象）**：事实冲突定点修复改写 ```` ```mermaid ```` 围栏内文字后**不重登记** `chart_predictions` → 前端 PNG 键（按旧登记码渲染）与后端内联码（新正文）漂移。导出双轨匹配走 `_norm_code = " ".join(str(code).split())` 折叠空白比对，两侧不一致必然 miss → 回落后端轨 → 命中根因 A → 红字。

**核心不变式**：任何改写 `sections.content` 且可能触碰 ```` ```mermaid ```` / ```` ```chart-json ```` 围栏内文字的写点，都必须在**同一事务**内按最终正文全量重登记 `chart_predictions`，使两侧逐字一致。

## 3. 核心改动

### 3.1 单一事实源原语（`_chart_pipeline.py`）
- `resync_inline_charts(db, scheme_id, section_id, content, *, enforce_limits=False)`（DB 版唯一出口）：原 `register_inline_charts` 实现体逐字搬入。
- `resync_inline_chart_rows(scheme_id, section_id, content, *, enforce_limits, ...)`（纯计算版）：产 `(正文, rows)`，不碰 DB，供「构建在锁外、apply 在锁内」纪律（P1-3）复用。
- `register_inline_charts` 改为薄封装**委派** `resync_inline_charts` —— 既有 25+ 直接调用点（含 B31）行为逐字不变。

### 3.2 各写点接线
- **sse**：autofix `applied` 块内、字数重算后，用 `resync_inline_chart_rows` 按修复后正文重建配对（`build_inline_chart_plan` 直调次数仍为 1，不破静态锁），锁内 `apply_inline_chart_plan` 写入的 rows 与最终正文一致。
- **repair_agent / repair_record**：新增可选参数 `resync_fn=None`（`async def resync_fn(db, section_id, content)`），锁内先重登记再 UPDATE 校正后正文；缺省不执行（向后兼容）。用注入模式规避 services 层 import routers 的分层约束。
- **review_autofix**：`_persist_fixed` 局部导入 `resync_inline_charts`，落库前同事务重登记；rollback 端点用 `_resync` 闭包注入。
- **consistency_repair**：模块级工厂 `_make_chart_resync(scheme_id)`；`repair()` 传回调，`confirm()` 恢复循环与 `rollback()` 各自接线。
- **sections.shrink_section**：压缩后、commit 前同事务重登记（`enforce_limits=False`，同手动保存口径）。

### 3.3 fail-soft
所有重登记异常一律保留原正文，绝不阻断主产物落库（退回引入前行为）。

## 6. 经验教训

1. 判据单一事实源：裸写点若各处自复制「先清后登」必然分叉；抽唯一出口 + 委派，把「重登记」变成不可绕过的动词。
2. 分层约束下补链用注入回调（`resync_fn`）而非 services 直接 import routers。
3. 「构建在锁外、apply 在锁内」纪律下，改写后重登记必须走纯计算版重算 rows，而不是引入第二次 DB 版直调（否则破既有静态锁与并发窗口设计）。
