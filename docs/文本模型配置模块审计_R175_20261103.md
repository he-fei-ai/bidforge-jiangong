## 0. 结论速览

- **明文密钥泄露路径**：未发现「把完整明文 API Key 写进 API 响应 / 日志 / 异常栈 / 导出文件 / 前端持久化」的确定路径。存在 4 类非全量泄露面：
  1. **设计内部分泄露**：`GET /ai/config` 回传末 4 位（`api_key="****"+key[-4:]`、`key_hint=key[-4:]`）。
  2. **潜在回显泄露**：厂商上游错误体被截 300 字符写入 `ai_audit_logs.error` 并由 `/ai/audit-logs` 原样返回；`/ai/config/test`、`/ai/config/fetch-models` 也回显上游 `raw`。
  3. **SSRF 外发面**：`normalize_base_url()` 只校验 scheme/hostname，可把带 Key 的请求发往内网/云元数据地址。
  4. **进程内明文缓存**：`_fallback_cache` 缓存**解密后的明文 Key**（TTL 300s）。
- **热更新是否真生效**：**是**。所有写操作路径（保存 / 切换 / 删除 / 清 Key / 降级顺序 / 导入 / 回滚 / 环境切换 / 运行时禁用 / 主密钥轮转）均调用 `invalidate_config_cache()`（清 5 类缓存 + 代际号 +1），provider 每次调用重建，并发上限在保存/切换/导入/回滚时重设。未保存的表单值只影响「测试连接 / 预检」，不影响运行态。
- **最该修的 3 项**：
  1. **BUG-01** 运行时禁用厂商 JSON 损坏 → `GET/PUT /runtime` 500，前端整卡隐藏，恢复入口自我锁死。
  2. **BUG-02** 前端「重加密」按钮不传 `legacy_key`，坏密文恢复路径在 UI 上不可达，而后端 inspect 明确承诺可恢复。
  3. **BUG-03** 标记「未启用」的配置仍被当作降级候选真实调用（UI 语义与运行时相反）。

**确定 BUG：10 项**（1 高、2 中高、4 中、3 低）。

### 3.3 `FERNET_KEY` 自动生成落盘与丢失后果

- 生成：`crypto.py:44` `Fernet.generate_key()` → `open(_KEY_FILE,"x")` 排他创建（:52-53）→ `chmod 600`（:65-68）。
- 优先级：`settings.fernet_key`（env）→ `data/secret_key.key` → 进程级临时密钥（`_get_fernet` :87-104）。
- 丢失后果：
  - env 存在但非法 → 回退持久化文件并 WARNING（:94-96）。
  - 持久化文件非法 → WARNING + 临时密钥（:101-104）。
  - **持久化文件存在但为空** → `_load_or_create_persistent_key` 走「生成新 Key → `x` 模式 FileExistsError → 重试 10×0.05s 仍空 → raise → 外层 except 返回临时密钥」（:40-72）；`_get_fernet` 拿到合法临时 Key，**不产生任何 warning**（:97-99）。实测：每次进程启动得到不同临时密钥、文件保持为空、`master_key_source()["source"]=="temporary"`、无日志。
  - 结果：库内全部密文变 `key_broken`，重启后依旧（除非手工补 Key 文件）。
- 轮转：`rotate_master_key` :250-300，`write_text` 非原子（:281），失败仅靠 `.bak`；`rotate` 端点在 `_reencrypt_apply` 前已改密钥文件（`key_rotation.py:213-221`），若 DB 迁移抛出，密钥已换、密文未迁移。

## 8. 确定 BUG 清单（10 项）

> 判定标准：有 `文件:行号` 代码证据 + 可复现路径（静态可证或已实测）。不凑数。

### BUG-01【中高】运行时禁用厂商 JSON 损坏 → `/runtime` 500，恢复入口自我锁死
- 证据：
  - `runtime.py:49` `disabled = await resolve_disabled_providers()` **未 try**；
  - `runtime.py:91` `disabled_now = await resolve_disabled_providers()` **未 try**；
  - `provider_factory.py:1087-1094` 非法 JSON → `logger.error` + `raise ValueError("运行时厂商开关配置损坏，请重新保存")`（fail-closed 设计本身正确）；
  - 对照：同一端点对 env 损坏专门 try（`runtime.py:56-59`）、`config.py:91-94`，测试 `test_ai_config_20260927_fixes.py:116-120` 也只覆盖 env；
  - 前端 `useAiConfigGovernance.ts:78-87` `catch {}` 静默 → `runtime` 保持 `null`；
  - 渲染条件 `AIConfigPage.tsx:1815` `{configs.length > 0 && runtime && (...)}` → 整个「运行时厂商开关」卡片消失。
- 影响：用户唯一的「重新保存开关以修复损坏值」入口被 500 + 卡片隐藏双重锁死，只能改库/删行。
- 修复方向：`GET/PUT /runtime` 对 `resolve_disabled_providers()` 加 try，回传 `disabled_error` 并允许空集保存；前端在错误态也渲染卡片。

### BUG-02【中高】前端「重加密」不传 `legacy_key`，坏密文恢复路径不可达
- 证据：
  - `AIConfigPage.tsx:615` `await aiApi.rotateKey({ mode: "reencrypt" })`，**无 `legacy_key`**；
  - `key_rotation.py:195-210` → `_reencrypt_apply(db, legacy_key)`，`legacy_key=""`；
  - `crypto.py:319-345` `reencrypt_token(enc, legacy_key="")`：先 `decrypt_api_key(enc)`；为空且 `legacy_key` 为空 → 返回 `""`（:339-340）；
  - inspect 文案 `key_rotation.py:169-171` 承诺「必要时带 legacy_key 一次性恢复」；
  - 前端无 rotate/legacy_key 输入 UI（仅 :2895 一个 reencrypt 按钮）。
- 影响：换过 `FERNET_KEY` 的用户点「重加密」必然 `failed`，文案却指向一条 UI 不可达的操作。
- 修复方向：重加密弹窗增加 `legacy_key` 输入（或提供 `rotate+new_key` 表单），`AIKeyRotationRequest` 类型已含 `legacy_key?`。

### BUG-03【中】「未启用」配置仍作为降级候选被真实调用
- 证据：
  - `provider_factory.py:1231-1233` `"SELECT * FROM ai_config WHERE 1=1" + _env_filter`（**无 `is_active` 过滤**）；
  - :1236-1248 仅跳过 `primary_id` 与无 Key 行；
  - 前端 `AIConfigPage.tsx:1077-1079`：`is_active=0` 显示「未启用」；
  - `config.py:306-308`：已是 active 时幂等返回，无「关闭」操作。
- 影响：用户看到「未启用」会以为它不参与调用，实际主配置失败后会调用它。
- 说明：`:1196-1203` 注释解释「曾因 `is_active=1` 导致链恒空」——这是历史修复造成的语义倒挂，需引入独立的 `enabled` 字段或明确文案。
- 修复方向：新增 `enabled`（默认 1）列参与降级过滤；UI「未启用」改为「非当前使用（仍参与降级）」。

### BUG-04【中】降级链 UI 与运行时不一致（所见非所得）
- 证据：
  - `AIConfigPage.tsx:1750-1752` 文案：「其余配置按下方顺序降级，越靠上越先尝试」——未提上限；
  - `provider_factory.py:1312-1316` 截断到 `ai_fallback_chain_max`（默认 3）；
  - :1293-1305 还按实时成功率**重排**，与原 priority 顺序不同。
- 影响：用户以为第 4 条也会被尝试；实际不会；且顺序可能被健康度改写。
- 修复方向：UI 标注「仅前 N 条参与降级（当前 N=3）」「顺序会按实时成功率微调」。

### BUG-05【中】视觉/OCR 路径绕过「运行时禁用厂商」（及熔断门禁）
- 证据：
  - `provider_factory.py:1506-1521` 只取主配置 + `_fallback_chain()`，**未调用 `resolve_disabled_providers()`**，也未走 `_gate_candidates`；
  - UI `AIConfigPage.tsx:1842` 宣称「被禁用的厂商**不参与任何 AI 调用**（连探测请求都不发）」。
- 影响：合规下线/欠费隔离对 OCR 视觉通道无效，与 UI 承诺矛盾。
- 修复方向：`get_vision_providers` 过滤 `disabled`，并对熔断 OPEN 的 provider 跳过。

### BUG-06【中】主密钥文件为空 → 静默使用临时密钥，且永不修复
- 证据：
  - `crypto.py:40-43` 文件存在但内容为空 → 继续生成新 Key；
  - :52-53 `open(_KEY_FILE,"x")` 抛 `FileExistsError`；
  - :54-64 重试 10×0.05s 仍为空 → `raise`；
  - :70-72 外层 `except` 返回进程级临时密钥；
  - :97-104 临时 Key 本身合法 → **不触发任何 warning**。
- 实测（临时目录、未写仓库）：连续两次调用得到不同密钥、`secret_key.key` 保持 0 字节、`master_key_source()["source"]=="temporary"`、无日志。
- 影响：每次重启换钥，全部密文变 `key_broken`；用户无任何提示。
- 修复方向：空文件路径显式 WARNING + 原子重写（或删除后重建），并在 `/ai/health` 暴露 `master_key_source`。

### BUG-07【低中】熔断器按 provider 维度，单条坏配置可拖累同厂商健康配置
- 证据：`workflows_base.py:139` `_per_provider`；:199-208 `record_failure(provider_name)`；`provider_factory.py:2990` 传 `pname`。
- 影响：同一 provider 下 A 配置 404 连续失败 → 熔断该 provider → B 配置（健康）也被跳过。
- 修复方向：按 `provider+model+config_id+base_url` 维度（与 reliability key 一致），或至少 config 维度。

### BUG-08【低】`env` 长度约束不一致（64 vs 32）
- 证据：`models.py:246` `max_length=64`；`provider_factory.py:955` `_ENV_MAX_LEN=32`、:969-970 抛 `ValueError`；前端 `AIConfigPage.tsx:2621` 无 `maxLength`。
- 实测：`normalize_env("a"*33)` → `ValueError("环境名过长（最多 32 个字符）")`。
- 影响：33–64 字符通过 schema 后在保存时 400，提示与表单能力不符。
- 修复方向：`AIConfigIn.env max_length=32`，前端加 `maxLength={32}`。

### BUG-09【低】`update_fallback_chain` 部分提交导致 priority 重复/乱序
- 证据：`config.py:369-377` 只对传入 `ids` 重排 `0..n-1`；未传入的配置保留旧 `priority`。
- 影响：前端若只提交子集（或并发删除后），库内出现重复 priority，运行时排序退化为 `updated_at`，顺序不可预期。
- 修复方向：保存前对全表统一重排（未列入者接在末尾）。

### BUG-10【低】`save_ai_config` 不 trim `api_key`
- 证据：`provider_factory.py:636` `data.get("api_key","")` 直接加密；`crypto.py:108-111` 仅 `if not raw` 判空；UPDATE `CASE WHEN ?!=''`（:686）。
- 影响：用户粘贴带前后空格/换行的 Key → 密文非空 → `has_key=true`，但 `Authorization` 带空白 → 全部 401。
- 修复方向：`(data.get("api_key") or "").strip()` 后再加密判空。
