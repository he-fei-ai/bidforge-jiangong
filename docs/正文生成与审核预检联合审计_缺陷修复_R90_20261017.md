## 2. 定稿缺陷

### BUG-RV-1 · P0 · 预检引擎 CON-06 检查器整体崩溃 + **consistency 分数虚高**

**位置**：`services/preflight_engine.py:207`（`_finding` 签名）、`:780-784`（截断分支调用点）

**两处独立缺陷叠加**（只修其一仍红）：

1. `_finding(rule_id, detail, *, evidence, section_id, section_title, suggestion)`
   **没有 `severity` 形参**，而 `check_duplication` 的截断分支调用
   `_finding("CON-06-TRUNC", ..., severity="low")` → `TypeError`。
2. `CON-06-TRUNC` 这种「基编号 + 非数字后缀」**无法**被 `_resolve_base_rule`
   解析（`audit_rules.py:620-623` 只剥离 `-<数字>`，遇 `-TRUNC` 直接 break
   → `return None`）→ 即便补上形参，`dimension=""` 仍会污染
   `unknown_dimension_count`、`title` 退化成裸串、`basis` 为空。

**探针实测（`MAX_PAIRWISE_COMPARISONS=0` 强制触顶）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `check_duplication` | **RAISED TypeError** | 返回 3 条 |
| `run_preflight` `engine_error` | **1** | **0** |
| CON-06 findings | **[] （全部丢失）** | `['CON-06-1','CON-06-2','CON-06']` |
| `unknown_dimension_count` | **1** | **0** |
| consistency 维度分 | **100.0**（虚高） | **82.0**（真实） |

**最恶劣的一面**：检查器崩溃让本方案的 consistency 维度**涨到满分** ——
用户看到的是更好的评级，而真实的成段雷同（评审硬伤）一条都没报出来。
根因是 `run_preflight` 的逐 checker `except`（`:1077`）把崩溃降级成
`engine_error` finding（`dimension=""`），而评分把空维度并入 deliverability。

**修法**：
- `_finding` 增**加法式** keyword-only 形参 `severity: str | None = None`
  （缺省取注册表值 ⇒ 六个既有调用点**逐字不变**）；
- 截断分支编号 `CON-06-TRUNC` → **`CON-06`**（已登记基编号，
  `consistency` 维度 / 有依据；与派生编号 `CON-06-N` 不撞键），
  `severity="low"` 走新形参，并补一条可执行 `suggestion`。

**为何既有护栏没抓到**：`test_audit_rules_namespace_20261003.py:41` 的扫描器
用 `_BASE_RE = ^[A-Z]{3}-\d{2}$` 过滤 ⇒ `CON-06-TRUNC` 结构上不可见。

### BUG-CG-1 · P0 · 正文「空章节」终态被改写成 stopped

**位置**：`routers/sse_handlers.py:5415-5418`（修复后）

```python
await _update_progress_safe(1.0, "没有待生成的章节", event="completed")
await finish_task(task_id, "completed")          # ← 修复：必须在 yield 之前
yield f"data: {...'event':'completed'...}"
return
```

**因果链**：前端 `useContentGeneration.ts:179` 收到 `completed` 立即
`await load(); break;` + 关闭响应体 → 生成器在 `yield` 处收到
`GeneratorExit` → 其后的 `finish_task` **永不执行** → `finally`
（`:7836` `has_active_task` → `task_id in _tasks`）仍为真 →
`:7853 finish_task(task_id, "stopped", "客户端断开，任务已终止")`
**覆盖**终态。用户点生成、方案本就无待生成章节的常见场景，看到「已停止」。

**为何既有护栏没抓到**（§5.14「判据锚点」同族）：
`test_content_deep_audit.py::TestTerminalOrdering` 只锚了 3 条路径，且锚点
绑死各路径独有的字符串（`_terminal_status` / `"用户已停止"` / `"任务已取消"`）。
第 4 条路径的载荷是内联字典字面量，而
`test_no_finish_task_after_completed_yield` 用
`src.index('yield f"data: {json.dumps(completed_payload')` —— `index` 取
**首次**出现，四条路径里只有正常完成那条含 `completed_payload` ⇒
**空章节路径落在两个断言的覆盖窗口之外**。

**修法 + 加固**：调换两行顺序；并把该不变量从「点名式」升级为
**AST 全量式**（枚举全部终态 `yield`，逐个断言同一语句列表内其后无
`finish_task`）。⚠️ 判据必须按「同一语句列表」判定 —— `finally` 里的兜底
`finish_task` **合法地**位于终态 yield 之后（属另一个列表
`Try.finalbody`），全局比行号会误伤（护栏已配反向锁确认这点）。

### BUG-RV-2 · P1 · 总检「导出预检」来源静默消失 → 分数虚高

**位置**：`routers/export.py::collect_export_issues`（5 处查询出口）、
`routers/compliance.py:1204`

**「意图 vs 行为」的直接物证** —— 消费点自己的注释写着：

```python
except Exception as e:
    # ✅ P1-6：读取失败必须让用户可见（否则该来源静默不参与评分、分数虚高）
    failed_sources.append("export_check")
```

但 `collect_export_issues` 的五路查询一律 `_db_fetch_all(strict=False)`
（`export.py:88-111`，默认 fail-soft 降级为空结果集）⇒ DB 瞬时故障时
**根本不抛异常** ⇒ 上面那条守卫对「DB 读失败」这一形态
**结构性不可达** ⇒ `export_check` 既不进 `sources` 也不进 `failed_sources`
⇒ 用户看到「六路来源正常」而**分数虚高**。

**修法**：`collect_export_issues(..., strict_read: bool = False)` 加法式开关，
五路查询透传；`export.py:88` 的 `_db_fetch_all` 已有 `strict`，
**补齐 `_db_fetch_one` 的 `strict` 形参**（原本没有）。总检侧传 `True`，
导出页 `export_check` 保持缺省（**逐字不变**，否则 DB 抖动会让导出预检 500）。

### BUG-RV-4 · P1 · `repair_record` 写路径「假成功」

**位置**：`services/repair_record.py`（全文 9 处裸 `db.execute`）

**为何存在**：R78 把审核预检的**四个 router** 收口到
`services/review_db.py` 单一出口，静态护栏 `TARGET_FILES` 也只覆盖 router
⇒ **services 侧是当时的漏网空白点**。

| 站点 | 假成功后的用户可见后果 |
|---|---|
| `mark_repair_status:183` | `/consistency/confirm`、`/rollback`、`/autofix/confirm`、`/rollback` 返回 `confirmed`/`rolled_back`，而 `consistency_repairs.status` **未变** |
| `rollback_snapshot` `restored += 1` | 不看写入结果，用户以为已恢复正文 |
| `save_repair` | 返回一个**从未落库**的 `repair_id`，后续操作全部找不到批次 |

**修法**：全部改走 `review_db.fetch_one/fetch_all/fetch_scalar/exec_write`。
写路径 `require_rows=True` ⇒ 未生效即 503，**绝不汇报假成功**。
调用点（两个 router）均**未**包裹 `except Exception`，503 如实冒泡
（护栏含反向锁）。
