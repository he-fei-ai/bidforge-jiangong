## 1. 核心发现：同一条作用域谓词有 **3 份**各自内联的副本

「作用域谓词」= 判断一行 `global_facts` 是否属于「本方案可见范围」的 SQL 片段。
它是本仓安全关键判据（§「安全关键」标注、项目共享层去重、提取后回退清 stale、
导出交付门控全部依赖它），因此必须是**唯一事实源**。实测盘点：

| # | 位置 | 形态 | 判定 |
|---|---|---|---|
| ① | `routers/global_facts.py:527` `_FACT_SCOPE_PREDICATE` | 全范围（方案私有 ∪ 项目共享） | 单一出口，**7 处内联副本已收口** |
| ② | `services/facts_extractor.py:2911` `FACT_SCOPE_SHARED_FRAGMENT` | **仅共享半句** | 另一份口径，供导出侧复用 |
| ③ | `routers/export.py:1159` | 全范围字面量**再内联一次** | ⚠️ **第三份副本，本轮未收敛** |

三份语义**逐字等价**（`scheme_id=? OR (project_id=? AND (scheme_id='' OR scheme_id IS NULL))`），
不是行为缺陷，而是「同一判据在 3 处各自实现」的结构性风险 —— 与本仓反复记录的
「幽灵图 / 假绿 / 口径分叉」同族。

### 1.1 ⚠️ ③ 为什么本轮**刻意不收敛**

理想做法是把 `export.py:1159` 改为 import ① 的常量。**但 ① 无法被 import**：

- `global_facts.py` 从 `facts_extractor` import 常量（`global_facts.py:57`）；
- ③ 若改为 `from global_facts import _FACT_SCOPE_PREDICATE` → **循环依赖**；
- 按本仓既有解法（§「JSON 模式兼容性判定」的 `json_mode_compat.py` 先例），
  正确方向是把谓词**下沉**到两者共同的下层（`facts_extractor` 或新建 `services/facts_scope.py`），
  再让两侧都 import 它。

这属于**跨模块重构**：需要同时改 3 个文件 + 全量回归（事实簇 503 例 + 导出簇 581 例），
且本轮同时存在并行会话正在改写 `global_facts.py`（-1594 行重构在途），
此时动 import 结构极易造成「后写者赢」。**故本轮只盘点 + 记录，不动刀。**

**事件**：为恢复 `export.py` 中一个疑似残缺的语法行，执行了

`size 307467 → 310403`，BOM=False / U+FFFD=0 / lone_CR=0 / bare_LF=0 / py_compile OK。
**89 例（R65 48 + closeout 41）全部转绿**。

### 2.1 三条可复用教训

1. **`git checkout` 前必须用 `git status --short` 确认目标文件的 diff 是否承载未入库工作**。
   本轮首查用的是 `git status --short -- <3 个文件名>`，**只检查了那 3 个文件**，
   未包含 `export.py` —— 检查范围不够宽，等于没查。§「行尾损坏 + 无备份的救援不可达」
   已记录过同源教训，本轮是**第二次**踩中。

2. **快照可能是「中间态」而非「最终态」**：9 份快照里 `layout_preset` 计数
   4 → 7 → 8 → 11 递增，说明并行会话在同一文件上反复迭代。
   取快照前必须**按时间戳取最新**，并按内容计数交叉验证（不能只看 mtime）。

3. **「残缺语法行」要先证伪再动手**：本轮最初诊断出 `global_facts.py:1707` 有一行
   `+ FACT_SCOPE_SHARED_FRAGMENT + "OR COALESCE(is_stale,0)=1 THEN 1 ELSE 0 END)"` 疑似残缺。
   实际复核该文件后，`FACT_SCOPE_SHARED_FRAGMENT` 全文件**仅 2 处**（import + 正常用法），
   **残缺行根本不存在** —— 那是并行会话写入的**瞬时中间态**，被其自身后续写入修正。
   ⚠️ **判据**：读到疑似损坏内容后，若目标文件正被其它会话写入，**先重读一次原文再下结论**，
   不要基于一次读取就做破坏性恢复动作。
