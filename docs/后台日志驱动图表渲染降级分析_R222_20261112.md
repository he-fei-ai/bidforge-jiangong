## 二、图表生成与渲染的工作机制 / 工作流程

### 2.1 三段式全链路

```
[生成] AI 编排 content_plan.CHART_TYPE_WHITELIST(7类)
        → prompts/content.py 格式A(Mermaid 语法) / 格式B(chart-json)
        → _chart_pipeline.build_inline_chart_plan / apply_inline_chart_plan
        → chart_predictions 落库 + 正文写入图表围栏
[预览] MarkdownRenderer / mermaidRuntime.ts (mermaid.js)
        → exportCharts.ts 渲染 PNG（仅排除 `{` 开头载荷）
        → fe_images 经 useExportRun.ts → _parse_frontend_images 传给导出
[导出] _prepare_export（取数段：DB读 + 块解析 + 指纹）
        → 缓存查询：命中直接回历史产物 / 未命中进入渲染段
        → _prepare_export_render（unique_codes → fe 优先 / HTTP / PIL 兜底）
        → _build_docx_sync → write_section（图号 + _add_inline_chart_from_bytes）
        → 交付段：degraded 判定 → 响应头 / 是否写缓存 / 审计旁车
```

### 2.2 类型与载荷形态（R221 已梳理，本轮沿用）

`chart_validators.PIL_RENDERABLE_CHART_TYPES` 7 类与 `content_plan.CHART_TYPE_WHITELIST`、前端 `chartTypes.ts` 三处一致；`MERMAID_KEYWORD_TO_CHART_TYPE` 还额外承认 12 类 HTTP-only 类型；`chart_predictions.chart_type` 是 TEXT 无枚举。**PIL v2 只对 4 类语法载荷有解析器**（`PIL_SYNTAX_CHART_TYPES`），其余语法载荷只能靠 HTTP Service 或前端 mermaid.js。

### 2.3 导出降级路径全景（本轮亲验）

| # | 降级路径 | 触发条件 | 成稿完整性 | 旧实现是否进 degraded | 旧实现用户可见性 |
|---|----------|----------|------------|----------------------|------------------|
| 1 | 前端 PNG 优先轨（fe） | `fe_images` 命中 | 完整 | — | 统计 `fe` |
| 2 | HTTP 失败 → PIL 兜底 | 语法载荷 + `allow_pil=True` | 完整（画法不同） | 否 | R221 起 `pil_fallback` |
| 3 | JSON 载荷直接 PIL | 以 `{` / `[` 开头 | 完整 | — | `backend_ok` |
| 4 | 跨章借图 | 本章无登记 | 图文可能不符 | 否 | `fallback_borrowed` |
| 5 | 甘特 >30 任务截断 | 大甘特图 | **内容不完整** | 否 | `gantt_truncated` |
| 6 | 渲染失败整块跳过 | `_chart_probe` 为 None | **缺图** | 仅当预渲染返回 None | `failed` / WARNING |
| 7 | **插入失败** | `_add_inline_chart_from_bytes` 返回 False | **缺图** | **否（bug）** | **仅日志，且统计仍记 backend_ok** |
| 8 | **有围栏但无登记代码** | `_resolve_chart_code` 返回空 | **缺图** | **否（bug）** | **完全静默** |
| 9 | **解析期跳过 / 去重跳过** | chart-json 未闭合、同图重复引用 | 部分缺图 | 部分（chart-json 已计入） | `chart_json_skipped` |
| 10 | **缓存命中复用历史产物** | 同指纹 | 取决于历史成稿 | 不适用 | **仅 `{"cached":true}`** |

第 7、8、10 项是本次事故的核心：**预渲染统计回答不了「图最终进没进 DOCX」**。

## 三、导出文档中的渲染是否降级？——定罪

**答案：是，而且「系统认为没降级」。**

代码实证（`backend/app/routers/export.py`）：

1. `render_stats` 只在 `_prepare_export_render` 的预渲染循环里累加 `failed`（`render_returned_none` / 异常）。构建期 `write_section` 的四个跳过出口 —— 无码 `:3881`、去重、探测失败、插入失败 `:3947` —— **都不回写 `render_stats`**。
2. `unique_codes` 只收「有码」的图表块（`:4958` 原逻辑）。有围栏但无登记代码时 `unique_codes` 为空 → 渲染段连 `渲染轨统计` 日志都不打（原 `:5149` 在 `if unique_codes:` 内）→ 日志零留痕。
3. 坏缓存守卫（DOCX `:6334` 附近、PDF `:6895` 附近）只看 `render_stats.failed` + AI 配图 + 空章 + 事实查询 + 残留 + 附录 + 丢章，**没有「成稿实际落图数」这一维度**。
4. 因此第 7/8 类成稿缺图会走 `X-Cache-Status: miss` 分支，执行 `_persist_export_cache_row`，把残缺产物写进缓存。
5. 缓存命中快速路径（DOCX / PDF 各一处）只回 `{"cached":true}`，前端 `parseChartRenderStats` 拿到后所有告警都不触发 → 用户以为复用的是完整成稿。

这也解释了 R221 报告里「改 `allow_pil_fallback` 默认值后甘特图恢复」为何仍不足以保证交付质量：**默认值只修了渲染器的一个出口，没修「渲染成功 ≠ 成稿有图」这条链路缺口。**

## 四、最优方案与 R222 落地

**方案定调**：不新增第二套统计体系，而是**把「交付侧实际落图数」作为单一事实源**，复用既有的 `fix_stats → render_stats` 桥（跨章借图同款，R177 护栏锁死「每链单一合流点」），一处记账、全链消费。

| # | 级别 | 修法 | 位置 |
|---|------|------|------|
| F1 | P1 | 新增线程局部累加器 `_chart_delivery_reset/_chart_delivery/_note_chart_delivery`；`_build_docx_sync` 入口 reset（线程池复用不串数据）；`write_section` 每处图表围栏记 `expected`，成功插图记 `inserted`，四类跳过记 `dropped` + 明细（cap 20），去重单列 `duplicate_skipped` 不误报 | `export.py:170`、`:3881`、`:3947` |
| F2 | P1 | DOCX / PDF **双链** degraded 判据纳入 `_chart_delivery_dropped(fix_stats)`（单一判据出口 `:203`）；成稿缺图 → `X-Cache-Status: degraded` + `X-Export-Degraded: charts-dropped` + **不写缓存** | `export.py:6334`、`:6895` |
| F3 | P1 | 结构化日志 `export_chart_degraded scheme=… expected/inserted/dropped/duplicate_skipped reasons=…`（`:4281`）；`渲染轨统计` 移出 `if unique_codes`，零图路径补「无待渲染图表代码」INFO（`:5338`），消除日志零留痕 | `export.py` |
| F4 | P2 | `_merge_borrowed_stats` 扩展为统一桥，把交付统计映射为 `chart_expected/chart_inserted/chart_dropped/chart_duplicate_skipped/chart_dropped_details`（加法式，旧统计形状逐字不变）；合流点提前到写旁车之前（DOCX），PDF 上移到判据之后并**保持全链恰好 3 处** | `export.py:211` |
| F5 | P2 | 审计旁车加法式固化 `chart_delivery` 统计（不改 `_AUDIT_SIDECAR_VERSION`，读侧 `.get` 容错）；新增 `_read_chart_delivery_sidecar`（`:3149`）；DOCX/PDF 命中路径回传 `cached_stats` / `cached_degraded`，**旧旁车仍返回原字面量 `{"cached":true}`**；PDF degraded 时补 `ai_image_pending`/`ai_image_download_pending`，与 DOCX 同口径 | `export.py` |
| F6 | P2 | 前端新增 `chartDeliveryWarning` / `cachedChartDegradedWarning`、`chartRenderStatsParts` 追加「成稿落图 M/N 张（缺 K 张）」、`EXPORT_DEGRADED_TEXT` 补 `charts-dropped`；`useExportRun` 消费两个新告警 | `exportResponse.ts` / `useExportRun.ts` |

**契约安全**：全部响应键为**加法式**；`X-Export-Degraded` 新信号 `charts-dropped` 与既有信号逗号拼接；旧旁车 / 旧后端响应逐字兼容；零迁移、零 DDL、零新增配置项。

**刻意不改的设计取舍**：
- `pil_fallback` / `fallback_borrowed` / `gantt_truncated` 属于「内容可能不完整但成稿有图」，**只做可见性提示，不阻止写缓存**（否则默认部署 HTTP 不可用时永远不缓存，属性能灾难）。
- 不伪造占位图（R201 已锁「不做红字占位 + 不占图号」）。
- 12 类 HTTP-only 类型仍需前端 mermaid.js 或部署 Mermaid Service，本轮只让失败可见。

## 六、运维与遗留

- **需重启后端**（`app/routers/export.py` 常驻）；**需重建前端**（`exportResponse.ts` / `useExportRun.ts`）。
- **零迁移、零 DDL、零新增配置项**；响应键仅加法式。
- **效果复算锚**：正文含 1 处 `[CHART_TYPE: gantt]` 但无登记代码的方案 → 导出后 `X-Chart-Render-Stats` 带 `chart_expected=1, chart_inserted=0, chart_dropped=1, failed=0`，`X-Cache-Status=degraded`、`X-Export-Degraded=charts-dropped`，前端弹出「成稿有 1 张图表未插入…本次不写入缓存」；正常出图方案仍为 `miss`。缓存命中历史缺图件时前端提示「复用了上次导出的成果…建议重新导出」。
- **历史缓存**：坏缓存守卫只拦「本次降级」，此前已落盘的缺图产物仍可能命中；本轮通过旁车回传让复用可见，但**是否清理存量 `export_cache` 属运维动作**（可等内容指纹变化自然失效，或手工按方案清理）。
- **日志复采建议**：本样本仅 4 天且以 UI 轮询 GET 为主，真实导出事件稀少。`export_chart_degraded` / `export_chart_delivery` / `渲染轨统计` 上线后建议复采一周，按模板聚合统计成稿缺图率与降级率。
- **仍待处理**：内容不完整类（甘特截断 / PIL 兜底 / 跨章借图）不阻止写缓存的产品裁决；12 类 HTTP-only 图的根治（前端轨全覆盖或部署 Mermaid HTTP Service）；生成侧 `apply_inline_chart_plan` 限额/校验失败时的细粒度上报。
- **护栏文件**：`backend/tests/test_chart_delivery_r222_20261112.py`（13 例）、`frontend/src/tests/chartDeliveryR222.test.ts`（15 例），含端到端复现、双链同口径源码锁、旁车容错锁。

## 七、教训归档

1. **「渲染成功」不等于「成稿有图」** —— 预渲染统计与交付侧落图是两个事实域；只盯 `backend_ok` / `failed` 会把「插入失败」「有围栏无码」整类数据丢失判成正常。
2. **可观测性要与判定同源** —— 日志零留痕不是「没问题」，而是降级出口根本没接统计；修复要同时补日志、判据、响应头、前端四处，缺一处仍是静默。
3. **既有的 `fix_stats → render_stats` 桥是最优落点** —— 跨章借图已验证过这条通道，DOCX/PDF 天然同口径；另起炉灶只会再造第三份统计。
4. **护栏锁「调用次数」时新增合流点必红** —— 应按意图重排调用位置（上移 + 删重复），而不是放宽断言或改计数期望。
5. **「历史产物」是坏缓存守卫的盲区** —— 守卫只管本次；命中路径必须回带历史统计，否则用户会长期复用一份残缺件且毫无提示。
