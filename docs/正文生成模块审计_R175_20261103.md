**结论：存在确定的进度失真结构路径**
1. `ping` 的 `progress` 取自未过单调护栏的 `_weighted_progress`（`_sse_outline_build.py:210`），前端 `SchemeWorkbenchPage.tsx:3519-3522` 无 `max` 守卫（对比目录链 `:2650` 有 `evt.progress > lastP`）。
2. 现实触发点：`guarded_gen` 的 `finally` 先移除 running 记录（`:4329`），`run_all_generations` 后自增 `done`（`:4357-4360`）；此窗口内的心跳会把该章「已投入进度」算丢 → 低于历史 max → 前端回退。
3. `section_stage` 携带的单调细粒度进度未被消费，单章内进度条只靠 10s 心跳推进。
4. 章节计数两套口径：运行期 `done` 含失败（`:4360/4363` 文案「已完成 10/10」），终态/重挂 checkpoint `done` 只含成功（`_sse_content_payloads.py:125`）→ 同一屏内进度卡 10/10、终态消息与重挂摘要 8/10。

终态丢事件：客户端断开时 `finally` 只写 checkpoint 不 yield（`:5091-5130`），属设计；前端通过 `tasksApi.list(id)` + `pollTaskUntilTerminal` 重挂（`:3670-3725`），不构成缺陷。

日志「延迟/错位」成因（均为结构事实，非数据错误）：
- 事件按**完成序**产生（`asyncio.as_completed(p):4349`），章节号序与事件序无关；`upsertSectionLog` 会把已有项移到列表末尾（`contentEvents.ts:282-287`），`SectionLogList` 再 `reverse()` 展示（`SectionLogList.tsx:37-42`）→ 视觉上章号乱序。
- `section_done` 在 DB commit 之后才 yield（`:4111` 调用 `_persist_and_notify`，其内部 commit 于 `:3183`，事件于 `:4171`），因此**不存在「事件先于落库」**；延迟来自慢客户端队列背压与心跳粒度。

### 5.2 编号冲突处理结论

- AI 写 `3.2.1` / 错号 / 跳号：⑥ 按存储编号 `stored_id_to_prefix` 重算并重写子标题行（`numbering.py:460-591`），与导出 `_compute_subheading` 同算法 → 预览/落库/导出一致。
- 存储编号非法（UUID/脏数据）：直接原样返回（`numbering.py:493-499`），导出侧才纠偏 → 此类方案前端预览仍可能显示 AI 原始编号。
- 有 DB 子章节时走 body 命名空间（`numbering.py:486-487, 535-548`），避免与子章节 `x.y` 冲突。
- **时序缺口**：⑥ 在 ⑧ 之前，事实修复可改正文；⑩ 只告警不重写。若事实修复动到子标题行（如标题内含「90 日历天」被改成「120 日历天」），编号前缀通常不变，故不判为 BUG，列为技术债 T-3。

### 5.3 列表样式被拍平

- 正文清洗（`content_polish.py:189-203`）只做词替换/空白收敛，不动行首 `-`/`1.`，**不会拍平**。
- 压缩链的保护区只有「围栏 / 图片 / GFM 表格」（`content_shrink.py:39-78`），**列表行不在保护区**；`replace/delete` 只校验 `target_text` 唯一（`:149-161`）→ AI 若把列表项作为 target 替换为整段文字，列表即被拍平。自动压缩在选定字数档时默认开启（`sse_handlers.py:1804-1806`，`_shrink_default = 有 tier/override`）。

### 5.4 乱码与公式转义路径

- 落库正文**不做** HTML 反转义 / mojibake 清理：`_html_unescape` 仅在导出侧（`content_blocks.py:532-535`，调用方 `_export_docx_parts.py`）；`docx_math.clean_text` 也只在导出链。
- 因此 DB 中的 `<br><br><table>&lt;fcel&gt;` 类标签汤会原样进前端预览，而 DOCX 被清洗 → **预览与导出不一致**（技术债 T-4，非本轮 BUG）。
- 公式：正文生成侧无 `\\(` → `$` 转换；仅导出 `docx_math` 处理，属导出模块范围。

## 9. 确定 BUG 清单（4 项，全部有代码证据/实测）

### BUG-1（高）续写 >3000 字重抄残留，重复正文入库
- 证据：`sse_utils.py:133`（`tail=prev[-3000:]`）、`:156`（`max_probe=min(len(b),len(tail),4000)`）、`:164`（② 上限 300）；调用点守卫 `sse_handlers.py:3822` 同为 3000。
- 实测：`prev="甲"*4000, cont=prev[-3500:]+"新增内容"` → 返回 504 字，其中 500 字为重复；调用点守卫因含新内容而放行 → `result += "\n" + cleaned`（`:3823`）→ 重复落库。
- 根因：docstring 声称探针上限覆盖「≤4000」，实际 `tail` 截断为 3000，接缝错位即整段漏检。

### BUG-2（中）正常重复内容被误删
- 证据：`sse_utils.py:163-167` 的 ② 「`b[:n] in tail`」无位置约束；≥40 字前缀只要在最近 3000 字任意位置出现即裁掉。
- 实测：`prev2` 中间含 48 字标准条款，`cont` 以同一条款开头 → 返回只剩「补充说明如下。」（条款整段消失）。
- 影响：引用规范原文、模板化表述在续写中二次出现时被吞，正文语义断裂且无日志（调用点只在整体为空时记「已丢弃」）。

### BUG-3（中）进度条可回退 / 单章进度停滞
- 证据：`_sse_outline_build.py:210` 的 `progress` 用 `_weighted_progress`（无 `max` 护栏，`:89-106`）；`sse_handlers.py:2469-2474` 只对 `progress/section_stage` 施加 `max`；前端 `SchemeWorkbenchPage.tsx:3519-3522` 对 `stats/ping` 直接 `setProgress`，无 `> lastP` 守卫（目录链 `:2650` 有）。
- 触发：`guarded_gen` 的 `finally` 移除 running（`:4329`）与 `run_all_generations` 自增 `done`（`:4357-4360`）之间的窗口，或阶段 EMA 校准后 raw 值低于历史 max。
- 附带：`section_stage.progress`（`:2507`，已过护栏）被前端忽略（`:3498-3510`）。

### BUG-4（低）章节计数两套口径
- 证据：运行期 `done=completed_count`（含失败，`:4357-4360`，注释 `_sse_outline_build.py:92-93`）；终态 `done=len(done_ids)`（仅成功，`:5015`；`_sse_content_payloads.py:125` 同口径）；重挂摘要 `contentResultSummary` 读后者（`:3706-3711`）。代码注释 `:5009-5014` 说明「统一为成功数」是为对齐重挂口径的有意选择，但**未同步修正运行期 `done` 含失败**，故两套口径仍并存。
- 影响：同一屏内进度卡（`genStats.done`，来自心跳）显示「已处理 10/10」，终态消息/重挂摘要显示「成功 8/10、失败 2」，用户无法判断哪个为准。

### 已证伪（不作为 BUG）
- 「事件先于落库」：`section_done` 在 commit（`:3183`）后 yield（`:4171`）。
- 「清洗破坏未闭合围栏内代码」：未闭合区间保护到 EOF（`fence_common.py:278-279`）。
- 「整体重复复活」：R173 已修（探针 case1 = 0）。
- 「渲染失败占图号」：占位块/渲染失败块在导出侧整块跳过（`_chart_pipeline.py:816-820`，详见导出审计 R175）。
- 「断线终态丢事件导致丢结果」：checkpoint + 重挂 + `load()` 闭环（§6）。
- 已定稿改动（`_use_stepwise_for_budget`、`sections.py` 闸门/reorder、`outline_scheme`）未见缺陷。

## 13. R175 续（2026-11-04）事实提取 all_skipped 文案与计数口径

### 13.1 「全部跳过」两种来源区分

**现状取证**
- `sse_handlers.py` 原 `all_skipped` 早退统一回「全部 N 段均已提取过，无新增内容需要提取」，并 `finish_task(..., "completed")`。
- `facts_extractor.CompletedChunkSet.deferred` 会把**失败退避窗口内**的段并入完成集合（`load_completed_chunks` 返回 `done | deferred`）。当全部段都在退避窗口时 `all_skipped=True` 且 `chunk_hashes_ok` 为空 —— 用户此前从未成功提取，却看到「均已提取过」，同时按 completed 计成功。

**改了什么符号**
- 新增 `sse_handlers._facts_all_skipped_payload()`（`:5572`），返回 `(status, event, message, extra)`：
  - 全部为失败退避（`skipped > 0` 且 `chunk_hashes_ok` 为空）→ `failed` / `error`，文案「全部 N 段均处于失败重试退避窗口…暂无已提取成果」，并回传 `skipped / deferred / skipped_source=deferred_backoff`；
  - 确有历史成果 → `completed` / `completed`，文案明确「本次无新增内容」；混合场景附「其中 M 段处于失败退避窗口」。
- `generate-facts` 的 `all_skipped` 分支（`:5869`）改为消费该函数，`finish_task` 按返回状态上报。

**行为变化**
- 用户可见：增量跳过与「从未成功提取」不再共用一句话；全部退避时任务终态为 `failed`（不再假成功），并提示可用「全部重新提取」立即重试。
