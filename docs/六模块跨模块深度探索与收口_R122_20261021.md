## 五、本轮修复项（确凿 + 已测试）

### FIX-1 · 全局事实 AI 调整超长事实库截断无告警（P2，真实缺陷）
- **根因**：`global_facts.py:2722` 将事实库 `json.dumps(_facts_for_adjust_prompt(rows))[:30000]` 硬截断喂给模型。超长部分的事实模型**完全不可见**（既不会被改、也不计入 `ignored_ops` 回执），用户误以为"调整已覆盖全部事实"，且**无任何告警**。
- **修复**（加法式、零行为变更）：
  - 新增纯函数 `_count_visible_facts(facts_payload, limit)`（`global_facts.py`，估算上限内可完整序列化的事实条数，分隔符按 `json.dumps` 默认 `, ` 2 字符，与真实序列化一致）。
  - `else` 分支（AI 预览路径）：截断发生时 `logger.warning(...)` 回传 `scheme / total / visible≈ / rendered_chars / 上限`。
  - 响应体加法字段 `truncated`（被截断条数，0=未截断），旧前端忽略不报错。
- **验证**：`tests/test_adjust_facts.py` 新增 2 例（纯函数单测 + 超长 payload 触发截断回传 `truncated>0`）；针对性回归 `test_adjust_facts.py` + `test_global_facts_closeout_r75/route_contract/closeout_20261006` 共 **167 passed / 1 skipped / 0 failed**。
- **新增配置项**：无（`30000`/`3000` 沿用既有截断常量，未新增配置）。

### 经核验后**未改**的候选项（附证据，避免误改）
- **repair_agent 绕过 R13 收口（子代理误报）**：当前 `db.py` 为连接池模型，`db.execute` 失败抛异常（fail-loud），且 `repair_agent` 写库后均 `await db.commit()`（L472/L517）。非静默失败，判定误报。
- **四层落盘失败 `except: return {}` 静默吞（子代理标为 BUG）**：核验 `global_facts_docs.py:769` 文档明确"DB `parsed_markdown` 才是下游唯一硬依赖，四层可经 reparse 重建"；核心解析结果由 `_persist_parse_result`（L1176）单独落库且带 503 守卫。**属可恢复降级，非静默核心数据丢失**，按设计取舍不改。

## 八、遗留问题与后续建议

1. **解析模块**是六模块中加固最浅的环节（R 系列主要投入在目录/正文/导出/事实），建议下一轮优先：①解析失败重试/断点恢复；②reparse 自动触发 AI 提取；③分块级 OCR 补漏；④`project_info` 键名契约单一常量化。
2. **全局事实跨校验**仅 3 组规则且 `auto_resolvable` 恒 False，建议扩展规则集并支持半自动裁决，形成"检测→裁决→回写"闭环。
3. **事实库版本化**（version/快照/回滚）是数据治理缺口，建议独立迭代。
4. **R13 判空模式**在新连接池模型下多为冗余，建议统一在连接层消除（连接池/写失败抛异常），而非逐处判空——但属大改造，需独立排期（不纳入本加法式轮次）。
5. **语义/向量检索**（`write_semantic_index` 无读取方）尚未接入，属功能规划项。
6. **重复探索避免**：本轮已用子代理并行只读探索，未触发测试基线并行（避免聚类假失败）；解析/事实/审核三模块探索充分，目录/正文/导出沿用 R118–R121 报告，未重复消耗。

> 结论：本轮在"加法式、零回归"约束下，完成六模块跨模块探索与日志研判，确认主要历史缺陷已在 R118–R121 闭环；定位并修复 1 项确凿真实缺陷（全局事实调整超长截断无告警），核验证伪 2 项候选误报/设计取舍，输出功能缺口/技术债/接口不一致清单与后续建议。
