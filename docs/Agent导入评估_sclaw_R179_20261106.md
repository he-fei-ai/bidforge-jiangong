## 4. 许可合规判定（按「内部使用 + 可对外分发 + 部分对外提供服务」）

1. **强 copyleft（AGPL/GPL）**：本对象**未发现**任何 GPL/AGPL 文本，因此不触发「一律不可引入」的具体条款；但「未声明」不等于「宽松」，实际更严格 —— 无许可证 = 保留所有权利。
2. **弱 copyleft（MPL-2.0 / LGPL）**：本对象**未发现**；若未来出现，按「文件级隔离可行 / 库级静态链接需提供替换能力」分别处理，本轮无需展开。
3. **宽松许可（MIT/Apache-2.0/BSD）**：本对象**未发现**。这是本轮结论「不可用」的直接原因。
4. **运行时本体**：无源码、无许可文件；即便它是某个开源客户端的发行版，也必须在取得上游许可与 NOTICE 后才能谈「引入」，且还要满足署名与再分发义务。当前证据不足以放行。
5. **插件与连接器**：`agent/plugins/*` 与 258 项连接器属第三方资源，未见许可与数据处理条款；把它们随产品分发会同时引入版权与数据合规风险。
6. **传递依赖**：`portable-agent` 零第三方依赖（`requirements.txt` 为空 + `README.md:39`），传递依赖风险为 0；但「零依赖」不解决授权问题。
7. **「调用 API 不复制代码」的义务边界**：若对方将来提供独立进程/HTTP 接口，仅做数据交互通常不构成衍生作品（强 copyleft 的 §13 义务针对该程序自身，不自动扩展到调用方）；但只要随产品**分发其副本**，就必须随附其源码与许可声明。该边界需法务确认，本轮不依赖此路径。

| 任意外发 | `http_get` 接受任意 `http(s)` URL，无域名白名单、无大小外审计 | `core/tools.py:326-335`、`:201-211` |
| 资料发往第三方 | 默认供应商为 SCNet，所有提示词与上下文默认出境；另有 258 项连接器 | `agent/settings.json:3-4`；`agent/connectors/resource-catalog-v2.json` |
| 正面项 | 打印配置时对 key 做掩码（`***` + 末 4 位）；工具输出截断、超时 | `agent.py:53-54`；`core/config.py:32-34` |

结论：`portable-agent` 的「沙箱」只约束**相对路径参数**，不约束 shell 语义；在服务端接入场景等价于「提示注入 → 任意命令执行」。这是不建议内嵌的首要技术理由（许可问题更优先）。

## 6. 反向结论：不建议引入的部分

### 6.1 明确不建议引入

| 能力 | 为什么不建议 |

| `.sclaw` 运行时 | 无源码、无许可证、含凭据与用户会话；引入即不可控的再分发与数据合规风险。 |
| `portable-agent` 整体代码 | 无 LICENSE；架构为 CLI 单机，路径依赖 workspace；与 Flask/FastAPI 服务形态不兼容。 |

| `core/facts.py` 事实引擎 | 参数表与单位换算为硬编码常量；本仓 `facts_builder.py` 已有预算、账本与交叉校验。 |

### 6.2「看着能做，其实做不了」

1. **全过程编排 / 规划**：`core/loop.py` 是单轮工具循环，最多 12 步（`config.py:30`、`loop.py:44`、`:89-90`），没有 planner、没有任务图、没有阶段门禁、没有审批节点。它不能贴到四阶段流水线上做调度。
2. **长期记忆**：`workspace/MEMORY.md` 只有 202 字节模板；`AGENTS.md:5` 说明这几个 md 只是「每轮开头注入的用户上下文」，不是可写入、可检索、可衰减的记忆系统。`README.md:203` 还明确「上下文不做压缩」。
3. **工具生态**：只有 5 个本地工具，MCP `servers=0`；没有权限模型、没有工具级审批、没有并发隔离。
4. **PDF / 扫描件解析**：`core/readers.py:29` 明确放弃，直接 skipped。
5. **图表**：无任何渲染路径。
6. **多模型治理**：单 provider + 环境变量；无供应商注册、无并发闸门、无用量与成本统计。
7. **评分项 / 废标条款覆盖**：无该概念。
8. **并发与预热**：无异步、无并发上限、无预热编排。
9. **SSE 流式**：`core/llm.py` 有流式客户端，但领域生成 `core/generate.py` 是同步逐段，无事件流契约，不能直接对接本仓 SSE。

### 6.3 可借鉴的最小集合（抽象机制，最多 3 条，需独立实现）

1. **条款级判定对象（clause-level verdict）**：把判定结果从「等级 + 原因」升级为「命中的条款 id / 原文 / 来源 + 缺口字段 + 四态结论」。能解决本仓具体问题：`scheme_classification.py:783` 的 `evaluate_hazard_level` 已返回原因与缺参，但缺逐条款命中表，前端难以给出「依据哪一条、还缺哪几个条件」的可追溯说明。
