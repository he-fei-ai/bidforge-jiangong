## 0. 前提校正：文档假设的渲染栈与本仓不同

文档的代码样例是 **HTML/React + CSS `writing-mode`**，本仓架构图**不在前端渲染**：

| 环节 | 本仓实际 |
| --- | --- |
| 出图 | 服务端 PIL 自研渲染器 `_render_architecture_image_v2`（`@_render_hq` 2.5× 超采样 + 300 DPI） |
| 预览 | 前端 `chartsApi.render` POST chart-json → `/charts/render` 收 **PNG blob** |
| 导出 | DOCX / PDF 走**同一个**渲染器产出的 PNG |

⇒ **改一处渲染器即同时覆盖预览 + DOCX + PDF**；文档增强项 5（PNG 导出竖排）自动满足，
增强项 6（hover 高亮）**不适用**（前端拿到的是位图，无 DOM 节点可挂 hover）。
所有 CSS 规格需按「PIL 逐字绘制」重新解释，见下表。

| 文档条目 | 优先级 | 本仓落点 | 状态 |
| --- | --- | --- | --- |
| 1 竖排文字样式（`vertical-rl` + `upright` + `letter-spacing`） | P0 | `_draw_text_vertical_center()`（`mermaid_common.py:304`） | ✅ |
| 2 节点尺寸 130×50 → 60×200、间距 10→8 | P0 | `LEAF_VERTICAL_W/H/GAP = 96/232/12`（`mermaid_architecture.py:43-45`，按 2.5× 折算） | ✅ |
| 3 节点数自动检测（>6 切竖排） | P1 | `resolve_leaf_vertical_mode()`（`:272`） | ✅ |
| 4 长文本换行 | P1 | 列容量收敛 + `…` 截断（`mermaid_common.py:316-322`） | ✅ |
| 5 PNG 导出支持竖排 | P1 | 同一渲染器，自动覆盖 | ✅ |
| 6 hover 高亮 | P2 | 位图无 DOM | ➖ 不适用 |

## 1. 为什么真正的收益不是「省宽度」而是「字号放大」

导出 DOCX 是把整图**等比缩放到 16cm 栏宽**。画布越宽，同一字号在纸面上越小 ——
所以旧版 11 叶架构树（2740 设计像素宽）压到 A4 上，15px 字号只剩约 0.88mm，实际不可读。

竖排把画布宽度减半 ⇒ **同一字号的纸面相对尺寸放大约 2 倍**（实测见 §6）：
这才是文档 §2 说的「提升可读性」的机理，也是为什么**字号刻意不改**
（`LEAF_VERTICAL_FONT_SIZE = 15` 与横排同字号，收益全部来自画布收窄）。

## 2. 竖排绘制原语（`mermaid_common.py:304`）

CSS `writing-mode: vertical-rl` + `text-orientation: upright` 在 PIL 里的等价实现：

1. **逐字直立堆叠**（不旋转字形），自上而下；
2. **多列自右向左**流（`vertical-rl` 的「rl」语义）；
3. 整组**水平居中**于 box，每列**垂直居中**；
4. **容量收敛**：`per_col = (box_h + gap) // (char_h + gap)`、`max_cols = box_w // col_step`，
   超出 `per_col * max_cols` 时截断加 `…` —— **绝不越界画字**（护栏用「box 外墨迹像素必须为 0」像素级断言）。

放在 `mermaid_common` 而非 architecture 模块内：与 `_draw_text_center` 同族，
后续其它数据类型图表（劳动组织、对比表）可直接复用；并按拆包惯例在
`mermaid_renderer.py:1157` **re-export**，保持旧「从 renderer 导入」的兼容面。

## 3. 布局改造（`mermaid_architecture.py`）

### 3.1 单一事实源

旧实现把 `NODE_W/NODE_H/24/48/60` 等魔法数**内联在 DFS 与画布计算里**，且
「取子节点」的四行别名判断在 4 处重复。本轮全部收敛：

| 出口 | 位置 | 作用 |
| --- | --- | --- |
| 常量 | `:27-34` | 横排版式（值与旧实现逐字相同） |
| 常量 | `:43-51` | 竖排版式 |
| `_children_of()` | `:78` | `children/nodes/sub_units/branches` 四别名 + 非 dict 过滤的**唯一**口径 |
| `_dims_for()` | `:121` | `(宽, 高, 是否竖排)` 唯一判定 |
| `_gap_after()` | `:132` | 间距按前一子树根宽取，与 `_dims_for` 同源 |

⚠️ `_children_of` 必须是唯一出口：`count_vertical_leaf_candidates()`（`:260`）**刻意复用
`_build_nodes` 而不是另写一遍树遍历** —— 否则会出现「计数说 8 个叶子、实际只竖排 6 个」的口径分叉。

### 3.2 只竖排 L3 及更深（`LEAF_VERTICAL_MIN_DEPTH = 2`）

文档 §1 的优化对象是**最底部那一层**。二级（`depth==1`）节点恒为横排：
把中间层也画成竖条，标题就失去了横向可读性，且会让「哪层是叶子」在视觉上消失。

### 3.3 DFS 返回值语义变更（隐式约定显式化）

旧 `_dfs` 返回「子树右边界 **+ 一个 gap**」，父层再加一次 gap —— 混合间距（横排 24 / 竖排 12）下会算错步距。
现返回 `(occupied_end, own_root_w)`，尾随间距由调用方经 `_gap_after(child_root_w)` 补（`:218-220`）。

### 3.4 层高改为「按层取最大高」（`_assign_rows_y`，`:239`）

竖排叶子 232px 远高于横排 52px，旧公式 `y = depth * (NODE_H + V_GAP) + TOP_PAD` 会让下一层直接压进竖条里。
新实现逐层累加 `row_h[depth] + V_GAP`；**各层等高时精确退化为旧公式** —— 这条退化性质被
`test_horizontal_geometry_is_byte_identical_to_legacy_formula` 锁死，是「横排回退零风险」的核心证据。

### 3.5 契约

- `_layout_architecture_tree(root, vertical=None)`（`:279`）：仍返回 `(nodes, w, h)` 三元组，
  `vertical=None` 自动判定、显式 `True/False` 锁定版式（护栏与人工回退用）；
- 节点记录**只加一个键** `vertical`，旧字段全在（`test_layout_returns_three_tuple_with_legacy_keys_plus_vertical`）；
- `_unique_id` 的计数器时序**逐字保留**（含环/超深截断分支不自增 `leaf_counter`），
  避免自动 ID 与 AI 显式 ID 撞车的路径发生行为漂移。

## 4. 自动切换判据与运维通道

```
resolve_leaf_vertical_mode(root)          # :272
  = leaf_vertical_enabled()               # 环境变量总开关，默认开
    and count_vertical_leaf_candidates(root) > vertical_leaf_threshold()   # 严格「大于 6」
```

| 环境变量 | 位置 | 语义 |
| --- | --- | --- |
| `ARCH_LEAF_VERTICAL=0` | `:56` | 整体关闭竖排，**逐字回退旧横排版式**（`_OFF_VALUES` 认 `0/false/no/off/关闭`） |
| `ARCH_LEAF_VERTICAL_MIN=N` | `:57` | 调整阈值；非法值/负值回落默认 6，**绝不抛** |

阈值边界是**严格大于**（6 个叶子保持横排、7 个才竖排），与文档 §5 一致，已单独锁。

## 5. 顺带修复的既有 P0：环检测形同虚设（`:192-203`）

**Bug 类**：架构图含环数据时整张图静默丢失。

**根因**：旧 `_dfs` 用 `_unique_id()` 产出的 ID 做 `visited` 判重，而 `_unique_id` **保证任何两次调用返回值都不同**
（撞车时自动追加 `#2/#3`）⇒ `nid in visited` **恒为 False**，环检测从未生效过一次。
子节点直接/间接引用祖先 dict 时无限递归 → `RecursionError` → 被 `render_mermaid_to_bytes` 的兜底 `except` 吞掉，
用户侧表现为「架构图块凭空消失」，日志里只有一条泛化异常。

**修法**：改用**对象身份** `id(node)` 判重（同一 dict 被重复访问即判环），并加深度上限 `_MAX_DEPTH = 30`
防御超深链。两者均**按叶子截断**、不登记 `leaf_counter`，与旧实现的可观测行为逐字一致。

**可复用教训**：**用「全局唯一化函数」的返回值做 visited 判重，逻辑上永远不成立**。
判重键必须与「唯一化」目标相反 —— 要么用原始键，要么用对象身份。

## 7. 本轮最大教训：A/B 抓出两个「看着覆盖、实为盲区」的护栏

**M2（取消 depth 限定）与 M3（层高退回固定值）首轮变异后 38 例护栏全绿。**

根因不是变异太弱，而是**测试数据把被变异的行为等价化了**：
所有测试树的叶子都恰好落在**最底层一行** ⇒

- 「只有 L3 及更深竖排」与「所有叶子都竖排」在这些树上**结果相同**；
- 「按层取最大高」与「固定层高」在**只有一层需要高行**时**结果相同**。

修法不是加断言，而是**加树形**：引入 `_mixed_depth_tree()`，并对浅层树**显式传 `vertical=True`**
（把「版式判定」与「版式渲染」两件事拆开测，否则浅层树永远走不到竖排分支）。

配套两点：
1. **M2 的变异锚点必须包含紧随其后的 `return` 行** —— 只锚判定条件那半句，`in` 粗判会匹配到别处同形片段；
2. 参数化到两种树形后，`test_vertical_rows_do_not_overlap` / `test_vertical_only_touches_deep_leaves`
   才真正各自定向失败。

**可复用判据**：写布局/分支类护栏时，先自问「**是否存在一种输入，让这个分支和它的对照组产生相同输出**」。
若有，那个分支就是零覆盖 —— 变异测试是唯一可靠的发现手段（本轮再次证明：A/B 不是走流程，是真的会抓瞎）。

## 8. 运维提示

- **需重启后端进程**加载新渲染器；重启前旧进程仍按横排出图。
- 行为变化：**可竖排叶子数 > 6 的架构图**（组织架构图、架构树、质量/安全保证体系图）版式从横排变竖条，
  画布宽约减半、高约增五成。≤6 叶的图**逐字节不变**。
- 已有渲染缓存（`_render_cache` / 磁盘缓存）按 chart-code 键控，**代码未变则不会自动重刷**；
  如需强制重出图，调 `clear_render_cache()` 或重启（重启即清空内存缓存）。
- 紧急回退：`ARCH_LEAF_VERTICAL=0` 重启，无需改代码、无需回滚数据。
- 前端**零改动**（消费 PNG blob）。

## 9. 局限与未落地（记录以免重复排查）

1. **竖排不是万能解**。16 叶 / 4 组的极端宽树，竖排后纸面字号仍只有约 1.3mm。
   真正的解法是**限制单张架构图的规模**（AI 侧约束叶子数，或超宽时拆图），本轮未做。
2. **竖排标签有硬容量**（当前 box 约容 15 字），超出即 `…` 截断。
   刻意不做「自动增高节点」—— 那会让层高反过来影响整案画布，收益不稳定。
3. **文档 §3.3 的 `word-break: break-all`（词内断行）未实现**：中文逐字堆叠天然等价，
   英文/数字串（如 `BIM`）会占满整列，实测可接受。
4. **hover 高亮（文档增强项 6）**：位图渲染无 DOM，**结构性不适用**；琥珀橙高亮在竖排下保留并有像素断言。
5. **其它数据类型图表（劳动组织 / 对比表 / 平面布置 / 时间轴）未接竖排**：
   原语已放 `mermaid_common` 供复用，但各图自身宽度瓶颈与语义不同，需按图单独评估，本轮刻意不铺开。
