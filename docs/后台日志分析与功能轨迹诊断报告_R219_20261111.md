## 五、按模块问题根因与代码修复方案

### 5.1 FIX-1 [P2] · `backend/app/middleware.py` · `RequestLogMiddleware.__call__`

**根因**（不是「请求真的慢 7 小时」）：
- `await self.app(...)` 对 `StreamingResponse` 会一直推流到连接关闭才返回，`:186` 的 `cost` 因此是**连接生命周期**而非请求处理耗时；
- 日志格式 `METHOD PATH -> STATUS (Nms)` 未区分流式与普通请求，两类量混进同一分母 → 混合口径 P95=6289ms / P99=120000ms，而真实普通请求 P95=250ms；
- `:146` 用 `time.time()`（墙钟）测差值，NTP 校准 / 休眠 / 改系统时间会污染。

**修复**（加法式，普通请求日志逐字不变）：
| 位置 | 改动 |
|---|---|
| `middleware.py:17` | 新增纯函数 `_format_stream_duration(ms)` → `7h21m23s`，非法值 fail-soft 归零 |
| `middleware.py:168-175` | `start = time.monotonic()`；新增 `is_stream` 标记位 |
| `middleware.py:190-200` | 在 `http.response.start` 按 `content-type: text/event-stream` 只读识别流式 |
| `middleware.py:220-232` | 流式日志追加 `kind=stream conn=<可读时长>`；普通请求走原 `logger.info` 原样 |

**效果**：分析工具可按 `kind=stream` 分离统计；`test_r178::test_access_log_format_unchanged` 的既有格式断言原样通过。

### 5.2 FIX-2 [P1 · 安全方向] · `backend/app/services/preflight_engine.py` · `check_hazard_params`

**根因链**（代码级，非表象）：
```
clip_text_logged(joined, 2000)  →  return text[:2000]（头部硬截）
        ↓ 日志实证 3725→2000，丢弃 46%
danger_check → classify_scheme(scheme_name, params, extra_text)
        ↓ extra_text 只用于 match_category_keywords 命中危大子类
子类不命中 → evaluate_hazard_level 连阈值规则都不评估
        ↓ 即便 params = {"depth": 16.0}
check_hazard_params 的 hits = [h for h in hazards if h["hazard_reasons"]] → 空
        ↓
SAF-08「事实参数已达危大阈值但方案未标注」静默放行（安全红线方向漏判）
```
关键在**两个通道不对等**：`params` 走结构化全量事实（不受截断），`extra_text` 走拼串截断；而阈值规则必须经「子类命中」才会被查表。`fp_earthwork` 规则为 `depth>=3` 危大、`>=5` 超规模。

**行为实证（同一份 facts，反证 + 正例）**：
```
OLD_TOTAL 7450 → OLD_KEPT 2000，"开挖" 被裁掉
OLD_HITS []                      ← 旧口径零子类命中（漏判成立）
NEW_FINDINGS ['SAF-08']          ← 修复后报出，evidence 带 depth=16
```

**修复**（`preflight_engine.py:638` 前新增 `_hazard_keyword_hints()`，`:695-705` 接线）：
- 从事实**全量条目**扫描 `scheme_classification.HAZARD_CATEGORIES`（单一事实源，不复制第二份词表），提取已命中的类目关键词，去重保序成短串；
- 把该短串**前置**到拼串文本，再走原有 `clip_text_logged(..., 2000, "危大判定匹配文本")` ⇒ 类目匹配信息恒定落在保留区，**总预算仍是 2000 字**（`classification.source_text` 不膨胀）；
- 无关键词 / 分类表导入失败 → 返回空串，**逐字回退旧行为**（fail-soft）；

## 七、优化建议

**运维（需人工，不可代码修复）**
1. 重启后端使 `middleware.py` / `preflight_engine.py` 生效（零迁移、零新配置）。
2. 更新 `backend/.env` 的 agnes 令牌（3 次 401「该令牌状态不可用」）；按部署面决定是否开启 `API_AUTH_TOKEN` 与 `PROMPT_REDACT_SENSITIVE`。

**可观测性（重启后）**
3. 用 `python scripts/log_audit_r219.py logs/backend.log <输出>` 复算基线，确认 `kind=stream` 已出现、普通请求 P95 稳定在 ~250ms；长连接单列观察，不再污染慢请求告警。
4. 再现 ≥5s 事件循环阻塞时，直接读 R218 栈采样的「在途任务栈」定位同步 CPU 段；重点观察 `review/autofix/stage`、`export/docx`、`compliance/check` 三类慢请求。

**后续轮次（登记，不在本轮改）**
5. **Token usage 埋点缺口**：访问日志/审计日志未落 `prompt_tokens` / `completion_tokens`，本窗口只能采到 2 条 `max_tokens` 放大记录 ⇒ 无法建立真实 Token 消耗基线。建议在 `provider_factory` 成功返回处加法式落结构化字段（带 `trace`/`task_type`/`model`），与既有 `cache_metrics` 同源。

7. **计算书能力建设**：若产品需要 JGJ 130 / JGJ/T 231 验算，须作为独立模块立项（参数表、工况组合、规范阈值、计算书模板），当前 `placeholder_sections` 只做占位，不能靠日志修复补齐。
