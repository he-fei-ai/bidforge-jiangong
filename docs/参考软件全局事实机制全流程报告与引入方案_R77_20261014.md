## 0. 总体结论（先说结论）

1. 参考软件的全局事实存在 **V1 分段流水线（`globalFactsTask.cjs`，逻辑完整但未挂载）** 与 **V2 Agent 工作区（`globalFactsTaskV2.cjs`，生产在用）** 两套；`taskService.cjs:5` 只 import V2（`taskService.cjs:1445-1459` 挂载）。
2. **生产链路顺序是「标书分析 → 目录生成 → 全局事实 → 正文生成」**，全局事实排在目录**之后**（`TPS:193-195` step 枚举；`TechnicalPlanHome.tsx:407-409` 门禁）。**目录生成对全局事实的读取点为 0 处**（全文检索 `facts/Fact/全局/事实` 于 `OG`、`outlineAdjustmentTask.cjs`、`feasibilityOutlineTask.cjs` 均零匹配）—— 目录是事实的**上游**，不是消费者。
3. 全局事实进入正文的机制是**两级漏斗**：编排阶段 AI 只见**标题清单**（`CG:828-830`）→ 生成阶段程序按标题取回**完整内容**只注入当前章节（`CG:171-177, 4218`）。
4. 一致性保障是「生成后审计 + 定点替换」闭环：审计只查**已明确写出**的冲突（`CG:1667-1671`）→ AI 返回 `old_text/new_text` → 程序**唯一命中才替换**（`CG:1584-1616`）→ 失败回灌重试（上限 2 次，`CG:5697-5824`）→ 仍失败转人工（`CG:5995/6029`）；Agent 修复靠「标记包裹全文 + 程序解析校验 + 只回写差异小节」（`CG:1471-1515, 5490-5528`）。
5. 本软件**已有**相当完整的事实体系（统一门控 `_FACTS_INJECT_WHERE`、逐章精选、交叉校验、定点编辑 `consistency_edits`），差距集中在**接线深度**：① 生成后检出的事实冲突不进修复闭环；② 目录子目录事实注入无按章精选；③ 正文不记录 `fact_id` 级溯源。本轮已按 P0 落地 ① ② 并建 21 例护栏。

## 第一部分 · 全局事实提取工作流程和思路报告

### 1.1 定义与定位

**精确定义**（V1 system 提示词 `GF:52-58` 逐字）：

> 你是专业的投标技术方案事实变量整理助手……整理后续正文需要统一采用的全局事实变量。
> 1. 全局事实变量**不是**招标要求摘录、评分规则摘要或待办事项清单，而是技术方案正文中需要保持一致的**确定性方案事实、响应设定、承诺口径或执行安排**。
> 2. 用户资料已经给出明确事实时，优先使用资料中的事实值。
> 3. 用户资料只给出要求、约束或评价口径时，**不要原样摘录为要求句**；如果该内容会影响后续正文的一致写法，应**转写为本方案已经采用、已经具备或统一承诺的事实表达**。

V2 同构表述见 `GFV2:192`。**与「招标要求摘要」的本质区别**：

**应用算法**（程序侧，`CG:1584-1616`）：

```pseudo
applyExactConsistencyPatch(content, patch):
  old/new 归一化；old=='' 或 new=='' 或 old==new → throw
  if start_line/end_line 合法且 extractLineRangeText == old:   # :1530-1538, 1600-1605
      return replaceLineRange(...)                             # 行范围优先
  matches = findExactOccurrences(content, old)                 # indexOf 全量扫描, :1517-1528
  matches.length == 0 → throw 'old_text 未在当前小节正文中找到'
  matches.length >  1 → throw 'old_text 在当前小节正文中出现多次，请提供更多上下文确保唯一定位'
  return 唯一命中处拼接替换
```

**重试与人工兜底**（`CG:5697-5824`）：`for attempt in 1..2`：AI → patches 为空记 failures；`applyConsistencyRepairPatches` 成功计数 + 失败收集 errors（`:1618-1646`）；`appliedCount>0` 保存小节（`:5774-5786`）；errors 非空 → 回灌下一轮；两轮后 `return {failed:true}` → 日志「一致性修复需人工核对」（`:5995`）。汇总日志（`:6029` 逐字）：`一致性审计完成：发现 N 个冲突小节，成功修复 M 个，K 个需人工核对。`

## 第六部分 · 引入本软件方案（已实施 P0，记录 P1/P2）

### 6.1 引入原则的落地方式

1. **复用成熟思路不照搬代码**：易标的 Agent 工作区范式不移植（本软件是 FastAPI 服务端架构）；移植的是「两级漏斗 + 生成后审计 + 唯一命中定点替换 + 失败回灌 + 转人工」五件套的**语义**。
2. **保持架构/接口/数据链兼容**：全部改动为加法式——新模块、新函数、新提示词、新配置键、报告新键 `fact_autofix`；零 DDL、零数据迁移、零依赖新增。
3. **不破坏已有功能**：新开关均可用配置逐字回退；无冲突章节零新增 AI 调用（成本中性）。
4. **按建筑工程专项方案定位适配**（对易标机制的刻意偏差）：
   - 易标「必保工期/运维期/交货时间至少一个」→ 本软件事实侧已有危大判定参数 + 工程地质水文要求（`danger_check:610`），**不引入"交货/运维"必保项**（专项方案无意义，会诱导编造）；
   - 易标 `fabricate` 默认可杜撰 → 本软件 `is_simulated` 值**永不进正文**（注入门控 `is_simulated=0`），工程语境更严；
   - 易标审计「不报缺失」→ 本软件保留该纪律（`fact_value_missing` 是 warning 不进修复），但**缺失在预检/审核侧另有人工通道**（专项方案缺失即事故的判据由 SAF/DLV 族承担，不在本闭环内扩大）；
   - 易标人员 few-shot 示例 → 本软件示例改用工程参数语境。

**行为契约**：

- 仅在 standard_report 检出 **error 级事实冲突**（`value_mismatch` / `value_conflict` / `model_conflict`）的章节触发一次 AI 调用；无冲突章节**零调用**（成本中性）；
- `old_text` 不唯一/找不到/过短一律拒绝（复用 `consistency_edits` 同一判据，不造第二份）；
- AI 可返回空 edits（判定并非真实矛盾时宁可不改）；
- 修复后**重算**标准校验报告，使 `error_count`/`issues`/字数/SSE 载荷/落库正文五处口径一致；
- 结果写 `last_generation_report.fact_autofix` 新键：`{attempted, applied, rejected, conflicts, attempts}`（加法式契约）；
- 任何异常 fail-soft，绝不阻断正文落库；
- `content_fact_autofix_enabled=False` → 逐字回退引入前行为。

**为什么允许 standard_report 的第二次（条件性）调用**：原护栏 `test_report_is_not_recomputed_in_event_path` 钉「每章只扫一次」（缺陷：事件侧重扫）。本次第二扫受 `if _fa_res.get("applied"):` 门控（仅冲突被实际修复的极少数章节），且护栏已**精确化**为「恰好 2 处 + 第二次必须位于修复块内 + 必须在写锁前」（见 `tests/test_content_standard_sse_wiring.py` 修订注释）——原成本缺陷不会回归，新重扫的位置被钉死。
