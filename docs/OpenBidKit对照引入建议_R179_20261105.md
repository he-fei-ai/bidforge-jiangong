## 4. 缺失项（对方有、本项目没有 / 未取证到）

> 共 **6 条**。按"是否与专项方案业务直接相关"排序；全部要求独立重写。

### M1. 评分项→目录映射校验（P1，3-4 人日）

- **对方**：先抽技术评分项 → 评分分组 → 目录规划 → `collectScoreMappingCoverage` 校验"每个评分项都有目录落点"，并报告 `matched / missing / unexpected` 标题；目录审核把"评分覆盖"作为四维之一（`outlineGenerationTaskV2.cjs:74-156`、`419-462`、`944-967`）。
- **本方**：解析阶段已抽取"技术评分要求"（`bid_analysis_service.py` 技术评分项），但目录生成与校验链路**未见任何评分项映射/覆盖率校验**（全仓检索"技术评分|评分项|score_item|scoring_item"无目录侧使用）。
- **影响**：目录"看起来专业"但可能漏掉评分点，评审直接丢分；这是本报告**最值得引入**的一条。
- **建议做法（独立实现）**：目录生成后增加一个确定性校验器：评分项 → 关键词/语义匹配到的叶子节点列表；输出覆盖率与未覆盖清单；作为**软提示**回灌目录修复（不阻塞导出）。
- **成本/风险**：3-4 人日；需评分项结构化字段（现为自由文本，需先归一）。回退=关闭开关，保留原目录结果。
- **许可**：可借鉴思路（须重写）。

### M2. "任务状态 + 业务状态"原子 checkpoint（P1，3-5 人日）

- **对方**：`checkpointTask` 在同一处完成"业务状态落库 + 任务状态落库 + 广播"，避免"业务已写、任务仍显示 running"的撕裂态（`taskService.cjs:775-831`）。
- **本方**：各域 checkpoint 为**提示词上下文构建**（如 `content_checkpoint.py`、`outline_checkpoint.py` 提供上下文片段），任务状态与业务数据由不同路径更新；**未见统一原子封装**（需复核 `task_registry.py` 与各 SSE handler 的落库顺序）。
- **影响**：断点续跑时可能出现"进度与数据不一致"，重跑重复计费或漏章。
- **建议做法**：在现有任务表上增加"单事务更新业务快照 + 任务阶段"的服务函数，逐个任务域替换调用点；先补 3-5 个撕裂态回归用例。
- **成本/风险**：3-5 人日，跨多个任务域；回退=保留旧双写路径，新路径开关控制。
- **许可**：可借鉴思路（须重写）。

### M3. 前端统一 AI HTTP 错误对话框（P1，1-2 人日）

- **对方**：全局错误队列 + 对话框，展示状态码、请求 URL、原始响应体（可复制），区分文本/生图来源，并识别 HTML 错误页（`AiHttpErrorDialogProvider.tsx:6-60`）。

- **影响**：403/404/网关错误时用户只看到"生成失败"，无法判断是密钥、地址还是供应商故障。
- **建议做法**：新增全局 Provider，接管 AI 相关 SSE/HTTP 错误事件；保留原 toast 作为降级；错误体脱敏后展示，提供"复制诊断信息"。
- **成本/风险**：1-2 人日；需后端在错误事件里加法式补 `status_code/request_url/body_excerpt`（旧字段不动）。
- **许可**：可借鉴思路（须重写）。

### M5. 资料块噪声过滤清单（P2，2 人日）

- **对方**：入库前过滤页码块、目录块、封面、签字页，再做语义标题合并，避免"页码/目录"被当事实来源（`knowledgeBaseService.cjs:123-210`）。

- **本方**：**已有单点预热**（`bid_analysis.py:137` 固定等待 5s，先跑第一个必选项），但正文逐章生成、一致性审计等阶段仍全部并发，**未按提示词变体分组串行暖场**；usage 表虽有 `cached_tokens` 列（`provider_factory.py:1873-1916`），但注释自认"三列从无写入方"，**做 A/B 前需先补该字段埋点**。

## 6. 不值得引入项（对方更差或路线不适用）

> 这一节用于证明报告不是"什么都想搬"。共 **8 条**。

### N1. Agent 化目录生成 + 自动确认（不可引入）

- 对方把目录生成交给编码 Agent（`@earendil-works/pi-coding-agent`）在临时 workspace 读写 JSON，并用 8 秒倒计时自动确认 Agent 的反问（`outlineGenerationTaskV2.cjs:974-1148`、`autoConfirmationService.cjs`）。
- **理由**：目录生成本质是确定性结构化任务，交给通用 Agent 会引入不可复现、难测试、成本不可控三类问题；自动确认还会把"未被人确认的假设"写进成果。本项目的"单点判定 + 结构化校验"路线更可控。
- **替代**：只借鉴其"评分项映射校验"（M1）与"目录审核三态"（U4），不借鉴 Agent 编排。

### N2. 用表格模拟"章节框线"排版（不可引入）

- 对方把章节内容包进大表格，用单元格边框做出章节框（`exportService.cjs:321-437`）。
- **理由**：表格承载正文会破坏文档语义（大纲、复制粘贴、无障碍、后续编辑），且分页行为不可控；本项目已有样式化的段落排版与后处理，不需要这种视觉 hack。

### N3. 废标项检查 / 错别字 / 逻辑谬误（业务域不适用）

- 对方是"投标人写标书"工具，废标项检查面向"投标文件是否会被废标"（`rejectionCheckTask.cjs`）。
- **理由**：本项目产出专项施工方案，没有"投标文件递交/废标"的业务对象；强行引入会产出无处置路径的告警。
- **替代**：本项目的规则审核 + 预检已覆盖方案合规性，只需补证据链（U1）。

### N4. 多份投标文件查重 + 文件同源取证（业务域不适用）

- 对方解析 OLE/CFB、PDF ID、`word_rsid` 等做"串标/同源"检测（`duplicateCheckService.cjs:319-970`）。
- **理由**：本项目是单方案编制，不存在"多家投标文件互查"的数据场景；若未来做"历史方案复用检测"，只需本方已有的 `duplicate_detection.py` 句式/骨架查重，不需要文件取证链。

### N5. 导出模板库（对方自身未接通）

- 对方 `export_templates` 表 + UI 选择项存在，但导出管线不消费模板（schema 注释自认），`templateStore.cjs` 只做 CRUD。
- **理由**：半成品，无参考价值；本项目如需模板能力，应直接设计"模板 → 样式映射表 → 导出消费"的完整闭环，而不是照搬其表结构。

### N6. 遥测 Worker + Dashboard（不可引入）

- 对方用 Cloudflare Worker + D1 收集流量、Agent 运行、错误日志、配置使用、IP 黑名单，并下发公告/插件/许可证（`analytics/**`）。
- **理由**：本项目为内部/私有部署，外发遥测涉及数据合规与运维成本；此外其"许可证/公告下发"属于其商业运营设施，与本项目无关。
- **替代**：本地诊断日志 + 现有活动栏/审计日志足够。

### N7. 提示词散落为常量 + 假 "Prompt Lab"（反面教材）

- 对方 61 个提示词常量散落在 8 个 service 文件，`shared/prompts` 仅 13 KB；文档宣称的版本化 Prompt Lab 是静态演示页（`DeveloperDemoPage.tsx:19-36`）。
- **理由**：本项目已有提示词注册表 + 版本 + 指标 + 编辑/审计/回滚（42 个提示词文件），对方这是明显的反向示范，**不可学**。

### N8. 无 lint / 无测试 CI 的工程习惯（不可学）

- 对方无 ESLint、无 test 脚本、CI 只发版，15 个测试文件撑 2.3 MB 主进程代码。
- **理由**：与本项目"整树回归 + 零点校验"的红线完全相反，任何"引入"都不应顺带削弱本项目的工程约束。
