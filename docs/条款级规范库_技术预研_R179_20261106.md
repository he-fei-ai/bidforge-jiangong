## 2. 检索可行性实测

### E1：FTS5 是否编译

见 §1.1。`ENABLE_FTS5` 存在，`CREATE VIRTUAL TABLE ... USING fts5(...)` 成功。**结论：可用。**

### E2：`unicode61` 对中文到底怎么切

命令：

```powershell
python "$env:TEMP\r179_clause_exp\exp1_tokenizer.py"
```

原文：`深基坑支护结构应进行变形监测，监测频率不应少于每天一次。`

`unicode61` 的 token 表：

```text
['深基坑支护结构应进行变形监测', '监测频率不应少于每天一次']
```

关键实测：

```text
MATCH '基坑支护'        -> 0
MATCH '变形监测'        -> 0
MATCH '深基坑支护结构应进行变形监测' -> 1
```

原因：`unicode61` 把「，」当分隔符，但**连续汉字不会被切词**，整段「深基坑支护结构应进行变形监测」是一个 token。因此：

- 只有与整段 token 完全相等时才命中；
- 任意子串/短词查询都落空；
- 不能靠调 `separators` 解决，因为汉字之间没有分隔符。

**结论：`unicode61` 不能单独承担中文条款检索。** 只有两种补救：（a）入库前用领域词典预分词并加空格；（b）改用 `trigram`。前者需要持续维护词典，后者是 SQLite 内建、零依赖，优先选 `trigram`。

### E3：逐字加空格的 `unicode61` 反例

把「基坑支护结构」写成「基 坑 支 护 结 构」，`unicode61` 会切成单字；查询「基坑」变成 `"基" AND "坑"`：

```text
'"基" AND "坑"' -> rowid [1]
'"模" AND "板"' -> rowid [2]
'"混" AND "凝"' -> rowid [3]
```

单字 AND 会在任意共现位置命中，误召不可控。**该方案不采纳。**

### E4：`trigram` 的切分与查询语义

同一句原文，`trigram` token 是 3 字滑窗（含标点）：

```text
['深基坑', '基坑支', '坑支护', '支护结', '护结构', '结构应', ... '测，监', '，监测', ...]
```

查询行为实测：

| 查询 | 结果 | 说明 |
|---|---|---|
| `基坑`（2 字） | 0 | trigram 需要 ≥3 字符，2 字无法构造 trigram |
| `基坑支`（3 字） | 命中 | 子串命中 |
| `基坑支护`（4 字） | 命中 | 整体按子串匹配 |
| `基坑监测`（4 字，但原文是「基坑支护…监测」不连续） | 0 | **trigram 是子串匹配，不是分词 AND** |
| `基坑 监测`（两个 2 字词） | 0 | 每个词都 <3 字，整体失效 |
| `"基坑支" AND "监测频"` | 命中 | 引号包裹 3 字以上片段后可用 AND |
| `"基坑支" OR "模板支"` | 命中多篇 | OR 可用 |

**关键结论：**

1. `trigram` 的 `MATCH` 语义是「连续子串」，不是「中文分词后 AND」。用户输入「基坑 监测」时，如果两个词都只有 2 字，直接 0 命中。
2. 查询必须预处理成 **≥3 字的片段**，并且每个片段用双引号包起来，避免 `-`、`*`、`OR`、`.` 触发 FTS5 查询语法错误。
3. 无空格连写（「基坑支护验收」）也不是万能：如果原文是「基坑支护**工程**验收」，整串不是连续子串，仍会 0 命中；需要 **3 字滑窗展开**（见 §3.1 与 §7.5）。
4. 2 字短词（「基坑」「验收」「监测」）永远不要指望 trigram，必须走 LIKE 或作为加权项。

### E5：短查询的召回与误召

40 条模拟语料上的实测（S3 脚本）：

| 查询 | 字数 | trigram 命中行 | LIKE 命中行 |
|---|---|---|---|
| `基坑` | 2 | **0** | 6 |
| `模板` | 2 | **0** | 5 |
| `监测` | 2 | **0** | 5 |
| `验收` | 2 | **0** | 3 |
| `水平位` | 3 | 2 | — |
| `连墙件` | 3 | 2 | — |
| `报警值` | 3 | 1 | — |
| `三级配` | 3 | 1 | — |
| `垂直度` | 3 | 3（跨 **3 个标准**） | — |
| `混凝土` | 3 | 6（跨 **4 个标准**） | — |

**结论：3 字查询能召回，但跨标准误召明显。**「垂直度」同时命中塔机、扣件脚手架、盘扣支架；「混凝土」同时命中模板、混凝土施工、混凝土验收、地基基础。条款检索不能只看文本命中，必须叠加标准号/专业域过滤与覆盖率重排。

### E6：`bm25()` 在中文条款上是否合理

`bm25()` 返回负值，越负越相关。实测两个现象：

1. **词频/堆词偏好**：同一查询「基坑支护」，一条 22 字的正常条款 bm25 为 `-0.332`；另一条 25 字但把「基坑支护」重复 4 次的文档为 `-0.551`，后者排在前。说明堆词可以压过正常表达。
2. **同域误排**：查询「脚手架 连墙件 间距」时，仅按 bm25 排序会把「脚手架拆除…连墙件…」排到「脚手架连墙件…间距」前面（前者命中「脚手架」「连墙件」，后者还多命中「间距」）。覆盖率重排可纠正。

40 条语料、10 查询上的对比（S3）：

| 方案 | Hit@1 | Hit@3 | Hit@5 | MRR | 平均召回@5 | top5 误召总数 |
|---|---|---|---|---|---|---|
| A 纯 LIKE（≥2 字 token AND） | 0.70 | 0.70 | 0.70 | 0.700 | 0.600 | 0 |
| B 朴素 trigram（整串 MATCH） | 0.00 | 0.00 | 0.00 | 0.000 | 0.000 | 0 |
| C trigram 分片 AND + 短词 LIKE | 0.70 | 0.70 | 0.70 | 0.700 | 0.600 | 0 |
| D 精确号 + C + 结构加权 | 0.70 | 0.70 | 0.70 | 0.700 | 0.600 | 0 |
| E OR 候选 + 覆盖率重排 | **1.00** | **1.00** | **1.00** | **1.000** | **0.867** | 10 |
| F 仅 bm25（OR 候选） | 0.90 | 1.00 | 1.00 | 0.950 | 0.867 | 10 |

**结论：** bm25 的方向是可用的，但它只应作为排序信号之一（建议权重 ≤0.15–0.20）；主排序用「查询词覆盖率 + 适用条件/章节匹配 + 精确号硬命中」。纯 LIKE 在 40 条小语料上并不差，说明「小库 + 短查询」时 LIKE 完全可做降级方案。

### E8：FTS5 查询语法与转义

用户输入里的 `-`、`*`、`(`、`)`、`OR`、`NEAR` 会改变 FTS5 查询语义，未加引号时 `GB 50007-2011` 会报语法错误。实测：对每个片段做 `term.replace('"','""')` 后包进 `column:"..."`：

```text
'GB 50007-2011' -> 命中
'第5.2.1条'      -> 命中（前提是该文本在已索引列）
'三级配电'       -> 命中
'OR'             -> 0（被当作普通字符串，不解释为运算符）
'验收*'          -> 命中（仅因原文含字面 `*`；不再当通配符）
'(三级配电)'     -> 命中（括号不再是分组）
'"三级配电"'     -> 0（引号被转义为字面量，原文不含引号）
'-'              -> 0（原文不含 `-`，且不触发语法错误）
```

说明：`OR`/`验收*` 的命中与否取决于原文是否含该字面量；关键是**不再被解释为 FTS5 运算符/通配符**，也不会抛语法错误。未加引号的对照（S1）会直接报 `no such column: 2011` 或 `syntax error near "."`。

**结论：所有用户片段必须双引号包裹并转义内部双引号；禁止把原始查询直接拼进 `MATCH`。** 标准号/条款号仍应优先走 SQL 精确查询，不依赖 FTS 文本匹配。

### E9：约束、幂等、归一化、部分失败

**（a）CHECK 约束**（S4）：

```text
500 字插入: OK, length= 500
501 字: 已拦截 -> CHECK constraint failed: length(excerpt) BETWEEN 1 AND 500
空摘录: 已拦截
license 空白: 已拦截
非法状态: 已拦截
```

多列 CHECK 也实测可用（S7）：

```text
verified 缺 verified_by: 拦截
verified 完整: 通过
无来源: 拦截
```

外键指向 `UNIQUE` 文本列 + `ON DELETE CASCADE` 实测可用。

**（b）幂等 upsert**（S4）：

```text
行数: 1 内容: [('id1', '新摘录', 'b2')]
```

同一 `(standard_code_norm, version, clause_no_norm)` 第二次导入更新内容而不是新增行。

**（c）条款号归一化**：

```text
'第5.2.1条' -> 5.2.1
'5.2.1'     -> 5.2.1
'5.2.1条'   -> 5.2.1
' 第 5.2.1 条 ' -> 5.2.1
'5.2.1款'   -> 5.2.1
'5.2'       -> 5.2
'附录A.0.1' -> 不匹配（需单独规则）
```

**结论：** 条款号必须先归一化再入库；附录条款需要单独规则（`A.0.1` 带 `clause_kind='appendix'`），不能硬塞进主正则。

**（d）逐行 SAVEPOINT 部分失败**（S5）：

```text
已入库: [('K1', 'ok1'), ('K2', 'ok2'), (None, 'none-key'), ('K3', 'ok3')]
失败登记: [('K1', 'UNIQUE constraint failed: t.k')]
```

注意：输入 5 行，最终入库 4 行——其中 `(None, 'none-key')` 被插入了，因为 **SQLite 的 `TEXT PRIMARY KEY` 历史行为允许 NULL**。这是重要坑：业务主键必须显式 `NOT NULL`，或直接用 `INTEGER PRIMARY KEY`。设计里两者都做了（`id INTEGER PRIMARY KEY` + `clause_uid TEXT NOT NULL UNIQUE`）。

### E10：LIKE 降级性能

同一台机器、40 字左右的条款文本：

| 行数 | 查询 | 耗时 |
|---|---|---|
| 1 万 | `LIKE '%基坑支护%'` | 1.6 ms |
| 1 万 | `LIKE '%基坑%'` | 1.2 ms |
| 1 万 | trigram `MATCH '基坑支护'` | 1.5 ms |
| 10 万 | `LIKE '%基坑支护%'` | 15.8 ms |
| 10 万 | `LIKE '%基坑%'` | 14.1 ms |

（另：trigram 虚拟表上的 `LIKE '%基坑支护%'` 为 8.1 ms、`LIKE '%基坑%'` 为 2.9 ms，均慢于普通表，见 S2。）

**结论：** 条款库在 1 万–10 万条量级时，LIKE 全表扫描完全可以作为 FTS5 不可用的降级路径；超过 10 万条再考虑额外索引或强制要求 FTS5。实测中 trigram 虚拟表上的 LIKE 并不比普通表快，**不要把 trigram 当作 LIKE 加速器**，它只用于 `MATCH`。

### E11：rowid / VACUUM / NULL 主键

S5 实测：

- `TEXT PRIMARY KEY` + 外部内容 FTS：VACUUM 前后 rowid 未变（本 build 保留了 1/3/4/5），`integrity-check` 通过；
- `INTEGER PRIMARY KEY` + `content_rowid='id'`：同样通过，且删除行后 FTS 检索仍正确；
- SQLite 文档明确说 VACUUM **可能**改变无 `INTEGER PRIMARY KEY` 表的 rowid，因此不能依赖本次「未变」的观察。

**设计决策：** 用 `id INTEGER PRIMARY KEY` 作为 FTS 的 `content_rowid`，业务侧用 `clause_uid TEXT NOT NULL UNIQUE` 引用。这样即使 VACUUM 重排，FTS 外键仍稳定。

**另一个坑：** `TEXT PRIMARY KEY` 允许 NULL（实测），`UNIQUE` 也允许多个 NULL。所有业务键必须显式 `NOT NULL`；`clause_uid` 已加。

### E12：NFKC 的双刃剑

`unicodedata.normalize('NFKC', ...)` 能修全角编号：

```text
'ＧＢ ５０００７－２０１１' -> 'GB 50007-2011'
```

但会改工程单位：

```text
'25℃ 15kN/m² 30mA 10Ω 4‰' -> '25°C 15kN/m2 30mA 10Ω 4‰'
```

**结论：** NFKC 只用于**查询串与标准号**归一化，**不要**对入库的 `excerpt` 做 NFKC，否则会破坏「℃」「m²」等原文单位。单位别名另建映射（`m²/m2/平方米`、`℃/°C`），不要靠 NFKC 统一。

## 3. 混合检索设计

### 3.1 查询预处理

输入：用户原串 + 可选上下文（标准号、方案类型、章节标题）。

步骤：

1. **NFKC** 归一化查询串（只对查询，不对摘录）。
2. **精确号解析**：
   - 标准号：`(GB/T|GB|JGJ/T|JGJ|CJJ/T|CJJ|DB\d+/T|T/CECS)\s*\d+(?:\.\d+)?\s*[-—－–]\s*\d{4}`；
   - 条款号：`第?\s*(\d+(?:\.\d+)+)\s*条?`；附录：`附\s*录\s*[A-Z]\s*[.．]\s*\d+(?:\.\d+)*`。
3. **文本切块**：
   - 按空白与标点切成块；
   - 块长 2 字 → 只作为 LIKE/加权项，不单独作为 trigram 条件；
   - 块长 3–5 字 → 直接作为 trigram 片段；
   - 块长 ≥6 字 → **3 字滑窗展开**（`t[i:i+3]`），用 OR 组合；
   - 数字+单位（`18m`、`30mA`、`25℃`、`15kN/m2`、`4‰`）单独保留，用于数值硬匹配/加权。
4. **同义词扩展**（人工维护，见 §10）：`塔吊→塔式起重机`、`附墙→附着`、`测温→温度监测`、`降水→地下水控制`、`临电→临时用电` 等。
5. 每个片段用双引号包裹并转义内部双引号，禁止把原串直接塞进 `MATCH`。

实测依据：无空格连写查询「基坑支护验收」「模板支撑跨度18m」等 10 条，按整串 MATCH 时 Hit@1 为 **0.00**；加 3 字滑窗后 Hit@1 为 **1.00**（S3，§7.5）。

### 3.2 两段式检索

**第一段：精确段（结构化，不走 FTS）**

| 输入形态 | 动作 | 返回 |
|---|---|---|
| 标准号 + 条款号 | `WHERE standard_code_norm=? AND version=? AND clause_no_norm=?` | 精确命中，置顶，`match_type='exact'` |
| 标准号，无条款号 | `WHERE standard_code_norm=?`，再在结果内做正文排序 | 标准内候选，`filter='standard'` |
| 只有条款号，无标准号 | 不猜测；返回 `needs_context` 或列出多标准候选并标注歧义 | `ambiguous` |
| 标准号无年份 | 先按 `standard_base_norm` 找现行版本；多个现行版本 → `ambiguous` | `version_selected` |
| 标准已废止/不在注册表 | 不检索正文；返回 `invalid_standard`/`unknown_standard` | 提示替代标准 |

**第二段：正文段（FTS5 或 LIKE）**

- 候选生成：`standard_clauses_fts MATCH 'excerpt:"片段1" OR excerpt:"片段2" ...' LIMIT 50`；
- 标准强过滤：仅当查询显式含标准号，或方案类型经 `CATEGORY_STANDARDS` 高置信映射到单一专业时，追加 `standard_code_norm IN (...)`；否则只做加权，避免误杀跨专业条款；
- 短词：2 字词不参与 `MATCH`，作为候选重排的加权项；若查询只有 2 字词且无标准/专业上下文 → `needs_context`；
- 去重：`excerpt_hash` 去重；同一标准最多 2 条，除非精确命中。

**为什么需要强过滤 + 正文两段式：**

- 精确号必须不被文本相关性稀释；`GB 50007-2011 第5.2.1条` 如果走文本检索，`第5.2.1条` 里的 `.`、`-` 会触发语法问题，且不同标准的同一条款号会混；
- 正文检索必须保留模糊召回；只做标准过滤会把「用户没写标准号但意图明确」的查询锁死；
- 「垂直度」「混凝土」这类 3 字词的跨标准误召（S3 实测 3–6 行、跨 3–4 个标准）只能靠专业域/标准号过滤压下去。

### 3.3 排序公式（建议初值，实施后调参）

```
score = 0.55 * coverage
      + 0.20 * applicability_match
      + 0.15 * bm25_norm
      + 0.10 * prior

coverage = Σ w(t) * hit(t) / Σ w(t)
  w(t) = len(t) / (len(t) + 2)          # 长词权重高，2 字词权重低
  hit(t) = 1 if t 出现在 excerpt/chapter/applicability 中
bm25_norm = min(1.0, max(0.0, -bm25(...) / 3.0))
prior = 1.0 if verification_status='verified'
      + 0.3 if mandatory=1 且查询意图含「强条/强制」
      + 0.3 if 查询中的数值/单位与 clause 的 condition_json 匹配
```

硬规则优先于分数：

1. `status='active'`；
2. 已废止标准/条款不进入生成上下文；
3. `verification_status='doubtful'` 只用于审计，不进入生成；
4. 精确命中永远排第一，不参与加权。

### 3.4 检索输出契约（生成侧只拿这个）

```python
@dataclass(frozen=True)

    clause_uid: str
    standard_code: str          # GB 50007-2011

    version: str                # 2011 / 2015年版
```

生成侧禁止拿到「整段规范正文」；只拿 `excerpt` + 引用元数据。Prompt 注入格式建议：


### 3.5 两个示例

**示例 1：精确号**

输入：`GB 50007-2011 第5.2.1条`

- 解析：code=`GB 50007-2011`, clause=`5.2.1`；
- 归一化：`GB50007-2011`；
- 精确 SQL 命中 C01，`match_type='exact'`，直接置顶；
- 不再依赖 FTS；即使 FTS5 不可用也能命中（这是降级路径的关键保底）。

**示例 2：模糊意图**

输入：`深基坑 监测 报警值`

- 片段：`深基坑`(3)、`监测`(2)、`报警值`(3)；
- FTS：`excerpt:"深基坑" OR excerpt:"报警值"`（`监测` 只有 2 字，默认不参与候选生成，只作为加权项）；

- 覆盖率：C09 命中 2 个查询词，C11 命中 2 个，C10 命中 1 个；
- 若方案类型=基坑工程，追加 `CATEGORY_STANDARDS` 中的 `GB 50497-2019` 加权/过滤，排除跨域噪声；
- 返回 top3 + `status='ok'`；若该标准未入库 → `no_corpus`，返回「无法判定」。

### 4.4 FTS5 外部内容表与触发器

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS standard_clauses_fts USING fts5(
    excerpt,
    clause_uid UNINDEXED,
    content='standard_clauses',
    content_rowid='id',
    tokenize='trigram',
    detail='full'
);

CREATE TRIGGER IF NOT EXISTS standard_clauses_ai
AFTER INSERT ON standard_clauses BEGIN
    INSERT INTO standard_clauses_fts(rowid, excerpt, clause_uid)
    VALUES (new.id, new.excerpt, new.clause_uid);
END;

CREATE TRIGGER IF NOT EXISTS standard_clauses_ad
AFTER DELETE ON standard_clauses BEGIN
    INSERT INTO standard_clauses_fts(standard_clauses_fts, rowid, excerpt, clause_uid)
    VALUES ('delete', old.id, old.excerpt, old.clause_uid);
END;

CREATE TRIGGER IF NOT EXISTS standard_clauses_au
AFTER UPDATE OF excerpt, clause_uid ON standard_clauses BEGIN
    INSERT INTO standard_clauses_fts(standard_clauses_fts, rowid, excerpt, clause_uid)
    VALUES ('delete', old.id, old.excerpt, old.clause_uid);
    INSERT INTO standard_clauses_fts(rowid, excerpt, clause_uid)
    VALUES (new.id, new.excerpt, new.clause_uid);
END;
```

实测依据：E2 中同样的外部内容 + 三触发器模式，插入、更新、`snippet()`、`integrity-check` 全部通过。`AFTER UPDATE OF excerpt, clause_uid` 避免状态字段更新触发无意义重建。

**索引列选择：** FTS 只索引 `excerpt`；标准号/条款号走 SQL 精确过滤，不放进 FTS，避免代码片段污染文本相关性和跨列误召。

```json
      "source_url": "https://example.org/...",
      "page_ref": "",
      "source_kind": "official_web",
      "verification_status": "verified",
      "verified_by": "李四",
      "verified_at": "2026-11-06",

```

### 5.3 必填与校验矩阵

| 字段 | 规则 | 失败动作 |
|---|---|---|
| `standard_code` | 必填；NFKC；`normalize_standard_code`；必须能通过 `is_known_standard` 或 `is_known_base_number`；废止标准直接拒绝 | 拒绝该行；批次记录原因 |
| `version` | 必填；与 `standard_code` 年份一致，或为「2015年版」这类修订版 | 拒绝 |
| `clause_no` | 必填；按 §3.1 正则归一化；附录单独规则；同批次内不得重复 | 拒绝；标注重号 |
| `excerpt` | 必填；1–500 字符；禁止控制字符/零宽字符；超长拒绝；`excerpt_type` 不得为 `full_text` | 拒绝；提示字数 |
| `license_note` | 必填；去空白后非空；建议包含标准名、条款号、来源、权利声明 | 拒绝 |
| `source_url` / `page_ref` | 至少一个非空；`official_web` 必须有 URL；`book_scan` 必须有页码 | 拒绝 |
| `mandatory` | 接受 `0/1/是/否/true/false`，统一存 0/1 | 拒绝非法值 |
| `verification_status` | `unverified`/`verified`/`doubtful`；`verified` 必须带 `verified_by` + `verified_at` | 拒绝 |
| `effective_from` / `effective_to` | 可空；格式 `YYYY-MM-DD`；`to < from` 拒绝 | 拒绝 |
| 重复键 | 同批次内重复 → 拒绝该行；与库内重复 → 按 upsert 策略 | 见 §5.4 |
| 脏字符 | `\x00-\x08\x0b\x0c\x0e-\x1f`、`\u200b-\u200f`、`\ufeff`、`\u2028\u2029`、NBSP | 拒绝，或按规则清洗后入库并记录 |
| `excerpt_hash` | 归一化（去空白、统一标点）后 sha256；用于跨批次去重/审计 | 重复哈希仅告警，不单独作为拒绝理由 |

### 5.4 幂等与部分失败（**设计建议，实际未实现**）

**幂等：**

```sql
INSERT INTO standard_clauses (...) VALUES (...)
ON CONFLICT(standard_code_norm, version, clause_no_norm)
DO UPDATE SET
  excerpt = excluded.excerpt,
  excerpt_hash = excluded.excerpt_hash,
  applicability = excluded.applicability,
  license_note = excluded.license_note,
  source_url = excluded.source_url,
  batch_id = excluded.batch_id,
  updated_at = datetime('now','localtime');
```

保护规则：

- 已 `verified` 的行默认拒绝被覆盖；只有 `--force` + 操作人 + 批次审计才允许，并先把旧值写入审计表/批次错误报告；
- 同一批次重复执行 → 行数不变，`updated_at` 变化，`batch_id` 相同；用 `file_sha256` 做批次指纹，重复文件直接返回「已导入，无变化」；
- 变更检测用 `excerpt_hash`，哈希不变则跳过写。

**部分失败：**

- 默认 **strict**：先全量校验，任一必填/格式错误 → 整批不写，`status='failed'`，返回逐行错误 CSV；版权场景下这是更安全的默认。
- 可选 `--allow-partial`：逐行 `SAVEPOINT`，好行提交、坏行回滚并登记；批次 `status='partial'`，错误报告包含行号/字段/原因；
- 实测（S5）：逐行 SAVEPOINT 能隔离唯一键冲突；注意 NULL 主键历史行为，已在 DDL 用 `NOT NULL` 规避。
- 无论哪种模式，**先写批次记录，再写条款**；中途崩溃可凭 `batch_id` 定位残留并重跑（幂等）。

## 6. 版权边界的落地方式

### 6.1 结构性强制

1. **表里没有全文字段**：只有 `excerpt`，且 `CHECK(length(excerpt) BETWEEN 1 AND 500)`；
2. `excerpt_type` 只允许 `summary`/`key_sentence`/`data_point`，不允许「full_text」；
3. `license_note` 非空 + `source_url`/`page_ref` 至少一个非空；
4. `source_kind` 区分官网、正式 PDF、纸质书扫描、人工录入；`checksum` 只存哈希，不存文件；
5. 批次表强制 `confirm_license=1` + `operator`，无确认不允许导入。

### 6.2 导入时强制

- CLI：`python -m app.tools.import_standard_clauses --file ... --confirm-license --operator 张三`；缺少 `--confirm-license` 直接退出；
- API/后台：管理员角色 + 请求体显式 `confirm_license=true`；前端二次确认弹窗必须展示「只导入摘录、不导入全文」；
- 每行 `license_note` 必填，模板：

```text
摘录自《{standard_name}》（{standard_code}）{clause_no}；来源：{source_url}；
权利归{publisher}所有；仅用于施工方案编制参考，不替代标准原文。
```

- 应用层拒绝：`excerpt` 超 500 字、`excerpt_type='full_text'`、`license_note` 空白、无来源；
- 数据库 CHECK 再做最后一道兜底（E9 实测）。

### 6.3 生成侧与展示侧

- 检索结果只回传 `excerpt`（≤500 字）+ `standard_code/version/clause_no/source_url/license_note`；
- Prompt 中明确「只可引用上述摘录，不得补写原文」；
- UI/导出标注「摘录，非全文」，并附来源链接；
- 不把来源 PDF、扫描件放进仓库或数据库 BLOB。

### 6.4 法律提示

500 字是**技术护栏，不是法律结论**。短条款可能 500 字就接近全文；因此：

- 优先要求 `excerpt_type='summary'`（编写要点，而非逐字复制）；
- 生产导入前需法务/合规审核 `license_note` 模板与来源合法性；
- 若权利方要求下架，按 `source_url`/`batch_id` 能快速定位并删除（`standard_clause_sources` 有级联）。

## 7. 检索质量小样本评测

### 7.1 语料

- 40 条模拟条款，覆盖 14 本标准、14 个专业/适用域；
- 含数字阈值：`18m`、`8m`、`15kN/m2`、`25℃`、`2℃/d`、`30mA`、`10Ω`、`4‰`、`20%`、`5m`、`2 步`、`3 跨`、`1.2m`、`7d/14d`；
- 语料为**评测用模拟摘录**，不是标准原文，不进入产品库；
- 标注为单人或单轮标注，存在主观性。

### 7.2 七种方案

| 方案 | 说明 |
|---|---|
| A 纯 LIKE | ≥2 字 token 全部 AND，`LIKE '%t%'` |
| B 朴素 trigram | 整串 `MATCH excerpt:"原查询"` |
| C 分片 AND | ≥3 字片段 AND；2 字片段作 LIKE 过滤 |
| D 精确号 + C | 先精确 SQL，再 C，加结构加权 |
| E OR + 覆盖率 | 3 字片段 OR 候选；覆盖率 + 适用条件 + 强条重排 |
| F 仅 bm25 | 同 E 候选，仅按 bm25 排序 |
| G 滑窗 | 长串按 3 字滑窗展开，其余同 E；用于无空格连写 |

> 说明：评测中的 E/G 使用简化评分（查询词覆盖率 + 适用域加权 + 强条 0.1），**不是** §3.3 的最终权重；§3.3 是待实施后调参的建议初值。F 仅用 bm25，用于对照。

### 7.3 主结果（带空格查询，k=5）

| C 分片 AND | 0.70 | 0.70 | 0.70 | 0.700 | 0.600 | 0 |

### 7.5 无空格连写查询（更接近真实输入）

| 查询 | E Hit@1 | G Hit@1 | E MRR | G MRR | G 平均召回@5 |
|---|---|---|---|---|---|
| 10 条去掉空格的同义查询 | **0.00** | **1.00** | 0.000 | 1.000 | 0.867 |

G 明细示例：

```text
Q01 基坑支护验收        -> C12, C03, C04
Q02 模板支撑跨度18m     -> C17
Q06 大体积混凝土测温温差 -> C39, C05, C15, C19, C21
```

**结论：** 无空格连写是必须覆盖的输入形态；3 字滑窗展开是零依赖、可解释的解决方案。若不处理，trigram 方案的 Hit@1 会直接归零。

### 7.6 误召归因

| 误召来源 | 例子 | 处理 |
|---|---|---|
| 3 字通用词跨专业 | 「垂直度」→ 塔机 C38 + 脚手架 C27/C30 | 专业域/标准号过滤 + applicability 加权 |
| 2 字词 LIKE 过宽 | 「验收」→ 基坑、盘扣、临电 | 不单独用 2 字词做召回；只做加权或要求上下文 |
| 同域非答案 | 「基坑支护 验收」→ C04/C03（设计/稳定性） | 覆盖率重排把 C12 置顶；生成侧 top3 截断 |
| 同词异义 | 「混凝土强度」→ C05 桩身强度、C10 模板 | 保留，但在输出中标注章节/适用条件供编排器判断 |

### 7.7 结论边界

本评测只能证明「机制可行」，不能给出生产命中率：

- 40 条、14 标准、10 查询，样本太小；1 条差异就能让 Hit@1 变动 10 个百分点；
- 语料是模拟摘录，非真实条款，真实条款的措辞、长句、跨句引用会更难；
- 单人标注，未做标注一致性；
- 无真实同义词词典，Q05/Q06 目前靠其他词兜底；若查询只有「塔吊 附墙」这种纯同义词，仍会 0 命中；
- 未测 300+ 条、50+ 查询、nDCG/Recall@10、冷启动与长尾；
- bm25 未调参、未做字段权重；覆盖率权重是拍脑袋初值。

**上线前必须补：**

1. 300–500 条经法务审核的真实摘录；
2. 50+ 条真实用户查询（含标准号、条款号、专业口语、错别字）；
3. 两人独立标注 + 一致性校验；
4. 指标扩展到 Recall@10、MRR@10、nDCG@10；
5. 同义词/单位词典的覆盖测试；
6. 与「无条款库」基线对比，证明条款层确实提升方案引用准确率。

### 8.2 生成侧如何拿数据

- 新增服务函数（设计）：`get_clause_context(scheme_name, section_title, query, top_k=3) -> ClauseSearchResult`；
- 返回 `ClauseRef` 列表，**只有条款号 + 版本 + 适用条件 + ≤500 字摘录 + 来源**；
- `get_standards_text` 不动；两类数据分开注入，避免把「标准全文」与「条款摘录」混在一个字段；
- 现有调用点无需改签名：`sse_handlers.py:4082/4534`、`consistency_scanner.py:289`、`preflight_engine.py:83-88/464/493`、`compliance.py:107`、`content_checkpoint.py:1002-1008` 继续用标准级能力；条款级能力作为新调用点接入。

### 8.3 与预检的关系

`preflight_engine.py` 现有 STD-01/03 只校验「标准号是否存在/是否废止」（`:469`、`:493`）。条款层可增加 **STD-06「条款号可核性」**：

- 引用「标准号 + 条款号」→ 查到：通过，附 `verification_status`；
- 标准存在但条款号未收录 → **警告，不阻断**，理由是语料天然不完整；
- 标准已废止 → 复用 STD-01；
- 条款 `status='superseded'` → 警告并给出替代条款；
- **绝不能**因为「没查到条款」就判「违反」——这是三态原则的核心。

## 9. 降级与三态

### 9.1 状态定义

| 状态 | 触发条件 | 返回语义 | 禁止行为 |
|---|---|---|---|
| `ok` | 有候选且通过过滤 | 返回条款 + 核验状态 | 不得把未核条款说成已核 |
| `no_corpus` | 条款表为空，或该标准无任何条款 | **无法判定：条款库未收录** | **不得说「无问题」** |
| `no_match` | 有语料，但查询无命中 | **未检索到相关条款，不能作为合规依据** | **不得说「无问题」** |
| `needs_context` | 只有 2 字词，且无标准号/专业上下文 | **请补充标准号或方案类型** | 不得随机返回结果 |
| `unknown_standard` | 标准号不在注册表 | **无法判定：标准未收录** | 不得猜测条款 |
| `invalid_standard` | 标准在废止清单 | 提示替代标准，不返回条款 | 不得按现行标准引用 |
| `degraded_like` | FTS5/trigram 不可用 | 返回 LIKE 结果 + `degraded=true` | 不得静默降级不告知 |
| `ambiguous` | 只有条款号/多个现行版本 | 列出候选，要求用户确认 | 不得替用户选标准 |

### 9.2 FTS5/trigram 探测

```python
def fts5_trigram_available(conn) -> bool:
    try:
        conn.execute("CREATE VIRTUAL TABLE temp.fts5_probe USING fts5(x, tokenize='trigram')")
        conn.execute("DROP TABLE temp.fts5_probe")
        return True
    except sqlite3.OperationalError:
        return False
```

- 进程内缓存结果；
- 只探测 FTS5 存在不够，必须探测 `trigram`（SQLite 3.34+ 才有；老系统 Python 可能链接低版本 SQLite）；
- 探测失败 → `FTS5_AVAILABLE=False`，检索走 LIKE；
- 启动日志记录 SQLite 版本与探测结果，运维可告警。

### 9.3 LIKE 降级

同接口、同排序，仅候选生成不同：

```sql
SELECT ... FROM standard_clauses
WHERE status = 'active'
  AND (? = '' OR standard_code_norm = ?)
  AND (excerpt LIKE '%' || ? || '%' ESCAPE '\'
       OR excerpt LIKE '%' || ? || '%' ESCAPE '\')
ORDER BY ...
LIMIT 50;
```

- 用户词先转义 `\`、`%`、`_`；
- 最多 8 个词，防止 SQL 过长；
- 2 字词可以参与 LIKE（这是 trigram 做不到的），但仍受「needs_context」约束；
- 性能实测：10 万条 14–16 ms（E10），可接受；
- 精确号查询在降级模式下仍走 SQL，不受影响；
- 返回 `degraded=true`，前端/日志标注「当前为降级检索，结果可能不完整」。

### 9.4 「无法判定」的统一出口

所有非 `ok` 状态统一返回：

```text
状态：无法判定
原因：{no_corpus / no_match / unknown_standard / invalid_standard / needs_context}
说明：当前条款库无法支持该结论；不得据此认定方案「无问题」或「不符合」。
建议：{补充标准号 / 换用现行标准 / 人工核对 / 等待条款库补录}
```

硬性约束：**检索服务永远不返回 `compliant=true`**；合规结论只能由规则引擎在「至少一条已核条款支持 + 无冲突」时给出。

**残留风险（按严重度）：**

1. **版权风险（高）**：摘录边界需法务确认；建议默认要求「要点摘录」而非逐字复制。
2. **误判「无问题」（高）**：语料缺失时最危险；三态出口与「禁止 compliant」必须写进服务契约与测试。
3. **标准更新滞后（中高）**：条款层与注册表版本不同步会引用旧条款；导入时必须校验版本与现行性。
4. **跨专业误召（中）**：3 字通用词（垂直度、混凝土）误召已实测；依赖专业域过滤与人工抽检。
5. **FTS5 打包差异（中）**：开发机 3.50.4 有 FTS5+trigram，生产镜像未必；必须探测 + 降级。
6. **rowid 依赖（低）**：已用 `INTEGER PRIMARY KEY` 规避；但外部内容表仍需定期完整性检查。
7. **小样本结论过度外推（中）**：本报告指标不能当生产 SLA；上线前必须用真实语料复测。
