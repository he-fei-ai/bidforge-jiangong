### 2.3 风险点（探查前登记）
1. 两条程序化早退以 `passed=True` 短路 AI 审核 ⇒ 任何「只挂在 AI 审核之后」的检查在长方案常态下不生效；
2. 标题是**位置编号的唯一载体** ⇒ 写入带内嵌编号 = 双重编号（展示层再套一次）；
3. 同一判据多副本（issues 类别标签表前后端各一份）⇒ 新增类别静默丢失；
4. 长方案受 `OUTLINE_FIX_MIN_COVERAGE` 退化护栏约束 ⇒ 整份重写极易「保留原目录」；
5. CRLF 仓库 + 中文锚串 ⇒ 字节级补丁必须 `read_bytes/decode/write_bytes`。

## 3. 深度探查结果

### 3.1 第一轮（根因 A / B / 缺口 C）
- **根因 A（主）**：`detect_generic_titles` 于 2026-10-10 接到 `_review_and_fix_outline`，但接在
  **AI 审核之后**；两条程序化早退（`programmatic`、`programmatic+surgical`）在其**之前** return
  ⇒ 只要填了编制要求 / 有方案解析（长方案常态），占位标题**从未被检出、从未被修**，直接落库。
  既有测试 `test_outline_generic_titles_20261010.py::TestReviewInjection` 靠
  `monkeypatch OUTLINE_REVIEW_MODE="always"` 才命中检测分支 —— 恰证程序化路径从未被覆盖。
- **根因 B（次）**：修复被采用后一律 `passed=True` 并追加「✅ 已根据审核意见自动修复」，**无复检**
  ⇒ 占位仍在却谎报已修（结论/日志不准确）。
- **缺口 C**：唯一修复手段是整份目录重写 ⇒ 长方案下极易被退化护栏拒回「保留原目录」。

## 8. 遗留问题与后续建议

1. **`review_mode` / `suggestions` 前端无消费方**（Grep 0 命中）：`programmatic*` 与
   `programmatic+titled` 的区分目前只进后端日志，用户在界面看不到「这次结论的程序化程度」。
   建议下一轮在审核依据区并列展示，属呈现增强、非缺陷。
2. **`_coverage_recheck` 的成本面**：补齐/改名未真正覆盖时会多 1 次 AI 审核调用（120s 超时上限）。
   如生产观察到高频触发，应在提示词侧强化「必须逐条覆盖 suggestions 列出的缺失项」，
   而不是放宽复检（复检就是防谎报的那道闸）。
3. **占位标题判据的形态覆盖**仍靠 26 条精确模式 + `（N）` 碰撞规则；纯语义空话标题
   （「相关安排」「有关要求」）会漏检，属检出率上限、非本轮缺陷。
4. **长方案语料结构性不足**（本机仅一个真实方案，同 R70 §12 Round 7 记录）：
   F4/F6 的红态取自最小化构造夹具；真实多方案端到端复测需用户生成新方案后补做。
5. `content_stable_prefix_enabled=False` 且 D1 开启时 `_plan_guidance` 静默丢弃（R71 前既有，
