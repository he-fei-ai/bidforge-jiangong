> 方法：逐条比对文档声明的能力与本仓**实际代码**（`app/` 全量检索 + 运行验证），
> 每条结论均给出本仓的文件路径与函数，或明确标注「已具备 / 判定为非缺陷」。

## 0. 六模块全景图（文档口径）

```
上传招标文件
   │
   ├─①解析提取  文件内容提取 → 项目概述 → 技术评分要求（评分项/权重/标准）
   │            ── 提示词分层：稳定上下文前置、任务差异后置（缓存命中 ~10x）
   ↓
   ├─②目录生成  一级目录 ← 与技术评分大类一一对应
   │            → 逐个生成二三级（并发 + other_outline 防重）
   │            → JSON 解析 → Schema 校验 → 业务校验 → 定向修复 → 分步兜底
   │            → 目录审核 {passed, suggestions} → 建议回灌 → 二次生成
   ↓
   ├─③全局事实  第一步 生成（切分→分段提取→知识库补充→原方案优先→合并去重→用户确认）
   │            第二步 编排注入（AI 只看标题判需要，程序按标题取全文注入当章）
   │            第三步 生成后二次检查（分组比对，返回 old_text/new_text 精确替换）
   ↓
   ├─④正文生成  收集叶子节点 → 正文编排（表格/Mermaid/AI 生图事前规划）
   │            → 并发生成（project_overview + parent + sibling + 编排决策）
   │            → 配图执行
   ↓
   ├─⑤审核预检  全文一致性审计（分组 + 全局事实）→ 冲突清单
   │            → 精确修复（old_text 唯一命中才替换）→ Agent 修复模式
   │            → 目录审核 → 规范符合性 / 专家论证
   ↓
   └─⑥导出文档  Mermaid 代码块 → 校验 → 修复 → 转图片插入 Word
                AI 生图（风格约束）→ 数量分段择优 → 类型二选一
```

## 2. 逐项差距详述

### G1【P0】技术评分要求提取（文档 §一.4）

**文档要求**：自我反思式结构化提示词，识别技术评分/评标方法/评分标准/技术参数/
技术要求/评审要素章节；**忽略**商务、价格、资质；输出「评分项名称 + 权重/分值 +
评分标准 + 数据来源」；处理模糊表述、表格（按行提取标注）、分层结构（缩进/编号）；
单位统一为分或 %；**验证**覆盖性与权重总和。

**本仓现状**：`ANALYSIS_ITEMS` 18 项中无该项。`audit_rules.py` 的 `weight` 是
**审核评分规则**的权重，与「投标技术评分项权重」语义完全不同。目录生成因此缺少
「一级目录对齐评分项」的唯一依据。

**影响**：目录只能按固定 `NINE_CHAPTERS` 生成，无法保证「全面覆盖评分要点」。

### G2【P0】old_text/new_text 精确替换（文档 §三.4 / §五.1）

**文档要求**：修复时返回精确 `old_text/new_text`；程序**仅在 old_text 能唯一
命中当前小节时才替换**；找不到或多处相同内容都**拒绝修改并重新尝试**。
理由：「修改冲突时只动必要位置，不重写已经正确的内容」。

**本仓现状**：`consistency_repair.py` 让 AI **重写整章**，再用 `snapshot_id`
做**整章级**接受/拒绝回滚。冲突定位靠 `text_quote`（§`consistency_audit_system`
确有 `content_quote`），但**替换是整章覆盖**。

**影响**：一处工期错误 → 整章被重写，已正确的内容可能被改动；且「拒绝某条冲突」
会把该章**整体**退回修复前快照（同章内其它已修好的冲突也一起丢）。

### G3【P1】一级目录 ← 评分大类 一一对应（文档 §二.4「一一对应模式」）

**文档要求**：从技术评分要求提取评分大类 → **程序构造一级目录**（锁死标题顺序
与评分项关联）→ 模型只生成二三级 → 最后校验一级目录与评分大类一致。

**本仓现状**：`scheme_classification.NINE_CHAPTERS` 是硬编码的九大章节
（依据建办质〔2018〕31号），`source_items` 指向固定的 item_id 列表。
**不读取**任何评分要求。

**影响**：九大章节是**法规要求**（正确），但「每个评分大类都有对应章节」这一
**覆盖性保证**没有机制。

### G4【P1】知识库非 RAG 构建流程（文档 §七）

**文档要求**：① 按标题/段落/表格/列表切 block + 语义合并 + 编号；② 清理无效
block（页码/目录/封面/签章/过短碎片）；③ 第一轮 AI 提取**可复用主题**（只出标题
+ 使用方式）；④ 第二轮补漏；⑤ 合并去重生成稳定条目 ID；⑥ **分批**让 AI 判断
每个条目对应哪些 block，**只返回 block 范围**；⑦ 未匹配 block 补漏；⑧ 程序按
block ID **拼回原文** → 最终条目 = 标题 + 使用方式 + 原文素材。
核心思想（skill 式）：AI 请求时**只带元数据**，判断要用才读正文 → 避免 RAG 的
语义误召回（「消防改造」召回「装修改造」）。

**本仓现状**：`knowledge_base` 表 + 4 个 CRUD，`content` 由**用户手填**，
无任何自动构建流程。上一轮已把它接成事实补充源（`facts_enrich`），但**条目从哪来**
仍是空白。

### G5【P1】正文编排 / 预编排（文档 §四.5）

**文档要求**：生成正文**前**先规划本小节是否需要表格 / Mermaid / AI 生图，
产出 `knowledge/table/mermaid/image` 四段 JSON（含 priority 3/4/5）；
**AI 负责提名、程序负责拍板**；类型二选一；数量分段择优（避免前几章用完额度）；
正文生成时拿到编排结果，「围绕图片表达重点来写」，避免正文与图两张皮。

**本仓现状**：`sse_handlers.py:4721-4723` 明确写「图表与正文一体生成：不再注入
预编排配图规划」，`chart_predictions` 表**只由正文同步登记**。
即：本仓是「写完正文再让 AI 自己找图」，与文档的「事前规划」相反。

**影响**：图片集中在前几章 / 额度不可控 / 正文与图不呼应。

### G6【P2】提示词顺序优化的系统化（文档 §四.4 / §九）

**文档要求**：system 只放稳定规则 → 最大最稳定上下文前置（招标文件全文、
项目概述、评分要求、目录树、上级章节链）→ 任务差异最后 → **同一份数据组织格式
保持稳定**（标题写法/换行/列表顺序一致，不 strip 不 strip 混用、不塞时间戳）。
实测缓存命中后输入成本降约 10 倍。

**本仓现状**：第十五轮已做「通用 system + 标段上下文独立第二条 system」，
但**未**建立跨模块的分层消息契约与格式稳定性护栏。

### G7【P2】表格起止标记

**文档要求**：Word 用 `[表格内容]/[表格结束]`，PDF 用 `[表格 n]/[表格结束]`
包裹表格，供 AI 判断「这是表格」而非散文。

**本仓现状**：`file_parser` 输出标准 Markdown 管道表格，**无显式起止标记**。
AI 靠 `|` 推断，可行但不如显式标记稳。

## 3. 判定为「不引入」的两项

- **opencode 运行时集成（文档 §八）**：文档自述其动机是「开源软件无法针对每个
  模型定向优化 JSON」。本仓已有 `collect_json_response`（Pydantic 级校验 +
  定向修复 + 重试 + 统一编号）与 provider 降级链，**针对性更强**；引入第二套
  AI 运行时会产生第二套配置、第二套审计、第二套失败模式。
- **Agent + Skill 模式（文档 §三.6 / §八.3）**：文档自述不可行的三条理由
  （超长上下文、交互轮次、缓存不可控）在本仓同样成立。本仓的
  「AI 只产出最小操作计划 + 程序执行」（`/global-facts/adjust`、
  `/bid-analysis/results` 人工校正）正是**同构且更可控**的方案。

## 5. 本轮落地（P0 项）

### G1【P0】技术评分要求提取（§一.4）—— 已落地

- **落点**：`bid_analysis_service.ANALYSIS_ITEMS` 新增 `techScoring`（`json`），
  `GROUPS` 新增 `scoring` 分组，`_ITEM_PROMPTS` 新增自我反思式结构化提示词
  （目标定位 / 提取内容 / 处理规则 / 验证 / 只返结果 五段）。
- **关键取舍**：`sort_order=19` **追加到末尾**而非插到前面 —— 既有 18 项的
  sort_order 是**历史数据契约**（前端展示顺序 + 已落库行顺序），插队会让老项目
  的消费顺序错位。`required=0`（招标文件可能没有技术评分章节，不卡流程）。
- **两域零交集保持**：另一域的 `techRequirements` 属**招标响应域**（默认关闭），
  与本项业务域不同，故不合并——护栏断言两域 item_id 仍零交集。

### G2【P0】old_text/new_text 定点替换（§三.4 / §五.1）—— 已落地

- **落点**：新增 `services/consistency_edits.py`（纯逻辑 `find_unique_span` /
  `apply_unique_edits` + AI 调用封装 `collect_repair_edits`），
  新增提示词 `consistency_repair_edits_system/user`。
- **核心不变式**：`old_text` 必须**唯一命中**才替换；多处命中 / 找不到 / 过短
  （<8 字）一律拒绝并记原因，**不猜** —— 无法确定改哪一处时，猜错比不改更糟。
- **接线方式**：`repair_agent.repair_section` 改为**定点优先 + 整章重写兜底**。
  兜底保留是刻意的：部分模型不支持稳定 JSON 输出，没有兜底会让修复能力整体失效。
- **依赖注入**：`collect_repair_edits(chat_fn=...)` 接收调用方的
  `chat_with_fallback` 引用 —— 既有单测 monkeypatch 的是
  `repair_agent.chat_with_fallback`，不注入就会绕过它们去打真实 provider。
- **效果**：一处「工期 120 vs 90」不再连带改写整章；未冲突段落逐字保留。
