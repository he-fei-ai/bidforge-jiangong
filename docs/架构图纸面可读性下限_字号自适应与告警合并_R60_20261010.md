## 1. 问题重述与机理（决定方案的那一条推导）

R59 把 L3 叶子改竖排后画布约减半，但极宽的树在纸上仍然偏小（16 叶/4 组实测纸面 1.31mm）。
更糟的是 R59 的切换**只看叶子数**：一张「6 叶 + 1 直属岗」的横排图只有 7 个叶子节点，
却排到 1764px 宽 → 纸面 1.36mm，**比 16 叶的竖排图还小**。

真正的尺度不在像素，而在**纸面**。DOCX 插图走 `backend/app/routers/export.py:1829 _fit_image_cm`
（栏宽 16cm、高 22cm 双上限，读 PNG 自带 300 DPI），于是：

```
纸面字号(mm) = 图内字号(px) × scale × 2.54 / DPI × fit × 10
宽度受限时   fit = 16cm ÷ 纸面宽  ⇒ scale 与 DPI 全部约掉
            ⇒ 纸面字号 = 160 × 字号(px) ÷ 画布宽(设计px)
```

**只有「字号 ÷ 画布宽」这一个比值决定纸上多大。**该闭式已用真实 PNG + 真实 `_fit_image_cm`
逐例核对（护栏 A 组 `test_model_agrees_with_real_export_fit`），不是推演。

由此得出本轮的核心判断：**遗留项①的正解不是「限制规模」（那要删内容），而是让字号跟着画布宽走**；
「限制规模」是字号封顶后仍救不回来时的**第二步**（并行的预算守卫/自动拆图正好补在第二步）。

## 2. 决策与取舍

| 决策 | 取舍理由 |
|---|---|
| 目标下限取 **2.4mm**（≈6.8pt） | 中文印刷「小六」2.3mm ~ 「六号」2.65mm 之间；低于此即交付文档不可读 |
| **只放大、永不缩小** | 窄图（≤~756 设计px）按自然尺寸插入，本就达标；缩小会造成零回归面之外的真实变化 |
| 各版式**硬上限**来自物理 box，不是审美 | 横排节点 220×52：`_draw_text_center` 的 `line_h = 字高+4`，2 行需 `2(f+4) ≤ 44` ⇒ **f ≤ 18 恰好**（19 就压边框）；竖排叶子 96×232 余量大 ⇒ 28；标题画在框外无容量约束 ⇒ 30 |
| **不做**「预编排/指定画什么」 | 沿 R57 §9 结论：读 `chart_predictions` 的规划字段是陈旧结论陷阱 |
| **不做**两阶段 AI 排版 | 每图 +1 次调用，且漏召回直接变成正文【待补充】（本仓红线） |
| 字号下限置 0 = **整套关闭** | 一个环境变量回到 R59 逐字行为，是运维唯一可信的回退通道 |

## 3. 落地清单（全部在 `backend/app/services/ai/`，行号为落盘后实测）

### R60-1 竖排容量单一事实源（`mermaid_common.py`）
- 抽出 `_vertical_text_capacity(box_w, box_h, char_h, char_gap=4)`（`mermaid_common.py:304`），
  返回 `(每列字数, 可容纳列数, 总容量, 纵向步进, 横向步进)`；`_draw_text_vertical_center`（`:320`）
  改为调用它，**绘制侧与「字号选择侧」从此共用一套公式**，不留两套口径。
- `_draw_text_vertical_center` 现在**回传真正画出来的文字**（`-> str`，空输入也返回 `text` 而非 `None`）
  —— 这是 C 组「端到端不新增省略号」护栏的前提：判据必须是实际落墨的文字，不能是近似公式自证。

### R60-2 纸面字号模型 + 自适应字号（`mermaid_architecture.py:56-88` 常量块）
- `paper_font_mm(font_px, canvas_w, canvas_h=0, title_h=0)`（`:366`）——与 `_fit_image_cm` 同口径的纯函数，
  宽/高双上限都参与（高图走 22cm 分支）。
- `resolve_paper_font_px(canvas_w, *, base, ceiling, min_mm, canvas_h, title_h)`（`:388`）——
  不变量：`≥ base`、`≤ ceiling`、`min_mm ≤ 0 → 返回 base`。
  **`min_mm` 是必填关键字参数**（本轮最大收获，见 §7 教训 1）。
- `resolve_leaf_vertical_font_px(...)`（`:411`）——竖排叶子在纸面下限之上再加一条硬约束：
  **放大不得新增省略号**（字号↑ ⇒ 容量↓，逐px回退直到最长标签容得下）。

### R60-3 可读性驱动的竖排升级（`:650 resolve_leaf_vertical_mode`）
旧规则只有「叶子数 > 阈值」。现叠加**第二条独立判据**：按横排版式量一次画布宽
（`horizontal_canvas_width`，`:638`，与布局公式同源），若 `NODE_FONT_MAX` 都印不到下限
→ 直接切竖排。两条规则**各自可关**：`ARCH_LEAF_AUTO_VERTICAL=0` 只关升级、保留数量规则与字号自适应。

### R60-4 可观测性
渲染启动/完成日志携带画布毫米口径；`compose_readability_warning`（`:592`）见 R60-5。

### R60-5 双告警合并为单一出口（`:592` + 渲染器 `:750-759`）
本轮的可读性告警与并行的预算告警**在同一张超大图上同时成立**，旧形态是连打两条
「请拆分」，读起来像两个独立故障。二者实为一因一果（超预算=因、纸上印不下=果），
现合并为**一条**，同时保留各自唯一可操作量：纸面毫米数（为什么非拆不可）与预算数字（拆成几张）。
判据下沉为纯函数 `compose_readability_warning(...)` —— 渲染器只做「算数量 → 调一次 logger」，
逻辑不再埋在函数体内（R57 教训：埋在闭包里的判据没有任何护栏能变异它）。
必须守住的**跨轮字面契约**：`架构图超出规模预算` / `建议拆分` 两个子串在超预算分支中在位
（`test_arch_size_budget_20261010.py::TestBudgetRenderIntegration` 锁的就是这两个字面量）。

三条必须一起读的结论：
1. **收益曲线先升后降**：拆图拿宽度换高度，份数一多 22cm 高上限反超 16cm 宽上限，整张拼接图（含每一张子图）被**二次缩放** ⇒ 越拆越小。上表 R61 的自然份数只有 **2/8** 落在曲线顶点，另有 **3 组交付比「完全不拆」还差**（4×7、6×6、8×6）。
2. 所以 R62 把「拆几张」改成**由纸面毫米决定**（`plan_architecture_split` 扫 parts∈[2,上限] 取最差毫米最大者），叶子预算降级为搜索上界 + 每份硬约束；8/8 用例全部严格变好，无一例劣于不拆。
3. **达标口径是「叶子/有效字号」这一档**，不是全图最小落墨：40叶/8组 拆到 1.98mm 时，同一交付里的**节点字只有 1.27mm**。§3 的告警与本轮判据同口径（沿 R59/R60 定义），此处如实记下，避免后人误以为「拆完就全达标」。

## 5. R59 §9 遗留项④ 的量化结论：其余 PIL 图表**全都**低于下限

探针 `artifacts/r60_paper_font/_r60_measure_others.py`：monkeypatch 各模块 `_image_font` 记录**真实像素字号**、
读真实 PNG 尺寸与 DPI、走**真实** `_fit_image_cm`，不套公式近似。

| 渲染器 | 样本 | 画布(px) | 插入 | 主字号→纸面 |
|---|---|---|---|---|
| timeline | 8 事件 | 5220×825 | 16.0×2.53cm | 30px → **0.92mm** |
| timeline | 16 事件 | 10300×825 | 16.0×1.28cm | 30px → **0.47mm** |
| timeline | 24 事件 | 15380×825 | 16.0×0.86cm | 30px → **0.31mm** |
| layout | 6 区 | 2310×1170 | 16.0×8.10cm | 30px → **2.08mm** |
| layout | 16 区 | 3770×1960 | 16.0×8.32cm | 30px → **1.27mm** |
| comparison | 14 项 | 2450×1845 | 16.0×12.05cm | 32px → **2.09mm** |
| gantt | 12 / 30 任务 | 4750×1990 / ×4150 | 16.0×6.7 / 13.98cm | 55px → **1.85mm** |
| labor | 12 人 | 2930×1845 | 16.0×10.08cm | 30px → **1.64mm** |
| architecture | 16叶/4组 | 1832×532 | 16.0×5.14cm | 28px → **2.45mm**（本轮后） |

结论（写清以免后人重复排查）：
1. **机理是图表通用的**：六类渲染器都是 `scale=2.5` + `@_render_hq`(300DPI) + 同一个 16cm/22cm 上限，
   所以 §1 的闭式对每一类都成立；`mermaid_architecture.paper_font_mm` 是可直接复用的纯函数。
2. **本轮之前架构图并不是最差的**。timeline 才是重灾区：`total_w = max(960, n×230 + (n-1)×24)`
   （`mermaid_timeline.py:134`）**随事件数线性增长且无上界**，8 个事件就已经 0.92mm。
3. **gantt 是「固定宽 + 行数只长高」**（`axis_w=1100×scale` 恒定，`mermaid_gantt.py:369`）
   ⇒ 病永远在**宽**这一侧（1.85mm，与任务数无关），加行只会让高度逼近 22cm 上限。
4. **labor / comparison / layout 是「内容压进固定宽」**（列宽随条数变窄），
   失效形态是**重叠/省略**而不是纸上过小 —— 这正与并行轮「labor 接竖排、其余不接」的结论吻合，
   两侧证据互相印证，不是巧合。
5. **本轮不动这五个渲染器**：每个都需要各自的 box 容量分析 + 各自的硬上限 + 各自的端到端护栏
   （架构图一项就用了 61 例护栏 + 11 轮变异），打包在一轮里改五处 = 本仓反例。
   后续建议按 **timeline（无上界，最严重）→ layout → gantt（改宽不改字）→ labor/comparison（已达标方向另议）** 排期。
6. **R62 复测（次日 01:09，探针同上不改）**：把本表 9 个样本重跑一遍，画布尺寸与纸面毫米**与本表逐字相同**（timeline 8事件 5220×825 → 0.92mm、layout 6区 2310×1170 → 2.08mm、comparison 2450×1845 → 2.09mm、gantt 1.85mm、labor 1.64mm）——
   即并行的 R61「三图加宽」（timeline 节点宽 180→230、layout 区宽 220→260、comparison 条形区 480→540 + 标签 112→152）**没有让这五类图的纸面字号再变小**，因为本表当初就是在加宽后的画布上量出来的（timeline 8 事件 5220px = `200 + 8×575 + 7×60`，正是 230 那一档；加宽前应为 4220px → 1.14mm）。
   ⚠️ 反过来也成立：**加宽本身就是拿纸面毫米换「不丢字」**，timeline 24 事件已经 0.31mm，仍是全仓最差；本轮仍未动这五个渲染器（理由见上一条第 5 点）。

## 8. 本轮三条教训

1. **【本轮最大收获 · 由自己的失败测试撞出】「必填」比「默认值」安全。**
   `resolve_paper_font_px(..., min_mm=None)` 旧写法只能二选一：默认取**常量** → 忘记传参的调用点
   对运维的 `ARCH_LEAF_PAPER_MIN_MM=0` **静默失明**；默认取**环境** → 函数不再是纯函数、无法逐例对账。
   改成**必填关键字参数**后「忘传 = TypeError」，并由 `pytest.raises(TypeError)` 钉住。
   可复用判据：**默认值会让某一类错误静默消失时，取消默认值就是最便宜的修复。**
2. **判据必须落在「条数」上，不是「文本」上。**合并双告警若只用「日志里同时有两个短语」做断言，
   拆回两条仍然全绿。真判据是 `len(warns) == 1` + AST 级「函数体内 `logger.warning` 恰 1 处」两条一起。
3. **跨轮字面契约要在 docstring 里点名来源。**`架构图超出规模预算` / `建议拆分` 不是本轮想写的措辞，
   是并行轮护栏的字面判据；不写清出处，下一轮「润色文案」就会把别人的护栏打挂。
