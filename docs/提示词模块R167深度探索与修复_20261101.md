### 2.2 依赖方向与调用方

- **写入侧**：`routers/prompts.py` → `_registry.update_prompt/reset_prompt`（内存）+ `prompt_templates`（DB）→ `reload_prompt_cache()` → `_cache._prompt_cache`。
- **读取侧**：约 40 处 `render(key, **kwargs)`（目录/正文/事实提取/图表修复/审核修复），全部经 `_registry.render` → `_cache.get_prompt`（DB 优先）。
- **横切侧**：`content_runtime`（正文上下文）→ `sse_handlers.generate_content`；`prompt_governance`（预算/围栏/脱敏）→ 同一 SSE 闭包；`_metrics` → `/system/prompt-metrics`。
- **无反向依赖**：`_registry` 不 import 任何路由器；`_cache` 只依赖 `_registry` + `_metrics`（叶子）。

### 2.3 风险点（按爆炸半径排序）

1. 注册表是**进程级可变全局**（`_ALL_PROMPTS`）—— 任何原地改写都会影响后续所有读取（本轮实际踩中，§五-1）。
2. DB 覆盖优先于出厂默认 —— 用户编辑直接决定线上提示词，需保存期体检 + 版本回滚（已具备）。
3. 三处开关存在**隐式耦合**风险（本轮发现一处，§五-2）。
4. 同一判据多处分叉（围栏/占位符/可选区块）—— 仓库历史上最高频缺陷族（本轮发现一处残存副本，§五-3）。

## 八、遗留问题与后续建议

1. **`get_prompt_with_validation`（G5）**：全仓仅 `__init__` 导出，无生产调用方 —— 建议确认产品是否需要“读取即校验”的调用方，否则删除。
2. **变量校验基线（G4）**：`validate_prompt_variables()` 用 `_ALL_PROMPTS[key]["content"]`（内存注册表）作基线；
   生产 PATCH 同时改内存与 DB，口径一致；但**外部直接写库**（脚本/迁移）时，注册表基线仍是出厂版，
   DB 新增占位符只会由 `render_prompt` 的 `unresolved placeholders` 告警兜底。建议把该告警计入指标（D4）。
3. **双口径装配（D2）**：本轮已第三次踩中“只在 stable 分支生效”（前两次 R74 `_plan_guidance`、R162 `_l3_leaf_struct`）。
   结构性收敛（列表单点装配）应作为下一轮独立立项，否则同类问题必然复发。
4. **惰性注册 WARNING（G6）**：`register_lazy_prompts()` 在直接 `import _registry` 时打印

### 10.2 G4：缺变量校验基线改为「实际生效模板」

**根因**（R167 §八-2 已留证）：`validate_prompt_variables` 的 `required` 来自
`_ALL_PROMPTS[key]["content"]`（内存注册表的**出厂基线**）。生产 PATCH 同时改内存与 DB，
口径恰好一致；但脚本 / 迁移工具 / 外部进程直写 `prompt_templates` 时内存仍是出厂版，
DB 新增的占位符进不了 `required` → 缺变量告警**静默漏报**；DB 删掉占位符则反向**误报**。

**方案（三处改动，形成一个闭环）**：

1. `_cache._select_prompt_content(key)` —— 把原先只写在 `get_prompt` 内部的
   「DB 覆盖优先 / 空内容回退出厂默认 / 未知 key」选择逻辑抽成**唯一判据**，
   返回 `(content, source)`，`source ∈ {db, empty_db, factory, missing}`。
2. `_cache.get_effective_prompt_content(key)` —— 只读钩子：只做选择，**不解析
   `{SHARED_*}`、不渲染、不计指标、不告警**（避免校验侧触发二次渲染/指标污染）。
3. `_registry._effective_template(key)` + `validate_prompt_variables(key, _template=None, **kwargs)`
   —— 校验侧的 `template` 与 `required` 都改为从**生效模板**取；`_template` 为内部参数，
   `get_prompt` 热路径把本次已选好的正文直接传入，校验与渲染看到同一份文本，
   且校验侧不必重复读缓存 / 判水位。

**行为矩阵**（实测口径）：

| 场景 | 生效模板来源 | 缺变量判定 |
| :-- | :-- | :-- |
| DB 无该 key | 出厂默认 | 与旧实现逐字等价（隐式路径 == 显式 `_template=factory` 路径） |
| DB 有非空白定制内容 | DB 内容 | 跟随定制形态：新增占位符如实报缺、删掉的占位符不再报缺 |
| DB 有行但内容为空/纯空白 | 出厂默认 + WARNING | 按出厂形态判定（与 `get_prompt` 的空值回退同口径） |
| 未知 key | 无 | `_effective_template` 回退 `_ALL_PROMPTS.get`（空串）→ 沿用 `get_prompt_variables` |

**工程约束与取舍**：
- 循环依赖：`_cache ↔ _registry` 双向 import，`_effective_template` 用**函数级 import**
  打破加载期循环（与既有 `_registry.render` 同款手法）；读取失败一律回退内存基线。
- 参数命名刻意用 `_template`（下划线前缀），避免与业务占位符 `{template}` 撞名。
- 热路径零额外开销：`get_prompt` 显式传入 `_template`，不触发第二条读取链。
- 副作用边界：`validate_prompt_variables` 由「纯内存函数」变为「会读缓存」。生产侧
  唯一调用方是 `_cache.get_prompt`（永远带 `_template`），因此该变化只影响
  测试 / 运维直接调用的路径。
