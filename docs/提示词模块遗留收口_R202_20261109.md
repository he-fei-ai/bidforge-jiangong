## 2. 修复清单（4 项，均有代码依据与测试锁定）

### FIX-1 · G1：注入防护「检测与围栏解耦」——默认部署下不再零可观测

**问题**：注入防护整体挂在 `prompt_injection_defense`（**默认 False**）之下 ⇒ 默认部署下**既无围栏、也无任何检测**。运维无法知道「用户上传的招标文件里带了越狱指令」；`prompt_governance.scan_prompt_injection` 这套已写好的 6 类手法检测，此前**只在围栏开启时**才会被调用。

**最优解**：按「是否改字节」拆成两层——

| 层 | 行为 | 改字节？ | 开关 | 本轮处置 |
|---|---|---|---|---|
| 检测 | 只读扫描出站消息，命中告警 + 计数 | **否** | **默认常开** | ✅ 新增 |
| 围栏 / 脱敏 | 包裹只读数据边界、替换疑似凭据 | 是 | 沿用既有开关（默认 False） | 不变 |

**落地**：
- `app/services/prompt_material_guard.py::scan_outbound_messages()` —— 只读扫描，返回**原列表对象**（逐字节不变）；命中记 WARNING + 指标，不阻断生成（误报成本高：招标文件出现「忽略以上要求」并不罕见）。
- `app/services/ai/provider_factory.py::_call_provider()` —— 全部 provider 调用的**唯一出口**接线（与既有 `redact_outbound_messages` 并列），覆盖所有链路（含直接拼 f-string 的链路）。
- `app/services/ai/prompts/_metrics.py` —— 新增 `prompt_injection_scans`（扫了多少）/ `prompt_injection_hits`（命中多少，按手法名）两个计数器 + 快照 + reset。
- **误报实测**：9 条真实施工语料（基坑参数 / 技术要求 / 编制依据 / 监测要求等）**零误报**；检测开销实测 **6.8 ms / 6 万字消息**（相对单次 AI 网络调用可忽略）。
- **覆盖边界（如实核对）**：全仓除 `_call_provider` 外仅两处直连 `provider.chat`，且**均无用户文本入模**，故不在文本检测面内 —— ① `routers/ai_config/connectivity.py:213`（固定串「回复ok」）；② `services/ocr.py:320`（图片 base64 + 固定模板提示词，图像内文字本身即待识别数据）。

### FIX-2 · G6：调整指令上限与上下文安全上限联动（不再是写死常量）

**问题**：`INSTRUCTION_PROMPT_MAX_CHARS = 6000` 的推导锚定「32k token 窗口」，但它是**写死常量**——用户换小窗口模型后，6000 字（≈4k token）指令 + system 模板 + 资料段仍可能撑爆窗口（502）。且本仓 `ai_config` 表**不持久化**每模型上下文窗口（`context_tokens` 只在 `GET /models` 拉取瞬间存在，见 `routers/ai_config/models.py:143`）。

**最优解**：新增配置项 `prompt_instruction_max_chars`（默认 0 = 自动），上限按「用户自述的上下文安全上限」`context_length_limit` 推导：

```
effective_instruction_cap() =
    prompt_instruction_max_chars > 0  → clamp(显式值, 600, 6000)
    context_length_limit      > 0    → clamp(context_length_limit × 0.25, 600, 6000)
    两者都未配置                        → 6000（既有行为，逐字节不变）
```

**落地**：`prompt_material_guard.effective_instruction_cap()`；接线 `routers/sections.py`（目录调整）与 `routers/global_facts.py`（事实调整，含 do_apply=False 的纯账面路径）两处「调整要求」裁剪点；新增 `config.py::prompt_instruction_max_chars`。
**向后兼容**：默认配置下上限恒为 6000 ⇒ **逐字节不变**；仅当用户显式配置了 `context_length_limit` 或新项时才会收紧。

### FIX-3 · G2：三处「模型可见静默截断」改为可观测

| 位置 | 旧行为 | 新行为 |
|---|---|---|
| `routers/_sse_outline_review.py::_truncate_context` | 找到句末边界的**常见路径**直接 `return window[:cut+1]` —— 模型收到半份上下文却**看不到任何截断痕迹**，会据此断言「资料里没有提到 X」 | 切点算法不变，一律附加模型可见说明 `[……上下文已截断：原文 N 字，此处保留前 K 字，已省略 M 字]` + 日志/指标账目 |
| `services/review_autofix.py::_context` | `content[start:end].strip()[:300]` 静默截断（该片段作为「命中上下文」送进 AI 自动修复提示词） | 超限追加 `…（上下文已截断）` |
| `services/content_blocks.py::_clean_chart_title` | 图题 `[:40]` 静默截断（图题随图表 JSON 送进模型） | 超限追加 `…` |

新增原语 `prompt_material_guard.clip_text_notice_at(text, cut, label)`（按**给定切点**记账），说明文本格式与 `clip_text_notice_report` **逐字一致**（有测试锁定两者的输出相等）。

### FIX-4 · G5：表级水印不可用从「静默」变为「一次性 WARNING」

`_query_prompt_watermark` 失败（极旧库缺 `updated_at` 列）此前只打 DEBUG ⇒ 默认日志级别完全不可见，而失效判据会退回「库 mtime 变新即全量重载」（R108 修掉的重载风暴在极旧库上静默回归）。现首次失败记一条 WARNING（只打一次，不刷屏），并在 `_load_prompt_cache_sync` 的同款失败路径上复用同一告警。

## 3. G2 的另一面：全仓裸切扫描「入库 + 自动化棘轮」

**问题**：《提示词硬截断全仓扫描与清零》(20261108) §6.2 指出——既有 AST 棘轮只扫提示词命名空间，全仓口径扫描是**临时脚本、未入库**，口径会漂移、复核靠人工。

**落地**：
- **`tools/prompt_bare_slice_scan.py`（新入库）** —— 全仓 AST 扫描 `backend/app/**/*.py`（219 文件），判定口径：切片是否被裁剪原语包裹 / 邻近是否有留痕 / 所在函数是否有留痕调用 / 是否留下模型可见标记；并区分「模型可见路径」与「非模型路径」（**整词匹配**，避免 `provider_factory` 的 `fact`（factory）被误判）。输出 `file:line` 明细 + 总数/零留痕/模型可见零留痕三个计数，`--json` 供机器消费，退出码 1 = 存在模型可见零留痕裸切。
- **`tests/test_prompt_bare_slice_scan_ratchet_20261109.py`（新入库，11 项）** —— 双层棘轮：
  - **L1 严格层**：模型可见路径的零留痕裸切**必须逐条登记**（`MODEL_FACING_REGISTRY`，当前 **18 条**，每条写明「为什么这不是模型可见的静默丢字」）；未登记 → 红。
  - **L1 反向**：登记条目若已不存在（修掉了 / 代码改写了）→ 红（**僵尸豁免必须删**，白名单不许悄悄长回来）。
  - **L2 计数层**：非模型可见零留痕裸切数量不得增长（基线 **51**）。

**现状数据**：全仓裸切 132 处 → 零留痕 69 → **模型可见零留痕 18**（全部为「条目个数上限 / 错误摘要 / 文件名 / 标题派生」类，已逐条登记；模型可见的**文本**静默截断经 FIX-3 后已归零）。

## 6. 遗留与后续建议

| 编号 | 项 | 优先级 | 处置建议 |
|---|---|---|---|
| L-1 | 围栏/脱敏仍默认关闭（默认部署下资料**不带**只读围栏、疑似凭据**原样外发**） | **P3→建议运维开启** | 面向外部署前，在 `.env` 或 `PUT /system/governance` 开启 `prompt_injection_defense` 与 `prompt_redact_sensitive`；检测已默认常开，可先据指标评估暴露面 |
| L-2 | `context_length_limit` 只是**窗口代理**（真实模型窗口未持久化） | P4 | 若 `ai_config` 后续持久化 `context_window`，把 `effective_instruction_cap()` 改为按真实窗口推导 |
| L-3 | 扫描器仍只认**直接切片**；中间变量传递后的切片、非切片截断（`partition`/`rsplit`）静态不可见 | P3 | 保留季度人工抽查（本工具已把口径固化，人工只需看输出差异） |
| L-4 | 注入检测**不阻断**（误报成本高） | P4 | 如需硬拦，需先积累误报样本再评估分级策略 |
| L-5 | `clip_text_logged` 仍限 2 个内部判定作用域 | P4 | 沿用既有棘轮，新增调用点必须评审 |
| L-6 | 非模型可见零留痕裸切 51 处（条目数上限 / 错误摘要 / 文件名） | P4 | 已登记 + 计数不增棘轮；如要清零需逐个改为账目化，收益低于成本 |

```bash
  tests/test_prompt_bare_slice_scan_ratchet_20261109.py -q

# 全仓裸切扫描（人工复核 / CI）
py -3.14 tools/prompt_bare_slice_scan.py --root backend/app        # 人读摘要

```
