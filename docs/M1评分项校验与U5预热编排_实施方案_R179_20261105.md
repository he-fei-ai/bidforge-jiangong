## 0.1 基线修正（重要：以下两条推翻此前结论）

### B1 · 现有 5s 等待在本仓默认配置下**收益为 0**

- **事实**：5s 预热等待定义在 `backend/app/routers/bid_analysis.py:137-138`（`PROMPT_CACHE_WARMUP_DELAY_MS = 5000`），同步入口 `:1453-1458`、SSE 入口 `:1666-1677` 都是「跑首项 → `sleep(5s)` → 剩余项进信号量」。
- **但**项级并发 `bid_analysis_item_concurrency` 默认 **1**（`backend/app/config.py:924`），`_item_concurrency()` 的兜底值同样是 1（`backend/app/routers/bid_analysis.py:173-180`）。
- **因此**在默认配置下，等待之后的「剩余项」仍然一次一个：5s 只增加延迟，**不产生任何并发收益**，缓存预热收益为 0。
- **验证方式**（任选其一，无需真实 AI）：
  1. 静态核对：
     ```bash
     grep -n "PROMPT_CACHE_WARMUP_DELAY_MS" backend/app/routers/bid_analysis.py
     grep -n "bid_analysis_item_concurrency" backend/app/config.py backend/app/routers/bid_analysis.py
     ```
     应看到常量 5000、默认值 1、信号量初值来自 `_item_concurrency()`（=1）。
  2. 动态核对：在 `backend/app/routers/bid_analysis.py:1458`（同步）与 `:1666-1677`（SSE）的 `asyncio.Semaphore(...)` 创建处读取 `semaphore._value`，用 3 个假项跑一次，断言同时在飞 ≤1；再与「关闭等待」对照组比较总耗时（差值 ≈5000ms，且无并发提升）。
- **对设计的影响**：U5 若只在 `bid_analysis` 接线、又不提供阶段级并发，等于空转；而直接把 `bid_analysis_item_concurrency` 抬到高位，会迅速打满全局硬上限 `max_concurrency=5`（`backend/app/services/ai/provider_factory.py:438-447`），重演历史 429。本版因此**不改该默认值**，改为给 U5 自带阶段级并发（默认 2，见 §2.4 与配置自检）。

#### 1.4.1 归一化（唯一出口，禁止各处各写一份）

```python
def norm_title(s: str) -> str:
    s = unicodedata.normalize("NFKC", s or "")      # 全角→半角
    s = s.casefold()
    s = re.sub(r"^\s*(?:第[一二三四五六七八九十百]+[章节]|[0-9]+(?:[.．、）)]|\s*、)", "", s)
    s = re.sub(r"[#>*`|_~\-—\[\]()（）【】:：,，。；;、'\"“”‘’!！?？\s]+", "", s)
    return s
```

- 复用 `bid_analysis_service._NORM_STRIP_RE` 的字符集口径（`backend/app/services/bid_analysis_service.py:2188`），但**必须新增 NFKC 与序号前缀剥离**；不直接 import 私有常量，避免跨模块耦合。
- 停用词/结构词（「本章」「以下」「措施」「方案」「要求」「管理」「工作」）只从 keyword 分词中剔除，不影响 exact/contains。

#### 1.4.2 四级匹配与阈值

| 步骤 | 条件 | 置信度 | method |
|---|---|---|---|
| S1 精确 | `norm_title(item_name) == norm_title(node_title)` | 0.95 | `exact` |
| S2 包含 | 互为子串，且较短串长度 ≥4 且 `len(short)/len(long) ≥ 0.60` | 0.85 | `contains` |
| S3 关键词 | 内容 token 集合 Jaccard ≥ 阈值：高档 0.65 / 中档 0.55 / 低档 0.45 | `min(0.90, 0.50 + 0.40*J)` | `keyword` |
| S4 评分标准回退 | `criteria` 与节点标题共享 ≥2 个内容 token，且 Jaccard ≥ 高档 0.45 / 中档 0.40 / 低档 0.30 | ≤0.50 且 `needs_review=true` | `criteria` |

**分值档位（`score_band`）**：

- `score_ratio = score / total_score`（`total_score` = 本次所有有效评分项分值之和）。
- `high`: ratio ≥ 0.15；`low`: ratio < 0.05；其余 `mid`。
- 任一分值缺失 → 该评分项按 `mid`；全部缺失 → 全部 `mid`。

**目标节点约束**：

- 优先叶子（无子节点且 level 为目录最小叶子级）。
- 高档评分项**只接受叶子匹配**；若只命中父节点 → 记为 `weak` 并按 `missing` 统计（避免高分项被父章「假覆盖」）。
- 中/低档允许命中父节点，但父节点必须已有子节点（表示聚合覆盖），且该父节点的所有后代视为「已支撑」，不进入 extra。

#### 1.4.3 多对多判定

| 情形 | 判定 | 输出 |
|---|---|---|
| 一个评分项命中多章节 | 允许 | `matched_sections[]` 全量保留；`primary_match` = 置信度最高 → 层级最深 → `sort_order` 最小；其余进 `also_matched` |
| 多个评分项命中同一章节 | 允许 | 该节点 `item_count` 累加；当 `item_count ≥ max(3, ceil(items/leaf_count))` 打 `overloaded=true`（**仅提示，不影响 mapped 状态**） |
| 同一评分项重复出现（同编号同名） | 抽取层按 `id` 去重（保留分值更高/证据更全者） | 报告层计数以去重后为准 |
| 评分项命中结构与 extra 白名单节点 | 命中仍有效，但该节点不进入 extra | — |

#### 1.4.4 `extra` 判定（只查叶子，避免噪声）

`extra` = 满足全部条件的节点：

1. 无子节点（叶子）；
2. 未被任何评分项命中；
3. 其任一祖先未被评分项命中（父级映射覆盖子树）；
4. 归一化标题不在结构白名单（默认：`封面`、`目录`、`编制说明`、`编制依据`、`附图`、`附表`、`附件`、`参考文献`）；
5. 标签不是纯占位/泛化标题（复用 `outline_quality` 的泛化判定口径，见 `backend/app/services/outline_quality.py:458`）。

白名单可通过 `scoring_extra_whitelist`（JSON 数组）覆盖，默认值 = 上述 8 项。

### 1.5 输出三态（四标签）与降级语义

**四标签定义**（与需求逐字对齐）：

| 标签 | 层级 | 含义 |
|---|---|---|
| `mapped` | 评分项 | 找到至少一个达阈值章节 |
| `missing` | 评分项 | **已成功解析到该评分项**，但找不到章节 |
| `extra` | 章节 | 叶子章节没有任何评分项支撑 |
| `unmatched` | 报告 | **无法判定**（整个抽取不可用，或部分来源解析失败） |

**`unmatched` 的强约束（本项目降级规范，不得违反）**：

- 抽取未跑过（`none`）、抽取整体失败（`failed`）、或成功但 0 条有效评分项（`empty_items`）→ 报告 `status = "undetermined"`。
- `undetermined` 时：`summary.coverage_rate = null`（**不得输出 0%**）、`items` 中**不得**出现任何 `missing`（未解析到 ≠ 全部缺失）、前端文案固定为「无法判定（未解析到评分项）」。
- 部分来源失败（`partial`）→ 报告 `status = "partial"`，成功来源照常 `mapped/missing`，失败来源进 `unmatched[]` 并附原因；前端同时显示「部分来源未解析，结论不完整」。
- 只有 `status ∈ {ok, partial}` 才允许输出 `missing` 与覆盖率。

### 2.2 编排模型

**改动落点（新文件）**：`backend/app/services/ai/warmup.py`

```python
@dataclass
class WarmupPlan:
    key: str                      # 阶段名
    items: list[Any]
    concurrency: int              # 实际并发上限（调用方已按配置钳制）
    representative_index: int = 0 # 固定第一个（规范序）
    prefix_fingerprint: str = ""  # 共享前缀指纹（模型+模板+共享上下文）
    delay_ms: int | None = None

async def run_grouped(plans: list[WarmupPlan], runner, *,
                      enabled: bool, default_delay_ms: int,
                      fallback_serial: bool = True,
                      on_event=None) -> list[Any]
```

**并发取值（唯一入口，避免调用点各写一套）**：

```python
def stage_concurrency(stage: str) -> int:
    if not settings.ai_warmup_enabled:
        return 0  # 0 = 不接管，调用方沿用现状（bid_analysis 即 _item_concurrency()=1）
    raw = json_map(settings.ai_warmup_stage_concurrency_map).get(stage,
                  settings.ai_warmup_stage_concurrency)
    return max(1, min(int(raw), settings.max_concurrency))
```

- 调用点统一写法：`conc = stage_concurrency(stage) or <该阶段现状并发>`。开关关闭时 `stage_concurrency()` 返回 0，`or` 分支直接取现状值 —— **逐字现状**，无需在各调用点写 if。
- `stage_concurrency() == 1` 时 `run_grouped` 走「现状调度」分支（§2.4 自检②：开了但上限=1 也等于现状）。

**调度结构（每个阶段独立执行）**：

```text
if not enabled or len(items) <= 1 or concurrency <= 1:
    -> 现状调度（串行/原信号量并发），不加任何等待
       # 这里的 concurrency<=1 就是 §2.4 自检②「开了但阶段上限=1 也等于现状」的执行分支

else:
    rep = items[representative_index]
    res_rep = await runner(rep)                     # 串行 1 个
    if not ok(res_rep):
        -> 失败语义见 2.3
    else:
        if remaining:
            await sleep(delay_ms)                   # 默认 5000ms，与现状等值
        await run_remaining_concurrently(           # 沿用阶段原信号量
            remaining, concurrency, runner)
```

**分组键**：`(stage, prompt_template_key, model_name, prefix_fingerprint)`。同一分组内**共享前缀必须一致**，否则预热无效。`prefix_fingerprint` 由调用方传入（正文阶段可用「系统提示 + 全局事实 + 目录上下文」的哈希；事实注入逐章变化时必须纳入，否则分组错误）。

**代表请求选择依据（固定第一个，不选最短/最典型）**：

1. 预热的目标是让**共享前缀**进入上游缓存，而不是找「质量代表」；同组内任意一项都覆盖同一前缀。
2. 固定第一个可复现、可测（单测可断言调用顺序），不依赖历史统计。
3. 「最短」会偏向退化项（空描述/短章节），反而可能不覆盖完整前缀；「最典型」需要历史数据，当前无此类指标，且会引入非确定性。
4. 组的规范序沿用各阶段既有顺序（目录 `sort_order`、正文 DFS/任务列表、事实分段序号），保证「代表」稳定。

### 2.3 失败语义（已拍板：语义冻结，不做调整）

> 本表为**冻结契约**：实施轮不得「顺手优化」，任何改动都会改变 U5 的失败边界。

| 代表请求结果 | 判定依据 | 动作 |
|---|---|---|
| 成功 | `runner` 返回成功且解析通过 | 等待 `delay_ms` → 其余并发 |
| 解析失败/内容不合格 | `success=True` 但解析失败（`parse_failed`） | 换**下一个**代表重试**仅一次**；仍失败 → 退回整组串行 |
| 429 / 限流 | `error_class=rate_limit` 或异常含 429 | **不换代表**；整组退回串行（并发=1），沿用 `Retry-After` 冷却（U5-E13） |
| 超时 / 网络 / 上游 5xx | `error_class ∈ {timeout, network, upstream_5xx}` | **不换代表**；整组退回串行 |
| 认证/配额/配置错误 | `is_non_retryable_error`（U5-E13 同口径） | **整组放弃**，按现有失败事件上报，不重复烧调用 |
| 用户停止 | `is_stopped(task_id)` | 整组立即停止，不补跑剩余项 |

**部分失败聚合**：沿用现有口径，不新造字段。

- 正文阶段：既有 `failed_sections` / `partial`（`backend/app/routers/sse_handlers.py:2039-2046` 已带 `failed_chapters` 同族语义）。
- 事实阶段：沿用 provider 层 `parse_skipped` / `partial` 回传口径（`backend/app/services/ai/providers/base.py` 现有返回结构），不得新开事件名。
- 编排器只加法式回传一个 `warmup` 诊断对象（见 2.5），不参与判定。

**退回串行的实现**：不是「重新跑剩余」，而是**尚未开始发起的剩余项按并发 1 顺序执行**；已开始的请求不取消（避免上游重复计费与中断半截结果）。

| `max_concurrency` | `5`（**不动**） | 全局硬上限 | 编排器不得绕过 |
| `bid_analysis_item_concurrency` | **`1`（不动）** | 既有项级并发 | **已拍板：保持 1**，U5 不依赖也不改变它 |

**为什么不动 `bid_analysis_item_concurrency`（已拍板）**：

- 该项抬到高位会把项级请求直接压向全局硬上限 `max_concurrency=5`（`backend/app/services/ai/provider_factory.py:438-447`），与历史 429 故障的触发条件重合（本项目已为此收敛过并发）。
- U5 的目标是「先 1 个代表探路、成功后再放开到 2」，不是整体抬高全局并发；因此放大量由 **U5 自己的阶段上限**控制，默认只放 2。
- 取值规则（实现契约）：`effective = ai_warmup_enabled ? min(ai_warmup_stage_concurrency, max_concurrency) : _item_concurrency()`。即**开关关时逐字沿用现有 `_item_concurrency()`（=1）**；开关开时由 U5 阶段上限接管该阶段的并发读数，但仍受 `max_concurrency` 夹取。

**配置自检（必须写死，不能靠人记）**：

启动时在 `backend/app/main.py` 的 startup 钩子里打一条结构化日志 `AI_WARMUP_CONFIG`，并按下列三条判定（同样作为单测断言）：

| 自检项 | 判定条件 | 期望输出 |
|---|---|---|
| 等价性① | `ai_warmup_enabled=False` | `status=disabled` + `equivalent=verbatim`（**逐字现状**，不读其余 `ai_warmup_*`） |
| 等价性② | `ai_warmup_enabled=True` 且有效阶段并发 ≤ 1 | `status=enabled_but_no_gain` + `equivalent=verbatim`（**也等于现状**；警告：预热无收益，请检查 `ai_warmup_stage_concurrency`） |
| 越界夹取 | 有效阶段并发 > `max_concurrency` | `clamped=true` + 实际值 = `max_concurrency`（并记 warning） |

- 等价性②是本版新增的**显式自检**：开启总开关但阶段上限仍为 1 时，行为与现状完全一致，避免「以为开了就有并发」。
- 该自检只读配置、不发起任何 AI 调用；开关关时不读其余字段（保证逐字等价）。

**与 429 退避的配合**：

- 编排器不另造退避；代表请求的 429 已由 provider 层处理（`Retry-After` 冷却、配额节流，见 `provider_factory.py:2193-2243`、`:3969-3971`）。
- 代表 429 后本组立即退化串行；若连续 2 组退化，记录 `AI_WARMUP_DEGRADED` 日志，供运维把该阶段临时移出 `ai_warmup_stages`。
- 编排器**永不自行提高** `concurrency`；上限始终取调用方传入值，且受 `max_concurrency` 覆盖。

```json
"auto_confirm": {
  "ready": true,
  "blockers": [],
  "checked_at": "2026-11-05T10:00:00"
}
```

旧前端忽略未知键；新前端只有在「开关开 && ready && 无已有正文」时才启动倒计时。

### 3.4 倒计时状态机与打断矩阵

**前端新文件**：`frontend/src/pages/schemeWorkbench/useOutlineAutoConfirm.tsx` + `OutlineAutoConfirmModal.tsx`

状态机：`idle → armed → (cancelled | saving) → saved | failed`。

| 事件 | 行为 |
|---|---|
| 开关关 | 永不 arm；走原 `openOutlineGate`（`useOutlineGate.tsx:115`） |
| `auto_confirm.ready=false` | 不 arm；走人工闸门，并把 blockers 展示在生成日志/风险条 |
| 已有正文（`hasAnyContent(tree)`） | 不 arm；走人工闸门与二次确认（N1-E3 的 destructive 分支） |
| 倒计时中用户点击/键盘/滚动勾选框 | 暂停并**取消自动确认**，停留在人工确认 Modal（不再是「暂停后继续」，避免误触后仍自动提交） |
| 切换工作台 Tab / 路由 / 页面隐藏 | 取消 |
| 保存报错 | 取消，弹错误，回人工确认 |
| 触发二次确认（任何 destructive 弹窗） | 取消自动确认（自动确认永不代答二次确认） |
| 用户点「立即确认」 | 立即保存（不等计时） |
| 用户点「取消」 | 取消，目录保留预览未入库 |

**实现要点**：

- 新增**独立 Modal**（AntD `Modal` + `open` state），不复用 `modal.confirm`；人工路径仍用 `modal.confirm`（N1-E3）不动。
- 勾选 UI 复用 `OutlineGateList`（N1-E4），`selectedRef` 初始为全选；自动确认时使用全选集合。
- 计时器用 `useEffect + setTimeout`，所有打断路径统一走 `cancelAuto()`（clearTimeout + 置 `cancelled`），并在 `useEffect` cleanup 中清理，避免切页后仍触发保存。
- **倒计时固定 8 秒（已拍板）**：终端用户界面**不暴露秒数配置**（无输入框、无下拉、无设置项）；`8` 作为默认值硬编码在 `outline_auto_confirm_delay_ms = 8000`（`backend/app/config.py` 纯追加；开关关时不读）。
- **仅运维可通过环境变量改**：`OUTLINE_AUTO_CONFIRM_DELAY_MS` 写入 `backend/.env.example`，并在该条目上方注明原文：`# 面向运维，不建议用户改（终端界面不暴露此项；改小会缩短自动确认等待，改大可能让用户以为卡住）`。前端不提供任何修改入口。

### 3.5 自动确认执行 + 快照回退

#### 3.5.1 保存与快照

- 前端自动保存调用**与人工完全相同**的 `doSaveGate(filtered)`（`useOutlineGate.tsx:166-182`），仅额外传 `snapshot_before: "outline_auto_confirm"`。
- 后端 `save_outline` body 新增可选键 `snapshot_before`（缺省 None = 完全现状）。当传入且白名单值合法时，在 `_save_outline_to_db` 的同一事务内、**删除/重建章节之前**：
  1. 读取当前 `sections` 全量行（允许列：`id, parent_id, title, description, level, sort_order, content, status, word_count, word_budget, word_status, locked, outline_json, chart_predictions, flowchart_json, gantt_json, review_status`）；
  2. 序列化为 JSON，写 `scheme_snapshots(type="outline_auto_confirm")`（N1-E7，无需改表）；
  3. 响应通过既有加法式键透传常量回传 `snapshot_id`（N1-E11）。
- **快照存哪**：`scheme_snapshots.sections`（JSON 字符串）。`type` 区分场景，不污染一致性修复/编号版本。
- **保留策略（已拍板，写死）**：同一方案同 type 仅保留最近 **5** 条，插入后按 `created_at DESC` 裁剪（在快照服务内完成；**5 为常量，不做配置项**）。该条同步列入 §4.3 实施清单，不靠实施者记忆。
- 快照失败策略：**fail-soft**——快照失败不阻断保存，但响应不返回 `snapshot_id`，前端改显示「本次无可回退版本」；不得因为快照失败而让用户失去目录。

#### 3.5.2 一键回退

**后端新文件**：`backend/app/services/outline_versions.py`

```python
async def create_outline_snapshot(db, scheme_id, *, snapshot_type="outline_auto_confirm") -> str
async def list_outline_versions(db, scheme_id, *, limit=5) -> list[dict]
async def restore_outline_snapshot(db, snapshot_id, *, chart_resync_fn=None) -> dict
```

**新增路由**（`backend/app/routers/sections.py` 内追加，沿用现有前缀）：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/schemes/{scheme_id}/sections/outline-versions?limit=5` | 列出版本（`snapshot_id, created_at, node_count, has_content, type`） |
| `POST` | `/api/v1/schemes/{scheme_id}/sections/outline-versions/{snapshot_id}/restore` | 回退到该版本 |

**回退实现（单事务）**：

1. 先为「当前状态」再建一个快照（`type="outline_rollback_undo"`），保证回退本身可撤销（沿用 N1-E8 的思路）。
2. `DELETE FROM sections WHERE scheme_id=?`。
3. 按快照行逐条 `INSERT`（含 `parent_id / level / sort_order / content / status / word_count / locked / review_status`）。
4. `UPDATE schemes SET word_count=SUM(...)`，并触发既有目录变更失效逻辑。
5. commit 后：`invalidate_export_cache`（`backend/app/services/facts_extractor.py:3830`）、`invalidate_consistency_scan_cache`（`backend/app/routers/sections.py:316`）；逐章调用 `_chart_pipeline.resync_inline_charts`（`backend/app/routers/_chart_pipeline.py:1054`），由 router 注入回调（与 `consistency_repair.py:479` 同模式，services 层不 import routers）。

**回退后动作（已拍板，写死）**：

- 回退**必须**失效「导出缓存」与「一致性扫描缓存」——两条失效调用不可省略、不可条件化，且必须先于响应返回（否则用户拿到回退成功却导出旧内容）。
- 回退后**不自动重跑一致性扫描**（避免额外 AI 调用与不可控耗时）；前端只提示「如需重新扫描请手动触发」。
- 上述两条与「快照保留 5 条」一并列入 §4.3 实施清单，代码评审按清单逐项核对。

**回退后下游处理**：

| 下游 | 处理 | 说明 |
|---|---|---|
| 正文 | 快照内 `content` 原样恢复 | 与自动确认前逐字一致 |
| 全局事实 | 不处理 | 事实按 `project_id` 存储（`global_facts` 域），不绑定 section（N1-E8 快照也不含事实） |
| 图表登记 | 逐章 `resync_inline_charts` | 避免「正文回退、图表登记未回退」两侧漂移（项目既有教训） |
| 导出缓存 | 失效 | 复用 `invalidate_export_cache` |
| 一致性扫描缓存 | 失效 | 复用 `invalidate_consistency_scan_cache` |
| 章节审核状态 | 跟随快照 `review_status` 恢复 | 不做推测性重置 |

**前端回退入口**：自动确认成功后的提示 toast/风险条追加「回退到上一版目录」按钮；点击先二次确认（destructive），成功后 `load()` 刷新树，并展示恢复的章节数。

### 3.6 风险提示常驻

- 开关开启时，OutlineTab 顶部常驻 `Alert`：`自动确认已开启，目录将由系统在 8 秒后生效`（其中秒数取后端下发的有效值，默认 8000ms；运维改环境变量后文案自动跟随，**前端不提供修改入口**），右侧按钮「切回人工」（直接 PUT false + 刷新开关状态），并使用 `data-testid="outline-auto-confirm-banner"`。

- 任何一次自动确认成功，生成日志追加一条：`自动确认已生效（快照 <snapshot_id>），可在目录 Tab 一键回退`。

## 4. 统一实施顺序与冲突点

### 4.1 建议顺序

| 顺序 | 批次 | 依赖 | 说明 |
|---|---|---|---|
| 1 | M1-1 ~ M1-2（后端数据与算法） | 无 | 先建立可核对的数据与结论，UI 后置 |
| 2 | M1-3（前端只读面板） | M1-2 | 只展示，无破坏性动作 |
| 3 | M1-4（缺失项「新增建议章节 + 定位」） | M1-3 | 涉及目录写操作；**不生成正文、不接入补齐** |
| 4 | U5-1（编排器 + 单测） | 无 | 完全独立，可并行 |
| 5 | U5-2 ~ U5-4（接线，开关默认关） | U5-1 | 先 bid_analysis，再正文/目录/事实；**不改既有并发默认值** |

| 7 | N1-3 ~ N1-4（开关与倒计时 UI） | N1-1/2 | UI 最后 |
| 8 | U5-5（A/B 基准） | U5-2 ~ U5-4 | 按数据决定是否默认开启 |

**顺序理由**：

- **N1 与 M1 已解耦**（M1 评分覆盖不再是 N1 的硬前置，见 §3.3），因此 N1 可在 M1 之前或之后独立上线；本表仍把 N1 排在 M1 之后，唯一原因是两者共用 `OutlineTab.tsx` 的 UI 落点（先合 M1 面板可少改一次 props）。
