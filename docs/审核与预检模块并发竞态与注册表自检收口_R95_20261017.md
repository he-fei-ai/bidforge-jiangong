### 3.2 GAP-1（R90 遗留⑥）：审核状态三处 UPDATE 无乐观并发 —— compare-and-set 收口

`review.py` 批量审核（原 389）、单章审核（原 433）、方案提交（原 557）三处
UPDATE 均不带状态期望：SELECT 与 UPDATE 之间隔着 await，并发请求（另一标签页、
批量与单章交叠）可在窗口内改写状态 →

- 旧状态机校验基于过期快照，`rejected → approved` 这类非法流转可借窗口发生；
- 评审留痕写入 `from_status=已被替换的旧值`，轨迹出现伪记录；
- 方案提交侧更严重：放行门禁（预检 blocked/指纹过期）校验的是读取时刻的行，
  写回时行可能已被并发流转。

修法（全部 `require_rows=False` + 调用方判读 0 行，契约文档同步更新）：

1. `batch_review_sections`：`WHERE id=? AND COALESCE(review_status,'')=?`
   带期望；0 行 → 响应体加法式新键 `conflicts`（不落留痕、不假成功）。
2. `review_section`：同谓词；0 行 → **409**（503 语义保留给连接瞬时异常，不混用）。
3. `submit_scheme_review`：`AND (? = '' OR COALESCE(review_status,'') = ?)` —
   期望为空串时不加状态约束，保留 2026-09-17 既有语义（库内非法/空
   review_status 残留行允许直接覆盖推进）；非空期望被并发挤掉 → 409。

NULL 归一口径：`COALESCE(review_status,'')` 与读取侧 `row[...] or ""` 同源，
护栏 C 组用**真库 sqlite3** 实证谓词语义（失配 0 行 / NULL 命中 / 逃生门），
桩连接只能证明「参数传到了」不能证明「条件写对了」，两层各锁一头。

前端同步：`ReviewWorkflowPanel.tsx` 批量反馈链路识别 `conflicts`
（老后端无该字段按空数组，向后兼容），有冲突时降级 warning 并点名
「并发操作修改未生效，请刷新后重试」；截断余量计算同步扣除 conflictN。

### 3.3 GAP-2（R90 遗留①）：validate_rule_registry 生产零消费

规则注册表双向自检（rule_id 格式/维度/严重度/mode/外部映射/引擎产出可解析）
此前**仅在 CI 测试时触发** —— 生产环境改规则而漏登时，用户拿到的是静默
塌陷的 title/basis/dimension（AGENTS.md 头部注释自认的病灶）。

接线：`GET /api/v1/compliance/rules` 每次调用即执行
`validate_rule_registry(mapping=_EXPORT_ISSUE_RULE_MAP,
emitted_rule_ids=_PROGRAM_EMITTED_RULE_IDS)`；响应体加法式新键
`registry_problems`（健康 = 空列表，前端可忽略）；非空记 ERROR 日志。
export 映射用**函数内懒导入**规避 router 间循环依赖。选择 /rules 的理由：
「规则说明」抽屉正是分叉的第一现场，自检与展示同端点即取即用，
不在 /overview 热路径上增加开销。

## 7. 经验教训

① **源码锚点测试必须随被锚函数迁移**——拆分/搬移类重构（R94 渲染段拆分）
的审查清单里，`inspect.getsource` 锚点应作为机械普查项一并订正，本轮基线
2 红即上一轮漏订正的直接后果；护栏 E 组把「双锚点」静态锁死。
② **桩连接只能证「参数到了」，真库才能证「条件写对」**——CAS 谓词用
sqlite3 :memory: 实证失配/NULL 归一/逃生门三语义，行为层与语义层分层锁定。
③ **加法式契约收口竞态**：响应体新增 `conflicts` 而非改变既有字段，
前端 `?? []` 兜底即双向兼容；409 与 503 语义分列（竞态 vs 连接异常），
不把 R13 的单一出口叙事搅浑。
