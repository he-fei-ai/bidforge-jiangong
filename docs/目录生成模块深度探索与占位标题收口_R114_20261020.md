### 2.3 依赖模块与分层边界

- `sse_handlers`（router 层，编排）→ `services/outline_quality`（纯函数判据）→ `services/outline_title_fix`（外科式重写）→ `services/ai/*`（`collect_json_response` / prompt registry / 缓存）
- `sections`（router 层，落库）→ `services/numbering`（编号唯一事实源）+ `services/outline_title_fix`（**单一实现**）+ `services/outline_quality`（`attach_generic_residual`）+ `services/scheme_scope` / `services/scheme_basis`（**本轮新接线**，纯确定性、零 IO 之外只读名称）
- `upload_outline`（router 层）→ 复用 `sections._build_generic_fix_context`（**同层 router 复用，不违反**「禁止 router → sse_handlers 私有符号反向 import」护栏）
- 唯一被本轮打破的旧边界：`sections` / `upload_outline` 首次从 `services.scheme_scope` / `services.scheme_basis` 取上下文（**服务层，正向依赖**，合规）。

### 2.4 数据链与存储

```
AI(JSON) → _as_children/_sublevel_validate_fn → 目录树(list)
        → [长方案] _merge_unit_results 保序归位
        → _review_and_fix_outline（审核 + 外科式标题重写/补齐）
        → SAVE：sections._save_outline_to_db
             _preserve_original_ids → renumber_outline_nodes（编号唯一事实源）
             → autofix_generic_titles_on_save（占位重写，检出才付费）
             → attach_generic_residual（加法式回传 generic_residual）
             → INSERT/UPDATE sections（同一事务锁根）
             → _renormalize_all_section_contents（正文子标题编号同步）
             → invalidate_consistency_scan_cache + invalidate_export_cache
```

**关键不变量（本轮核验通过，未改动）**：
1. `renumber_outline_nodes` 是编号的**唯一事实源**；`strip_outline_numbering_tree` 负责剥离内嵌编号；正文 Markdown 子标题由 `normalize_section_content_subheadings` 同步 ⇒ **DB 子章节编号与正文子标题同源，不存在两套编号**。
2. `generic_residual` 为**加法式**键（仅在检出非空时挂载），前端据此提示；本轮**完全未改**该契约 ⇒ 前端零改动、无需重建。

## 四、根因分析

### 根因 A：落库前占位重写拿不到项目上下文（FIX-A）

`outline_title_fix_system`（`prompts/outline.py:309`）声明了 `{scheme_name} {scheme_type} {scheme_basis} {construction_scope} {project_brief} {project_facts} {requirements} {standards_text}` 八个上下文变量。

但两条落库路径：

- `sections._save_outline_to_db` 旧代码只查 `SELECT name, type FROM schemes`，只传 `scheme_name`/`scheme_type`；
- `upload_outline.save_as_outline` 旧代码**什么都不传**（连 `scheme_name` 都是空串）。

⇒ 提示词里「这个专项具体做什么施工」「编制要求是什么」全为空。模型无从判断该写「灌注桩支护施工」还是「专项6」，只能回占位名 —— 再被 `_apply_title_updates` 的六条保守红线（仍泛化 / 带（N）后缀 / 与同级重名 …）**整批拒收** ⇒ `applied=0` ⇒ fail-soft 原样落库。

**这与 R89 G3 是同一根因**，只是 R89 修的是生成链路（`_review_and_fix_outline` 调用点），落库这条**最后一道自动修复机会**一直空转。

### 根因 B：生成期对占位标题零闸门（FIX-B）

`_sublevel_validate_fn`（`sse_handlers.py:1573`）只判「`outline` 为非空数组 + 每项有 `title`」—— `专项6` 完全合法。

唯一拦截点是收尾的 `_review_and_fix_outline`，而它的外科式重写有 `hits[:40]` 体量红线（`outline_title_fix.py:85`）与 `OUTLINE_FIX_TIMEOUT` 超时 fail-soft。

**「源头不限 + 末段限额」** = 用户看到的「三级标题**大量**是占位名」。

> **为何不靠「继续改提示词」解决（关键证据）**：三处目录生成提示词**早已明文禁止**该症状，且措辞与用户反馈逐字对应 ——
> - `outline_level1_system` L58：「一级标题严禁使用泛化占位名称（如“专项6”“总体实施策划（2）”“其他”“通用”等）或带“（N）”编号冲突后缀」
> - `outline_sublevel_system` L88：「二三级小节标题必须具体到本项目的施工对象/部位/工序/参数，严禁使用泛化占位名称（如“专项6”“总体实施策划（2）”“其他”“主要内容”“通用”等）或带“（N）”编号冲突后缀」
> - `outline_sublevel_batch_system` L289：同口径
>
> 历史轮次已把提示词写到「点名禁止」的强度，**模型仍不遵守**（长方案单章生成时上下文被截断/注意力分散）。因此它不能作为**唯一**保障 —— 必须有「产出后立即检出 + 把具体失误回灌」的程序化闸门。FIX-B 不是重复提示词纪律，而是把**同一纪律变成可验证的前置条件**。

### 根因 C：停止 / 全章失败成果未经审核且不可归因（FIX-C）

`_finish_stopped_with_partial`（`sse_handlers.py:2065`）直接返回 `holder["outline"]`，收尾审核从未跑过；旧日志对此零留痕 ⇒ 用户与运维都无法判断这批占位名来自哪条链路。

### 根因 D（本轮新发现）：脏+失败组合导致整章丢失（FIX-B2）

把「失败重试」与「占位重试」合并为同一份预算后，出现一个旧编排从未覆盖的组合：**首轮有可用产出但脏 → 次轮调用失败**。旧代码直接 `failed`，而 `failed` 章在编排层的语义是「该章无子目录」⇒ 用户看到**整章凭空消失**（比占位标题更严重的可用性事故）。

> 1. `test_review_autofix_closeout_r55_20261008.py::TestFrontendRealExecution` 的 3 项会**启动 npm 子进程**跑 `tsc --noEmit` / **完整 vitest** / eslint，耗时可达 10 分钟以上且 CPU 几乎全占用；与其余 9100+ 项串行时表现成「进度跑到 89% 长时间无输出」，本轮曾两次误判为卡死并 kill（浪费时间且无收益）。
> 2. 该文件的 `test_sse_escape_text_not_expanded_to_raw_bytes` 存在**既有环境性假红**（与本轮改动无关）：旧断言 `b"\\x0d" not in b` 要求前端 `index.ts` **零 CR 字节**，而本仓 `core.autocrlf=true` 决定工作区副本必为 CRLF（实测 CR=1480 / CRLF=1480 / 孤立 CR=0）⇒ 在任何 Windows 检出上恒红；且同文件 `test_no_lone_cr_or_control_bytes` 的 docstring 明写「纯 CRLF 与纯 LF 都合法」。

## 九、遗留问题与后续建议

| # | 项 | 判定 | 理由 |
|---|---|---|---|
| L1 | **确定性兜底改写**（直接去「（2）」后缀） | **刻意不做** | 对用户症状无效：`总体实施策划（2）` 去后缀后仍命中 `is_generic_title`（`^总体实施策划` 前缀）必被跳过；而合法具体基名（如「深基坑支护（2）」）在 `detect_generic_titles` 里**根本不算** `conflict_suffix`（需 `norm_count>=2` 才报）。硬造限定词属「改坏」，违反 R79 起的「不静默改写用户输入」红线 |
| L2 | `hits[:40]` 单次体量红线 | 登记（本轮只做**透明化**） | 改上限需实测 token/时延与拒收率；当前改为「本次送 40 条 / 共 N 条」日志，且 FIX-B 已把源头压低 |
| L3 | 轮次预算 `outline_autofix_generic_retries=2`（默认 3 轮 × 40 = 120 条） | 登记 | 与 L2 同一权衡；调整需产品确认 |
| L4 | 停止链路**确定性清洗**（不是只记日志） | 刻意不做 | 部分成果缺上下文（哪些章已完成、哪些未开始），无信息可依；硬造会改坏已生成成果 |
| L5 | 收尾审核 `OUTLINE_FIX_TIMEOUT` 超时 fail-soft | 登记 | 长方案下提高超时会把用户等待时间同比拉长；FIX-B 已把「必须靠收尾修」的量降下来 |
| L6 | `_fetch_unit_children` 批量路径**不做**逐章占位重试（只回退单章一次） | 有意 | 批量单位成本已较高；回退单章已拿到「一次重写机会」，再叠加重试会让最坏调用数×2 |
| L7 | 前端对 `generic_residual` 的提示文案 | 无需改 | 本轮零契约变更 |
| L8 | `test_review_autofix_closeout_r55` 的 SSE 判据与本仓 `core.autocrlf=true` 互斥 | **本轮修（判据）** | 旧断言要求零 CR 字节，在任何 Windows 检出上恒红；改为「孤立 CR = 0」并保留字面量强锁（详见 §8.5） |
| L9 | `TestFrontendRealExecution` 3 项与后端全量串行时的长时无输出 | 登记（不修） | 它们是真的在跑 tsc/vitest/eslint；建议后续给它们打 mark（如 `@pytest.mark.frontend`）并在 CI 里单段跑 |

**后续建议（按性价比排序）**：
1. 用 FIX-B 的 `WARNING`（「第N章子目录含 M 处占位/泛化标题」）做**生产占比统计**，验证源头压降效果，再决定是否调 L2/L3；
2. 若某类专项（如「监测」「临时用电」）反复出现同一批占位名，考虑在 `outline_sublevel_system` 里补该类别的**正例标题库**（比提高重写上限更省）；
3. 把 `_children_retry_feedback` 的正例改为**按 scheme_type 动态取**（当前是固定的基坑类正例）。
