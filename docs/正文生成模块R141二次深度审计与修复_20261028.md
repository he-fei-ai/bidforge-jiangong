### 3.2 工作流程（一次「刷新页面接管后台任务」—— 本轮缺陷核心路径）

1. 页面加载/刷新 → `useEffect([id, load])` → `tasksApi.list(id)` 找 `status ∈ {running, paused}` 的任务。
2. `stuckFull = allRunning.find(t => t.progress >= 0.95)` 预检（僵尸快出）。
3. 未命中僵尸 → 取 `active` → `genTypeMap[active.task_type]` → `setGenerating(true)` / `setGenType(gt)` / `setTaskPaused(...)`。
4. 进入内联 `for (i = 0; i < 400; i++)` 循环：每 3s `tasksApi.status(active.id)`：
   - 终态（`isTerminalTaskStatus`）→ `resetTakeover()` + 按 `outline_result`/`completed`/`degraded`/`failed`/`stopped` 分支恢复 → `return`。
   - `progress >= 0.99` 连续 3 次 → stuck 兜底 `completed` + `resetTakeover()` + `load()`。
   - **`catch { return; }`（旧缺陷 M1）**：任意一次查询失败 → 直接 `return`，**不调用 `resetTakeover()`**。
   - **循环自然跑满 400 次（旧缺陷 M2）**：静默退出，**不调用 `resetTakeover()`**。

## 七、修复项清单（2 处，均在前端 `SchemeWorkbenchPage.tsx` 刷新接管循环）

> **共同根因**：正文/目录/事实的 **SSE 断线重连**早已收敛到 `reattachTaskImpl` + `pollTaskUntilTerminalImpl`（netFailTolerance=5 / maxPolls=200 / 404 立即放弃 / stuck-at-0.99 兜底），但**刷新页面接管后台任务**的 `useEffect` 内联循环是**第三套**未收敛实现，且存在两个「退出不复位」缺陷——与 R139 FIX-1 的 hook 无上限轮询同类（漂移温床 + 界面永久卡死）。

### FIX-1 · 接管循环 catch 不复位（P2）

- **文件**：`SchemeWorkbenchPage.tsx:5195-5210`
- **现象/根因**：旧实现 `catch { return; }` —— 在**任意一次** `tasksApi.status` 失败（瞬时网络抖动 / 5xx / 404 任务已清理）时直接放弃接管，**且不调用 `resetTakeover()`**（后者只在终态 / stuck-at-full 分支被调用）。后果：`generating=true` / `genType` / `taskPaused` / `activeTaskIdRef` 永久保持，页面停在「生成中」，暂停/停止按钮控制的是已失效任务，唯一出口是手动刷新。
- **修改**：catch 块改为 `catch (e: any) { console.warn(...); resetTakeover(); return; }` —— 任何查询失败都复位接管状态，绝不把界面留在「生成中」；后台任务不受影响（仍在跑），用户可再次刷新重新接管。
- **向后兼容**：行为变化仅限「失败时不再卡死」（从卡死 → 复位），无新增配置项。

### FIX-2 · 接管轮询跑满 400 次不复位（P2）

- **文件**：`SchemeWorkbenchPage.tsx:5211`（for 循环闭合后、外层 catch 前）
- **现象/根因**：for 循环**正常跑满 400 次（≈20 分钟）**后静默退出，**不调用 `resetTakeover()`** —— 与 FIX-1 同类。超长任务 / 后端状态列陈旧 / 进度停在 0.95 的目录僵尸都会触发此路径。
- **修改**：循环后补「有界退出」复位：`console.warn(... 轮询 400 次未达终态 ...); resetTakeover();` —— 对齐 `pollTaskUntilTerminalImpl` 的「maxPolls 有界退出」语义。
- **向后兼容**：从「静默卡死 20 分钟」→「20 分钟后有界复位 + 告警」。

### 新增护栏 · `contentTakeoverResetR141.test.tsx`（4 例）

| 用例 | 判据 |
|------|------|
| 前提：页面源码取到 + 接管循环存在 | `for (let i = 0; i < 400; i++)` + 循环体非空（找不到即红，暴露重构） |
| FIX：catch 块必须复位（旧 `catch{return}` 静默放弃） | 循环体内 `catch (e: any)` + `resetTakeover()` + `状态查询失败` + `not.toContain("catch {")` + 复位在 return 之前 |
| FIX2：轮询跑满必须复位（旧静默退出） | 循环标记→外层 catch 区域含 `轮询 400 次` + `未达终态` + `resetTakeover()` ≥2 次 + 告警先于复位 |
| 反向锚：断线重连仍走收敛实现 | `reattachTaskImpl(` + `pollTaskUntilTerminalImpl(` 均在页面 |

## 八、被否证 / 记录的发现项（未改，留痕）

### FINDING-2 · hook 建连阶段断连不重挂（潜伏缺陷，仅测试引用的第二条链路）
`useContentGeneration.ts:229` 的断线重挂仅 `if (taskId) { pollTaskUntilTerminalImpl(...) }` —— **taskId 为空（SSE 在首个携带 task_id 的事件前断连：30s 建连超时 / 网络抖动 / 网关重连）时整个重挂分支被跳过**。页面早已用 `reattachTaskImpl` 按 `typeFilter` 检索解决此问题（:6646）。hook 无生产调用方（R139 范围声明），且干净修复需把 `reattachTaskImpl` 下沉叶子（避免 hook 反向 import 巨型页面）。**记录为 L 项**，与「页面切 hook」的 L1 同批处理。

### FINDING-3 · 接管预检 `>=0.95` 误判正文一致性阶段（阈值权衡）
`SchemeWorkbenchPage.tsx:5094` 的僵尸预检用 `progress >= 0.95`；而 `content_progress.SECTION_PHASE_MAX = 0.95`（:16）使**正文在一致性扫描/修复阶段（0.95→0.99→1.0）合法停留于 ≥0.95**。用户恰在该窗口刷新 → 被误判为「已完成」，提前 `load()` + 提示，任务仍在后台修复，最终（修复后）内容不被加载。这是**真实但低概率**的阈值冲突（一致性阶段通常仅数秒~数十秒）。修法需任务类型感知（content 用 0.99、outline 用其封顶），改阈值有跨类型回归风险（outline 0.95 封顶的僵尸将改由循环兜底）。**记录为 L 项**，不做无依据改动。

## 十五、判据教训归档

1. **「同一功能三条链路」必然漂移，且缺陷只堆在未收敛的那条** —— 正文断线重连早已收敛（reattachTaskImpl），但刷新接管是第三套内联实现，两处缺陷（catch/跑满不复位）全堆在这里。判据要枚举**所有**轮询入口（断线重连 / 刷新接管 / hook 重挂），不能只测最显眼的一条。
2. **「轮询退出必须复位状态」是通用判据** —— 无论正常跑满、异常 catch、还是 404，任何退出路径都不能让 `generating` 卡在 true；`pollTaskUntilTerminalImpl` 的 maxPolls 有界退出 + netFailTolerance 分级就是范本。
3. **源码锚要锁「退出形态」而非「符号出现」** —— 断言 `resetTakeover()` 出现不够，要断言它**在 catch 内、在 return 之前**（M1 即证明：只数符号出现会让「复位挪到别处」漏网）。
4. **阈值语义必须单一事实源** —— `0.95` 在 `SECTION_PHASE_MAX` 是「生成封顶」，在接管预检是「僵尸判据」，两处共用同一字面量但语义不同（FINDING-3）；改阈值前必须探针实测各类型进度封顶，避免「改一处、坏另一类」。
5. **A/B 变异脚本必须二进制安全往返** —— 页面为纯 LF（实测 CRLF=0），文本写回不污染 sha；若为 CRLF 需按 R138 教训⑨归一，否则 `sha_match` 假阴性。
6. **「环境型假红」要单跑复验** —— R139 基线 8 个 skip 用例本轮运行通过（无并行争抢 + Node 更快），证明此前 skip 是环境/争抢导致，非代码缺陷；单跑复验后再定性，不误报回归。
