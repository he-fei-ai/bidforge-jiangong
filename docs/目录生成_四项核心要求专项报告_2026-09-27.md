## 二、探查结论（先证伪，再动手）

### 2.1 核心发现：「围绕方案名称」的能力**早已具备但从未接线**

`services/scheme_basis.py` 把方案名称确定性解析为 `SchemeBasis`（纯函数、零 IO/零 AI）。
全仓调用点探查（`Select-String` 全 app/ 目录）结果：

| 能力 | 定义位置 | 调用点 | 结论 |
|---|---|---|---|
| `SchemeBasis.is_dangerous`（名称字面危大） | `scheme_basis.py:323` | **0** | 死字段；目录只看 `schemes.type` |
| `rank_by_relevance`（相关性前置） | `scheme_basis.py:368` | **0**（仅模块内自调用） | 死代码 |
| `text_keywords` / `relevance_score` | `scheme_basis.py:183/201` | 仅 `SchemeBasis` 内部 | 死代码 |
| `basis.template_key`（24 个标准章节模板） | `scheme_basis.py:330` | **0**（`prompt_text()` 也不含） | 能力闲置 |
| `settings.outline_basis_relevance` | `config.py:401` | **0** | 死配置（注释承诺"相关小节 ×boost 倍份额"） |
| `settings.outline_relevance_boost` | `config.py:404` | **0** | 死配置 |

**直接后果（要求一/四失效的根因）**：目录生成拿到的"方案名称"此前只有
`【方案名称主要施工内容】`一行（2026-09-26 前连这个都没有），
危大判定、相关性排序、全面性校验**三项全部缺席**。

### 2.2 名称危大与 type 脱钩（实测）

```
is_dangerous(深基坑支护专项施工方案, type=其它)  → 修复前 False / 修复后 True
is_dangerous(装饰装修专项施工方案, type=其它)    → 修复前后均 False（无误报）
```
`config.py:377` 注释早已写明"type 命中 DANGEROUS_TYPES **或** 名称字面命中六大类危大"，
实现只有前者 —— 典型"文档与实现不符 + 配置静默失效"。

### 2.3 解析提取内容的调用链与"围绕名称"的缺失

链路：`bid_analysis_items(status='success')` → `_build_structured_brief` →
`format_downstream_context`（按 `ANALYSIS_ITEMS` **权威顺序**输出 18 项）→
`_rank_sections_by_basis`（**本轮新增**）→ `_budgeted_truncate_sections(4000 字)`。

- 修复前**无任何与方案名称相关的排序或过滤**：与本方案无关的项（商务条款/报价）
  照样占位，相关的项可能落在被截断的尾部（每项保底 150 字、单项封顶 35%）。
- 现在按名称相关性**前置**（只重排、不删除、不改各小节配额算法）。

### 2.4 上下文注入（要求二）

| 注入点 | 变量 | 预算 | 载体 |
|---|---|---|---|
| 短方案 system | `construction_scope` `scheme_basis` `standards_text` `project_facts` | facts ≤6000 | 模板变量 |
| 短方案 user | 四项输入逐条拼接 | brief 3000 / 目录库参考 2000 | 字符串拼接 |
| 一级目录 system | + `project_brief` 2000 / `reference_outline` 1000 / facts 1500 | — | 模板变量 |
| 二三级 system | + `other_outline` 1200 / `prior_chapters` 1500 / `requirements` 1500 / facts 1000 | — | 模板变量 |
| 批内跨章去重 | `prior_l2` 增量追加 | `_join_tail_budget` 尾部预算 | 内存列表 |
| 审核/补齐 | `outline_json` 骨架（≤150 节点、description 截 60 字） | — | 模板变量 |

**连贯性设计已到位**：`prior_chapters` 防跨章重复 + `other_outline` 防同级重复；
`prior_l2` 增量维护（O(n) 而非每章重建 O(n²)）。本轮**未改动**注入方式，
仅补齐缺失的 `{scheme_basis}`（上一轮）与相关性前置（顺序即见性）。

### 2.5 连续性（要求三）

| 维度 | 现状 | 缺口 |
|---|---|---|
| 层级 | `clamp_outline_depth(3)` 硬裁剪 + `renumber_outline` 回写 level | 生成**后**无自动校验 |
| 编号 | `numbering.renumber_outline_nodes` 唯一实现；增删改拖拽 4 入口 + 整表重建 3 入口全部重排 | 生成**后**无自动校验 |
| 内容 | `_outline_validate_fn`（结构）/ AI 审核判重 | 无**程序化**同名章节检测 |
| 状态 | 分步 `_merge_unit_results`（上轮修复）+ checkpoint 续生成 + 8 处 409 守卫 | 无"续生成后编号一致性"断言 |

**本轮新增**：`outline_quality.check_outline_continuity` —— 层级跳级 / 有父无子 /
同名章节 / 编号错位 四类可检出，生成后自动执行、写日志 + 进 `review.quality`。

### 2.6 全面性（要求四）

- 已有：`_check_requirements_coverage`（编制要求 + 危大 10 章，**只查 L1 标题**）、
  `DANGEROUS_TYPES`、提示词 0.2「与九大章节骨架相容」、`NINE_CHAPTERS`（事实侧字段表）。
- 缺失：**方案名称关键词 → 目录章节**的匹配分析完全缺实现。
  "目录是否覆盖方案名称里的每项施工内容"这件事，**生成前后都没有任何程序判定**。
- **本轮新增**：`analyze_name_coverage`（覆盖矩阵 + 缺失清单）、`find_redundant_titles`
  （冗余候选，只报告不删除），并把缺失项并入既有 `_try_outline_patch` 外科式补齐
  （不新增调用范式：缺失才多 1 次小调用，全覆盖反而省掉 AI 审核）。

## 五、连续性校验表（要求三 · 生成后自动校验）

校验器：`services/outline_quality.py::check_outline_continuity`（纯函数、零 IO）。
生成后在**短方案与长方案两条链路**都自动执行（`_attach_quality_report`），
结果写 `review_obj["quality"]["continuity"]` + 日志，**不修改目录**。

| 检查项 | 判据 | 修复前 | 修复后（实测） |
|---|---|---|---|
| 层级跳级 `level_gaps` | 子节点 `level` ≠ 父层级 + 1 | 无检出能力 | 检出并给 `declared/expected` |
| 有父无子 `empty_parents` | `children` 非空但其下无有效标题 | 无检出能力 | 检出并给 `path/count` |
| 同名章节 `duplicate_titles` | 标题归一后重复（附首次出现路径） | 仅 AI 审核事后判 | 程序化检出 |
| 编号错位 `numbering_mismatch` | 点分 id ≠ 位置编号 | 无检出能力 | 检出并给 `id/expected` |
| 规模 | `nodes` / `max_level` | — | 上限 3 级由 `clamp_outline_depth` 保证 |

状态连续性（分步/续生成）由上一轮修复保障：`_merge_unit_results` 保证"停止不丢成果、
缺结果不静默"；checkpoint 存 `_partial_holder`；`normalize_outline` 收尾统一重排编号。
