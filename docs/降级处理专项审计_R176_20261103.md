## 0. 开篇结论

**是，存在"静默失真"级降级，且不止一条。**

最危险的 3 条：

1. **导出预检在 DB 抖动时返回"0 问题"** —— `POST /export/check` 调 `collect_export_issues()` 时未启用严格读，`_db_fetch_all(strict=False)` 把读失败降级为空结果集，页面据此渲染"预检通过"（`backend/app/routers/export.py:107-117`、`:428-451`、`:562-576`）。这是"失败被当作成功"的教科书形态：用户看到的是干净报告，实际是没读到数据。
2. **全局事实读取失败 → 成稿静默缺失"项目关键事实"，且状态响应头无人消费** —— `_query_global_facts()` 异常时 `return []` 并只写 `WARNING`（`export.py:3140-3144`），后端虽回写 `X-Global-Facts-Status: query_failed`（`export.py:1916-1922`、`:4219`），但前端全仓**零消费**（`frontend/src` 检索无命中），导出仍 200 且产物看起来正常。
3. **合规审核只审前 6000 字，"未检查章节"标记到不了 UI** —— 后端 R175 已把截断显式化为 `partial` / `truncated_sections`（`backend/app/routers/compliance.py:96-98`、`:461-488`），但前端未展示该字段，用户看到的仍是"已检查完毕"。

**统一策略一句话**：*外部依赖失败一律"可见降级"（可机读状态 + 用户提示 + 有限重试 + 不写缓存）；数据/缓存完整性失败一律 fail-fast（显式错误码 + `Retry-After`）；任何 `except` 都必须同时产出"留痕 + 可消费状态"，否则视为缺陷。*

**降级路径清点结果**：共 **53 条**。
- 风险分级：**高 4 / 中 15 / 低 34**；
- 其中 **27 条**已有可见信号或回归护栏（"闭环"，作为正面样板保留）；
- 危险类型命中：**静默失真 9 条**（D-02/D-06/D-16/D-23/D-34/D-39/D-41/D-47/D-51）、**污染固化 3 条**（D-04/D-16/D-17）、**承诺落空 5 条**（D-02/D-06/D-23/D-39/D-41），可重叠。

> 说明：R175 系列报告已修复的项（导出空章不写缓存、ZIP 完整性判据、渲染器版本失效、一致性失败不写缓存、SSE 未知态横幅、导出错误体解包等）本轮**逐条抽查确认**，作为"闭环样板"纳入总表，不再重复计为缺陷。

## 4. 外部最佳实践引用与适配建议

> 以下引用均已实际抓取页面内容；要点为原文/摘要的转述，未做扩写。

### 4.1 降级需要"透明"，不能让用户以为一切正常

- **Google SRE · Handling Overload**：优先"serve degraded responses"，但当降级也做不到时应"serve errors"；总原则是 *"redirect when possible, serve degraded results when necessary, and handle resource errors transparently when all else fails."*
  来源：<https://sre.google/sre-book/handling-overload/>
  **适配**：本项目的 D-02 / D-06 / D-41 违反"transparently"——降级发生了，但没有任何面向用户的透明信号。修复方向不是取消降级，而是把"已降级"作为一等状态返回。

- **Azure · Circuit Breaker pattern**：`Closed → Open → Half-Open`；实现方必须能处理异常，可选择"临时降级功能、调用替代操作、或把异常报告给用户并要求稍后重试"；同时强调 **Monitoring**（对失败与成功都要有可观测性）与 **Manual override**（管理员手动复位）。
  来源：<https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker>
  **适配**：`workflows_base.py:114-225` 的三态熔断与 429 冷却已符合该模式（D-31 闭环）；缺口在"Manual override"——前端/管理端没有"重置熔断/重测 provider"入口，建议 B3 补。

- **AWS Builders' Library · Resilience lessons from the lunch rush**：熔断器越过延迟/失败阈值后 Open，退避后进入 Half-Open，仅放少量请求探测；另强调 load shedding 与 well-behaved clients。
  来源：<https://aws.amazon.com/builders-library/resilience-lessons-from-the-lunch-rush/>
  **适配**：与 D-31 一致；可借鉴其"half-open 只放少量探针"用于 `provider_factory` 降级链的健康探测，避免所有候选同时被打。

### 4.2 失败响应不可缓存，临时不可用要带 `Retry-After`

- **MDN · 503 Service Unavailable**：503 表示"服务器暂时无法处理请求"，应尽量带 `Retry-After`；并明确指出 *"a 503 indicates a temporary issue and responses shouldn't usually be cached"*，否则修复后客户端仍拿到旧错误。
  来源：<https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/503>
  **适配**：
  1) D-02 的"读失败"应返回 **503**（或 200 + 显式 `degraded=true`，二选一，不可继续 disguised as success），并带 `Retry-After`；
  2) D-14/D-17 的缓存负结果不得持久化；D-19 的 10 分钟内存负缓存符合"短期负缓存"精神；
  3) `export.py:3327-3329` 图表登记读失败已返回 503，但**未带 `Retry-After`**，建议补齐。

- **MDN · Retry-After**：可用于 503（服务预计不可用时长）与 429（下次请求前等待时长），值为 HTTP-date 或秒数。
  来源：<https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Retry-After>

### 4.3 统一错误契约（机器可读 + 人可读）

- **RFC 9457 · Problem Details for HTTP APIs**：`type`（问题类型 URI）、`title`（稳定的短摘要）、`status`、`detail`（本次实例的具体说明）、`instance`；媒体类型 `application/problem+json`。
  来源：<https://www.ietf.org/rfc/rfc9457.html>
  **适配**：当前项目错误体多为 FastAPI 默认 `{"detail": "..."}`，`exportResponse.ts` 已能解包（D-49 闭环）。建议 B3 引入 `code`（稳定枚举，如 `DB_READ_FAILED` / `EXPORT_FACTS_UNAVAILABLE` / `AI_PROVIDER_EXHAUSTED`）+ `retryable` + `retry_after` 三个加法字段，前端据此决定"重试/提示/阻断"，而不是靠文案匹配。

### 4.4 缓存一致性与"失败不写缓存"

- **Azure · Cache-Aside Pattern**：缓存不保证与数据源强一致；写入后失效、下次读取再填充；外部进程可随时改动数据。
  来源：<https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside>
  **适配**：本项目已有"内容指纹 + 版本号 + 开关入指纹"（`_export_cache.py:92-222`），方向正确；缺口是"失败结果与真实空结果同键"以及"坏文件判可用"（D-16/D-17）。

### 4.5 与现有 R175 修复的对照

| 外部原则 | 项目内已落地 | 仍缺口 |
|---|---|---|
| 降级透明 | `X-Export-Degraded`、`X-Chart-Render-Stats`、`X-Fix-Stats`、`failed_sections` | 事实状态头无消费（D-51）、合规截断无 UI（D-41） |

## 5. 统一降级策略规范（可直接落地的条款）

> 建议作为 `docs/` 下的长期规范，并在 CI 中以静态检查 + 代码评审清单执行。

**R-D01（可见性红线）** 任何降级必须同时满足两条：① 产生面向用户的可见信号（界面提示 / SSE 事件 / 响应头 + 前端消费）；② 产生结构化留痕（`logger.warning` 以上，含模块、对象 id、降级类型）。只满足其一的，视为缺陷。

**R-D02（禁止 `except Exception: pass`）** 全仓禁止空 `except`。`# noqa: BLE001` 必须附 `# degradation: <ID>` 注释，且该 ID 必须登记在 §2 总表；新增未登记的 BLE001 直接 CI 失败。

**R-D03（数据完整性 fail-fast）** 以下场景必须**抛错**而非返回空：读正文/章节/图表登记/事实/缓存行用于**产物生成**或**评审判定**。错误出口统一为 503 + `Retry-After`（见 R-D06）。只读装饰性信息（活动栏、历史趋势）可 fail-soft。

**R-D04（缓存写入白名单）** 只有"已验证产物 + 完整指纹 + 无降级信号"三者同时满足才允许写缓存。验证至少包含：非空、结构有效（DOCX=ZIP 完整性；PDF=`%PDF-` 头 + 可解析页数）、内容完整（无空章/缺图/待生成占位）。失败结果一律**不写**。

**R-D05（负缓存有界）** 允许短期负缓存（如配图失败 10 分钟、进程内存、重启失效），但必须：有 TTL、有命中计数日志、不落盘、不参与内容指纹之外的长期命中。

**R-D06（错误契约）** HTTP 错误统一返回：`{"detail": 人可读中文, "code": 稳定枚举, "retryable": bool, "retry_after": 秒数|null}`（兼容现有 `detail`，纯加法）。前端按 `retryable` 决定是否自动重试，禁止按文案匹配。

**R-D07（降级信号聚合）** 一次请求/任务的所有降级信号收敛到一个 `degradations: [{kind, module, severity, object_id, message}]` 列表：HTTP 走响应头（`X-Degraded`）+ 响应体（加法字段），SSE 走 `degradation` 事件。禁止每个模块各自发明一个头。

**R-D08（外部依赖能力探测）** 启动时探测 Word COM / LibreOffice / Tesseract / Mermaid HTTP，结果缓存并暴露 `/system/capabilities`；前端据此置灰按钮或前置提示。禁止"按钮永远可点、点了才 501"。

**R-D09（内容截断必须显式）** 任何 `[:N]` 预算截断都必须在产物/结果中标注：`truncated=true` + `truncated_items` + `checked_chars`；前端必须展示。禁止"静默取前 N 字"。

**R-D10（可恢复性）** 每个降级必须定义恢复路径：自动重试（次数/退避）、TTL 自愈、用户手动接管三者至少其一；否则必须在 UI 明确"不可自动恢复"。

### 14.1 知识库 `build_knowledge_text` 统计口径

`build_knowledge_text(..., stats_out=dict)` 非空时写入**精确**统计（不做估算）：

| 字段 | 取值方式 |
|---|---|
| `original_chars` | 仅统计被裁/被丢条目：`len(content.strip())`（与实际参与切片的字符串**同一份**） |
| `kept_chars` | 截断条目 `min(len(content), per_item)`；整条丢弃条目 `0` |
| `dropped_chars` | `original_chars - kept_chars`（逐条相加，非汇总估算） |
| `truncated_items` / `dropped_items` | 单条超 `per_item` / 总量超 `max_total` 的条目数 |
| `items` | 逐条 `name` / `state`（`truncated`\|`dropped`）/ 三个字符数 |

- **事件复用**：不新开事件名。`_record_knowledge_budget` 把统计并入既有 `context_degraded`，`field=knowledge_text`、`reason=budget_truncated`、`segment_id=knowledge_text`，`extra` 带 `cut_items` / `truncated_items` / `dropped_items` / `items`。
- **正常路径零事件**：`truncated_items + dropped_items == 0` 时 `_record_knowledge_budget` 直接返回，`_context_degraded_events([])` 输出空列表。
- **接线点**：目录链 `_sse_outline_build._build_knowledge_text`（装配期事件随目录生成下发）；正文链 `_knowledge_text_for` 记账 → `gen_one` 在上下文构建返回后立即 flush。
- **顺带修复**：上一轮把 `yield` 写进了普通 `async` 函数 `_build_generation_context`（该函数 `return` 5 元组），导致 `SyntaxError: 'return' with value in async generator`、模块整体不可导入；现改为由异步生成器 `gen_one`（两个调用分支）flush，语义不变。

### 14.2 事实 `_render_facts_text` 三态账本

| 结局 | 判定 | 记录位置 |
|---|---|---|
| **完整注入** | 实际进入文本的事实正文长度 == 原始长度 | 仅计入 `injected_titles`，不产生截断明细 |
| **截断注入** | `kept_chars < original_chars`（单条 `per_fact` 或预算分配切片） | `truncated_out`→`truncated_facts`，`audit_entries` 中 `status="truncated"` |
| **整条丢弃** | 分配额度为 0 / 组标题超预算 / 尾部 room 为 0 | `audit_out`→`budget_dropped`，`audit_entries` 中 `status="dropped"` |

- **字符口径**：`original_chars = len(content)`（未切片前的事实正文）；`kept_chars` 只算**真正进入文本的事实正文**（扣除 requirement 口径前缀与低置信度前缀，按实际 `_body_slice` 长度计算）；`dropped_chars = original - kept`。
- **恒等式**：`complete_injected_count + truncated_count + budget_dropped_count == ledger_rows_total`。`ledger_rows_total` 为渲染器 `prepared` 行数（逐章相关性预筛/坏行剔除后的真实账本行数）；带 `leaf` 时它可能小于调用方传入的 `rows_total`，故新增该字段而不复用 `rows_total`。
