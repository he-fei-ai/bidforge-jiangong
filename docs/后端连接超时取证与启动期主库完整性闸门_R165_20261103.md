# R165 · 「后端连接超时（30s 无响应）」取证收口 · db.py 启动期主库完整性闸门

> 日期：2026-11-03（取证 2026-11-02 深夜 ~ 11-03 凌晨） · 用户指令：读取后台运行日志，定位正文生成时
> 「后端连接超时（30s 无响应）：请确认后端服务是否正常运行（可查看 logs/backend.log）」的 BUG 并修复。

## 一、取证链（logs/backend.log，2026-10-29 ~ 11-01）

1. **症状定位**：文案出自前端 `frontend/src/api/index.ts` `sseFetch/sseGetStream` 的
   **建连阶段 30s 超时**（响应头 30s 未到达）。正文生成 SSE 路由在返回
   `StreamingResponse` 前已有 DB 装配查询/注册写（sse_handlers:5596 起）；
   DB 层 `busy_timeout=15s` —— 预流阶段 ≥2 次写各等满 15s 即突破前端 30s 建连窗。
2. **日志铁证（2026-11-01）**：
   - `15:28:12 WARNING db: WAL 自愈：丢弃 WAL 后主库仍损坏，还原备份: ('wrong # of entries in index idx_system_logs_trace',)`
     —— **主库自身早已损坏**，且发生在自愈尝试之前；
   - `18:58:49` 起每个请求：`system_logs 写入失败（fail-soft）: database disk image is malformed`（188 条）；
   - `19:00:18 / 19:00:52`：`save-outline`/`PATCH schemes` → `sqlite3.OperationalError: database is locked`；
   - `19:00:55 / 19:01:56`：`POST /sse/generate-content/...` →
     `RuntimeError: database disk image is malformed`（sse_utils.with_heartbeat 上抛）。
3. **损坏范围（对 36MB 主库副本跑 `PRAGMA integrity_check`）**：
   `system_logs` 表（root 5675，"Child page depth differs"）+ `idx_system_logs_level`
   （root 5713，"2nd reference to page ×N"）+ 四个 system_logs 索引
   （"wrong # of entries"）；sections/schemes/projects/task_registry 等业务表全部完好。
4. **既有自愈为何没接住**：`db._self_heal_corrupt_wal` 第一道闸是
   `if not wal.exists(): return False` —— **无 WAL 就完全不探测**；而主库损坏
   （本次 -wal 为 0 字节）恰在该盲区里静默运行数小时。

## 二、根因结论

- **直接根因（数据面）**：`system_logs` 表/索引 B 树结构性损坏（"2nd reference to page"
  属经典页双重引用损坏；本库在 USB 外置盘 J: 上，历史轮次 R27 已有同类先例）。
- **放大器（代码面 · 本轮修复点）**：启动自愈只覆盖「WAL 损坏」形态，主库损坏
  **零探测、零告警**，应用带病运行 → 每请求 fail-soft WARNING 刷屏、普通写路径
  `database is locked`、SSE 生成链路 `RuntimeError`，前端只看到误导性的
  「后端连接超时（30s 无响应）」，运维无法从启动日志得到可行动信号。
- 现场备注：取证期间工作树已切到 master 线（易标 G1/G2/G3），live 库已于 11-02 14:37
  由并行会话重建（integrity ok）；`system_logs`/observability 子系统在 r126+ 分支线，
  master 不存在 —— 故本轮代码修复落在**两条线共有的 db.py 启动自愈缺口**上。

## 三、修复（master · `backend/app/db.py`，加法式）

新增 `_startup_db_integrity_gate()`，接线在 `init_db()` 最前（WAL 自愈之后）：

1. **零成本放行**：`PRAGMA quick_check(64)` 完好（唯一返回行 `ok`）→ 直接返回；
2. **范围归属**：错误消息只认三种可判别形态（`Tree <root> page ...` /
   `wrong # of entries in index <name>` / 无前缀 `page <n>`），经 `sqlite_master`
   rootpage→(type, name, tbl_name) 映射归属到**所属表**；任何一条归属失败
   （业务表、freelist、schema 页、无法解析）→ **绝不触碰**，WARNING 点名保持原状；
3. **可再生重建**：全部错误归属到白名单 `_REGENERABLE_CACHE_TABLES`
   （封闭集：`consistency_scan_cache` / `export_cache`，均为设计上可丢弃的缓存表）
   → 先备份 主库+WAL+SHM 到 `data/recov_bak_<ts>_gate/`，移走 WAL/SHM 防回放污染，
   DROP 表（索引级联）+ 按 DDL 重建 → 复检 quick_check 全绿才收工；
4. **不雪上加霜**：备份失败 / DROP 或建表失败 / 重建后复检仍有异常 →
   还原备份逐字节回滚，保持原状让应用以原始错误暴露根因；
5. **逃生开关**：`DB_INTEGRITY_GATE=0` 完全禁用（逐字回退旧行为）。

修法纪律：只有可丢弃缓存允许进重建白名单（表头注释显式禁止业务表进入）；
错误数达探针上限（64）即视为范围无法确证、放弃自愈。

## 六、成因定罪（遗留①收口 · 2026-11-03 取证）

Windows 事件日志（System；取证脚本 `artifacts/r165/forensics_eventlog.ps1` /
`forensics_count.ps1`）：

- **直接事件**：`2026-10-31 18:26:09` 同一秒内三连 ——
  1. `disk Id=51` 寻页错误风暴（`\Device\Harddisk5\DR5`，同秒数十条重试）；
  2. **`Microsoft-Windows-Ntfs Id=140`：「系统无法将数据刷新到事务日志。可能发生损坏：
     VolumeId: J:，DeviceName: \Device\HarddiskVolume13」**（"可能发生损坏"级显式告警）；
  3. `Ntfs Id=50 {延迟写入失败}`：`J:\$Mft` 与
     `J:\编程\专项方案工具箱\backend\tests\__pycache__`（事发时有 dev/test 进程在写 J:）。
- **佐证**：当晚 17:30:45 → 18:26:11 → 18:37:23 → 19:24:07，J: 卷设备号
  Volume13→14→15→16 连续变更 4 次 = USB 盘反复掉线重挂。
- **DB 头部法医学**（偏移 24 change_counter / 92 version_valid_for）：损坏副本
  （11-01 16:12）、15:28 自愈备份、当前健康库三者均 change_counter == version_valid_for
  （非撕裂头部）⇒ 损坏在**索引/表内容页**，与「事务日志刷新失败丢失特定数据页」形态吻合。
  15:28 备份 quick_check 同报 `wrong # of entries in index idx_system_logs_trace`
  （change_counter 3523 < 损坏副本 3541）：损坏先于自愈尝试，且 15:28→16:12 间仍有
  18 次成功写（损坏页未被触碰，属**潜伏损坏**——写操作绕开坏页即可继续成功）。
- **风险升级**：disk Id=51 按天计数 **10-31: 54 / 11-01: 502 / 11-02: 558** ——
  J 盘正在持续劣化，同类损坏随时可能复发。

**结论（定罪）**：J: USB 外置盘硬件/链路级故障（丢页 + 反复掉线重挂），于
2026-10-31 18:26:09 的一次事务日志刷新失败中损坏 `scheme_assistant.db` 的
system_logs 索引页；与应用代码无关，但应用此前对「主库损坏且无 WAL」形态
零探测零告警（已由 R165 启动闸门修复）。

## 七、R165b · 运行期完整性巡检（遗留①引出的加固 · 已落地）

取证显示 J 盘持续丢页，而启动闸门只覆盖进程启动时刻、带病长跑的服务对运行期

- pytest / TestClient 进程**不创建任务**（与 R142 同口径，防测试任务泄漏）；任务幂等；
- 零新增配置项（`os.environ` 直读通道，与 A-5/R165 逃生开关同款）。
