## 一、改动清单（文件 / 函数 / 作用）

### 1. `app/config.py`
- 新增 3 个配置项（默认行为不变、向后兼容）：
  - `parse_retry_max: int = 2`（落库瞬时失败最大重试次数）
  - `parse_retry_base_ms: int = 300`（指数退避基数）
  - `parse_retry_cap_ms: int = 3000`（退避上限封顶）

### 2. `app/db.py`（`_migrate`）
- 幂等创建辅助表 `doc_parse_checkpoints`（纯辅助、删除即退回旧行为、无数据风险；遵循 R80 零迁移惯例，新增表走 `CREATE TABLE IF NOT EXISTS`，不在 `SCHEMA_SQL` 内）。

### 3. `app/routers/global_facts_docs.py`
- 新增辅助函数（模块级，R123 标记）：
  - `_load_parse_checkpoint(db, doc_id)` —— 读取检查点。
  - `_save_parse_checkpoint(db, doc_id, stage, status, error, text_cache)` —— 幂等写（INSERT/ON CONFLICT UPDATE），失败可忽略。
  - `_clear_parse_checkpoint(db, doc_id)` —— 成功/force 时清除。
  - `_persist_parse_result_with_retry(...)` —— 落库瞬时失败指数退避重试（调同模块 `_persist_parse_result`，避免模块级未定义的 `_gf` 引用）。
- 改造 `parse_document` 提取→落库→成功块：
  - **断点续跑**：入口先读检查点；若上次 `persist/layers/stale` 阶段失败且缓存了已提取文本，则复用缓存文本跳过代价高昂的重新解析（`force` 先清旧检查点，走完整流程）。
  - **落库重试**：`_persist_parse_result` 返回 False 时指数退避重试至 `parse_retry_max` 次，耗尽仍失败才 503；重试期间记录检查点（缓存文本）。
  - **阶段记录**：extract 成功、persist 成功、layers 完成、stale 完成各写检查点；全成功末尾清除检查点。
  - 既有语义（结构性失败 400 不重试、503 失败、stale 标记、导出缓存失效、截断告警）**完全保留**。

## 三、测试（专项回归）
- 新增 `tests/test_parse_retry_checkpoint.py`（5 例，均 PASS）：
  1. `test_persist_retry_then_success` —— 落库前两次失败、第三次成功 → ok，persist 调用 3 次，检查点清除。
  2. `test_no_retry_on_structural_parse_error` —— 结构化失败（ParseError→400）不重试，persist 不被调用。
  3. `test_checkpoint_resume_skips_extract` —— persist 失败后检查点缓存文本，续跑跳过提取、用缓存文本、成功后清除。
  4. `test_checkpoint_records_failed_stage` —— persist 持续失败 → 检查点 `stage=persist/status=failed` + 抛 503。
  5. `test_force_parse_clears_stale_checkpoint` —— force 清除旧失败检查点、走完整提取（不续跑旧失败态）。
