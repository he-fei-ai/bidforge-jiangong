## 一、全局事实与项目信息提取

### 1.1 易标做法（证据）

- **数据结构 GlobalFactGroupState**：`client/electron/src/types.ts:192`（经《全局事实模块深度探索报告》转述并核实），字段仅 4 个：`id / title / content / updated_at` —— **组级**模型，一组事实一段自由文本（title 是组名，content 是打包的正文）。
- **触发时机与两遍分析**：V1 分段流水线（分段提取→分批合并→知识库 patch→原方案 patch→最终整理）为"两遍分析"的原始载体；V2 收敛为持久 Agent 任务 `globalFactsTaskV2`（工作区文件 + global-facts.json + Schema 校验 + `max_retries: 0`）。V1 在 2026-09-14 版已无调用者（报告核实结论）。
- **合并去重 / 用户编辑**：合并阶段按 key 聚类去重；用户在 UI 直接编辑组 content，`updated_at` 随之刷新。
- **项目信息三分离**：项目概述 / 技术要求 / 评分项来自招标文件解析产物（原始信息），与"本方案统一使用的事实"（全局事实）严格两码事 —— 全局事实是**裁决后的口径**，项目信息是**证据原文**。

### 1.2 本软件现状（证据）

- **表模型是超集**：`backend/app/schema_sql.py:288-344` `global_facts` —— 行级事实（`title/content`）+ 组结构（`group_id/group_title`）+ 四维标注（`category/chapter/fact_attr/source_kind/is_shared/value_kind`）+ `updated_at`。易标的 GlobalFactGroupState 4 字段在本软件全部有对应且粒度更细（行级可单条裁决/溯源）。
- **提取流水线**：`backend/app/services/facts_extractor.py:43-71` —— 分段提取 `CHUNK_SIZE=8000`（段重叠 500、上限 60 段）、段内重试 2 次带 429 长退避；归一化 key 聚类合并去重（L1-11 头注释、`_norm_dicts` 规格/单位/机具名归一）；同 key 多值→矛盾标记→人工裁决（`conflict_arbiter`）。
- **缺值模式对齐**：`backend/app/services/facts_patches.py`（经 `facts_extractor.py:40-41` 注释证实）`normalize_missing_value_mode` 对齐易标 `globalFactsMode`（fabricate/omit/placeholder 三态）。
- **九大章节分类**：`backend/app/services/facts_classification.py`（`facts_extractor.py:36-37` 引入）—— 用户要求的"按九大章节分类适配"**已经落地**（`chapter` 字段）。
- **项目信息**：`backend/app/services/bid_analysis_service.py:157/162/265/304` —— `projectOverview`（项目概述）/`techRequirements`（技术评分要求）/`businessScoring`/`group="scoring"` 均在 `bid_analysis_items` 结构化提取 18 项内，与全局事实表物理分离 —— 与易标"两码事"的同构设计。

### 1.3 判定与理由

**已有且模型更丰富，不引入。** 易标组级 blob 模型若"引入"反而是降级（丢行级裁决/溯源/维度）。唯一差异是易标把"两遍分析"显式化为流水线阶段，本软件以"分段提取+分批合并+矛盾裁决"达成同效，无结构缺口。

## 二、目录与正文如何调用提取内容（核心机制）

### 2.1 易标做法（证据）

- **编排阶段 AI 只看标题**：`contentGenerationTask.cjs:134` `formatGlobalFactTitlesForPrompt(globalFacts)` —— 给 AI 的只是一份**标题 JSON 数组**（不含内容），AI 在章节内容计划里返回 `factTitles`（需要哪些事实）；`normalizeFactTitles` 做白名单钳制（L134 附近，编造标题被丢弃）。
- **生成阶段程序按标题取全文**：`contentGenerationTask.cjs:171` `resolveGlobalFactsByTitles(titles, globalFacts)` → `:2151` `resolveSelectedFactsText(contentPlan, globalFacts)` → `:125` `appendSelectedFactsMessage(messages, selectedFactsText)` —— **AI 挑标题、程序取内容**，注入的是选中组的完整事实文本，且只注入当前章节。
- **编排阶段可见上级/同级**：`contentGenerationTask.cjs:832-849` `buildChapterContentPlanMessages` —— 编排请求携带上级章节链与同级章节，用于判断"本章需要哪些事实、避免与邻章重复"。
- **目录生成读事实**：经《目录生成模块深度探索报告》核实，目录阶段读取项目概述+全局事实标题层，影响章节裁剪（结构层面，不逐字引用）。

### 2.2 本软件现状（证据）

- **D1 编排已在，但输出不驱动注入**：`backend/app/services/content_plan.py` —— 编排产出 `{writing_focus, knowledge_names, fact_titles, table_needed}`，注释明确"**只做软建议不硬限制，回避 R57 预编排陈旧结论陷阱**"；调用点 `backend/app/routers/sse_handlers.py:6530-6739`（`plan_section_content`，`fact_titles` 候选池 = 程序预筛出的 `_f_pool`），产出的 `_plan_guidance` 仅作为文字提示拼进任务段。
- **实际注入走另一通道**：`sse_handlers.py:6530+`（R58）—— 程序按 2-gram 相关性预筛事实 → `core_facts`（进稳定前缀）/`rest_facts`（进任务段）分段注入，预算 `fact_injection_audit`（总量 6000 / 单条 300）。**编排 AI 选没选某条事实，与它最终是否被注入、以什么粒度注入，没有因果关系。**
- **默认关闭**：`backend/app/config.py:700-755` `content_plan_stage_enabled=False`（D1 整条编排链路默认关）。

### 2.3 判定：缺口 G1（部分）

本软件缺的是易标的**闭环**：`编排挑标题 → 程序按标题取完整事实 → 强注入当前章节`。现状是"程序预筛决定一切、AI 编排意见被降级为软文字"。差异的真实影响：
1. 编排关（默认）时完全靠 2-gram 预筛 —— 语义相关但字面不同的事实（如"混凝土强度等级 C35" vs 章节写"主体混凝土标号"）可能漏注入；
2. 编排开时 AI 判断被浪费 —— 选中标题没有获得"全文必注入"的待遇，仍受 6000/300 预算截断（`per_fact=300` 会把一条完整事实截成残段）。

**这正是用户引用 citation:10 强调的核心机制，列为第一引入候选。**

## 三、上下文注入机制

### 3.1 易标做法（证据）

- 注入函数：`contentGenerationTask.cjs:116` `appendGlobalFactsMessage`（"全局事实变量（正文涉及时优先使用这些变量值，避免各章节随机变化）"）、`:125` `appendSelectedFactsMessage`。
- 装配顺序（`:888-967` `buildChapterContentMessages`）：system（16 条硬约束）→ 项目概述 → preSectionInstruction → selectedFacts → 知识库素材 → 用户额外要求 → 编排决策 → **当前章节任务放最后** → 字数要求 —— 稳定在前、易变在后，为 Provider Prompt Cache 命中服务。
- 硬约束第 15/16 条（`:913-914`）：① 提供了事实变量必须优先使用、不得前后矛盾；② 未提供时**不要主动编造具体人员、周期、质保、品牌、型号**。

### 3.2 本软件现状（证据）

- **稳定前缀**：`sse_handlers.py:6530+` R57 注释"稳定前缀"—— system/项目概述/核心事实在前，当前章节任务在后（与易标同序）。
- **注入内容对照**：project_brief（项目概述）✅；parent_chain / sibling_lines（上级/同级）✅；事实分段注入（core/rest）✅；图表意图：本软件以 `chart_predictions`（`routers/export.py:1095` 消费）承载"配图/图表意图"，✅（形态不同、语义对应）。
- **硬约束**：`backend/app/services/ai/prompts/content.py:82-83` —— "提供的全局事实必须优先使用、不得矛盾"与"未提供不得编造人员/周期/质保/品牌/型号"逐条对应（本软件还多出数据真实性红线段 L336 附近）。
- **审计兜底**：`backend/app/services/input_coverage.py:1-42` —— 已调用/缺失/截断三态差集台账，易标无对应物（本软件更强）。

### 3.3 判定：已有，不引入

注入**通道**本软件齐备且带审计；G1 缺的是"注入**内容**由编排决定"，属机制二范畴，不构成机制三缺口。

## 四、正文按目录顺序生成的连续性

### 4.1 易标做法（证据）

- 目录生成写 `sort_order`，正文只读；`collectLeafContexts`（`contentGenerationTask.cjs:2080-2091`）DFS 产出叶子 + `parentChapters/siblingChapters`；按目录树顺序分批、批内并发批间串行；暂停/恢复不丢已完成（`completed_stages` 断点续生成，报告核实）。

### 4.2 本软件现状（证据）

- 目录表含 `sort_order`（生成侧只读，与易标同契约）；SSE 生成走**窗口式调度器**（并发 1~5 自适应，`sse_handlers.py` 生成主链路），按 DFS 序取叶子；`backend/app/services/task_registry.py` 提供暂停/恢复/停止；逐章生成即落库（`word_count/status` 随写），重跑按已完成章节跳过 = 断点续生成；`backend/app/services/content_runtime.py` `should_continue_round` 控制单节续写轮。
- 历史轮已核对：本软件"落库/展示/导出顺序一致"在 R 系列轮次多次验证（AGENTS.md R117-R121 导出链取证）。

### 4.3 判定：已有，不引入

易标"批内并发批间串行"与本软件"窗口调度"是同一目标的两种实现（前者固定批、后者滑动窗），本软件实现在 provider 限流自适应上（`provider_factory` 全局信号量）甚至更稳，不做改造。

## 五、正文与全局事实/项目信息高度吻合

### 5.1 易标做法（证据）

- 生成前：全局事实统一数据源、关键数据禁各章独立编造（硬约束第15条 `:913`）。
- 生成中：上级/同级注入防重复断裂（编排层 `:832-849`；生成层 R102 同族机制）。
- 生成后：一致性审计（见机制六）。
- **覆盖率审计（扩写模式）**：原方案分段最大 6000 字符（常量 `ORIGINAL_PLAN_SEGMENT_MAX_CHARS=6000`，`contentGenerationTask.cjs:28-45` 常量区），逐段验证覆盖，缺口修复最多 2 次（`ORIGINAL_COVERAGE_REPAIR_MAX_ATTEMPTS=2`）。
- **最小字数循环**：单节不足→扩展，最多 3 轮（`MAX_WORD_ADJUSTMENT_ROUNDS=3`）；**成稿级批量调度批大小 10**（`TOTAL_WORD_ADJUSTMENT_BATCH_SIZE=10`，同上常量区）。

### 5.2 本软件现状（证据）

- 生成前统一数据源 ✅（global_facts + 软建议注入，G1 另计）；生成中防重复 ✅（parent_chain/sibling_lines + R102 `content_prev_leaf_context=True`，`config.py:700-755`）。

- 覆盖率审计 ✅：`input_coverage.py:9-22`（build_inventory + audit_prompt_coverage 差集三态）——语义覆盖易标"分段验证覆盖"，且为台账化而非修复计数式；单段预算截断告警在本软件为 WARNING+REST 查询而非"修复≤2次"循环，差异属实现风格，不列为缺口。
- 单节字数循环 ✅：续写（`content_runtime.py:319-341`、R66 触发线 `max(0.8×预算, min(300,预算))`、轮次封顶）+ 缩写（`content_shrink.py:29-30` `SHRINK_MAX_ROUNDS=3`、`SHRINK_SETTLE_RATIO=1.15`，头注释 L4 明确对齐 OpenBidKit buildWordAdjustmentMessages）；生成链路内自动压缩调用点 `sse_handlers.py:7080-7082`。
