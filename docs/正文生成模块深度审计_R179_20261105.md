### 2.2 工作流程

1. `POST /schemes/{id}/generate-content` 进入 `generate_content`，解析 `mode/section_id/concurrency/word_budget`，注册任务与并发闸门。
2. 查询目录叶子 → 构建每章上下文（系统提示词 + 本章事实 + 前章摘要 + 图表规范 + 编号约束）。
3. `_generate_first_draft` 调 `chat_with_fallback(scene="content_draft")`；不足预算进入 `_continue_if_needed`（`scene="content_continue"`，最多 `CONTENT_CONTINUE_MAX_ROUNDS` 轮，8s 去重窗口 8000 字）。
4. `_persist_section`：围栏归一（`auto_fix_unclosed_fences`）→ 质量审计 → 图表登记/删坏块 → 小节编号规范化 → 生成标准校验 → 事实冲突定点修复 → 段落结构/字数收尾/注入审计 → 落库并回填 `report_json`。
5. 逐章 `section_start` / `section_stage` / `section_done|section_error`，终态 `completed|degraded|stopped|error`；每章检查点在终态/停止/断连时写入。
6. 前端按事件更新日志与进度；SSE 断线后 `pollTaskUntilTerminal` 认领终态并从 `content_result` 恢复失败明细。

### 2.3 AI 调用与提示词

- 正文提示词注册键 `content_generation_system`（content.py L73），含：图表与正文一体生成（L191 起）、每节最多 1 图、触发词/排除场景、段落/列表格式约束（L165、L169）。

## 4. 修复项清单

### FIX-1 列表样式被拍平（后端 · `backend/app/services/content_shrink.py`）

- **改了什么**
  - 新增 `_LIST_LINE_RE`（L43）：无序 `-/*/+`、有序 `1.`/`1)`/`1、`、中文括号 `（1）/(1)`。
  - 新增 `_collect_list_ranges`（L48）：连续列表项 + 缩进续行合并为**一个**保护区间（与表格同构，防碎片绕过）。
  - `collect_protected_ranges`（L80）合并列表区间；拒绝文案扩展为「…代码块或表格、列表」（保留旧前缀，兼容既有断言）。
- **为什么**
  - 旧保护区只含围栏/表格/图片；AI 压缩操作 `delete/replace` 可命中列表行，导致列表被压成一段散文（层级丢失、导出成稿出现「1. xxx 2. xxx」连排）。列表是结构元素，应与表格同属压缩禁区。
- **如何验证**
  - 新增 5 例：无序列表/有序+括号编号/缩进续行均落入保护区；删除列表项、跨列表替换被拒；列表前后普通段落仍可压缩。
- **测试结果**：`tests/test_content_shrink.py` 由 9 → 15 passed，0 failed。
- **向后兼容**：不改任何现有保护语义；仅扩展禁区。列表章节可能压缩不动，此时按既有「宁可超字数不可损坏正文」策略返回原字数口径，不改正文。

### FIX-2 日志延迟错位（前端 · `frontend/src/utils/contentEvents.ts` + 测试）

- **改了什么**：`upsertSectionLog`（L295）由 `[...filter, item]`（更新即移动尾部）改为「按 `section_id` 定位 → 原位替换；不存在才追加」。
- **为什么**
  - 日志面板倒序渲染（`SectionLogList.tsx` L48–54）。旧实现下每次 `section_stage/section_done/section_error` 都把该章顶到最上方，已完成的后继章被反复下压，章号顺序随事件到达时间跳动——即「日志延迟错位」。
- **如何验证**：重写 `contentEvents.test.ts` 的 `upsertSectionLog` 组：
  - 新增项仍追加（尾部=最上方）；
  - 替换保持原位置（旧语义 `[b,a]` → 新语义 `[a,b]`）；
  - 返回新数组、不原地改入参；
  - 连续阶段更新顺序稳定。
- **测试结果**：`contentEvents.test.ts` 通过；正文域前端 79 passed / 0 failed。
- **向后兼容**：纯前端展示顺序，SSE/接口/数据字段零变更。

### FIX-3 未闭合围栏吞正文不可见（后端 · `backend/app/routers/sse_handlers.py`）

- **改了什么**
  - `_persist_section` 内 `_swallowed` 提前初始化（L3044），继续汇总 `swallowed_prose`（L3055）。
  - 在报告收尾阶段新增 warning issue（L3354–3379）：`code="fence_swallowed_prose"`、`message="未闭合围栏自动补齐后，仍有 N 行疑似正文被困在代码块内，请人工核对本章成稿"`，并 `warning_count += 1`。
- **为什么**
  - `auto_fix_unclosed_fences` 只能在文末补闭合，救不回已被当代码吞掉的正文（content_utils L665–668 明确此限制）。旧实现只写 `backend.log`，前端「质量告警/生成标准校验」Popover 完全看不到，用户误以为已修复。
- **如何验证**：新增端到端用例 `TestSwallowedProseVisibilityR179`：桩 AI 返回「未闭合 mermaid 围栏内夹中文正文」，断言 `section_done.standard_report.issues` 含该 code 且 `warning_count>=1`，同时原围栏补齐仍生效。
- **测试结果**：`test_content_fence_contract_20260929.py` 14 → 15 passed。
- **向后兼容**：仅当 `swallowed>0` 时新增 issue；`passed` 仍由 error 决定；不改正文、不进修复链路、不改事件字段名。无围栏吞正文的章节报告与改动前逐字节一致。
