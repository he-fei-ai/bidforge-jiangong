## 1. 缺陷定稿

### 1.1 FIX-8（P1 · 后端）白名单式透传 —— 同一反模式在**同一函数**上复发

`outline_library.apply_library_and_save` 的返回体是**手写白名单**，逐个挑选
`_save_outline_to_db` 的回传字段。白名单每加一个新键就漏一次：

| 时间 | 新增的加法式键 | 是否透传 |
|---|---|---|
| 2026-09-30（P1-7） | `cleared_content_sections` | ✅ 当时补上了 |
| R79（C3） | `generic_residual`（**明细清单**） | ❌ **又漏了** |

后果：套用目录库命中占位标题时，`_save_outline_to_db` 算出了明细、
`attach_generic_residual` 也打了 WARNING 日志，**用户界面零感知**。

> 这正是 AGENTS §4.14 反复记账的「**同一返回契约在 2 处各自使用、改一处漏一处**」
> 在**同一行代码上**的第二次复发。上一次已为此加过注释，注释防得住人、**防不住下一次新增**。

### 1.2 FIX-9（P1 · 前端）套用目录库消费点**两个键都不读**

`SchemeWorkbenchPage` 的 `applyAndSave` 消费点（`:7862`）拿到响应后直接
`msg.success`，**既不读 `cleared_content_sections` 也不读 `generic_residual`**。

而该函数的**自身注释**（`:7860-7861`）明写「套用是**整表重建**，已有正文不保留」——
即它**会级联删除已生成正文**，而后端为这件事专门量化回传了 `cleared_content_sections`。
前端不读 ⇒ **用户静默丢正文**（AGENTS §4.13 第 6 条 P1-7 想修的那个洞，在这一个点上从未修好）。

### 1.3 FIX-10（P2 · 测试基础设施）R87 护栏本身在并行负载下假红

R87 新写的 `outlineNumberingR87.test.ts` 有 **5 处** `await import("../pages/SchemeWorkbenchPage")`。
该页面组件 12k+ 行，每个用例各自付一次模块图 transform 成本，撞上 vitest **默认 60s**
用例超时即假红。

实测证据：与另一文件并跑 → 本文件 **93s**、该用例 `Test timed out in 60000ms`；
**隔离跑 8.72s 全绿**。⇒ 隔离绿、全量红属负载 flake，但** flaky 护栏仍是护栏自身的缺陷**
（AGENTS §4.22.8「护栏判据/结构有问题比不写更糟」）。

修法：合并为**一次 `beforeAll` 预热 + 显式 120s 超时预算**，并加一条
「预热确实完成」的用例（防 `formatOutlineTitle` 为 `undefined` 时断言恒假的空转）。
**实测 95s → 31.5s（与另一文件并跑），且超时不再可能触发。**

## 2. 落点

### 2.1 FIX-8 · 生产方声明一次（`sections.py`）

```python
SAVE_OUTLINE_ADDITIVE_KEYS: tuple[str, ...] = (
    "cleared_content_sections",   # 整表重建清除了多少章已生成正文
    "generic_residual",           # 检出占位/泛化标题的明细
    "roots_locked",               # 一级章节是否已锁定
)

def passthrough_additive(result: dict) -> dict:
    """挑出 `_save_outline_to_db` 的**加法式回传键** —— 唯一透传口径。"""
    return {k: result[k] for k in SAVE_OUTLINE_ADDITIVE_KEYS
            if result.get(k) is not None}
```

消费方（`outline_library.apply_library_and_save`）改为 `**passthrough_additive(result)`，
**删掉两段手写 `if result.get(...)` 条件 splat**。

关键取舍：
- **判据用 `is not None` 而非真值** —— `if result.get(k)` 形态会把 `0` / `False`
  当缺省丢掉；`cleared_content_sections == 0` 是**真实信息**（清空目录但没正文可清）。
- **不并入基础契约键**（`ok` / `count` / `tree`）—— 它们是响应骨架、允许按名直取；
  硬禁会逼后来者把骨架也塞进 helper，反而更糟。

### 2.2 FIX-9 · 前端消费点接线

```tsx
const { data } = await outlineLibraryApi.applyAndSave(lib.id, { scheme_id: id });
msg.success(`已套用「${lib.name}」，共 ${data.count || 0} 个章节`);
notifyClearedContent(data);     // R88 新增
notifyGenericResidual(data);    // R88 新增
```

两函数 R86 已建并有纯函数护栏，本轮只**接线**、不改其行为。

## 7. 可复用的三条判据

1. **「加法式契约」的正确方向是「生产方声明一次」**。
   白名单式透传 = 「消费方逐个挑选」= 每加一个键漏一次；本仓已因此漏了两次
   （`cleared_content_sections` 修好后 `generic_residual` 又漏）。
   ⇒ 消费侧用 `**passthrough(result)` + 常量清单，**并用反向锁禁止手写挑选长回来**。

2. **计数型护栏对「同时缺失」完全失明**。
   `notifyClearedContent 计数 == notifyGenericResidual 计数` 在**两个通知同时没了**的点上
   恒成立 —— 而 R88 FIX-9 修的恰恰就是这种点。⇒ 凡「成对出现」类契约，
   必须补一条**按位置**判据（定位到具体消费点），计数相等只能当**辅助**。

3. **判据既不能过宽也不能过严，两个方向都要避免**。
   本轮 B/C 组首版三次假红都不是源码缺陷而是**判据选错对象**：
   看右值而非目标、漏扫第二条返回出口、禁掉合法的骨架键直取。
   ⇒ 判据锚定的必须是「**该义务真正所在的那个对象**」，且**反向锁与正向锁要成对**。

## 8. 运维

- 需重启后端（`sections` / `outline_library` 常驻）；前端**需重建**（页面改动）。
- **无需清库**：零 DDL、零数据迁移、零新增配置项。
- 行为变化（均为**加法式**，既有消费方不受影响）：
  套用目录库命中占位/泛化标题时，响应新增 `generic_residual`，前端弹**可操作明细**
  （含原文标题，用户可直接据此改名）；若本次套用清除了已生成正文，前端**明确提示**
  「已清除 N 章正文」。无残留时响应**逐字不变**。
