## 三、模块结构探查（11 维度）

### 3.1 功能架构（分层）

```
HTTP/SSE 层   routers/sse_handlers.py（9566 行，生成主闭包 + 终态收尾 + 进度）
              routers/sections.py（正文读写/重置）、routers/tasks.py（状态/控制）
业务层        services/content_runtime.py（生成调度/检查点）
              services/content_utils.py（围栏/清洗/字数）、content_polish.py（sanitize + quality_issues）
              services/numbering.py（小标题编号）、content_format_contract.py（七类格式自检）
              services/content_progress.py（阶段模型/权重/推送节流）
              routers/_chart_pipeline.py（图表计划 + 锁内 apply）
存储层        sections.content / section_charts / content_checkpoints / tasks / export_cache
前端层        pages/SchemeWorkbenchPage.tsx（11369 行，**线上主路径**，内联 SSE 消费）
              hooks/useContentGeneration.ts（286 行，第二条 SSE 消费链路，当前仅被测试引用）
              utils/contentEvents.ts（归一/终态判据）、utils/taskPolling.ts（终态轮询单一实现）
```

### 3.2 工作流程（一次「一键生成全文」）

1. 前端 POST `/sse/generate-content/{scheme_id}`（`sseFetch`），后端创建 task，记录并发档位、字数预算、`regenerate_requirement`、`task_standard`。
2. `generate_content` 为本次任务建**独立 Semaphore**；`guarded_gen` 内 `wait_resume()` **先于** `acquire()`（暂停时不占并发槽位）。
3. 章节任务按 `_dispatched_order` 派发 → `gen_one`：上下文装配 → 分阶段模型调用（context/draft/continue/persist）→ 字数/续写 → `_persist_section`。
4. `_persist_section` 按**既定顺序**做自动修复与自检（顺序不可调换：先归一再质检、先事实修复再重建图表配对、最后锁内写库）。
5. `_persist_and_notify` 校验后发 `section_done`（携带 `content/quality_issues/chart_count/charts_dropped[_count]/generation_standard/standard_report/word_*` 等）。
6. 全部完成 → 终态三拼装点之一（`_content_ckpt_payload` / `_stopped_payload` / `_error_payload`），顺序固定为 **checkpoint → finish_task → yield 终态事件**；`finally` 内断线兜底 + `asyncio.shield(settle_global_conn("content_finally"))`。
7. 前端收终态：`isTerminalContentEvent` → 收敛 running 日志 → `load()` 回读正文。

### 3.3 AI 调用与提示词

- 阶段模型：`content_progress.STAGE_MODEL`（context / draft / continue / persist），每阶段有独立 expect（用于进度外推）。
- 场景登记：`provider_factory.KNOWN_SCENES`（R137 已补 `outline_agent` / `content_agent_repair`）；正文主链路走场景化配置，未登记路径只能共用主配置。
- `content_agent`（正文 Agent 修复）默认关闭（`content_agent_repair_enabled=False`），**不在主链路**，故不构成本轮回归面。

### 3.4 SSE 流式生成

- 有界队列 `maxsize=1000` + `DONE_SENTINEL`：**只靠哨兵 break**（去掉 `queue.empty()` 竞态），生产端/消费端全链路阻塞式 `await put/get` 形成天然背压。
- 事件族：`task_start / section_start / section_stage / section_partial(progress) / section_done / section_error / stats / consistency_* / degraded|completed|stopped|error`。
- 终态判据单一事实源：`contentEvents.isTerminalContentEvent`（含 `degraded`）—— 页面与 hook 共用。

### 3.5 进度体系（本轮重点核查项）

| 机制 | 实现 | 作用 |
|------|------|------|
| 阶段内插值 | `_section_partial`：`base + span × elapsed/expect`，封顶 85% | 长章节不假装完成 |
| 阶段时长校准 | `_calibrate_stage_expect`：EMA(0.3)，5–600s 夹紧，**仅在阶段切换点**更新 | 首章慢不永久拖累 |
| 加权汇总 | `_weighted_progress`：`SECTION_PHASE_MAX=0.95 × (done + Σ进行中本章比例)/total` | 完成前永不 100% |
| 不可回退 | `_monotonic_progress(prev,new)` | 断线重连 / 阶段回跳不倒退 |
| 统计推送 | `_snapshot_stats` + `STATS_PUSH_INTERVAL=3.0s`（eta_ms 按阶段有效进度外推、avg_section_ms 秒→毫秒统一） | 前端 ETA 稳定、不抖动 |

### 3.6 日志展示（前端）

- 页面：`createSseBatcher`（rAF 合批）+ `setReviewTick` + 选中章节实时刷新；`pickStats`/`statsEqual` 防「同值 setState」渲染抖动。
- hook：逐事件 `upsertSectionLog`，`section_done` 装配 `chart_yield / quality_issues / generation_standard / standard_report`（**R139 修复前缺 `chart_yield`**）。
- 终态统一收敛：`finalizeRunningLogsIn` / `mergeFailedSectionsInto`。

### 3.7 数据链与存储

`sections.content`（正文）→ `section_charts`（图表行）→ `content_checkpoints`（断点/失败明细）→ `tasks`（终态）→ `export_cache`（导出缓存，key 含正文指纹）。

### 3.8 路由与接口

`POST /sse/generate-content/{scheme_id}`（流式）、`GET/POST /sections/*`、`GET /tasks/{id}`、`POST /tasks/{id}/control`、`POST /export/check`、`POST /export/docx`。

### 3.9 图表同步

- 锁外 `build_inline_chart_plan`（每节 ≤1 + 全方案同类型限额 + 校验失败删块 + `_apply_chart_fence_edits` 按**围栏序号**精确编辑，不按文本匹配）。
- 锁内 `apply_inline_chart_plan` 复核；`insert_failed` / `insert_none` 进 `skipped_types` 并**裁剪正文占位**（防「图号虚跳」/「渲染失败占号」）。
- 删图理由为**封闭枚举**（`per_section_limit / scheme_type_limit / validation_failed / missing_prompt / empty_envelope / invalid_json / insert_failed / insert_none`）→ 前端 `normalizeChartYield` 归一展示。

### 3.10 编号与格式

- `normalize_section_content_subheadings`：正文小标题重排；**围栏代码块内的 `#` 行不参与编号**（`_from_fence`，R118 修「编号虚跳」）。
- `validate_section_content_numbering`：显式 `skipped` 而非静默通过；跨章编号由目录/导出侧统一。
- 格式契约 `content_format_contract` **七类**自检（未闭合围栏 / 图表块 / 表格 / 公式 / 标题层级 / 列表 / 引用），在 `_persist_section` 内先于写库执行。

### 3.11 容错 / 缓存 / 并发 / 配置

| 维度 | 结论 |
|------|------|
| 容错 | 单章异常 → `section_error`（不中断整批）；`continue_failed` 显式下发；终态 `degraded` 与 `completed` 分离 |
| 缓存 | 导出缓存 key = 正文/标题/层级/前端渲染像素/导出器版本 ⇒ **改正文必然 miss**（「缓存未失效」已闭环） |
| 并发 | 每任务独立 Semaphore；暂停不占槽；`_dispatched_order` 保证派发可追溯 |
| 配置 | 本轮**零新增配置项**（详见 §十三） |

- 后端：pytest（`-p no:randomly`）+ 大量 `test_r*_*.py` 定点护栏 + `_ab_*.py` 变异脚本。
- 前端：vitest + jsdom + RTL；源码锚（`import.meta.glob(?raw)`）用于「结构性判据」；`--hookTimeout` 对巨型页面动态 import 敏感。

## 七、修复项清单（3 项，均在前端 hook）

> **共同根因**：正文生成前端有**两条 SSE 消费链路**——页面内联版（线上主路径）与 hook 版。页面版逐轮加固，hook 版长期只被测试引用，**没有跟随演进**，形成「同一次操作、两种结果」的字段级漂移。

### FIX-1 · 断线重连收敛到单一实现（P1）

- **文件**：`frontend/src/hooks/useContentGeneration.ts:232-247`
- **现象/根因**：旧实现是文件内联的 `new Promise(() => { const poll = async () => { … setTimeout(poll, 3000) } })` **无上限递归**。后台任务若永不进入终态（僵尸任务 / 状态列陈旧），`await` 永不返回 → `finally` 不执行 → `setGenerating(false)` 永不发生 → 界面永久「生成中」且不可取消。页面版早已收敛到 `pollTaskUntilTerminalImpl`（`maxPolls=200`≈10min 硬上限、404 立即放弃、`stuckThreshold=3` 的「progress≥99% 仍 running」兜底、`netFailTolerance=5` 瞬时网络容错）。
- **修改**：
  ```ts
  const fin = await pollTaskUntilTerminalImpl(
    taskId,
    async (id) => (await tasksApi.status(id)).data as any,
  );
  if (!fin) {
    msg.warning("未能确认后台任务终态（轮询超时或任务已失效），请稍后在任务列表查看");
  }
  ```
- **向后兼容**：默认参数（3000ms / 200 次 / 3 / 5）与页面版完全一致，无新增配置项；有界退出时**显式告警**，不留「静默卡住」。后续 `fin?.content_result` 逻辑全部走可选链，`null` 安全。

### FIX-2 · `section_done` 装配图表闭环字段（P2）

- **文件**：`frontend/src/hooks/useContentGeneration.ts:124`

## 十五、判据教训归档

1. **「同一功能两条链路」必然漂移** —— 页面版与 hook 版各有独立的事件处理代码，页面每轮加固而 hook 不动，缺陷就只在 hook 上堆积；判据必须做**字段级**对称（只比「处理了哪些事件」会漏掉「字段被丢弃」）。
2. **类型里声明了字段 ≠ 会装配** —— `chart_yield` 可选，编译器不会报「从不赋值」；可空字段须靠**行为级**用例（真实事件 → 深相等）锁，源码锚只能防「整段删除」。
3. **源码锚要断「调用形态」而非「符号出现」** —— 只 import 不调用时旧实现可存活；A2 因此断言 `await pollTaskUntilTerminalImpl(`。
4. **假设必须先用探针打穿再改代码** —— FIX-4 若无探针就会白改 47 行 helper（且引入「删块后重算」的新分支），探针 10 分钟否证，省下一次无依据改动。
5. **A/B 脚本本身也是被测代码** —— GBK 解码失败让「未抓到缺陷」与「抓到了但读不到」表现一致（`CAUGHT=False`）；变异脚本的 I/O 健壮性与断言同等重要。
6. **「环境型假红」必须单跑复验后再定性** —— 基线 R87 失败在并行争抢下是 hookTimeout，单跑 37 passed/86.66s 证实与代码无关；不单跑就会误报回归。
