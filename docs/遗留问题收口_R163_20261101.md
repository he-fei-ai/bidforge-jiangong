## 二、F1 · 删除 `NUL` 环境产物（恢复全仓检索）

- **根因**：PowerShell 的 `> NUL` 重定向把 `NUL` 当作**普通文件名**创建（与 cmd 的设备名语义不同），留下 0 字节文件；Windows 保留设备名使常规 `Remove-Item` / `Get-ChildItem` 静默失败。
- **修法**：走扩展路径 API `[System.IO.File]::Delete("\\?\<repo>\NUL")`（绕过 DOS 设备名解析），删除后 `[System.IO.Directory]::GetFileSystemEntries` 与 `git status` 均不再列出。
- **验证**：删除后全仓 Grep `目录结构不合规，请先修复目录` **正常返回 6 个文件**（此前直接报错退出）。
- **加固建议（未落代码，避免过度工程）**：脚本重定向一律用 `> $null`（PowerShell 原生空设备），禁止 `> NUL`。

## 七、判据教训归档

1. **「维持」也要付取证成本**：9 项维持全部以当前代码/进程实读复验（调用方计数、行数、页面引用、端口探测），不引用前轮结论——判定有时效性。
2. **放宽型标准翻转会让旧遗留项失效**：「L3 旧正文向 L4 迁移」在 R151 是产品决策，在 R162 下**目标不存在**；遗留清单必须随标准翻转重判，否则会长期挂着不可能的待办。
3. **检索工具故障先怀疑环境产物**：全仓 `rg` 报 `os error 1` 的真因是 0 字节 `NUL` 文件（PowerShell 重定向副作用），不是编码/权限问题；Windows 保留设备名删除必须走 `\\?\` 扩展路径 API。
4. **存量不合规要区分「判据放宽可自动消除」与「需生成域编造内容」**：前者零迁移，后者必须走 AI 端点 + 用户确认，脚本不得自动改数据（R151 §4 裁定）。
5. **写进报告的「承诺」必须落成测试锚**：R162 的零迁移结论此前只存在于 docstring 与报告，任何收紧型改动都不会被现有护栏抓住；本轮 3 项不变量锁 + 3 变异 A/B 才把「放宽」变成可验证判据（M1/M2 首版取值范围还踩了「变异幅度小于合法区间」导致 MISSED，按实际区间收紧后才 CAUGHT）。
