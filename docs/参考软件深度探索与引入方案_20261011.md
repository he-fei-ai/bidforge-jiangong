## 0. 关键澄清：用户前提中的反转性偏差（必须首先纠正）

用户在任务书中提出若干"参考软件如何做"的假设，经逐文件取证后，以下三点**与代码事实相反**——它们实际描述的是**本软件（专项方案工具箱）**，而非参考软件：

| 用户假设 | 代码事实（参考软件 `client/`） | 实际归属 |
|---|---|---|
| 招标文件解析"Word 用 docx2python、PDF 用 pdfplumber" | 参考软件 Word 用 `mammoth`、PDF 用 `pdf-parse`+`pdfjs`、`convert.mjs` 导入清单全库对 `docx2python\|pdfplumber` **0 匹配**（`electron/services/doc2markdown/convert.mjs:9-18`） | **本软件** `file_parser.py:749` 用 `docx2python`、`:1045/:1192` 用 `fitz`/`pdfplumber`/`pypdf` |
| 全局事实"按九大章节分类" | 参考软件全库对 `九大` **0 匹配**；事实以可变 `groups`（`facts.category`）组织，非固定九大章（`globalFactsTask.cjs:178`） | **本软件** `scheme_classification.py:NINE_CHAPTERS`、`facts_classification.py:classify_chapter_from_text`、全局事实表 `chapter` 字段 |
| 目录分支用 `branch_id` 稳定关联 | 参考软件全库对 `branch_id` **0 匹配**（该词是用户引入，非代码符号）；"分支"为语义概念 | 本软件亦无 `branch_id` 字段（subagent 检索 0 命中），九大章 `chapter` 即稳定归属键 |

**另外**：参考软件**没有**按"模型强弱/标书长短"切换不同强度模型的分支。所谓"短标书+强模型一次性 / 长标书+普通模型分步 / 弱模型稳定输出"实际由**同一配置模型 + 多阶段状态机 + 宿主确定性校验**共同保证（见 §1.3 / §2.3）。本软件的 `use_stepwise = word_budget > OUTLINE_STEPWISE_MIN_WORDS`（`sse_handlers.py:3614`）+ `OUTLINE_ONESHOT_FALLBACK`（`config.py`，默认 True）是同一思路的等价实现。

## 一、参考软件整体探索报告

### 1.1 整体架构与技术栈

参考软件是 **Electron + React 19 + TypeScript + Vite + Cloudflare Worker** 桌面客户端（AGENTS.md:1-53、README.md:196-230）：

- **桌面端**：`client/electron/`（Main/Preload，CommonJS `.cjs`）提供本地能力；`client/src/`（Renderer，ESM TS）通过 `window.yibiao` 调用。
- **数据**：业务状态权威存储为 `userData/workspace/yibiao.sqlite`；Schema 以 `electron/services/sqliteDatabase.cjs` 为准，变更同步 `sql/workspace_schema.sql`。

- **启动**：`cd client; npm ci; npm run dev`（README.md:175-194）。无 root `package.json`，命令都先 `cd client`。

## 二、目录章节生成思路与工作流程（参考软件）

### 2.1 输入、格式与预处理

入口 `runOutlineGenerationTaskV2`（`electron/services/outlineGenerationTaskV2.cjs:744`）。从 `workspaceStore.loadTechnicalPlan()` 取上游产物并校验前置（`:749` 强制要求技术评分要求 `status==='success'`）：

| 输入 | 来源字段 | 写入 Agent 工作区文件 |
|---|---|---|
| 招标文件解析结果 | `bidAnalysisTasks.techRequirements` / `responseFileRequirements` | `技术评分信息.md` / `响应文件要求.md` |
| 项目概述 | `storedPlan.projectOverview` | `项目概述.md` |
| 原方案 | `storedPlan.originalPlanFile` | `原方案.md` |
| 知识库 | `referenceKnowledgeDocumentIds` → `knowledgeBaseService.readReferences` | `参考知识库/参考资料-N.md` |
| 全局事实 | `storedPlan.globalFacts` | **V2 目录 prompt 未直接消费**（主要用于下游正文） |
| 目录模式/字数 | `payload.outline_mode` / `word_control_options` | 注入 prompt + Schema |

### 2.2 生成思路（三种"模式"的真实实现）

**代码中没有按模型强弱切分支**。三种形态由 `mode + 形态 + 来源约束`决定（全部同一 Pi 模型分阶段）：

- **有技术评分项（默认）→ 完整状态机**：`score-planning → leaf_allocation → children_generation → leaf_adjustment → outline_review`（分步生成长/复杂标书）。
- **无技术评分项** `noTechnicalScoreMode`（`isMissingTechnicalScoreItems` 判定）：跳过 score-planning/leaf_allocation，直接 `createNoTechnicalScoreChildrenPrompt` 一步生成（短/简标书"少阶段"）。
- **技术文件独立成册** `standaloneTechnical`：一级目录直接=评分大项。
- **仅用原方案** `originalOnly`：强制 `ORIGINAL_ONLY_DIRECTORY_RULE`，只从原方案提取补齐。

**层级与编号**：最多 6 级；一级 `1,2`、二级 `2.1,2.2`；一级含 `attr`（通用/商务/资信/技术/其他），子目录不含；叶子必须含 `content_mode`，父节点不得含；任意非叶子 `children≥2`（禁单子冗余）。**编号"图 章-序"式可读编号在导出期**由 `outlineNumbering.ts` 的 `formatOutlineNumber` 生成，**不在生成阶段**（生成阶段 title 只写纯标题，无编号）。

### 2.3 工作流程（状态机）

`piRuntimeService.cjs` 的 `continueTask` 回调按 `workflow_stage` 推进（`:929`）：

```
[initial-outline] → outline.json(一级) → waitForOutlineSelection()(UI 确认)
[outline-selection] → renumberOutline + 锁定 roots
[score-planning | children_generation] → technical-score-groups.json + score-directory-plan.json(+ask-user)
[leaf_allocation] → leaf-allocation.json
[children_generation] → outline.json(完整)
[leaf_adjustment](数量不符, +ask-user)
[outline_review] → outline-review.json(passed/simple_fix/user_feedback/user_refuse)
→ renumberOutline + stripOutlineInternalFields → checkpointTask
```

- **分步生成**：每阶段 Agent 只改"当前应改文件"，其他文件"不得修改"。
- **一一对应模式**：`score-directory-plan.json` 的 `mappings.requirement_id ↔ target_title` 实现评分项↔目录节点对应；`branch_id` 是稳定关联标识（见 §0：该词代码无，为语义概念）。
- **编号统一**：宿主 `renumberOutline`(`:291`) 每阶段末重排点号 id。

### 2.4 提示词（System/User 摘录）

- 初始一级目录 `createInitialPrompt`(`:514`)：要求生成 `{outline:[ROOT_NODE]}`，一级 `id` 连续、`title` 不得含"第一章"等前缀、`attr` 五选一；写完后调 `json-validation`。
- 子目录 `createChildrenPrompt`(`:615`)：叶子必填 `content_mode`（ai-generate/template-fill/point-to-point/other），父节点禁填；`children≥2`；最多 6 级；id 用层级点号。
- 评分规划 `createScorePlanningPrompt`(`:591`)：评分项↔节点逐一同级对应；`branch_id` 重排后仍稳定关联。
- 审核 `createOutlineReviewPrompt`(`:704`)：四维审核（AI 叶子数目标±2、评分覆盖、重复目录、专业合理性）；先完整审核形成问题清单再修。

**期望 LLM 返回 JSON 结构**（Schema `:19-183`）：
- `outline.json`：`{outline:[{id,title,description,attr?,content_mode?,children?}]}`
- `score-directory-plan.json`：`{allow_root_changes, branches:[{branch_id,root_id,mappings:[{requirement_id,target_title,...}]}], extra_titles}`
- `outline-review.json`：`{status, issues:[{category,problem,repair,confirmation_required}], summary}`

### 2.5 校验与修复

三层校验：
1. **JSON + Schema（Ajv）**：`piJsonValidationTool.cjs:57` 用 `Ajv({allErrors,strict})`，Schema 经 `jsonValidationSchemas` 注入。
2. **业务规则（宿主确定性）**：`buildOutlineReviewContext`(`:464`)→`collectOutlineStructure`（深度≤6、无单子、content_mode 合法）、`collectScoreMappingCoverage`（评分项↔标题机械比对）、`countLeavesByMode`（AI 叶子数 target±2）。
3. **语义审核**：Agent 在 `outline_review` 阶段做评分覆盖/重复/专业合理性。

修复：Agent 内"校验失败先改文件再校验"；宿主 `max_retries:0`（靠 Agent 自循环）；Pi 内层 `MAX_RETRIES=3` 自动修复；**仅瞬时 HTTP 错误**退避重试，**无"降级弱模型"**。

### 2.6 输出与存储

TS 类型 `OutlineItem`（`src/shared/types/outline.ts`）；SQLite 表 `technical_plan_outline_nodes`（`sqliteDatabase.cjs:104`）：`node_id,parent_node_id,level,title,description,content_mode,source_requirement_id,source_requirement_title,knowledge_item_ids_json,content`。`technicalPlanStore.saveOutlineData` 经 `flattenOutlineItems`(`:351`) 拍平 upsert。

### 3.2 生成思路

- **逐节生成**：`runOne`(`:4187`) 每叶子独立；原方案扩写走 `buildRestoredChapterContentMessages`(`:969`)。
- **上下文传递**：上级/同级**只在编排阶段**喂 `planOne`（避免重复）；事实编排只传 `titles`，生成时由 `resolveSelectedFactsText`(`:4218`) 展开并要求"优先变量值、不得编造"。
- **字数控制**：`computeGenerationWordTarget`(`:419`) + 生成后 `requestWordAdjustment`(`:4403`)、`adjustSectionToRange`(`:4474`)。
- **质量要求**：system "专业、准确、朴实无华、不假大空、不 AI 腔"。

### 3.3 工作流程

```
目录树 → collectLeafContexts →【正文编排 planAll/planOne】(0-12%) →【原方案还原】(12-18%)
→【并发生成 runContentTargetsWithWarmup/runOne】(18-58%) →【小节字数调整】(58-66%)
→【原方案覆盖审计/修复】(66-73%) →【全文一致性审计/修复】(73-81%)
→【去表格】(81-85%) →【最终复核】(85-90%) →【全文字数】(90-95%)
→【全文图片编排 runIllustrationPlanning】(95-98%) →【图片生成 runIllustrationGeneration】(98-99%) → done
```

- **并发**：`runItemsWithWorkerPool`(`:2639`)，`contentConcurrency` 默认 **10**(`:25`)、`imageConcurrency` 默认 **2**(`:26`)；先分组预热 prompt cache 再并发（`:4342`）。
- **重要纠正**：用户把"判断知识库素材/表格/Mermaid/AI生图"全归"正文编排"。实际 `planOne` 只判**知识库素材/事实变量/表格**三类（`buildChapterContentPlanMessages:807/811/815`）；**Mermaid/AI/HTML 图不在编排阶段**，而在独立 `runIllustrationPlanning` 由 Pi Agent 决定。

### 3.4 提示词

顺序：正文编排 `buildChapterContentPlanMessages:793` → 正文生成 `buildChapterContentMessages:888` → Mermaid 修复 `buildMermaidRepairMessages:173` → AI 生图 `buildAiImagePrompt:75` → 一致性审计 `buildConsistencyAuditMessages:1658` → Agent 修复 `buildAgentConsistencyRepairPrompt:5455`。

正文生成 prompt 强制"**严禁输出 Mermaid/flowchart 等图表代码块**，配图由系统另行处理"(`:906`)。

### 3.5 编排结果数据结构


### 3.6 配图阶段

### 3.7 审核阶段（一致性审计 + 原文覆盖审计）

### 4.5 汇总与引入通道

汇总 = SQLite `technical_plan_*` 持久状态；引入两条通道：

### 4.6 缓存优化
