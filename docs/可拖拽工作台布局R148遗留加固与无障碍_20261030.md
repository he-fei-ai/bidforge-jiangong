## 二、I1 修复方案

### 2.1 手柄（`SplitPane.tsx` 的 `ResizeHandle`）

- **可聚焦**：`tabIndex={disabled ? -1 : 0}`（禁用时不进 Tab 序）。
- **方向键调尺寸**：`onKeyDown` 每次 16px，方向与切分轴对应（横向切分→`←/→`；纵向切分→`↑/↓`），调用既有 `onDelta`（统一走 `clampRatio` 夹紧 + 持久化）。并行会话续接补 `onDragEnd?.()`（R148b）：键盘调整同样落 LocalStorage，与拖拽口径一致，键盘路径不是二等公民。
- **值语义**：新增可选 props `ariaValueNow/ariaValueMin/ariaValueMax`，透传到 DOM。

### 2.2 `SplitPane` 透传值语义

- `aria-valuenow` = `Math.round(ratio * 100)`（首面板占比 %）。
- `aria-valuemin/aria-valuemax` = `clampRatio(0)/clampRatio(1)` 换算百分比（即 px min/max 边界），容器尺寸未知（jsdom/初始渲染）时**省略**（避免无意义 0/100 边界）。
- 复用既有 `clampRatio`，零重复边界逻辑。

### 2.3 Layout region 1（独立手柄）

- 传 `ariaValueNow={sidebarWidth}`、`ariaValueMin={SIDEBAR_WIDTH_MIN}`、`ariaValueMax={SIDEBAR_WIDTH_MAX}`（px 单位，侧边栏宽本来就是 px）。

### 2.4 CSS（`index.css`）

- 新增 `.bp-resize-handle:focus-visible` 焦点环（亮色 `#1677ff` / 暗色 `#00d4ff`），键盘用户能看见当前可调整的分隔条。

### 2.5 护栏测试（`resizablePanelsR145.test.tsx`）

- **H**：横向切分 — `tabindex="0"`、`aria-valuenow="30"`、`ArrowRight` 16px→31.6%、`ArrowLeft` 回 30%。
- **H2**：纵向切分 — `ArrowDown`/`ArrowUp` 方向正确。
- **disabled**：`tabindex="-1"`、方向键不响应、`aria-valuenow/min/max` 透传。
- **测试基建**：`mockRects` 的 `getBoundingClientRect` 改为**从当前 `flex-basis` 推导实际 px**（此前固定 `firstSize`，多步操作后 rect 陈旧导致第二次计算错位）；既有单次拖拽用例读到初始值不变。

## 七、判据教训归档

1. **无障碍是功能需求的一部分** —— `role="separator"` 语义本身就要求键盘可操作性；「能拖但键盘不能调」是隐性缺陷，护栏应断语义（tabIndex/aria-value）而不只是行为。
2. **并行会话活跃时先取证再动手** —— 本轮发现 `SplitPane.tsx` 被并行会话（R148-p）加了双击重置、`SchemeWorkbenchPage.tsx` 被重构（+每 Tab 子布局）、临时 wiring 测试被增删。采样 mtime 确认并行会话静默后才编辑；编辑基于**当前**文件状态（重读而非凭旧上下文），避免覆写。
3. **测试 mock 要与真实布局语义一致** —— `getBoundingClientRect` 固定值会让「多步操作」读到陈旧尺寸（第二轮方向键从旧 rect 计算）。从 `flex-basis` 推导才是忠实模拟；单步既有用例读到的初始值不变。
4. **A/B 变异要断「调用形态」** —— 移除 `tabIndex`+`onKeyDown` 后护栏在 `tabindex` 断言失败（不是行为断言失败），证明语义锁比行为锁更稳（R116/R137 教训再验证）。
