**为什么 ②④ 没有照字面做**：
- ② 若做「预先指定本章画什么图」，必须读 `chart_predictions` 的规划字段 —— 那正是 `sse_handlers.py:4645-4651` 实证注释里被刻意删除的陈旧结论陷阱。

  而规则层已有确定性下界；本轮把它从「命中为空就全量」升级为「整案核心 + 本章专属」的**分段**，既按需又零新增调用。

## 1. F3 · 提纲一次性失败 → 切换分步（P1）

### 1.1 问题

`generate_outline` 只在**事前**按 `word_budget > OUTLINE_STEPWISE_MIN_WORDS`（50000）分叉。短方案走一次性直出，三处出口全部硬失败：

| 出口 | 旧行为 |
| --- | --- |
| AI 调用异常（`collect_json_response` 抛 `ValueError` / 超时） | 冒泡到外层 `:4063` → `finish_task failed` |
| `obj.get("outline")` 为空 | `finish_task failed` + `error` 事件 + return |
| `normalize_outline` 后为空 | `finish_task failed` + `error` 事件 + return |

用户只看到一句「请重试」，且 `_partial_holder` 为空 → **无任何可挽救成果**（前端 `SchemeWorkbenchPage` 的「部分成果」弹窗只在 `evt.outline` 非空时出现）。

### 1.2 落地（不抽取分步代码）

调研发现 3 条源码级护栏会拦住「把分步抽成独立函数」（`TestRenderDynamicBlindspots` 类同型）：
`test_outline_module_fixes_20261007.py:97`（`_attach_quality_report(` 计数 == 2）、
`test_outline_workflow_logs.py:111`（兜底块必须在 `generate_outline` 源码内）、`:120`（分叉判定不能移出）。
故采用**标志位 + 条件进入**，分步块一行不改：

| 位置 | 内容 |
| --- | --- |
| `app/config.py:307` | `outline_oneshot_fallback_stepwise: bool = True` |
| `sse_handlers.py:215` | `OUTLINE_ONESHOT_FALLBACK`（import 期固化，与既有阈值常量同口径） |
| `sse_handlers.py:3656` | `while _one_shot_ok:` —— 包裹一次性路径，失败点 `break` 跳出 |
| `sse_handlers.py:3737` | `if use_stepwise or not _one_shot_ok:` —— 分步块不再由 `else` 独占 |

三个必须同时做对的点：
1. **配额错误不切分步**：`if OUTLINE_ONESHOT_FALLBACK and not _is_quota_error(e)` —— 分步会按「一级 + 逐章」发起十几次调用，在注定失败的错误上全白烧（与 `_fetch_chapter_children` 既有判据同口径）。
2. **进度不倒退**：短路径已把 `last_p` 推到 0.55，而分步的 `level1` 是 `force=0.1`，会被 `max(p, last_p)` 顶住 → 切档时重置 `last_p / nodes / sub_done / sub_total` 并把 `stepwise` 置真。
3. **清空脏成果**：`_partial_holder["outline"] = []`，避免 `finally` 把空/脏成果落库。

`asyncio.CancelledError` 照旧透传（用户取消不能被兜底逻辑吃掉）。

## 2. F4 · 正文图表**配额感知**（P2）

### 2.1 问题

`_chart_pipeline.build_inline_chart_plan`（`sse_handlers.py:4876`）在生成后按 `enforce_limits` 删超限图表（每叶子 ≤1、同类型全方案 ≤3、ai_image ≤6）。
但 AI 写正文时**不知道**全方案已用掉多少 → 前半本把 3 张 gantt 用光，后半本再画 gantt **必被删**：生成成本白花，用户看到「明明写了图却没有」（删图可观测性里体现为 `scheme_type_limit`）。

### 2.2 落地

| 位置 | 内容 |
| --- | --- |
| `_chart_pipeline.py:115` | `_CHART_MIN_WORDS = 200`（与提示词「≤200 字不配图」同口径，消除第二份魔法数） |
| `_chart_pipeline.py:122` | `build_chart_quota_hint(type_counts, *, word_budget)` —— 纯函数、零 DB |
| `sse_handlers.py:5518` | 每章生成前 `_load_scheme_type_counts`（已排除本章）→ 生成提示 |
| `content_runtime.py:183` | 提示追加在**任务差异段末尾**（逐章量不得进稳定段） |
| `app/config.py:530` | `content_chart_quota_hint_enabled: bool = True` |

**三条刻意守住的边界**：
1. **不读 `chart_predictions` 的规划字段** —— 只读计数（当前真实占用），彻底避开陈旧结论陷阱；
2. **不指定画什么** —— 提示措辞是「剩余配额 / 必被删除 / 据此决定是否配图」，护栏断言不含「本章应画 / 必须画 / 推荐画」；
3. **不动硬限额** —— `build_inline_chart_plan` 继续兜底；并发下多章可能读到同一份快照（提示偏乐观），但这是**软提示**，代价远小于完全没有提示。

## 3. F5 · 事实**分段注入**（P1）

### 3.1 问题（含一个 P0）

R57 把事实文本放进 user 第①段「整案稳定上下文」，但 `facts_text` 是按 `_filter_facts_rows(rows, leaf)` **逐章**算出来的
（`sse_handlers.py:5394`）→ 所谓「稳定段」每章都在变，**Prompt Cache 前缀根本无法命中**，F1 的收益被这一处抵消掉大半。

同时 `_filter_facts_rows` 的两处回退（无关键词 → 全量；命中为空 → 全量）使它经常退化成「全量 6000 字」，与「按需」名不副实。

### 3.2 落地

| 位置 | 内容 |
| --- | --- |
| `facts_builder.py:57` | `core_facts_rows()` —— 整案核心（复用 `_FACTS_GENERIC_GROUP_HINTS` 唯一常量） |
| `facts_builder.py:87` | `exclude_rows()` —— 剔除已进入稳定段的行（身份 + 值双重判定，兼容 list/tuple 行） |
| `sse_handlers.py:5411` | 拆为「核心（稳定段）+ 其余按章命中（任务段）」 |
| `content_runtime.py:184` | `chapter_facts_text` 追加到任务差异段 |
| `app/config.py:536` | `content_facts_split_inject: bool = True` |

**信息零丢失证明**：原注入集合 = 通用组 ∪ 语义命中(全 rows)；新 = 通用组 ∪ 语义命中(rest)。
因 rest = rows − 通用组，语义命中(rest) ⊆ 语义命中(rows)，且通用组两边都有 → **两集合相等**，只是分处两段。

**`_sec_facts`（`standard_report` 的校验口径）刻意不改** —— 它用全量 rows 预筛，是**更宽**的校验范围，改窄会削弱事实校验。

## 4. F6 · `bid_analysis._repair_json` 统一化（P2）

### 4.1 旧实现的缺口

| 维度 | 旧 | 新 |
| --- | --- | --- |
| 解析 | 贪婪正则 `\{[\s\S]*\}`（字符串值里有 `}` 就错配） | `extract_json`（括号配对 + 代码块优先 + 转义修复） |
| 结构校验 | 无（裸数组/标量也放行） | `_validate_json_object`（顶层必须是对象） |
| 修复提示词 | **硬编码字符串**，DB 里改不了 | `render(GENERIC_REPAIR_KEY)` |
| 指标 | 无 | `record_ai_failure` / `record_repair_triggered` |
| 调用成本 | 1 次生成 + 1 次修复 | **相同**（`BID_JSON_REPAIR_RETRIES = 1`） |

### 4.2 落地与必须守住的契约

`bid_analysis.py:1761/1764/1776/1812`。关键取舍：

1. **用 `collect_json_response_with_chat` 注入 `ba.chat_with_fallback`**，而不是直接用 `collect_json_response` ——
   后者内部引用 `json_response` 自己的导入，会让既有测试对 `ba.chat_with_fallback` 的 monkeypatch **失效**（6 处测试）。
2. **返回值必须是模型原文 str**：下游 `is_missing_result` / `_safe_evidence` / 落库全按 str 处理；返回 `json.dumps(obj)` 会把 `{"ok":true}` 变成 `{"ok": true}`，打断既有逐字断言。
3. **永不向上抛**：上层只捕 `json.JSONDecodeError`，抛 `ValueError` 会被 SSE 版放大成**整项 3 次重跑**（`_item_retries=2` + 指数退避）。
4. **失败兜底必须是 `"{}"`**：`_json_all_empty` / `is_missing_result` 的失败哨兵；兜底成 `""` 会被判「不缺失」→ **假绿**。
5. **`repair_key` 传具名常量 `GENERIC_REPAIR_KEY`**（提取族，禁止 `OUTLINE_REPAIR_KEY`；AST 护栏会判非法）。
6. `_repair_json` 保留为兼容薄壳（既有测试直接调它），最后一道「正则抠 JSON」的确定性下界保留。

## 6. 本轮最大教训（两条）

1. **【行尾坑二次踩中，形态不同】** R57 是「编辑工具二次处理行尾」→ `\r\r\n`；
   R58 是补丁脚本用 `Path.read_text()` —— **它默认开启 universal newlines，把 CRLF 读成 `\n`**，
   写回后整个文件被改成 LF（`git diff` 判全文重写、真实改动无法 review）。
   **唯一可靠做法：`read_bytes` / `write_bytes`**，改完立即体检。判据已固化到 E 组与 R57 的 E 组。

2. **【`in` 判据在多处同形代码前是假护栏】** 见 §5.2 M10。断言必须带**位置/顺序/计数**约束，
   否则「代码改坏了、测试还是绿的」。

## 7. 运维提示

- 需**重启后端**加载新代码。
- 行为变化：
  1. 短方案（≤5 万字）一次性直出失败时，**自动切换分步生成**（新增 `outline_draft` 失败 → `outline_level1` 等调用）；关闭 `outline_oneshot_fallback_stepwise` 即回到硬失败；

  是原实现的审计缺口，上线后 `/ai/stats` 的失败数会**比历史多**（不是新增故障，是终于被记录）。
