## 二、根因与判据

### 2.1 假红机制（R120 §五 已定性）
B1/B2 为测 `pollTaskUntilTerminalImpl` 而 `await import("../pages/SchemeWorkbenchPage")`（12669 行）。该页面 import 会级联拉入整棵组件树 / antd / 全部 hooks；在全量并发（8-worker 冷 jsdom + 超大模块编译）下这一下动态 import 超过单测 `testTimeout=60000` 墙钟 ⇒ `Test timed out`。**单独无并发复跑 12/12 绿** ⇒ 非回归、非产品缺陷。

### 2.2 为什么「下沉」优于「抬超时」
- 抬 `testTimeout` 只把墙钟推后，巨型 import 的固定成本仍在，负载更高时仍可能翻红；且掩盖「一个纯函数测试却要编译整页」的架构异味。
- 下沉后被测函数落在真正的叶子，静态 import 极廉价；且经核实：
  - `pollTaskUntilTerminalImpl` 的**唯一运行时依赖** `isTerminalTaskStatus` 早已在叶子 `utils/contentEvents.ts`（零副作用纯函数）；
  - C 组用的 `useContentGeneration` hook 也**只 import utils/api/react、从不引页面** ⇒ 移走 B 组的巨型 import 后，**整个测试文件不再牵入页面**。
- 该函数本就注释为「提取为模块级实现（可注入依赖、可单测）」——下沉是兑现其原始设计意图，非新造结构。

### 2.3 泛型下沉（零类型分叉）
页面存在两份 `TaskTerminalInfo`（页面本地手抄 + 生成的 `types/checkpointSchema.ts`），直接让叶子引页面类型会造成循环、引 checkpointSchema 又要改页面 cast。故叶子用**最小结构约束 + 泛型**：

```ts
export interface PollableTaskTerminal { status: string; progress?: number; message?: string; [k: string]: unknown }
export async function pollTaskUntilTerminalImpl<T extends PollableTaskTerminal>(
  taskId, fetchStatus: (id) => Promise<T>, onPending?: (d: T) => void, opts = {},
): Promise<T | null> { /* 逐字原实现，仅 return {...data,...} as T */ }
```

页面两处调用点（`pollTaskUntilTerminal` 包装 / 停止协作用）的 `fetchStatus` 返回 `Promise<TaskTerminalInfo>` ⇒ `T` 推断为 `TaskTerminalInfo` ⇒ 返回类型与改前逐字一致，`tsc --noEmit` EXIT=0 佐证。
