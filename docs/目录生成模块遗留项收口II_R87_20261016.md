## 1. FIX-1 / FIX-2 · 前端是编号判据的**第三份副本**（R86 只封了后端一半）

### 复核证据

R86 把 `heading_templates.outline_number_parts` 的松过滤换成 `numbering.stored_id_parts`，
但**前端同族副本原封不动**：

```ts
// 改前 SchemeWorkbenchPage.tsx:201-204
String(id || "").split(".").map((p) => parseInt(p, 10)).filter((n) => !Number.isNaN(n))
```

node 真跑（`artifacts/r87`）实测分叉：

| stored_id | 导出成稿（后端，R86 后） | 改前前端目录树 |
|---|---|---|
| `abc1.2` | 无编号（fail-closed） | `2 现场布置` ← **凭空造出章号** |
| `0.3` | 无编号 | `3 现场布置` |
| `1.0.2` | 无编号 | `0.2 现场布置` |
| `1.2.x` | 无编号 | `1.2 现场布置` |
| `1..2` | 无编号 | `2 现场布置` |

⇒ **交付的 DOCX 里该章节没有编号，前端目录树却显示一个自信的错编号。**
13 个脏 id 中 **5 个分叉**。

**为何至今没被发现**：既有前后端 parity 护栏
（`test_import_outline_deep_fix_20260927.py::TestLeadingNumberRegexFrontendParity`）
**只锁剥离正则**（`_STRIP_NUMBER_RE` ↔ `LEADING_NUMBER_RE`），**不锁编号合法性判据**。

### 修法

新增 `frontend/src/utils/outlineNumbering.ts::storedIdParts`（与后端同口径），
`formatOutlineTitle` 改调之；非法编号一律**退回裸标题**（不编造编号）。
补 **FIX-2 跨语言行为 parity 护栏**：pytest 侧用前端**自己的 esbuild**
（`node_modules/@esbuild/win32-x64/esbuild.exe`）转译真源码 → node 真跑 →
与后端 `stored_id_parts` 逐条比对。

### 三处**刻意**差异（均朝「更严」方向，绝不朝「编造」方向）

| # | 差异 | 理由 |
|---|---|---|
| 1 | **覆盖全角数字** | Python `\d` 匹配 Unicode Nd（含全角），JS `\d` **不会**。不覆盖 ⇒ `１２.３` 前端拒、后端接受 ⇒ **反向**分叉。且 `Number("１２")` 在 JS 是 `NaN`，必须先折成 ASCII |
| 2 | **拒 float** | 后端 D-8a 的判据是 `isinstance(stored_id, (str, int))` —— **float 被显式拒绝**（`3.5` 会被拆成 `["3","5"]` 造出假编号）。JS 的 `typeof x === "number"` 含小数，不补 `Number.isInteger` 即分叉 |
| 3 | **拒一切 ≤ 0 号段** | 后端只拒字面量 `"0"`；0 号章节在任何合法目录里都不存在，展示层更严是安全的 |

> 差异 2 是**本轮护栏当场抓出来的**：`test_storedIdParts` 首版断言 `storedIdParts(3.2) === []`
> 而实现返回 `[3,2]` —— 即我自己的修复在 FE 侧留了一个 parity 缺口。

## 2. FIX-4 · 一个不可见字符即可让**全部**占位判据同时失效（P2）

### 复核证据（本人探针，非转述）

```
ZWSP 措\u200b施1   generic=False detect=False  <== ESCAPED
ZWSP 措施1\u200b   generic=False detect=False  <== ESCAPED
BOM  \ufeff措施1   generic=False detect=False  <== ESCAPED
（ZWSP / ZWNJ / WJ / BOM 各 3 种放置 = 12/12 全部逃逸）
```

且**连 R85 之前就有的** `GENERIC_TITLE_PATTERNS` 字面量枚举一并被打穿 ——
这不是「某条判据写窄了」，而是**所有判据同时失效**。

来源真实：AI 输出偶发零宽字符；从 Word / 网页复制粘贴的标题常带
U+200B / U+FEFF / U+00AD（软连字符）。用户界面上完全看不见。

### 修法

新增 `outline_quality._canon`：① 剥零宽族（U+200B–200F / U+2060 / U+FEFF / U+00AD /
U+180E / U+034F）② **NFKC 归一**（全角数字/字母/括号折成 ASCII，顺带统一同形异码）。
`_norm` 与 `has_trailing_counter_suffix` 均改走它。

⚠️ 只在**比较语境**使用（dict 键 / 正则入参 / 比较基准），**从不出现在任何用户可见
文本里** ⇒ 归一不改写用户数据。护栏锁定「纯 ASCII 常规标题逐字不变 + 规范化幂等」。

**效果**：12/12 逃逸形态全部收口；`_norm("措施１") == "措施1"`。

## 3. FIX-3 · 同模块两条判据值域不一致（P2）

`GENERIC_STEM_ORDINAL_RE` 用 `[0-9]{1,3}`（**ASCII 显式范围**），
而同模块兄弟 `_TRAILING_COUNTER_SUFFIX_RE` 用 `\d{1,4}`（Python `\d` 匹配 Nd，含全角）。
于是同一模块内出现**值域分叉**：

| 输入 | 括号路径 | 序号路径 |
|---|---|---|
| `_norm("措施（１）")` | `"措施"` ⇒ 结构判据**收** | — |
| `is_generic_title("措施１")` | — | 改前 **False（逃逸）** |

「括号路径收全角、序号路径不收」。修法：序号位改 `\d`（NFKC 归一是主防线，
改正则让谓词**自身**自洽、独立调用时也不分叉）。修后 `措施１ / 内容１ / 要点１` 全部收口。

## 9. 本轮方法论教训

1. **「半收口」比「没收口」更危险**：R86 把 L2 描述成「编号命名空间统一」并结案，
   但只改了后端两套，前端第三份原封不动。**判据是「命名空间」就必须在全仓
   （含前端、含反射可达处）穷举副本**，否则「统一」只是措辞。
2. **跨语言 parity 护栏缺席时，两侧会各自漂移**：既有 parity 只锁剥离正则，
   编号合法性判据完全没锁 ⇒ 缺陷潜伏到 R87 才被发现。新增 parity 必须
   **真跑**（esbuild 转译 + node），比对源码字符串只能锁住「写法相同」。
3. **护栏能抓住自己修复里的缺陷**：`test_storedIdParts` 首版就抓出我在 TS 侧
   漏了 float 拒绝（JS `typeof number` 含小数，后端 `isinstance(int)` 不含）。
4. **`node_modules/.bin/*.cmd` 在非 ASCII 仓路径下不可用**：`.cmd` 按 GBK 解码，
   `J:\编程\...` 被吃成 `J:\???\...`。跨语言用例必须直呼
   `node_modules/@esbuild/win32-x64/esbuild.exe` 本体（AGENTS §5.9 老坑再踩）。
5. **不要用「正则删类型标注」把 TS 当 JS 跑**：会随 TS 语法演进而静默失效。
   用仓库自己的 esbuild（与 vitest/tsc 同一条链路）。
