# 代码规范原则 —— Git 协作与构建约束

> 依据 2026-11-09 用户提供《大厂的 Git 代码规范》图例制定，并结合本仓既有红线
> （`commitlint.config.js`、`CONTRIBUTING.md`、行尾双轨约定、共享工作区提交铁律）落地。
> **自本文件生效起，本软件的一切开发、提交、合并、编译/构建行为均按本规范执行。**

---

## 一、分支模型（六类分支）

| 分支 | 功能 | 环境 | 可访问 | 说明 |
|------|------|------|--------|------|
| `main` | 主分支，稳定版本 | PRO | 是 | 生产环境主干，只接受 release / hotfix 合并 |
| `develop` | 开发分支，最新版本 | DEV | 是 | 开发环境分支，新代码一律基于此创建 |
| `feature` | 开发分支，实现新特性 | — | 否 | 命名 `feature/<模块名>`，如 `feature/export`、`feature/user_module` |
| `test` | 测试分支，功能测试 | FAT | 是 | 提测进入，版本相对稳定，供测试人员验证 |
| `release` | 预上线分支 | UAT | 是 | 验收通过进入，UAT 验证，建议由 test 或 hotfix 合并而来 |
| `hotfix` | 紧急修复分支，修线上 bug | UAT | 否 | 线上紧急修复，修复后**同步合并 main 和 develop** |

### 分支流转主线

```
基于 develop 创建 feature
        │
        ▼
   feature 开发完成 ──提测──▶ test ──验收通过──▶ release ──上线──▶ main
                                                          │
   线上 bug ──▶ hotfix ──修复后同步合并──▶ main + develop ◀┘
```

### 分支硬性规则

1. **禁止直接在 main 提交代码**（红线）。main 只接受 release 上线合并与 hotfix 修复合并。
2. 新功能一律 `feature/<模块名>` 命名，从 develop 最新代码创建；禁止无分支直接在 develop/main 上堆功能。
3. hotfix 修复完成后必须**双向合并**：合入 main（出修复版本）+ 合入 develop（防重复复发）。
4. 多人/多会话协作前，先拉取最新代码（`git pull` / 取证 mtime 与 git status），再开始改动。
5. test / release 分支仅做验证与修复性合入，不在其上直接开发新特性。

> 本仓现状适配：单人项目 + 多会话并行开发。日常开发落在 develop（或沿用既有批次分支，
> 如 `refactor/baseline-20261103`）；引入远程仓库后按上表启用 PRO/DEV/UAT 环境对应。

## 二、Commit 提交信息规范

格式遵循 Conventional Commits（与 `commitlint.config.js` 一致）：

```
<type>(<scope>): <subject>
```

| type | 含义 |
|------|------|
| `feat` | 新增功能 |
| `fix` | 修复 bug |
| `docs` | 仅文档更改 |
| `style` | 格式调整，不影响代码含义（不影响运行的空格、格式化等） |
| `refactor` | 代码重构，既不新增功能也不修 bug |
| `perf` | 改进性能 |
| `test` | 添加或修正测试 |

- `scope`（可选）：模块名，如 `export`、`outline`、`chart`、`frontend`、`lint`。
- `subject`：中文简述，简洁明确，结尾不加句号；头部总长 ≤120（commitlint 已配置）。
- 一行写不下时在正文补充细节。
- 校验方式：`npx commitlint --edit <msg文件>`（配置已就位，依赖暂未安装）。

示例：

```
feat(生成链路): 引入 G1/G2/G3 三机制编排选事实强注入
fix(export): 表格侧叠行拆分与尾部空列裁剪
chore(lint): 整仓 I001 import 排序（独立提交，与功能改动分离）
```

## 三、编译 / 构建约束（按分支分级）

任何分支上的合并与上线动作，必须先通过对应级别的构建检查：

| 动作 | 必须通过的检查 |
|------|----------------|
| feature 内提交 | 定向单文件测试 + `tsc --noEmit`（前端改动）+ 定向 eslint / `ruff check`（后端改动） |
| feature → test | 对应域测试基线对比（改前基线 vs 改后结果，红→绿过程留痕） |
| test → release | 后端 `pytest` 定向全量 + `ruff check` 0 error；前端 `tsc`、`eslint` 0 error、vitest 通过 |
| release → main | 整树全量回归绿灯（pytest / ruff / tsc / eslint / vitest），失败项逐一归因 |
| hotfix → main | 修复点定向测试 + 被修复域回归，事后同步合并回 develop 并跑对应域回归 |

构建期通用约束（延续既有红线）：

1. 全量测试启动前必须确认机器静止：无并发会话改写工作区、无僵死 pytest 进程。
2. 并行会话期间禁止跑全量 pytest / vitest / eslint，仅允许只读命令与限定单文件检查
   （pytest 加 `-p no:cacheprovider`）。
3. 整仓机械格式化（import 排序、行尾归一、全量 prettier/ruff format）必须**独立提交**，
   不与功能改动混在同一提交。
4. 行尾双轨：`.py` 保持纯 CRLF（0 裸 LF）；锁定的前端纯 LF 文件不得被翻转；
   `start_all.bat` 必须保持 GBK 编码。
5. 提交纪律：共享工作区提交必须**始终带 pathspec**（`git commit -m "..." -- <路径>`）；
   禁止 `git add -A`；提交前核对 `git diff --cached --stat` 清单，发现他人改动立即停止并登记。
6. 失败项归类处置：真回归（修代码）/ 锚点过时（改断言并说明新旧语义）/ 脆弱断言（改写为
   锁行为断言）/ 环境性（附证据），禁止为变绿删用例、放宽断言、skip/xfail 伪装通过。

## 四、协作守则（学习小贴士 → 硬约束）

1. **禁止直接在 main 提交代码。**
2. **commit 信息简洁明确**，type 用对（新功能 feat、修 bug fix、重构 refactor 不混用）。
3. **hotfix 修复后同步合并 main 和 develop**，漏一侧即视为未完成。
4. **多人协作前先拉取最新代码**，本仓延伸：开工前取证 git status 与目标文件 mtime，
   目标文件 10 分钟内有他人写入则跳过并登记。
