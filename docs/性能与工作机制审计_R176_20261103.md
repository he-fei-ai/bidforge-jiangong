## 0. 开篇结论

**最严重的 3 个性能瓶颈**

| 排名 | 瓶颈 | 一句话证据 | 影响 |
|---|---|---|---|
| 1 | **AI 吞吐硬上限 = 5 并发，且单章内初稿/续写/压缩是串行 await** | 全局 `max_concurrency: int = 5`（`backend/app/config.py:294`），正文并发再被钳到 `[1,5]`（`backend/app/services/content_utils.py:731-758`），每章一次非流式 AI 调用（`backend/app/routers/sse_handlers.py:3663,3683,3809`） | 300 章方案墙钟下限约 `300/5 × 单章耗时`；单章 30s ⇒ **≥30 分钟**，且并发退档时线性放大（`workflows_base.py:296-300` 记录过退到 1.5 造成 5× 墙钟） |
| 2 | **导出“缓存命中”仍不是零成本：全量 `SELECT * FROM sections` + 全量 `audit_content` + 全量指纹 + 两次写库** | `SELECT *`（`export.py:3265`）、`audit_content`（`export.py:3435`，位于缓存查询 `export.py:4251` **之前**）、指纹（`_export_cache.py:92-222`）、命中后仍 `_bump_export_round`+`_record_export_review_trace`（`export.py:4241,4263`） | 实测 120/300 章各 **27.4ms / 66.7ms** 审核 + **5.0ms / 11.7ms** 指纹，叠加全量 DB 读与 2 个写事务；高并发下与 SQLite 单写者争锁 |
| 3 | **事件循环上仍有 5~200ms 级同步阻塞 + DB 连接获取在锁内做真实 IO** | PIL `verify()` 在协程内（`export.py:3618`）、PDF 整文件 `f.read()`/`write_bytes()`（`export.py:4642,4673`）、上传分片 `out.write()`（`global_facts_docs.py:458`）；读写池获取连接时在 `async with _db_pool_cv` 内 `await _probe_conn`（WAL checkpoint，`db.py:134-155,1382,1558`） | P99 尖刺；所有 DB 获取被单条件变量串行化，并发越高越明显 |

**是否有事件循环阻塞**：**是，存在**。重 CPU 的 docx 构建（`export.py:4297 asyncio.to_thread`）、图表渲染（`export.py:3539` 信号量+线程池）、文件解析（`upload_outline.py:243` / `global_facts_docs.py` 的 `to_thread`）已经正确下沉；残留阻塞是**中短时长的同步调用**（单次 5~200ms），但会在 P95/P99 与并发导出/上传时叠加成可感知卡顿。

**基准方案一句话**：以“纯函数微基准 + 冻结工作树的端到端分段基准”双层方案落地，指标统一为 `sections/s、chars/s、P50/P95/P99、冷/热缓存耗时`，数据集分 S/M/L 三档，验收线以“用户可感知阈值 + 现有架构可控上限”双向取值（详见 §7）。

### 7.3 测量方法（冻结工作树判定）

1. **安静窗口前置条件**（全部满足才开测，否则结果作废）：
   - `git status --porcelain` 为空且 `git rev-parse HEAD` 记录在报告里；
   - 无并行会话（后端 `backend.log` 无并发任务、`task_registry` 无 running 行）；
   - 本机无其它 Python/node 构建任务；电源计划=高性能；杀毒实时扫描排除项目盘；
   - 数据库位于本地 SSD（若为网络盘，报告中注明并单列）。
2. **预热**：每档先跑 1 轮完整链路（结果丢弃），让模板/提示词/图表缓存进入稳态。
3. **重复**：正式 5 轮；每轮清空“业务数据”但**保留**图表缓存（热档单独测）；报告取轮中位数 + 轮内 P95。
4. **离群剔除**：按 IQR（>Q3+1.5IQR 或 <Q1−1.5IQR）剔除，剔除条数必须记录。
5. **并发档位**：AI 并发固定 5（`max_concurrency`），另测 3/8 两档作敏感性；DB 单写者不并行压测两套方案（会串行，属真实行为）。
6. **冷/热定义**：冷=清 `export_cache` + 图表磁盘缓存；热=仅清业务缓存、保留导出缓存行与磁盘产物。
7. **采样**：每请求记录 `t_start/t_first_event/t_end`，由客户端 `httpx` 计算；服务端仅提供 SSE 事件时间戳，避免双重计时误差。

`bench_api.py` 关键骨架：

```python
# 仅骨架，本轮不执行
import asyncio, json, time, statistics, httpx

async def sse_run(client, url, body, on_event):
    t0 = time.perf_counter()
    async with client.stream("POST", url, json=body, timeout=3600) as r:
        async for line in r.aiter_lines():
            if line.startswith("data:"):
                evt = json.loads(line[5:].strip())
                on_event(evt, time.perf_counter() - t0)

async def bench_once(client, case):
    marks = {}
    def on_event(evt, t):
        marks.setdefault(evt.get("type"), []).append(t)
    await sse_run(client, case["url"], case["body"], on_event)
    return {"total_s": max(max(v) for v in marks.values()),
            "first_section_s": min(marks.get("section_done", [9e9]))}

def summarize(samples):  # 轮内 P50/P95/P99 + IQR 剔除
    xs = sorted(samples); n = len(xs)
    return {"p50": xs[int(.50*n)], "p95": xs[min(n-1, int(.95*n))],
            "p99": xs[min(n-1, int(.99*n))]}
```

| 写池探活 | `db.py:1402` 锁内，`1429` 探活 | `PRAGMA wal_checkpoint(PASSIVE)` 在 `_db_pool_cv` 持有期间执行 | 锁内只做"弹出连接/维护计数"；**探活移到锁外**，失败后回锁归还计数并重试 | 中 |
| 读池探活 | `db.py:1580` 锁内，`1605` 探活 | 同上（`_read_probe`） | 同上；另可加连接级 TTL（30 s）跳过重复探活 | 中 |
| 全局单连接探活 | `db.py:349` | 不在池锁内 | 不动 | - |

**WAL checkpoint 探测能否移出锁：可以。** 依据：

1. 探活对象是已经从池中弹出的连接，已被当前协程独占，不存在并发使用；
2. 条件变量只保护 `_db_pool` 列表与 `_db_pool_total` 计数，探活不读写这两个结构；
3. 移出后必须保持"失败 → 回锁 `total -= 1` + `notify()`"的补偿路径，
   否则池容量会泄漏。

建议的第二层优化（可选，需实测）：把探活拆成两件事 ——
`SELECT 1`（每次取用，锁外）与 `wal_checkpoint(PASSIVE)`（单独 60 s 节流），
避免每次取连接都做一次 WAL 检查；探活 TTL 30 s 可把高频小查询的探活 IO 降到接近 0。
风险：连接"刚坏但未到 TTL"时首个查询失败，需确认调用侧有 `retry_db_op` 兜底。

"是否换异步库"的结论：

- **SQLite 不换**：`aiosqlite` 已把阻塞 IO 放到线程，问题在**锁的作用域**，不在库本身；
- **文件 IO 不引入 `aiofiles`**（本轮禁止新依赖）：`asyncio.to_thread` 足够，且与
  `upload_outline.py:243` 已有的 FIX-1 修复同口径；
- **PIL / CPU**：一律 `to_thread`，不要放进事件循环。

## 13. D2-3 实施记录：命中路径「轮次 + 留痕」合并为单事务（2026-11-04）

### 13.1 改动符号

| 符号 | 改动 |
| --- | --- |
| `_bump_export_round_and_trace`（**新增**） | 命中路径唯一写库入口：`UPDATE export_round` → 回读轮次 → 生成文件名 → 写留痕 → **一次 `commit`**；异常整体 `rollback` 并返回 `None` |
| `_write_export_review_trace`（**新增**） | 从旧 `_record_export_review_trace` 抽出的**纯写入段**：不提交、异常上抛，供单事务复用 |
| `_record_export_review_trace` | 改为薄包装（`commit=True` 缺省，语义与失败兜底**逐字不变**），未命中链路的 `_finalize_export_delivery` 调用点零改动 |
| `export_docx` / `export_pdf` | 缓存查询**提前**到轮次自增之前；命中分支改调 `_bump_export_round_and_trace`，未命中分支仍走 `_bump_export_round`（行为不变） |
| `test_r111_closeout_20261020.py` | 源码形状断言随符号更新（命中埋点仍必须在留痕事务之前），语义不变 |

**为什么必须把查询提前**：旧顺序是「自增并 commit → 查缓存 → 命中再 commit 留痕」，
轮次已经落库后就无法与留痕合并；只有先判定命中，才能由同一事务同时产出
「第 N 轮」与「第 N 轮已交付」两条记录。

### 13.2 事务失败语义（选择：**不交付 + 503**）

**选择**：合并事务失败 → 整体回滚 → **不返回缓存文件**，抛 `HTTPException(503)`，
提示"本次缓存命中已整体回滚、未交付文件，请稍后重试"。

**理由**：

1. **留痕是契约，命中是优化**。G12 要求事后可回答"这份成稿是不是评审后版本"；
   写不进留痕却返回 200，等于假报一次未留痕的交付，比慢几十毫秒严重得多。
2. **不转"未命中重建"**。重建尾部同样要写缓存行与留痕（还要多付一次全量渲染），
   DB 写入不可用时只会**放大成本**且仍可能丢留痕 —— 违背"一次失败不连锁写库"。
3. **503 可重试**。客户端重试时若 DB 恢复，事务正常完成；若仍失败，错误可见而非静默。
4. 该分支只在**写库失败**时触发；正常路径的可用性、延迟与命中率完全不变。

## 15. D2-4 · 指纹算法变更（判定：**不改**）

**它解决的到底是什么缺陷**：报告 §10.6 的原文是"指纹从拼巨串再 hash 改为增量
`sha256` 元组流"——这是**实现重构**（内存/常数因子），不是误判修复。复核现有的
`_content_fingerprint`：`config_hash` 与 `content_hash` 都把 scheme / sections /
charts（含 `data_json`）/ global_facts / appendix / config / fe_render /
fe_render_pixels / exporter 版本 / image_gen / subheading_demote /
appendix_sources_on / renderer / chart_fp **全维度**装进
`json.dumps(..., sort_keys=True)` 再 md5。

- 不存在"两个不同内容算出同指纹"的真实场景（md5 碰撞非现实风险，且无一字段被排除在摘要外）；
- 没有可复现的误判样本 → 按派单要求**不改**；
- 代价（全部存量缓存失效一次）> 收益（无）→ 未加 `_FINGERPRINT_VERSION`，
  也就不存在"新旧并行期"行为。

若未来真的扩展/更换覆盖域（或 `_EXPORTER_VERSION` 语义变更），再按
"版本前缀 → 旧缓存以版本不匹配自然失效"的方案执行（而不是换算法后静默错配）。

## 16. `db.py` · 探活移出 `_db_pool_cv` 锁（2026-11-04）

### 16.1 移出前提（独占性证明）

1. `_db_pool` 只在 `_acquire_pool_conn` 内 `pop()`、在 `_release_pool_conn` 内 `append()`；
2. 连接 `pop()` 后立即从池中移除，**不存在** in-flight 注册表或第二条把池连接交给
   其它协程的路径（全仓检索 `_db_pool` 仅这两处读写）；
3. 因此探活期间连接由**本协程独占**，不会被抢走 → 可以安全出锁。
   （读池 `_read_pool` / `_read_probe` 结构同构，同结论。）

### 16.2 改动

- 锁内只保留「出池 / 剔除 poisoned·dead / 预留 `total += 1` / `wait()`」；
  `_probe_conn`（`wal_checkpoint(PASSIVE)`）与 `close()` 全部移到锁外。
- 探活失败 → **回锁** `total -= 1` + `notify()`，再关连接（缺 notify 会让等待者永久睡死）。
- 新建连接重试期**保持预留**，只在最终放弃/非瞬态异常时归还一次并 notify
  —— 顺带修复此前暴露的 `total` 少计缺陷（实测 12 并发 × 3 次重试后可达 −24）。
- 读池 `_acquire_read_conn` 同口径（`_read_probe` = `wal_checkpoint(NOOP)`）。
- **未触碰** `facts_chunk_failures` / `facts_cross_conflicts` 两张表。

### 16.4 16 并发 P95 实测（旧实现复刻 vs 新实现）

方法：按 `git HEAD` 复刻旧 `_acquire_pool_conn`（探活持锁）；bench DB 置于 J:
