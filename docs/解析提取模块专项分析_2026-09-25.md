## 2. 现状分析（架构与实现）

### 2.1 模块边界与定位
`import` 是 6 步工作流的第 1 步（2026-09-23 起由旧「上传解析」「提取项目」两个顶层 Tab 合并为 1 个顶层 Tab + 2 内嵌子 Tab）。值域固定：`WorkflowTabKey = import / outline / facts / content / review / export`（`frontend/src/utils/workflowDerived.ts`）。

### 2.2 后端解析链路
入口：`routers/doc_pipeline.py`（`/api/v1/documents` 四层存储：原文层 `project_documents` → 解析层 `doc_chunks` → 提取层 `doc_extractions` → 语义层）+ `services/doc_pipeline/pipeline.py`（ingest_upload / ingest_parse_result / sync_extract_layer / build_completeness_report / compute_freshness / run_cross_check / detect_cross_source_conflicts / purge_document）。

文件内容解析核心：`services/file_parser.py::parse_file_content_ex(content, fname) -> (纯文本, 诊断字典)`。
- 按扩展名分流：`docx / pdf / md / txt / csv / xlsx / xls / png,jpg,...(OCR) / doc,wps(legacy)`。
- 诊断字典 `diag` 含 `file_type / text_len / truncated / warnings[]`，供路由层把「解析成功但内容不完整」告知用户（而非只进日志）。
- 编码解码：`_decode_text_ex` 回退顺序 `utf-8-sig → gbk → gb18030 → utf-8(errors="ignore")`，返回 `(文本, 告警列表)`。

格式识别：无独立 MIME 探测模块，依赖**扩展名**（`UPLOAD_FILE_ACCEPT` 前端白名单 + 后端 `ftype` 由 fname 后缀推断）。风险见 §3。

### 2.3 保存与分类（提取层）
项目提取（`extract` 子页）落到 `bid_analysis_items` 表：18 个解析项（`ANALYSIS_ITEMS`），其中 17 个必选（`REQUIRED_ITEM_IDS`）。结构化提取见 `services/bid_analysis_service.py`，标段识别见 `services/bid_section_detector.py`。

前端展示：`UploadParseTab` 内嵌 `ParseResultCategoryPanel`（variant `list-only` 左分类栏 / `detail-only` 右详情），两者经 `ParsePanelSharedState` 共享对象联动。

### 2.4 错误处理与 AI 调用
- 解析异常：`ParseError` 不可恢复时由路由层转用户可见消息（不当作正文入库）。
- AI 提取：`sse_handlers` 走 `provider_factory.chat`（熔断/配额冷却/自适应并发/对冲），所有 AI 调用点须显式传 `scene`（审计与场景路由白名单）。
- 后台任务状态栏 `TaskStatusBar`：SSE 优先、轮询指数退避（3s 起）兜底。

### 2.5 路由 / 容错 / 缓存 / 并发 / 日志 / 配置
- 路由：`/api/v1/documents`、`/api/v1/bid-analysis`、`/api/v1/outline-library`、`/api/v1/upload-outline` 均受 `ApiAuthMiddleware` 保护（仅 health/docs 等豁免）。
- 并发：解析用 `computeDocStats.actionableCount` 计数；页面层 `parsingDocs/parsingDocId` 防重入（避免 OCR 长耗时并发覆盖四层产物）。
- 日志：落盘 `logs/backend.log`，级别规范 ERROR/WARNING/DEBUG/INFO。
- 配置：解析上限（页数/行数/归档膨胀）由 `file_parser._guard_*` 控制；无新增环境变量（本次未引入配置项，详见 §5）。

### 2.6 测试现状
- 后端：`tests/test_file_parser.py`、`tests/test_bid_section_detector.py`（新增 39 用例）、`tests/test_bid_analysis.py`。
- 前端：`uploadParseTab.test.tsx`（detail-only 语义重写）、`parseResultCategoryPanel.test.tsx`（list/detail 联动）、`schemeWorkbench.test.tsx`（import 子 Tab 切换集成）、`TaskStatusBar.test.tsx`（SSE 夹具修复）。

## 4. 增强优化项（本次实施）

1. **可观测性增强**：`parse_file_content_ex` 返回诊断字典，解码告警（`warnings`）经 `diag["warnings"]` / `_note_info` 回流，路由层可透传用户。
2. **编码回退加固**：`utf-8-sig` 替代 `utf-8`，消除 Excel CSV 的 BOM 残留 `\ufeff` 导致的表头归一/去重/分类失败（L445）。
3. **CSV 结构化输出**：统一输出 Markdown 表格，打通 machinery_stat 高权重区与表格完整性保护（L1185）。
4. **CSV 流式截断**：边读边截断，内存峰值与输出一致（L1199）。
5. **标段识别双分支正则**：裸定义式不再误报总数（L70）。
6. **前端分类详情联动统一**：`UploadParseTab` 内置 detail-only 面板经 `sharedState` 与左栏 list-only 联动，删除页面层重复面板（§5 B4）。
7. **组件级交互测试补齐**：list/detail 联动、import 子 Tab 切换、TaskStatusBar SSE 契约、detail-only 语义断言。

## 7. 遗留问题与后续建议

### 7.1 建议立项（高风险/需单独评估）
- **G1 内容嗅探式格式识别**：引入轻量 magic-number 探测（PDF `%PDF`、ZIP `PK`、OOXML 实为 zip 等），与扩展名交叉校验；改后缀绕过属安全/数据质量问题，建议在 `file_parser` 入口独立加一层。需单独立项评估性能与误判率。
- **G2 编码告警前端透传**：后端 `diag["warnings"]` 已就绪，需在前端上传/解析结果处展示「源文件编码可能异常，建议确认」提示，避免用户无感知乱码。

### 7.2 观察项（暂不动）
- **G10 压缩炸弹阈值硬编码**：单条目上限仅在"达上限后仍有剩余"触发；建议将阈值（如 50MB/条目）提升为可配置项（环境变量）以便按需调整，属低优先优化。
- **超大 XLSX**：`_parse_excel` 是否同样存在整表物化问题，未在本次范围（聚焦 txt/csv/pdf/标段），建议后续专项排查。

### 7.3 本次未覆盖（用户原始 7 步中"并发竞态/缓存未失效/空超长特殊字符"）
- 并发竞态：页面层 `parsingDocs/parsingDocId` 防重入已覆盖上传解析主路径；`bid_analysis` 提取并发由 `AdaptiveConcurrencyController` 控管（已在 AGENTS.md §4.1 描述），本次未改。
- 缓存未失效：解析/提取结果无前端长缓存，路由层每次读表（`doc_pipeline`/`bid_analysis_items`），不存在陈旧缓存问题。
- 空/超长/特殊字符：CSV/文本截断与编码兜底已覆盖超长；空文件由 `ParseError` 或空正文正常处理。特殊字符（如 BOM）已在 B1 修复。

### 7.4 后续建议
1. 将 G1、G2 纳入下一迭代，补全"格式识别可信度"与"用户可感知编码告警"。
2. 持续跑全量回归（仓库无 git，依赖 pytest/vitest 计数基线），任何改动须复验标识符。
3. 编码告警如需前端展示，建议与 `DocumentPipelineSummary` 四层产物展示合并，统一"解析可信度"入口。

## 9. 截断信号端到端打通（2026-09-26 补充）

上一轮只做到「**把截断写进库**」（F2：`project_documents.parse_truncated`），但信号在下游
读路径上断成了三段——写在库里的值没有任何调用方消费。本节把三条断链逐一接回，
并把前后端扩展名白名单的漂移护栏补上。

### 9.1 根因定位：三类「写而不用」

| 断链 | 位置 | 具体故障 |
|------|------|---------|
| **D1 列名不存在** | `bid_analysis.py::_doc_is_truncated` | 判 `d.get("text_len") == -1`，但 `_list_parsed_documents` 的 SELECT **从未取过** `text_len` 列（`project_documents` 表也没有该列）→ 取值恒 `None` → 该分支结构性不可达 |
| **D2 语言口径错位** | `bid_analysis.py::_doc_is_truncated` | 兜底分支判 `pd.parse_warnings` 是否 `== "truncated"`（英文），而解析器实际写入的是**中文**告警（「第 50 页之后已截断」「已截断至 30000 字符」）→ 恒 `False` |
| **D3 报告分支写而不用** | `bid_analysis.py::_combine_doc_texts(report_truncation=True)` | 已实现 `source_truncated / truncated_docs / used_doc_count / dropped_doc_count` 的完整统计与日志，但**所有活跃调用点**都传默认 `report_truncation=False` → 截断信息只进后端日志 |
| **D4 预览只报预览截取** | `global_facts.py::_preview_document` | 只回传 `preview_truncated`（切片是否被截断）。被截断的 PDF 正文本身很短（远小于预览上限），`preview_truncated=False`，用户永远看不到内容缺失 |
| **D5 前端无消费点** | `SchemeWorkbenchPage.tsx` 预览弹窗 / `BidAnalysisTab` | 后端算好的一切都没人渲染；「编码降级」「OCR 兜底」等 `parse_warnings` 只在列表 Tooltip 里出现，预览弹窗与提取结果区完全无提示 |

> D1 + D2 叠加后 `_doc_is_truncated()` **在结构上不可能返回 True**——两条路径分别依赖
> 一个**永远取不到的值**（SELECT 里没有 `text_len`，故 `d.get("text_len")` 恒为 `None`）
> 和一个**永远不出现的字符串**（解析器告警全是中文），两个条件都注定不成立。

### 9.3 关键区分（不可互相覆盖）

预览弹窗的两种截断语义必须分开，这是本次最容易踩错的点：

- `truncated`（**解析级**）→ `warning`：内容真的可能缺了，给出「建议拆分文件后重新上传」。
- `preview_truncated`（**预览级**）→ `info`：只是本弹窗没显示全，完整内容仍在库里。

一份「解析到 30000 字后被截断」的 PDF，正文只有几十字，`preview_truncated` 为 `False`
——**只有解析级信号能暴露问题**。若两者用同一个字段，或让 info 覆盖 warning，
就退回到修复前的状态（用户看到一段看起来正常的短正文）。
`parseSourceNotice.test.ts` 专门有一条用例钉住这个不变量。
