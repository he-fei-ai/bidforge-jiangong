## 1. 角色转换总纲（**本文件的第一性原则**）

参考软件与本软件的**领域差异**是系统性的，不是换几个词：

| 维度 | 参考软件（标书智能体） | 本软件（专项施工方案） | 是否已有本仓资产 |
|---|---|---|---|
| **业务目标** | 响应招标文件、争取中标 | 编制危大/专项施工方案、保证施工安全与可实施 | ✅ |
| **产出物** | 投标文件（商务+技术） | 专项施工方案（含计算书、图纸、监测方案） | ✅ |
| **目录骨架来源** | 技术评分项（外部输入、数量不可控） | **九大章节**（建办质〔2018〕31号，固定 9 个） | ✅ `NINE_CHAPTERS` |
| **风险分类** | 废标项 / 响应偏离 | **危大工程六大类 + 超过一定规模** | ✅ `HAZARD_CATEGORIES`/`HAZARD_THRESHOLDS` |
| **关键事实** | 工期、响应时间、质保、人员数量、设备型号 | **基坑深度、支撑高度跨度、施工总荷载、集中线荷载、脚手架搭设高度、起重起重量、危大判定参数** | ✅ `HAZARD_THRESHOLDS` |
| **合规来源** | 招标文件评分办法 | 住建部令37号、建办质〔2018〕31号、建办质〔2021〕48号、地方法规 | ✅ `standards_registry` |
| **法定前置** | 无 | **超过一定规模危大 → 专家论证** | ⚠️ 仅预检，无闭环 |
| **编制依据** | 招标文件条款 | 法规+标准（含**已废止标准剔除**） | ✅ `ABOLISHED_STANDARDS` |
| **图纸** | 一般 | **计算书及相关施工图纸（法定必备章节）** | ✅ 第九章 |
| **图片风格** | 「适合投标技术方案插图」 | 「适合专项施工方案插图」（工程资料感，非广告感） | ✅ 可改写 |

**结论**：本仓在**领域资产**（危大分类、阈值、章节体系、编制依据、废止标准）上**已超出**参考软件；参考软件的价值集中在**工程机制**（弱模型稳定输出 JSON、分层缓存、全文一致性、图文控制、容错）。因此本轮策略是：

> **保留本仓领域资产 + 吸收参考软件工程机制**，而非用参考软件的标书语义覆盖本仓。

## 2. 角色转换的三条硬性纪律

1. **禁止把标书语义引入主线**：新增功能不得以「技术评分项」「投标文件」「响应时间」为骨架；若确需参考其机制（如 `branch_id`），必须**改名 + 重写提示词 + 换数据源**后才可落地。
2. **确定性优先于 AI 判断**：危大阈值（基坑 3/5m、脚手架 24/50m、模板 8/18/15/20）必须由**代码单一口径**（`HAZARD_THRESHOLDS`）注入，**不得交给 AI 判断**。参考软件的目录审核把评分覆盖性交给 Agent，本仓须改为确定性前置。
3. **单向兼容**：所有新增默认关闭、零数据迁移、关闭时行为逐字节一致（沿用 AGENTS.md §3.1.3）。

### 1.2 工作流程（本仓口径）

```
上传 → 解析器选择(可回退) → 文本化(表格标记/页码) → 截断诊断
     → 按文档分段(400000×0.8 均分，默认关闭；旧滑动窗口 16000/500)
     → 逐提取项 × 逐段 → AI 提取(json/markdown)
     → 分段合并 → 缺失标注三态判定 → 落库 bid_analysis_items
     → 物化 doc_extractions + 级联失效下游
```

### 1.3 核心逻辑

- **分段策略**：`400000×0.8` 段上限 → `ceil` 段数 → **尽量均分**；断点先搜严格窗口（`0.12×段长`）再放宽（`0.25×段长`）；候选点须过四重约束（段长区间 + **剩余长度 ≥ 剩余段数** 且 `剩余/段数 ≤ max`，防尾段塌缩）；硬切点做 Unicode 代理对保护。**默认关闭**，旧滑动窗口行为逐字不变。
- **标段上下文独立第二条 system 消息**（易标口径）：标段限定与「必须逐条输出结构化结果」等硬性纪律混在一段会**弱化作用域约束**；独立消息在**消息层级**上表达作用域。无 hint 时输出与旧版逐字一致。
- **提示词顺序优化**：`system`（稳定规则）→ 全文/资料（最大最稳定）→ 任务差异（最后）。同一份数据格式必须稳定（标题写法、换行、列表顺序一致，**不塞时间戳**）。

### 1.4 提示词

**参考原文要点**（技术评分项，五段式自我反思）：
> 目标定位（识别技术评分/评标方法章节，忽略商务价格资质）→ 提取内容结构化（评分项名称/权重/评分标准/数据来源）→ 处理规则（模糊按上下文、表格按行、缩进编号、单位统一分或%）→ 验证（覆盖性 + 权重总和一致）→ **只返回提取结果**。

**专项方案改写版**（危大辨识，建议新增 `hazardIdentification` 项）：

```
【目标定位】识别工程资料中与危险性较大的分部分项工程相关的章节：工程概况、地质勘察、
  建筑与结构概况、施工部署、施工工艺、监测方案、危大工程清单。忽略商务报价、投标承诺、
  资质业绩等与施工安全无关的内容。
【提取内容】按建办质〔2018〕31号附件一六大类组织：
  1 基坑工程 2 模板工程及支撑体系 3 起重吊装及起重机械安装拆卸工程
  4 脚手架工程 5 拆除工程 6 其他（幕墙/钢结构/预应力/地下开挖/有限空间/新技术新工艺新材料）
```

## 二、目录生成模块（outline）★ 角色转换核心

### 2.1 核心架构判断（本轮最重要的结论）

参考软件的「一级目录 ↔ 技术评分项一一对应」与本仓「一级目录 ↔ 九大章节」是**100% 同构**的四段式：

```
外部权威清单 → 目录骨架 → branch_id 稳定映射 → 机械覆盖校验
```

**但清单来源不同，这对本仓是净收益**：

| | 参考软件 | 本仓 |
|---|---|---|
| 清单 | 技术评分项（外部输入、数量不可控、可能为空） | **九大章节**（固定 9 个、**永不为空**） |
| 后果 | 需 `noTechnicalScoreMode` 完整旁路（3 套提示词）+ 处理项被合并/拆分/遗漏的审批流 | **两者都不需要** |
| 可靠性 | 依赖外部输入质量 | 规范固定，可枚举、可代码直出 |

> **⚠️ 为什么不用「危大六大类」作一级目录**：建办质〔2018〕31号中，危大六大类按**工程类型**分（基坑/模板/脚手架/起重/拆除/其他），九大章节按**方案内容**分（工程概况/编制依据/…/计算书及图纸）。二者是**交叉关系，不是包含关系**。且**非危大项目**（临时用电、消防、绿色施工等）用六大类作一级目录会**产出空目录**。
>
> **决策：一级目录 = 九大章节（代码直出）；危大六大类 = `detail_points` 约束 + 阈值确定性注入。**

### 2.2 功能清单

| # | 功能 | 参考软件 | 本仓状态 |
|---|---|---|---|
| O1 | 一级目录骨架 | 提示词约束 + 机械复核（**非代码硬锁**） | ✅ 已有 |
| O2 | **`branch_id` 稳定映射** | ✅ `attachBranchIdsToRoots`/`synchronizeScoreDirectoryPlan` | ❌ **缺** ★核心缺口 |
| O3 | 叶子数分配 | ✅ `createLeafAllocationPrompt` | ⚠️ 部分 |
| O4 | JSON Schema 校验 | ✅ Ajv + `json-validation` 工具 | ✅ `collect_json_response` |
| O5 | 目录审核 | ✅ **四态**（非 `{passed,suggestions}`） | ✅ `outline_quality` |
| O6 | 审核建议回灌重生成 | ✅ | ✅ |
| O7 | 目录可编辑（不破结构） | ✅ 三步保存 + 清空受影响正文 | ✅ `_save_outline_to_db` |
| O8 | 确定性前置 context | ✅ `buildOutlineReviewContext` | ⚠️ **需注入危大阈值** |

### 2.3 工作流程（改造后）

```
确定性前置（代码，非 AI）：
  枚举九大章节骨架 C1..C9 + 危大六大类 detail_points + HAZARD_THRESHOLDS 阈值
      ↓
一级目录 = 九大章节（9 分支，代码直出，消除 AI 猜测）
      ↓
叶子数分配（leaf_allocation）：按章节性质分配目标叶子数
      ↓
二三级目录生成（逐 branch_id 传 other_outline 防重复）
      ↓
JSON 解析 → Ajv Schema → 业务规则校验 → 定向修复 → 重试
      ↓
机械覆盖校验：九大章节是否 9/9 覆盖
      ↓
renumberOutline（程序统一编号，AI 不负责编号）
      ↓
目录审核（四态）→ 不通过则建议回灌 → 二次生成
```

### 2.4 核心逻辑

- **`branch_id` 是本模块最有价值的资产**：参考仓 `requirement_id: '^R[1-9]\d*$'` 是**纯格式约束零业务语义**，`branch_id: {minLength:1}` **完全无格式约束** → 换 `C1..C9` 只需改 pattern；且固定枚举对 `branch_id` 比对外部分类**更可靠**。
- **确定性 vs AI 的边界**：九大章节骨架**代码直出**；危大阈值**代码注入**；只有**二三级章节标题与描述**交给 AI。
- **`score_item_level: 1` 的 standalone 模式已跑通** ✅ ——「一级目录即分类本身」本仓已有先例，改造是同构扩展。

### 2.5 提示词（专项方案改写版）

## 三、全局事实模块（global_facts）★ 角色转换核心

### 3.1 事实语义改写（本模块转换的核心）

| 事实类别 | 标书语义 | **专项方案语义** | 本仓落点 |
|---|---|---|---|
| 工期 | 总工期 90 天 | 计划开工/竣工日期、总工期 | `deploymentSchedule` |
| 响应 | 响应 2 小时 | 应急响应时限、值班制度 | `emergencyResponse` |
| 人员 | 项目经理 1 人 | 专职安全员/特种作业人员配置 | `resourceAllocation` |
| 设备 | 塔吊型号 | 施工机具型号、监测设备 | `resourceAllocation` |
| 质保 | 质保 3 年 | 验收要求、监测周期 | `qualityAcceptance` |
| **危大参数** | ❌ 无 | **基坑深度、支撑高度跨度、施工总荷载、集中线荷载、脚手架搭设高度、单件起吊重量、起重容量、拆除规模** | ✅ `HAZARD_THRESHOLDS` 14 键 |

**根本矛盾点**：标书的全局事实解决「前后表述一致」；专项方案还要解决「**参数与阈值判定一致**」——第 1 章写「基坑深 6.5m」，第 5 章不能写「3m」，且**危大判定必须与之一致**。

### 3.2 三步流程（保留机制，替换语义）

1. **生成设定**：按上下文限制切分资料 → 分段提取「后续正文会反复使用、必须保持一致」的内容 → 知识库补充更具体且不冲突的技术设定 → 已有方案扩写**优先保留**原方案中的人员/设备/周期 → 合并重复、删除空泛 → 轻量事实清单 → **先让用户查看和修改**。
2. **编排期注入**：AI **只看事实标题**判断本章需要哪些事实；真正生成正文时，**程序按标题取出完整事实内容，只注入当前章节**。
3. **生成后二次检查**：按目录顺序把正文分组，每组 + 全局事实交 AI，**只检查已明确写出的事实冲突**；返回冲突章节/冲突原文/违反事实；修复返回 `old_text/new_text`；**唯一命中才替换**。

### 3.3 门控（本仓已超出，四条件 fail-closed）

```
has_conflict=0 AND is_resolved=1 AND is_simulated=0 AND is_stale=0
```
唯一出口 `facts_extractor.get_facts_inject_where()`。**四条件缺一即不注入**，绝不把模拟/矛盾/陈旧事实喂给正文。参考软件**无此门控**。

### 3.4 数据结构（本仓 `FactItem`，含四维标注）

```
{ id, title, value, source, confidence, is_simulated, is_stale, is_resolved, has_conflict,
  chapter(九大章节归属), fact_attr(定量/定性/关系/规范),
  source_kind(bid_doc/drawing/survey/overall_plan/manual), is_shared(跨章节共性) }
```

### 3.5 提示词（专项方案改写版：事实提取）

```
【角色】建筑工程专项施工方案参数提取专家。
【目标】提取后续正文会反复使用、必须全文保持一致的内容。
【重点】①工程地质与水文（地层、地下水位、渗透系数）；
  ②结构与荷载（层数、结构形式、基础类型、施工总荷载 kN/m²、集中线荷载 kN/m）；
  ③危大判定参数（基坑开挖深度 m、支撑搭设高度 m、跨度 m、脚手架搭设高度 m、
  起重容量 t、起升高度 m、单件起吊重量 kN、拆除对象规模）；
  ④施工资源配置（专职安全员、特种作业人员、特种设备型号）；

【纪律】必须是"本方案确定采用"的事实陈述，不是"招标文件要求"；

【只返回提取结果】
```

### 3.6 容错

- 门控 fail-closed（**本仓超出**）；
- 唯一命中才替换；找不到/多处相同**拒绝修改并重新尝试**（不猜）；
- 知识库补充与最终整理两阶段 **fail-soft**（失败记 warnings 后继续，绝不让已成功提取的事实整批丢失）；
- **一致性边界声明（必须保留）**：不能 100% 保证一致；全局事实本身错则正文会**一致地一起写错**；履约可行性、隐含逻辑与法律责任需专业人员复核。

### 4.2 分层消息结构（缓存命中关键）

```
[system] 稳定规则（角色+写作规范+输出要求）  ← 恒定，缓存命中率最高
[user]   项目/方案概述                        ← 同方案恒定
[user]   上级章节信息                          ← 同父章节下恒定
[user]   同级章节信息（防重复）                ← 同父章节下高度接近
[user]   当前章节任务（章节ID/标题/描述）      ← 唯一变化的，放最后
```
同一父章节下多个叶子节点，**只有最后一条变化** → 缓存命中。实测：OpenRouter + gemini-2.5-flash，第二次 `cached_tokens 19442/19737`，成本 0.0058→0.00067（≈10 倍）。

```
【写作规范】
```

### 6.1 Mermaid 三层执行链路（本仓已完整落地）

```

```

**修复提示词要点**（参考原文）：
> 只返回 JSON；目标是让 Mermaid 在浏览器前端稳定渲染；**优先最小必要修改**；优先 `flowchart TD`；节点 ID 只用 ASCII 字母数字下划线；中文标签必须写成 `A["中文标签"]`；不使用多节点连接简写；不使用分号；**不输出 Markdown 代码围栏**；过于复杂则简化为可渲染的核心流程图。

本仓已具备：`chart_validators.validate_mermaid` + `image_engine.repair_mermaid` + `prompts/charts.py`。

### 6.3 AI 生图（角色转换点）

- 用编排生成的 `image.prompt`，**补充固定风格要求**：
  - 图示风格：工程项目图示风格，结构清晰、专业克制，**适合专项施工方案插图**；避免品牌标识、水印、夸张营销元素和无关文字。
  - 实景风格：专业实景照片风格，真实、克制，**适合专项施工方案插图**。
- ⚠️ 生图模型易生成「宣传海报风、科技蓝大屏风」，放在方案里非常违和。**方案里的图应该像工程资料，不应该像广告图。**

### 6.4 配图类型最终过滤（AI 提名，程序拍板）

即使 AI 判断「既可用 mermaid 也可用 AI 生图」，**程序也要过滤只保留一种**：`illustration_type ∈ {ai, mermaid, none}`。
数量上限（本仓已落地）：每章同类型 ≤1；全方案同类型默认 ≤3；`ai_image` ≤6。

### 6.5 数量控制与预编排价值

- AI 可提名很多候选，最终按上限择优；候选小节**分段**，每段选优先级最高，避免前几章耗尽额度。
- 表格控制：少量 ≤20% / 适中 ≤40% / 大量宽松。
- **预编排价值**：正文生成前规划 → 成本可预估、图片分布均匀、正文与图片形成呼应。本仓同步登记**等价实现了「正文知道本节会配图」**，属已超而非缺失（G1）。

## 3.2 关键改写点详述

### ★ K1：目录骨架（最高价值）

```
参考：TECHNICAL_SCORE_GROUPS（技术评分大项，数量不可控，可能为空）
  → SCORE_DIRECTORY_PLAN（一一对应计划，requirement_id ^R[1-9]\d*$）
  → collectScoreMappingCoverage（机械覆盖校验）

本仓：NINE_CHAPTERS（C1..C9，固定 9，永不为空）
  → OUTLINE_BRANCH_PLAN（branch_id，C1..C9）
  → collectChapterCoverage（机械覆盖校验 9/9）
```
**收益**：①消除 `noTechnicalScoreMode` 整个旁路（3 套提示词）；②消除一级目录的 AI 猜测（代码直出）；③`branch_id` 固定枚举比外部分类更可靠。

### ★ K2：危大阈值必须确定性注入

参考软件把「评分覆盖性」交给 Agent 判断；本仓**必须**改为确定性前置：

```
HAZARD_THRESHOLDS（唯一事实源，14 键，全闭区间）
  → 按命中子类查阈值 → 渲染为 detail_points 文本
  → 注入 outline-review-context（确定性，不经 AI）
```
**理由**：危大阈值判错 = 安全事故风险；`evaluate_hazard_level` 已是确定性函数（§4.8 单一事实源），**不得让 AI 复算**。

### ★ K3：前置门禁

参考：`throw new Error('请先完成技术评分要求解析，再生成目录')` + `status !== 'success'` **强门禁**。
本仓：九大章节**永不为空** → **删除该强门禁**（收益最大：消除「必须先跑完提取才能生成目录」的硬耦合）。

### ★ K4：缺失判定

参考：`=== '没有提及'` 严格等值判定 + `isMissingTechnicalScoreItems` 四向专判。
本仓：改为**四态判定**（未提取到 / 没有提及 / 部分缺失 / 有效），避免 §4.11.2 的**假绿教训**重演。

# 第五部分：参考仓源码考古的否定性发现（重要纠错）

> ⚠️ **源文档（`全功能模块.txt`）多处描述与真实源码不符**。以下结论均经源码验证，**不可照文档实现**。

| # | 文档声称 | 源码事实 | 影响 |
|---|---|---|---|
| N1 | Pydantic 定义 `OutlineItem`/`OutlineResponse` 等 | ❌ **不存在 Pydantic**，用 **Ajv + JSON Schema** | 实现选型错误 |
| N2 | `collect_json_response` 蛇形命名 | ❌ 实际为 `collectJsonResponse`（27 处引用） | 检索失败 |
| N3 | `ChapterContentRequest` | ❌ **不存在**，等价物是 IPC `payload` | 设计对不上 |
| N4 | `check_json` 校验函数 + 3 次重试 | ❌ **无此函数名**；实际 `json-validation` 工具 + **重试 0 次** | 容错预期落空 |
| N5 | 目录审核返回 `{passed, suggestions}` | ❌ 实际是**四态** `{status, issues, suggestions}` | 契约不符 |
| N6 | `other_outline` 传参防重复 | ❌ **无此变量**；实际是「单一 Session + 文件传递」 | 机制描述错误 |
| N7 | 完整目录失败切换分步生成 | ❌ **源码中未找到** | 能力不存在 |
| N8 | 一级目录「程序锁死」 | ❌ 实为**提示词约束 + 文件名 + 门禁 + 门禁文案**四重硬编码 | 耦合度被低估 |
| N9 | 全局事实单一实现 | ❌ **两套并存**（`globalFactsTask.cjs` / `globalFactsTaskV2.cjs`），`taskService` 只挂一套 | 需辨别挂载 |
| N10 | `should_continue_round` | ❌ 命名不存在，等价物另有其名 | 检索失败 |

> **教训**：参考文档是**二手摘要**，与一手源码存在系统性偏差。本仓 AGENTS.md §4.15/§4.16 已两次记录「参考软件某能力本仓没有」的教训；本轮再次验证——**任何「引入参考能力」的动作都必须先读源码，不能只读文档**。
