### 2.2 编号命名空间模型（反推出的真实设计）

```
              ┌────────────────────────────────────────────────┐
  目录 (DB     │  L1 第一章 … L2 1 … L3 1.1 … L5 1.1.1.1        │  ← 章节命名空间
  sections)   └────────────────────────────────────────────────┘
                             │  冲突根源
              ┌────────────────────────────────────────────────┐
  正文子标题   │ has_children=False → X.Y / X.Y.Z（L3+，会撞号）  │
  (content ##)│ has_children=True  → 1）、/ a、（L6/L7，已隔离） │  ← E3 修复
              └────────────────────────────────────────────────┘
```

- 存储态 `outline_json.id` 用**结构编号**（`1` / `1.1` / `1.1.1`），
  展示态经 `stored_id_to_display` 映射（`1`→`第一章`，`3.2`→`2`）。
  依据 `test_numbering_unification.py:140-156`。
- AI 常以存储编号为基准自算（`3.2.1`），规范化函数负责纠回展示口径（`2.1.1`）。
  依据 `:183-189`。
- 「预览 = 落库 = 导出」三处同源由 `content_subheading_renumber` 单开关控制。
  依据 `:379-386` 与 `test_numbering_batch_perf_20260927.py:252-262`。

### 2.3 分步生成状态机（长方案）

证据来自 `app/db.py` 头部注释（`db.py:38-45`、`:889-893`）与
`test_content_generation_g12.py:1-29`：

- 真实生产事故链（`logs/backend.log` 2026-09-23 trace=9fe4498339da）：
  `task_registry.update_progress` 落库失败 ×4 → 保存目录生成 checkpoint 失败 →
  `finish_task` 终态落库失败（`database is locked`）→ 任务在 DB 里永远 `running` →
  前端 `pollTaskUntilTerminal` 死等。
- 已建守卫：`busy_timeout` 5s→15s；`finish_task` 内存清理进 `finally`（G12-5，
  `test_content_generation_g12.py:337-379`）；409 竞态守卫改为状态感知（G12-4，
  `:295-324`）。
- **已知盲区**：G12-5 的守卫用例 `task_type="content_generation"`；
  目录生成用的 `outline_generation` 走同一个 `finish_task`，却无等价守卫用例。
  对照 `:253-257` 只有「outline_generation 不参与手工保存 409 判定」的排除用例。
