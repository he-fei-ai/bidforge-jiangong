**本轮新发现（唯一真 BUG）**：

### BUG-1（P0 · 活体路径）：续写模式 `_plan_json` UnboundLocalError → 「续写本章」100% 失败

- **位置**：`sse_handlers.generate_content` → `gen_one`（修复前 L4102/L4182）。
- **根因**：`gen_one` 内 `_plan_json` 只在非续写分支由 `_build_generation_context` 五元组
  解包赋值；而落库调用 `_persist_and_notify(..., plan_json=_plan_json)` 为两种模式共用。
  Python 把「函数体内任意位置赋值过的名字」判为局部变量 ⇒ continue 分支执行到落库点时
  该名字从未绑定 → `UnboundLocalError` → 被 `guarded_gen` 的 except 兜成
  `section_error("生成异常: …")` → 终态 failed。
- **引入时机**：R70（2026-10-11，`plan_json` CASE WHEN 透传引入）。git show HEAD 证实
  HEAD 同构带病（L7033/L7106）。R70 注释明言「续写分支显式以 _plan_enabled=False 构建
  上下文，同样拿到 ''」—— 实现却把第 5 位解包丢弃成 `_`，注释与实现不符（本仓反复
  记录的「注释宣称已做、实现没做」族）。
- **为什么存活**：continue 模式**零端到端测试覆盖**（全 tests/ 无 mode="continue" 用例）；
  且该模式的叶子必有旧正文（`mark_db=False`），章节状态/字数都不变，症状只有日志区
  一条红字 —— 用户感知为「点了续写没反应」。
- **影响**：前端「续写本章」（SchemeWorkbenchPage L3588 → POST generate-content
  mode="continue"）自 2026-10-11 起 100% 失败。
- **修复**：续写分支同样绑定 `_plan_json`（`_plan_enabled=False` ⇒ 恒为空串，
  CASE WHEN 保留原列语义不变，与 R70 声明意图一致）。

## 七、遗留问题与后续建议

1. **`frontend/src/api/index.ts` CRLF/LF 混合行尾**（本轮基线红 #2，并行会话文件面不处理）：
   prettier/.editorconfig 引入后 `test_review_autofix_closeout_r55` 的 LF 纯度守卫红。
   建议由重构该文件的会话统一行尾策略（仓内 `.gitattributes` 显式声明或 prettier
   `endOfLine` 配置），否则该守卫在 autocrlf 环境会反复假红（R161 教训：强行归一回 LF
   不可持久）。
2. **continue 模式测试覆盖长期为零**：本轮已补 4 例（全链路 + 选章补集 + 静态锁）；
   建议后续把 `mode="section"`（单章强制重写）同样纳入端到端用例族（当前仅静态锚）。
3. **`hooks/useContentGeneration.ts` 双实现并存**：R106 登记的「生产零引用并行死实现」
   在本轮重构后仍存在（SchemeWorkbenchPage 未 import 它，正文生成仍内联在页面），
   且 contentTerminalParity 测试仍在引用其文件名作 parity 面。建议由前端重构会话
   决断：要么让页面切换到该 hook，要么删除该文件并同步 parity 测试锚。
4. **同族静态探盲**：本轮 BUG 属「分支条件赋值 + 无条件引用」类 UnboundLocalError，
   ruff/pyflakes 均不报。建议后续在 CI 加一条 AST 探针（对 sse_handlers 等巨型闭包文件
   扫描「名字仅在一个分支赋值、另一分支无条件引用」形态），防同类病再潜伏四年。
