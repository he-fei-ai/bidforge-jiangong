## 2. 修复清单（根因 + 证据 + 文件 + 关键函数）

### F-1 · 全局事实 R13 读路径判空补齐（P2 · 8 处）
- **根因**：`global_facts.py` 事实半区仍有 8 处 `await db.execute(...)` 后直接 `fetchone()/fetchall()`，无 R13 判空。R138 D4 只收口了部分读路径与写路径，这 8 处漏网。最危险的是 `_invalidate_item_update_caches`（1433-1437）在 `_apply_item_updates` **commit 之后**调用 —— R13 下把「已写成功」变成 500，且导出缓存与 `facts_updated_at` 不推进，界面永不提示「事实已变更」。
- **证据**：`_invalidate_item_update_caches`、`_apply_item_updates:1508`、`check_danger_scheme:1133`、`ack_fact_stale:2166`、`resolve_conflict:2323`、`batch_ack_stale:2271`、`batch_resolve:2500/2512`、`clear_all_facts:2410` 均无判空。
- **修法**：每处 `execute` 后插 `_require_fact_read_cursor(cur, "<操作>")`（既有 R138 出口），None → 503（可重试），日志文案区分操作名。
- **文件**：`backend/app/routers/global_facts.py`。

### F-2 · 内容 Agent 修复图表重登记不对称（P1 · 跨模块）
- **根因**：`content_agent.py:80` 的 `POST /content-agent/repair` 传 `resync_fn=None`，而 `repair_agent` 集成路径（`repair.py:313` 消费）在正文 UPDATE 同事务内**全量重登记本章内联图表**（R92 写点同步补链）。路由入口漏注入 ⇒ 经该端点的 Agent 修复回写正文后，`chart_registry` 与正文图表块可能失同步（旧图号/旧登记残留）。
- **证据**：`content_agent.py:80` 注释「路由层可按需注入 _chart_pipeline.resync」但从未注入；`consistency_repair._make_chart_resync` 展示正确口径（`resync_inline_charts(..., enforce_limits=False)` 返回校正后正文）。
- **修法**：路由内建同口径 `_resync`（懒导入 `resync_inline_charts`，`enforce_limits=False`），注入 `run_agent_section_repair`。
- **文件**：`backend/app/routers/content_agent.py`。

### F-3 · 批量自动修复 >4000 字章节截断（P1 数据丢失 · 跨模块）
- **根因**：`_fix_each_section:815` 把 `items[].after` 截为 `[:4000]`（仅预览），但 `_chain_section_fixes:923-936` 读 `rec["after"]`（截断）作链式累积 `content`，`stage_fixes` 经 `save_repair` 落库截断条目；`/confirm` 的 `_merged_after_if_prefix:338` 又读 `it.get("after")`（截断）→ `_persist_fixed` 落库截断正文。批量「一键修复全部阻断项」（默认 `accept_all=true`）主线即触发；单条 `/apply` 走 `pending` 全文不受影响（两入口不对称）。
- **证据**：`review_autofix.py:815/924/936`、`routers/review_autofix.py:338/540/192-198`；现有 `BatchFixModal.test.tsx` 样本均 ≤4000 字故漏过。
- **修法**：① `_chain_section_fixes` 链式累积改用 `sec_pending[0][2]`（全文），未变更回退 `content`；② 每条 item 加法式透传 `after_full`/`before_full`（全文），`after`/`before` 预览键保持 `[:4000]` 展示契约；③ `_merged_after_if_prefix` 优先取 `after_full`，旧批次（无 `after_full`）回退 `after`（向后兼容）。
- **文件**：`backend/app/services/review_autofix.py`、`backend/app/routers/review_autofix.py`。

### F-4 · repair_agent R13 假成功（P1 · 服务层盲区）
- **根因**：`repair_agent.py:517-522`（正文 UPDATE）与 `:562-566`（冲突状态 UPDATE）用裸 `db.execute` + `commit`，无 cursor/rowcount 检查。R13 下正文未落库却 `repaired_conflicts.update` + `status='repaired'` → 界面报「已修复」而正文一字未改。`review_db` docstring 自称「最后一个空白点」但只收口了 3 个 router，同模块 `repair_agent` 是护栏覆盖盲区。
- **修法**：写路径改走 `review_db.exec_write`（模块既定 R13 单一出口，`require_rows=True`）：游标 None 或 0 行 → 503，绝不假成功。
- **文件**：`backend/app/services/repair_agent.py`。

### F-5 · 导出阶段进度分母硬编码 `/3`（P3）
- **根因**：`SchemeWorkbenchPage.tsx:11739` 进度文案分母硬编码 `/3`，但 R126 下线 PDF 后 `EXPORT_STAGE_ORDER` 只剩 `{charts:1, docx:2}` 两阶段 ⇒ 进度永远少显示 1 格（`阶段 2/3`）。
- **修法**：模块作用域新增 `EXPORT_STAGE_COUNT = Object.keys(EXPORT_STAGE_ORDER).length`（React Compiler 不编译模块级代码，避免在组件渲染内用 `Object.keys` 触发 "Compilation Skipped"），JSX 分母用 `{EXPORT_STAGE_COUNT}`。新增阶段自动跟随。
- **文件**：`frontend/src/pages/SchemeWorkbenchPage.tsx`（:3024、:11739）。

### F-6 · `_EXPORTER_VERSION` 死副本漂移（P2 债）
- **根因**：`export_audit.py:163` 仍持有 R86 前本地字面量 `"22"`，而 `export._EXPORTER_VERSION` 已 `"31"`。任何 `from export_audit import _EXPORTER_VERSION` 都会拿到错误版本（旧缓存命中/指纹击穿）。
- **修法**：改为 `_EXPORTER_VERSION = _ex._EXPORTER_VERSION`（引用权威源），消除漂移，行为零变化。
- **文件**：`backend/app/routers/export_audit.py`。

### F-7 · 正文标准/格式契约 fail-soft 无降级信号（P2 · R137-F 教训）
- **根因**：`content_format_contract.py:431-432`、`content_standard.py:698-700/840-842` 均 `except Exception: return 空报告` 且模块**无 logger** —— 「自检器宕了」与「算法写错」在日志上毫无区别，截断正文最需自检时反而静默无结论（`checked=False, issues=[]`）。
- **修法**：两模块补 `logger`（`content_format_contract` / `content_standard`），三处 except 内 `logger.exception(...)` 留降级信号（fail-soft 行为不变，仅可观测）。
- **文件**：`backend/app/services/content_format_contract.py`、`backend/app/services/content_standard.py`。

### F-8 · review_status 变更不失效总检缓存（P2 · D3）
- **根因**：`/overview` 缓存键 `(content_fingerprint, facts_signature)` 不含 `review_status`（`compliance.py:1142`），`review.py` 三个状态写端点（批量/单章/submit）均不调 `invalidate_overview_cache` ⇒ DLV-09（review_pending/rejected/missing）结论最长 120s 陈旧且前端无「陈旧」提示。
- **修法**：三端点 commit 后懒导入 `invalidate_overview_cache(scheme_id)`（与 `schemes/projects` 删除方案同口径，懒导入防环）；批量端点仅 `changed>0` 时失效。
- **文件**：`backend/app/routers/review.py`。
