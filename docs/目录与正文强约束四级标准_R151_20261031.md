## 1. 生产库实况（只读实测，清洗方案的依据）

`data/scheme_assistant.db`：sections 共 525 行 = **L1 48 / L2 140 / L3 337，L4=0，L5=0**；
337 个 L3 **全部是旧叶子**（272 个带正文）；5 个方案全部是三级树。

两个直接推论：
1. **「现有 L5」在 DB 章节表中并不存在**——历史超深标题在落库前已被 `normalize_outline`
   裁剪进父级 description（2026-09 三级标准契约）。L5 合并属**防御性兜底**（直写 DB 脏数据）。
2. **真正的旧数据缺口是数量维度**：旧三级树按新标准全量不合规（L3 无四级子节点、
   L1 下二级普遍 2~3 个 < 3 等）。清洗报告实测 5 方案违规 59~111 处/方案，全部需 AI 标准化。

## 2. 单一事实源（新增 `app/services/outline_rules.py`）

```
OUTLINE_MAX_LEVEL = 4                # L4 为最小叶子，严禁 L5
CHILDREN_MIN = {1: 3, 2: 3, 3: 4}    # L1 下 3~5 个 L2、L2 下 3~5 个 L3、L3 下 4~6 个 L4
CHILDREN_MAX = {1: 5, 2: 5, 3: 6}
```

- `validate_outline_nodes(nodes)`：树形 JSON 判据（层级按树深度推导；数量区间查
  **level-1**（该层节点数=上一层父节点的子节点数）；L4 挂子级=DEPTH_EXCEEDED 且深层后代
  由该条统一承载不逐个上报；顶层 L1 组数量用户标准未约束、刻意不判——危大工程 10 章是常态）。
- `validate_section_rows(rows)`：DB 行判据（孤儿按根 fail-soft；额外校验点分编号子承父系）。
- `merge_section_rows_deeper_than_leaf(rows)`：确定性 L5+ 合并（自底向上，标题加粗行+正文
  追加进父 L4 content，纯函数不修改入参）。
- `format_violations_message`：标准文案「**目录结构不合规，请先修复目录**」+ 逐条点名
  （全仓唯一出现面，护栏锁死不得在路由/服务层复制第二份）。

## 4. 旧数据清洗方案（用户指令 五 · 两段式）

**第一段（确定性，本轮交付）**：`backend/_r151_clean_outline.py`
- 默认 dry-run 全方案体检；`--apply` 执行 L5+ 合并至父 L4（标题加粗行+正文原文追加进父
  content，行删除，合并后按树位置重算点分编号）+ 自动备份 DB + 报告落 `artifacts/r151/clean_report.json`。
- 生产库 dry-run 实测：5 方案 deep_rows_total=0（无 L5 可合并，幂等安全）；
  违规 59~111 处/方案，全部为数量不达标。

**第二段（AI 面，本轮交付端点）**：数量不达标需要**编造新章节标题**（属生成域，不虚构进
脚本），走前端「修复目录结构（AI 标准化）」按钮 → standardize-outline → 用户确认 →
save-outline 落库（正文按标题匹配智能保留）。存量 L3 上的旧正文**刻意保留**（闸门只拦
新生成、不清数据）；其 description/标题作为 AI 拆分四级子节点的依据输入。

## 7. 判据教训归档

1. **树形递归的数量索引陷阱**：「第 level 层节点数 = level-1 父节点的子节点数」——判数量
   区间必须查 `CHILDREN_MIN[level-1]` 并把违规归属到父节点；首版按 level 查会把「危大 10 章」
   误判违规（DB 行口径按行 level 查则正确，两口径并存时必须分别自证）。
2. **源码锚必须断完整赋值形态**（R116 教训③第四验证）：A/B M4 把
   `_gate_violations = validate_section_rows(...)` 改成三元短路后，只断函数名的锚照样绿；
   锚断 `_gate_violations = validate_section_rows(all_sections)` 整句才 CAUGHT。
3. **文案单一事实源的反向锚会被自己的 docstring 误伤**（R144 教训④再验证两次）：
   「目录结构不合规，请先修复目录」在 outline_rules docstring、standardize-outline docstring
   各出现一次，`count==1` 与「其他文件不得出现」两种写法先后翻车；最终判据=「全 app/ 只允许
   outline_rules.py 一个文件含有该串（含 docstring）」。
4. **A/B 判定函数按 pytest 摘要行写**（R144 教训⑥再验证）：全文 grep "error" 会被测试名
   （test_ai_failure_raises_502）与 stderr 噪声误伤；且 `caught` 语义必须等于「护栏失败」——
   本轮把 `return (not passed)` 改成 `return passed` 时连带把语义反转，M0 GREEN 掩盖了方向错误，
   直到看 M1 明明 1 failed 却报 MISSED 才定位。
5. **E2E 探针不得顺手触发真实 AI**：E5 首版用 adjust-outline 当「闸门未被占用」探针——它
   本身就是 AI 调用，无 key/429 重试下挂满 8 分钟；改进程内直查 registry（零 AI）后 118ms。
   E2E 打桩必须落在被测函数实际读取点（R149 教训⑤同族）。
6. **AI 桩耗尽会漏到真实 provider**：r84 并发窗口用例的 scripted chat 桩只编排了既有轮次，
   新增的合规修复调用落在桩外 → 打到真实 agnes（429 实名认证）→ 测试由「确定性」变「环境型
   假红」。凡给生成链路加新 AI 调用点，必须回扫全部 scripted-chat 测试并让夹具产出**合规树**
   （该批夹具同时是「新标准」的行为样本）。
7. **asyncio E2E 的退出挂起**：ASGITransport + observability 后台写线程持有 loop，脚本打印
   `E2E_EXIT=0` 后仍可能不退出（timeout 误报 124）；结果与退出码以打印行为准，进程退出用
   `os._exit` 显式收口。
8. **轮次编号避让要在建第一个文件前查**：本轮 R150 编号在实现中段才与并行会话的 AI 网关
   R150 相撞，被迫全仓 sed 改号（30 文件）；开局 `ls docs/ | grep R1xx` + 查未跟踪脚本清单
   应成为建基线前的固定动作。
9. **ruff --fix 会静默重写行尾**（新教训）：CRLF 文件被归一成 LF，纯自持的字节体检抓不到；
   字节体检判据必须是「与 HEAD 行尾约定一致」（git blob 对比），改动前先记基准。
10. **注册新提示词 = 三处同步**：模板 `_reg` + 契约表 `PROMPT_VARIABLE_CONTRACTS` +
    r132 基线清单（未解析占位符白名单）——漏任何一处都会被 r39/r38/r132 三道契约护栏拦下；
    这是「新增面必须回扫全部登记表」纪律的提示词版。
11. **生成链路加闸门 → scripted 夹具家族整体升级**：全量首轮 50 失败中 40+ 项是
    generate_outline/generate_content 的三级桩（r105×14 / window_step×8 / auto_match×3 /
    fence×3 / r149 / r137-E2E约定 / r132契约 / 节点上限锁…）。新 AI 调用点+新校验点落进
    生成主链路时，**全仓 scripted 夹具都是该链路的「行为样本」**，必须按新标准批量升级，
    而非只修直接相关簇。
12. **E2E 约定守卫锚定「最新脚本」**（r137-E `_current_e2e_script` 取 `_e2e_r*.py` 排序末位）：
    新增 E2E 脚本即继承全套约定（可选依赖声明 + `[SKIP]`/`E2E_EXIT`/`return 2` 语义 +
    `tmp = Path(tempfile.mkdtemp` 素材构造标记），新建脚本必须先读该守卫再动手。
13. **计数型锚要数全自己加的点**：checkpoint 统一日志前缀 13→15（我加了闸门与合规失败
    收尾两处，先按 14 修又错一轮）；改动前后 `grep -c` 实测再落断言。
