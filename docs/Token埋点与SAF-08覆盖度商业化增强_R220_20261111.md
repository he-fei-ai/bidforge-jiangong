## 一、需求拆解与商业化验收锚

| # | 用户诉求 | 商业化验收锚 |
|---|---|---|
| 1 | Token usage 埋点缺口 | 单次 AI 成功调用的成本**可采集、可聚合、可查询、可串联**；口径与既有统计端点同源；不落密钥/正文；埋点故障不影响主流程 |

## 二、落地前亲验（不采信探查代理结论）

**用量链路全景**：`BaseProvider._set_usage` / `_merge_usage` 已把各厂商字段归一成 `prompt_tokens`/`completion_tokens`/`cached_tokens` → `provider_factory.extract_usage(provider)`（`_attempt_candidate:3897` 成功分支）→ `ai_audit_logs` 三列 → `/ai/stats`（`routers/ai_config/usage.py`）与 `/system/activity`（`tokens_today`）。前端已消费 `tokens_today`。

- **真实缺口**：成功返回处**没有任何逐调用结构化日志**，只有落库后的聚合；R219 的 2658 行日志里只能采到 2 条 `max_tokens` 放大记录 ⇒ 真实 Token 消耗基线无法建立、无法按 `trace`/`scene` 归因。
- **本仓病根**：`usage.py:78-80` 与 `:124-126` 是 `round(cached*100.0/prompt, 1)` 的**两份内联实现**（口径漂移风险）。

**SAF-08 链路全景**：`preflight_engine.check_hazard_params` → finding → `audit_scoring` / `_persist_run`（整条 dict 透传、**无键过滤**）→ `/compliance/overview` 与 `/preflight` → 前端 `ReadinessDashboard`。

- **真实缺口**：`ctx.facts` 为空时直接 `return []`；「事实未装配」与「有事实、核对通过」在 finding 清单里**都是零条**，用户会把「根本没查」当成「已核对无危大超阈值」（安全方向假绿）。
- 前端对 SAF-08 特定字段**零消费**（全仓 `frontend/src` 检索 0 命中）。

## 三、增强 1 · Token 用量结构化埋点闭环

### 3.1 单一事实源（新增）

`backend/app/services/ai/usage_logging.py`（services 层叶子，只依赖 stdlib + `app.config`）：

| 出口 | 职责 |
|---|---|
| `normalize_usage_fields(u)` | 把 `extract_usage` 三字段扩成恒定五键（含 `total_tokens`、`cache_hit_rate`）；非法/缺列/负数逐项归零 |
| `compute_total_tokens` / `compute_cache_hit_rate` | **唯一计算出口**，与 `usage.py` 的 `SUM(prompt+completion)` 与 `cached/prompt` 口径逐字同源；`prompt=0` 返回 `None`（不伪造 0%） |
| `format_usage_log` | 单行 key=value（字段顺序固定），上下文值按白名单清洗成单 token，防换行/空格/控制字符破坏日志解析 |
| `record_usage_event` / `get_usage_snapshot` / `reset_usage_snapshot` | 进程内**有界**聚合（按 provider / scene），线程锁保护；快照为深拷贝 |
| `log_usage_event` | 一站式埋点（日志 + 快照），内部异常全吞 |

### 3.2 接线与收口

| 文件 | 改动 |
|---|---|
| `services/ai/provider_factory.py` | 成功分支 `u = extract_usage(provider)` **之后**接 `_log_ai_usage(...)`，带 `provider` / `model` / `scene` / `duration_ms` / `context_suffix()`（trace/pid 串联）；import 单一出口 |
| `routers/ai_config/usage.py` | `:78-80` 与 `:124-126` 两处内联命中率计算**收口**到 `compute_cache_hit_rate`，消除第二份实现（SQL 侧表达式保留并同源注释） |
| `routers/prompts.py` | `GET /system/prompt-metrics` 加法式回传 `ai_usage` 快照键（既有 `today` 等键逐字不变） |
| `config.py` | `ai_usage_log_enabled`（默认 `True`）、`ai_usage_snapshot_max_keys`（默认 `256`） |

### 3.3 真实产物（本轮实测）

```
ai_usage prompt_tokens=1200 completion_tokens=800 cached_tokens=300 total_tokens=2000 cache_hit_rate=25.0 provider=agnes model=gpt-x scene=outline duration_ms=1234 trace=abc123 pid=999

SNAP 2 {'prompt_tokens': 1500, 'completion_tokens': 900, 'cached_tokens': 300, 'total_tokens': 2400}
totals_cache_hit_rate=20.0  by_provider=['agnes','sensetime']  by_scene=['outline','content']
```

日志采集侧按 `ai_usage` 前缀过滤即可建立**逐调用**成本基线（provider / 模型 / 任务类型 / trace / 耗时 / 缓存命中率），补齐 R219 无法建立的 Token 基线。

### 3.4 设计约束（商业化红线）

- **fail-soft**：日志通道抛异常仍完成快照累计；埋点任何异常都不改变 AI 返回、不阻断降级链；端点读取失败降级为空结构。
- **不落敏感信息**：只记数值与 provider/model/scene，不记密钥、正文、提示词原文。
- **有界**：维度 key 超限归 `__overflow__`（调用次数与总量不丢），防长跑内存膨胀；快照重启清零，**不新增表/列/DDL**。
- **可控**：`ai_usage_log_enabled=False` 时零格式化、零加锁开销。

## 四、增强 2 · SAF-08 事实覆盖度（未检查 ≠ 通过）

### 4.1 反证（锁住「漏判真实存在」）

```
not_checked = check_hazard_params(PreflightContext(scheme_name="某住宅楼施工组织设计", facts=[]))   → []
checked_no_issue = check_hazard_params(... facts=[{"name":"建筑面积","value":"5000平方米"}])        → []
两者完全相等 ⇒ 单看 findings 无法区分「没查」与「查过没问题时」
```

### 4.2 二态设计与三层落点

`preflight_engine.build_fact_coverage(facts)` 为**唯一出口**，返回 `{state, participating, rules, reason}`：

| state | 含义 | 用户语义 |
|---|---|---|
| `unchecked` | 无有效事实参与 | SAF-08 **未执行**，结论不得据此判定方案非危大 |
| `checked` | 有事实参与 | 规则已执行（无论最终是否报出 finding） |

> **刻意不提供 `partial`**：路由层只装配「门控后可注入」的事实，无法从 `ctx` 反推被排除的总量；臆造分母会制造第二种假绿。

| 层 | 落点 |
|---|---|
| finding 级 | `check_hazard_params` 报出的 SAF-08 finding 加法式带 `facts_participating` / `facts_coverage_state`（主链整条 dict 透传，中途不丢） |
| 顶层响应 | `/compliance/overview` 与 `/preflight` **两处** `payload.update` 均加法式回传 `fact_coverage` |
| 前端可见 | `types/audit.ts` 新增 `FactCoverage` 接口 + `ReadinessOverview.fact_coverage?` + `PreflightFinding` 两字段；`ReadinessDashboard.tsx` 渲染三态：`unchecked` → 黄色警告「全局事实未参与本次危大参数核对（未检查）…这不属于核对通过…不得据此判定方案非危大」；`checked` → 次要文本「危大参数反哺已执行（SAF-08）：参与核对事实 N 条」；**旧后端无该键时不渲染**（加法式兼容） |

## 七、运维与后续建议

**部署**：需重启后端（`config.py` / `provider_factory.py` / `usage_logging.py` / `prompts.py` / `ai_config/usage.py` / `preflight_engine.py` / `compliance.py` 常驻）+ 前端重建（`types/audit.ts` / `ReadinessDashboard.tsx`）。零迁移、零 DDL；两项新配置可不设置。

**启用后验证**：
1. 任意触发一次 AI 调用，日志出现 `ai_usage prompt_tokens=... completion_tokens=...` 且带 `trace=`；
2. `GET /api/v1/system/prompt-metrics` 出现 `ai_usage` 键，`sample_count` 随调用递增；
3. 未装配全局事实的方案执行总检，页面显示黄色「未检查」警告；确认事实后重新总检，显示「参与核对事实 N 条」。

**采集建议**：日志平台按 `ai_usage` 前缀建索引，按 `provider` / `scene` / `model` 维度做成本看板；`trace` 与访问日志 `kind=stream`（R219）串联可还原「一次生成任务 → 每次 AI 调用 → 成本」全链。

**后续登记**：① 用量快照持久化（跨重启对账/计费）；② `fact_coverage` 扩展到其余事实类规则并在预检报告里落档；③ `ai_usage` 在前端运维页可视化（当前为运维端点，供监控平台消费）。
