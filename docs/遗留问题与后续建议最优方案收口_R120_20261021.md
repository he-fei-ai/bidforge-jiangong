## 二、L1 深挖：从「计时抖动」表象到「stale-node」真根因

### 2.1 第一层（R119 的初步定性，部分成立）
R119 把 `test_vitest_review_closeout` 的偶发红定性为「全量并发 CPU 争抢导致 RTL `waitFor` 计时抖动」。据此在 `setup.ts` 抬高 `asyncUtilTimeout`（RTL 默认 **1000ms**，独立于 vitest `testTimeout=60000` —— 既有 `vitest.config.ts` 只放宽了前者、漏了后者这个兄弟姐妹，与 R118「同族故障要回扫」教训同型）。

### 2.2 关键取证：仅抬超时**没能**修复（本轮实证）
- 后端包装层跑（仅带 asyncUtilTimeout 改动）：`BatchFixModal.test.tsx:193` **仍红**（`1 failed, 2 passed in 485.30s`）。
- 若真只是计时不够，5000ms（远超实测争抢延迟）应已兜住。仍白等 ⇒ **`api.stage` 根本没被调用**，抬超时治不了。

### 2.3 真根因（stale-node 点击）
组件 `BatchFixModal.tsx` L223「生成修复预览」按钮 `onClick={stage}`，而 `stage()`（L95）在点击当刻**同步**调 `reviewAutoFixApi.stage`。用例（L182-201）这样写：
```tsx
const sb = await waitFor(() => { … return btn("生成修复预览") });  // 捕获某一次渲染的按钮元素
fireEvent.click(sb);                                                // 用捕获引用点击
await waitFor(() => expect(api.stage).toHaveBeenCalledWith("s1", …));  // 等 stage 被调
```
`await waitFor` 解析后、到 `fireEvent.click(sb)` 之间，组件可能因 collect 落定/antd loading 态切换**再渲染一次**，`sb` 指向的 DOM 节点**已脱离文档树**；React 事件委托挂在 root/document，点脱离节点 ⇒ `onClick=stage` 不触发 ⇒ `api.stage` 永不被调用 ⇒ 第 193 行 `waitFor` 无论超时给多长都白等。

**旁证**：同文件「拒绝全部」用例（L205+）用的是「点击前重新查询」`fireEvent.click(btn(view(), "生成修复预览")!)`，一直绿；失败用例独独复用了捕获引用。

### 2.4 修复（根因级 + 防护网，加法式）
- **主修**（`frontend/src/tests/BatchFixModal.test.tsx`）：保留「按钮解禁」就绪门，但**点击时重新查询当前挂载按钮**并 `await act(async () => fireEvent.click(...))` 包裹（冲刷待发 effect/promise），与同文件稳健写法对齐。
- **辅修**（`frontend/src/tests/setup.ts`）：`configure({ asyncUtilTimeout: 5000 })` —— 覆盖全套件「吃默认 1000ms 的 waitFor」这一类争抢抖动（通过用例命中即早返回 ⇒ 零成本；显式 per-call `{timeout}` 不受影响；仍受 `testTimeout=60000` 兜底）。
- **护栏**（`frontend/src/tests/rtlAsyncUtilTimeoutR120.test.ts`）：断言 `getConfig().asyncUtilTimeout ∈ [5000, 60000)`，configure 被摘/调回 1000 即变红。
- **接线**（`backend/tests/test_review_autofix_closeout_r55_20261008.py`）：把新护栏纳入 `_FE_TEST_FILES`（4→5），让后端真跑通道同时执行该锁。

## 五、全量前端 2 条失败的定性（非本轮引入、与改动无关）
`contentDegradedTerminal20261010.test.tsx` 的 **B1 / B2** 在全量并发下报 `Test timed out`（该文件整体耗时 214s）：
- 这两个用例 **直接 `await pollTaskUntilTerminalImpl(...)` + 动态 `await import("../pages/SchemeWorkbenchPage")`（巨型页面模块）**，**不使用 `waitFor`** ⇒ `asyncUtilTimeout` 改动对它们无因果。
- 失败机制是「全套件 8-worker 冷 jsdom + 超大页面模块的 `import()` 在 CPU 争抢下超过单测 60s 墙钟」，属**基础设施争抢型假故障**（与 R118 FIX-3 墙钟抖动同族）。
- 单独无并发复跑 **12/12 通过（25s）** ⇒ 证实非代码回归。
