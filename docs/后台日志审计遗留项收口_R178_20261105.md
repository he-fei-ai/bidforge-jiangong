## 二、逐项详情

### FIX-1 · D-1 内置兜底豁免「判死剔除」（P1）

**根因**（file:line 级）：

- `provider_factory.py:1533-1545` 的设计注释明写「内置兜底从 chain 中独立出来（兜底不被截断）」，
  内置 `agnes` 被**独立**于用户降级链、在**成功率过滤之后**追加；
- 但它随后仍会流经 `_order_candidates`（`:2745`）的**死配置剔除** ⇒ 一旦兜底自身成功率过低
  （样本 ≥10 且成功率 <0.20），即被**静默剔除**——而这恰恰发生在**主配置也已不可用**的最坏时刻，
  即「兜底不得被截断」的设计意图被自己打破，兜底形同虚设。

**修法**：给内置兜底候选打**显式标记** `"_is_builtin_fallback": True`（`:1544`），
`_order_candidates` 的 `alive` 过滤对该标记**豁免判死**（`:2764-2771`）——**只降级不剔除**，
它在链内本就位于尾部，仍保持「最后兜底」序。

> **为何用显式标记而非按 `provider_name == "agnes"` 判定**：用户自配的 agnes 行有 `config_id`
> （统计键为 `cfg:{id}`），与内置（键为 `prov:agnes|model:url`）本就不串扰；按名字粗判会误伤用户配置。
> 护栏 `test_builtin_fallback_marker_not_used_for_user_config` 反向锁定「不得按名字粗判」。

### FIX-2 · D-2 三处「设计内节流」日志 WARNING → INFO（P2 降噪）

**生产实证**：`已剔除实时成功率过低的候选` 372 条 + `主配置 … 后置到候选链尾部` 642 条 +
`fallback 候选 … 已自动排除` 253 条 = **1014 条 WARNING，占全量 WARNING 的 24%**，
把真正的故障（429/401/锁冲突/库损坏）彻底淹没。

**修法**：三处由 `logger.warning` 降 `logger.info`（`:1556` / `:2783` / `:2796`），
**不删除日志**（自愈动作仍须留痕）。依据 R103 先例
（`test_config_health_closeout_r103_20261018.py:184-191`「熔断/配额冷却跳过是设计内节流，降为 INFO」
+「旧 WARNING 形态不得回流」）。

**反向棘轮**：护栏以 AST 定位「文案命中的 logger 调用」，断言**恰好 1 处**且级别**必须**为 `info`，
并额外断言这三处**不得**出现在任何 `logger.warning` 调用中。

### FIX-3 · D-3 保存配置时清实时成功率统计（P1）

**根因**：`save_ai_config`（`:889`）此前只清「确定性死连击」（`_det_dead_streak`），
**不清实时成功率统计**（`_provider_reliability`）⇒ 用户把模型名/端点/密钥**改对了**，
成功率却仍停在旧值（判死阈值 0.20 / 后置阈值 0.60）→ 改对了仍被剔除或静默后置；
且统计一旦冻结就**永远判死**，唯一出口是进程重启后 24h 预热。

**修法**：`:895` 增加 `_provider_reliability.pop(_reliability_key("", "", cid, ""), None)`
——只清「本次保存的那条配置」，不动其它配置的统计（护栏双测锁定）。

### FIX-4 · D-4 `content_plan` 输出预算地板 600 → 1536（P1）

**生产实证**：8 天内 **158 条**「离散编排阶段 LLM 调用失败，回退为无编排」——
编排阶段事实上长期处于关闭状态，而**用户毫不知情**（失败被静默降级为「无编排」）。

**根因**：`content_plan.py` 硬编码 `max_tokens=600`——对**推理模型**必然被思考过程吃光
（生产日志：custom 模型 600→1200 翻倍后仍「思考吞噬 max_tokens（正文为空）」），
对非推理模型也偏紧（编排 JSON 含 `writing_focus` 句 + `knowledge_names`/`fact_titles` 两个列表 +
`table_purpose`，容易触顶 → 截断 → 进 JSON 修复轮 → 仍失败 → 静默降级）。

**修法**：新增模块常量 `CONTENT_PLAN_MAX_TOKENS = 1536`（`:34`），
与正文首稿同口径（provider 层对推理模型还会再抬到 `ai_reasoning_output_floor`，默认 4096）。
**零新增配置项**（模块常量）。

### FIX-5 · B-4 预检计算移入工作线程（P1）

**根因**：`compliance.py` 的预检是**纯 CPU 的同步计算**（8 个 checker + CON-01 的 11 条数值正则 +
整章查重），此前在**事件循环内直跑** ⇒ 一次预检把整个事件循环卡住（SSE 心跳与其它请求全被拖）。

**修法**：新增阻塞版 helper `_preflight_findings_blocking(ctx)`（`:100-102`，判定口径逐字不变），
4 处调用点改为 `await asyncio.to_thread(...)`（`:1527` / `:1528` / `:1628` / `:1963`）。

### FIX-6 · F-13 4xx/5xx 失败原因入访问日志（P2）

**生产实证**：**14 条 400 的访问日志里零条**能看出失败原因——FastAPI 的 `HTTPException.detail`
只存在于**响应体**，服务端访问日志只记 status/cost ⇒ 400 完全不可反查。

**修法**（加法式，**不改既有访问日志格式**）：`middleware.py` 在 `send_wrapper` 中截取
4xx/5xx 响应体首段（≤1024 bytes → ≤300 字符，`err_detail`，`:149` / `:170-178`），
访问日志行之后**追加**一条 `logger.warning("%s %s -> %s 失败原因：%s [trace=%s]")`（`:189-193`）。

> ⚠️ `err_detail = ""` 必须在闭包**之前**初始化（否则 `nonlocal` 绑定失败 → `SyntaxError`）。
> 本轮体检曾抓到该错并已修正，护栏以「行为实证 + 格式不变」双测锁死。

### FIX-7 · B-9 PDF 导出 Word COM 进程级串行（P2）

**根因**：Word COM（`win32com.client.Dispatch("Word.Application")`）是**单例且不可重入**——
两个并发 PDF 导出会各自 Dispatch 一个 Word 实例争抢同一 COM 服务器，
源码注释已记录本机实测「4 次中 3 次失败」（0x800706BE RPC 失败）与文档损坏。

**修法**：新增模块级 `_PDF_CONVERT_LOCK = threading.Lock()`（`export.py:5593`），
`_convert_docx_to_pdf` 改为持锁包装（`:5594-5599`），真实实现拆入 `_convert_docx_to_pdf_unlocked`（`:5602`）。
调用点仍是 `asyncio.to_thread(_convert_docx_to_pdf, ...)`（`:5871`）⇒
**必须用 `threading.Lock`（跨线程串行），不能用 `asyncio.Lock`**。

### FIX-8 · B-1 跨章自检移入工作线程（P0，**实测基线支撑**）

本项是 R177 登记为「需先做性能基线再定」的 P0。本轮**先做基线、再定改法**：

**基线实测**（`artifacts/r178/bench_outline_rebuild.py`，章节正文 4000 字，同源判据）：

| 章节数 N | 搬运判定 | 数值一致性 | 合计 | 相对上一档 |
|---|---|---|---|---|
| 10 | 23.75 ms | 13.50 ms | **37.24 ms** | — |
| 20 | 56.38 ms | 26.16 ms | **82.54 ms** | ×2.22 |
| 40 | 133.66 ms | 61.18 ms | **194.83 ms** | ×2.36 |

隐含复杂度指数 **2.36** ⇒ **超线性（O(N²) 成立）**。
换算：N=40 的方案，**每章**生成后阻塞事件循环 **195 ms**，全书约 **7.8 秒**纯 CPU 卡在事件循环内。

**根因**：`sse_handlers.py` 每章生成后都把**全书**章节重跑一遍跨章判据：
`cross_section_copy_findings`（`content_checkpoint.py:795`）与
`cross_section_value_findings`（内部调 `preflight_engine.numeric_consistency_findings(全量, limit=0)`），
二者均为**纯 CPU 同步函数**，此前在事件循环内**直跑**。

**改法（与 FIX-5 同构，零判据改动）**：两处调用包进 `await asyncio.to_thread(...)`
（`:3497-3501` / `:3516-3520`）——**同一函数、同一参数**，只改执行位置。

**安全性论证**（护栏以 AST 锁定）：
① 本段位于 `_db_write_lock`（`:3534`）**之前**，AST 断言其**不在任何 `async with` 写锁内**
（`await` 让出控制权不得破坏互斥）；
② `_dup_secs` 在 `await` 前**已切片**，且 `_crossdup_snapshot` 后续**只增不改**
⇒ 让出控制权不影响判据输入；
③ fail-soft 语义逐字保留（异常只告警、绝不阻断正文落库）。

## 七、教训归档

1. **性能项必须先做基线再定改法**。B-1 若按直觉「O(N²) ⇒ 要做增量」去改，会触碰
   `preflight_engine` 的判据同源硬约束（生成侧自检与预检必须同判据）；
   实测后发现真正的成本是「**纯 CPU 跑在事件循环里**」⇒ 与预检同构的 `to_thread` 即可解决，
   **零判据改动**、风险极低、收益 195 ms/章。
2. **基线也能证伪**。B-2「目录整表重建长写事务」经实测**证伪**（写放大 < 3 ms）——
   若照 R177 登记直接动事务边界，反而会**破坏原子性**（重编号依赖主事务内未提交结果）。
   ⇒ 登记项不等于必改项，**证伪是合法且优先的裁决**。
3. **并发会话改写热文件会让回归出现「幽灵红」**。本轮 6 例 `NameError` 在隔离复跑后全绿；
   判定依据不是「我觉得无关」，而是**定义与调用在最新文件里双双在位** + **隔离复跑同组绿**。
   ⇒ 回归红必须**逐条查当前文件状态**，不得按印象归因（R167 教训的正面复用）。
4. **行尾漂移是并发写入的副作用，不要替别人归一**。`export.py`（32 处）与
   `middleware.py`（81 处）出现孤 LF，来源是并发会话的新增内容；
   本轮自身新增行**全为 CRLF**（体检逐行核过）。强行整体归一会在对方写入窗口内制造冲突（R106）。
5. **AST 判据的节点类型要选对**。`asyncio.to_thread(fn, ...)` 里的 `fn` 是 `ast.Name` 节点，
   按 `ast.Call` 找会**全部漏判**（首版 H 组判据因此假红）。⇒ 锁「调用点」时要区分
   「函数被调用」（`Call.func`）与「函数被当作参数传递」（`Name`）。
6. **`await` 引入让出控制权 ⇒ 必须复验锁边界**。跨章自检加 `await` 前，用 AST 沿父链证明
   该段不在 `_db_write_lock` 内、且输入已切片，才敢落刀。⇒ 「加 await」不等于「加 await 就安全」。
7. **探针子代理可能长时间无产出**。`bg_6f5fea87`（B-1/B-2 方案核定）运行 40+ 分钟零输出；
   主会话**亲验代码 + 自建基线脚本**反而更快拿到可执行结论 ⇒ 长跑探针不应成为阻塞路径。
