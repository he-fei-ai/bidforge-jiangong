## 0. 结论先行

### 0.1 推荐栈（可直接落地的最小组合）

| 角色 | 库 | 许可证 | 理由（实测依据见 §3、§4） |
|---|---|---|---|
| **主文本引擎** | **pypdfium2 5.14.0** | BSD-3-Clause / Apache-2.0（自带 pdfium 二进制第三方许可均为宽松） | 253 页真实招标文件文本一致率 100%、规范化字符数与 PyMuPDF 仅差 1 字；双栏顺序 100% 正确；486 页 0.72s / 33.4MB，比 PyMuPDF 快 35 倍、内存低 33% |
| **表格引擎** | **pdfplumber 0.11.10** | MIT | 合成表 100% 逐格一致；真实 253 页文档 1880/1881 格一致（99.95%）；跨页续表 43+4 行结构与 PyMuPDF 完全一致 |
| **兜底/元数据/加密预检** | **pypdf 6.21.4** | BSD-3-Clause | 486 页 6.42s；`is_encrypted` 可在打开前判定加密；对截断文件报错明确 |
| **不进入推荐栈** | pdfminer.six（作为 pdfplumber 的底座存在，不直接调用） | MIT | 直接调用时表格页阅读顺序崩坏（S06 一致率 4.76%、S08 2.2%）|
| **不进入推荐栈** | camelot-py | MIT（但默认后端 Ghostscript 为 AGPL） | 本轮**未安装、未实测**，依据上一轮许可取证与官方文档排除 |

> 关键约束：**不能用 pdfplumber 当主文本引擎**。它在双栏页（S12）文本一致率仅 15.44%，两栏被按行横向串读；而 pypdfium2 在同一页为 100%。

### 0.2 一句话保真度结论

**文本与表格可做到「内容无损、结构基本无损」；退化集中在三处：表格的页内过度切分、pdfplumber 的内存占用、以及 MuPDF 那套「畸形 PDF 唯一闸门」在换库后消失。**

- 文本：5 个引擎在 3 份真实样本 + 11 份合成样本上的**去空白字符总量完全一致**（S02 全引擎 norm=1765；S11 全引擎 norm=577764；S01 差异 ≤10 字）。差异只剩空白与阅读顺序。
- 表格：合成 3 份样本逐格一致率 100%（491/491 格）；真实招标文件 99.95%（1880/1881），但表数量 110 vs 106，存在 4 处页内过度切分。
- 渲染：同页同 DPI 像素平均绝对差 MAE 0.289～7.152，差异像素占比 0.35%～8.58%；扫描件 OCR 两引擎结果 100%/98.77% 覆盖，关键词全中。
- 性能：pypdfium2 文本抽取最快（S01 0.908s vs PyMuPDF 12.71s）；pdfplumber 最慢且内存最高（S11 峰值 1272.9MB vs 49.6MB）。

### 0.3 阻断是否解除

换掉 PyMuPDF 后，PDF 链路的**强 copyleft 归零**。候选闭包内只剩弱 copyleft 且均为**动态链接的独立二进制**（GEOS LGPL-2.1、FFmpeg LGPL-2.1，且这两者原本就在既有 OCR 可选栈里，不是本次换库新引入）。详见 §3.2。

## 1. 实验方法与许可取证方法

### 1.1 环境隔离

- 临时 venv：`%TEMP%\pymupdf_bench_venv`（由 `C:\Program Files\Python314\python.exe`（3.14.4）创建），**未安装进项目环境**。
- 工作目录：`%TEMP%\pymupdf_bench`（样本、脚本、原始结果），**仓库内只读**。
- 项目环境未变：`backend/requirements.txt` 未改、`backend/` 源码未改、无 git 提交。

### 1.2 许可证取证

- 逐包读取 venv 内 `dist-info/METADATA` 的 `License` / `License-Expression` / `License ::` 分类器，并读取 `dist-info/licenses/**` 下的 LICENSE/COPYING 原文首段；对 Aggregated 许可（pdfium、Pillow、numpy）逐段定位 GPL/LGPL 文本的归属。
- 表格中每条都写「证据来源」，未取到的一律标注「未获取到」，不猜测。
- 取证脚本：`%TEMP%\pymupdf_bench\collect_licenses.py`、`dep_tree.py`。

### 1.3 量化口径

- **文本一致率**：去空白后取每份样本前 3 页，`difflib.SequenceMatcher` 比值（%）。全 486 页做 O(n²) 比对不可行，故取前 3 页；另用**规范化字符总量**做全文覆盖校验。
- **字符覆盖**：全文字符集合（去重）交集 / 基线集合。
- **表格一致率**：按页对齐、页内按出现序号对齐；行数/列数不一致的表单独计数、不参与逐格比对。
- **渲染**：同页同 DPI=150，PyMuPDF 与 pypdfium2 的 RGB 位图逐像素比较（MAE、差值 >25 的像素占比）。
- **OCR**：完全复刻 `backend/app/services/ocr.py` 的 `_preprocess`（灰度→短边放大→autocontrast）后喂 RapidOCR，与项目现有 OCR 口径一致。
- **耗时/内存**：每个（引擎×样本）跑在独立子进程，`time.perf_counter()` 计时，`psutil` 取 Windows `peak_wset` 峰值。

### 1.4 本轮未验证（如实声明）

- `camelot-py` 未安装（默认后端 Ghostscript 为 AGPL，实测会污染结论口径），仅依据上一轮取证排除。
- 云 OCR（MinerU/视觉模型）未纳入对比，只测本地 RapidOCR。
- 项目锁定版本与实验版本存在小差异：实验用 pdfplumber `0.11.10` / pypdf `6.21.4`，项目锁定 `0.11.9` / `6.14.2`（差异评估见 §7）。
- 仅 Windows x64 实测。

### 3.3 强 copyleft / AGPL 排查结果

- **AGPL：仅 PyMuPDF 一项**，由 `backend/requirements.txt:32` 直接引入，运行时在 `backend/app/services/file_parser.py` 的 PDF 主通道、表格重建、OCR 渲染三处使用。换库后消除。
- **GPL：候选闭包内没有需要履行 GPL 义务的包**。命中的两处均为「文本存在但义务不适用」：

## 4. 逐能力量化

### 4.1 文本抽取

命令：`python run_bench.py`（5 引擎 × 15 样本，逐样本子进程）；指标由 `analyze_results.py` 汇总。

| 样本 | 指标 | PyMuPDF | pdfplumber | pdfminer.six | pypdf | pypdfium2 |
|---|---|---|---|---|---|---|
| S01 招标文件（253 页，真实） | 一致率% | 100 | **99.74** | 99.78 | **100** | **100** |
| | 去空白字符总量 | 151,974 | 151,984 | 151,984 | 151,984 | 151,975 |
| | 与基线差异 >5% 的页 | — | **0 / 253** | 0 / 253 | 0 / 253 | 0 / 253 |
| S02 概算汇总表（3 页，真实） | 一致率% | 100 | 99.55（仅"申报概算"列序前移） | **42.1** | 100 | 100 |
| | 去空白字符总量 | 1,765 | **1,765（完全相同）** | 1,765 | 1,765 | 1,765 |
| S05 纯文本 CJK | 一致率% / norm | 100 / 2,561 | 100 / 2,561 | 100 / 2,561 | 100 / 2,561 | 100 / 2,561 |
| S11 大文件（486 页） | 一致率% / norm | 100 / 577,764 | 100 / 577,764 | 100 / 577,764 | 100 / 577,764 | 100 / 577,764 |
| S12 双栏（阅读顺序） | 一致率% | **100** | **15.44** | **15.44** | 100 | **100** |

结论：

1. **内容层面零丢失**：所有引擎在所有样本上的去空白字符总量一致（S01 差 ≤10 字，属空白/连字符差异）。不存在"漏字"，只有"空白策略"与"阅读顺序"差异。
2. **pdfplumber / pdfminer 不能做主文本引擎**：双栏页（S12）一致率仅 15.44%，实际输出形如"左22 … 左1 … 左23 … 左2"按行横向串读；pdfminer 在表格页（S06 4.76%、S08 2.2%）把整列序号先吐出来。pypdf / pypdfium2 在同一批样本均为 100%。
3. **真实表格页存在列序差异**：S02 中 pdfplumber 把"申报概算"列提前到"序号"之前（只影响列序，不影响字符完整性）。该差异会影响"表头识别"，需在表格后处理中容忍。

### 4.2 表格结构

### 5.4 换完之后仍需人工复核的边界

- **竖排/旋转文本**、多栏（≥3 栏）、且栏间有跨栏标题的版面。
- **跨页表在页边界恰好断在合并单元格内部**（表头两行被拆到两页）。
- **扫描件 OCR**：印章遮挡、手写批注、低分辨率（<150 DPI）、表格线干扰（工具链不变，但换渲染源后边界需重抽检）。
- **加密 PDF**：AES-256 / R6、仅权限限制但带签名域、增量更新（Incremental Update）后的加密字典。
- **损坏 PDF**：MuPDF 修复模式能救、pdfium 拒收的"半坏"文件集合，需抽样确认是否可接受为"不可解析"。
- **字体子集/嵌入异常**：CJK 竖排字形、康熙部首、ToUnicode 缺失的旧扫描件文字层。
- **表格合并单元格**：两引擎都拍平为空格，语义（rowspan/colspan）已丢失——现状即如此，但人工复核时不能假定结构完整。
