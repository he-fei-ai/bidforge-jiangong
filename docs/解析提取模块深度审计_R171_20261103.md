## 二、PARSE-3 · 截断诊断三态（本轮修复）

### 2.1 根因

`upload_outline.parse_outline` 在以下两处写了诊断信息但**从未随响应回传**：

- `diag.get("truncated")` → 应回传 `parse_truncated=True`（:358-359）
- `parse_warnings` 列表 → 应回传 `parse_warnings`（:363-364）

**后果**：用户看到「识别成功」却收不到「内容可能不完整」告警，与 `global_facts` /generate-facts 口径不一致。

### 2.2 代码现状（已就位，护栏锁定）

```python
# :337
raw_truncated = len(raw_text) > 5000
# :349
(raw_text[:5000], ...)  # 落库截断
# :358-359
if diag.get("truncated"):
    result["parse_truncated"] = True
# :363-364
if parse_warnings:
    result["parse_warnings"] = parse_warnings
# :375-377
if raw_truncated:
    result["raw_text_truncated"] = True
    result["warning"] = f"原文 {len(raw_text)} 字，保存记录时截断至 5000 字..."
```

### 2.3 护栏覆盖（8 例）

| 用例 | 断言 |

## 三、PARSE-4 · `_OUTLINE_PATTERNS` 顺序锁（本轮修复）

### 3.1 根因

`file_parser._OUTLINE_PATTERNS` 是目录编号识别的**唯一判据**，顺序决定匹配优先级。此前无任何护栏锁定：

- 若后人调换顺序 → 低优先级 pattern 先命中 → 章节层级错判
- 若删除 OCR 容错注释 → 后人不知「为何允许 `\s*`」而擅自删掉

### 3.2 护栏覆盖（6 例）

| 用例 | 断言 |
|---|---|
| `test_patterns_order_fixed` | 8 条 pattern，第 0 条含「章/节/篇」、第 2 条含 `.`、第 4 条含 `、`、第 7 条含 `)` |
| `test_ocr_robustness_comment_present` | 源码含「容忍」或 `\s*` |
| `test_pattern_sequence_cannot_be_reordered` | 首条含「章」、末条 level=3 |
| `test_raw_text_slice_at_5000` | `raw_text[:5000]` 恰 1 处 |
| `test_raw_truncated_guard_present` | `raw_truncated = len(raw_text) > 5000` 在位 |
| `test_parse_truncated_key_assignment` | `result["parse_truncated"] = True` 在位 |
| `test_parse_warnings_key_assignment` | `result["parse_warnings"] = parse_warnings` 在位 |

## 八、教训归档

1. **A/B 脚本路径推导多算一层 dirname**：`Path(__file__).parent.parent` vs `parent.parent.parent` 差一级 → 首轮 0p/0f 假绿。判据：脚本里 print 出实际路径再核对。
2. **pytest 输出解析不能只看 exit code**：`out-file` 管道在 GBK 环境下会丢输出，改用 `decode("utf-8","replace")` 后正则提取 passed/failed 计数。
3. **`.encode("utf-8")` 对 bytes 输入会 AttributeError**：`_upload()` helper 需兼容 `str | bytes`，否则 monkeypatch 用例（传 bytes）必挂。
