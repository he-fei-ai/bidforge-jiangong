## 二、P0 锁族修复（四处写点 + 一处基建）

### 2.1 基建：`db.retry_db_op` 新增 `jitter` 参数
- 签名 `retry_db_op(coro_factory, max_retries=3, base_delay=0.05, jitter=0.0)`；退避 `base_delay * 2**attempt + uniform(0, jitter)`。
- **默认 0 逐字维持旧节拍**（存量调用零行为变化）；本轮四处新接线全部显式传 `jitter=0.05`——批量生成 + 审计 flush 并发下多个等待者同拍苏醒的惊群打散。
- `is_retryable_db_error` 判据不变：只重试 `database is locked` / `disk i/o error`，确定性错误原样上抛（不掩盖真故障）。

### 2.2 FIX-P0-1 图表登记 DELETE（`_chart_pipeline.apply_inline_chart_plan`）
- 生产实证：tracebacks block#8——`DELETE FROM chart_predictions WHERE section_id=?` 裸奔抛 locked 直通冒泡，**LLM 已生成正文随异常丢失**。
- DELETE 是 WAL 下「读事务升级为写」的**首条写语句 = 唯一锁获取点**，包进 `retry_db_op(lambda: db.execute(...))` 即覆盖整事务的锁窗口；后续同事务 INSERT 不再撞锁。
- 调用方 `sse_handlers._persist_section` 配套降级口径：`apply_inline_chart_plan` 异常不再冒泡——回滚半途图表写 → `_chart_apply_failed=True` 闸 → WARNING → **正文照常落库**（正文是主产物，登记残留下轮全量重登记自动收敛）；`if not _chart_apply_failed:` 门控后续字数重算/report 环节。
- 正文 UPDATE+commit 亦收敛进 `_persist_content_once` 闭包接 `retry_db_op`（locked 抛出时事务必未提交，UPDATE 重放幂等）。

### 2.3 FIX-P0-2 任务控制指令（`task_registry.set_task_status` + `sse_handlers.task_control` + 前端）
- 后端预算加重：控制指令写库 `max_retries=5` + `jitter`（旧 3×0.05/0.10/0.20 ≈ 0.35s 预算在轮询风暴+批量落库并发下实测耗尽 → 500×6）。
- **503 语义分流**：`task_control` 捕获 `is_retryable_db_error` → `HTTPException(503, "数据库写入繁忙，控制指令暂未持久化，请稍后重试", headers={"Retry-After": "2"})`；其余异常原样上抛（真故障不粉饰）。旧口径下异常直穿中间件成裸 500——内存 Event 已置位而 DB 仍 running，用户表现为「点了停止停不掉」且不知指令未持久化。
- 前端 `tasksApi.control`（`frontend/src/api/index.ts`）：收 503 按 `Retry-After` 节拍**自动重试一次**，重试仍败才报错给用户。

### 2.4 FIX-P0-3 导出缓存行（`export._db_exec` / `_persist_export_cache_row`）
- `_db_exec`（docstring 自称「写路径唯一出口」但锁直通）接 `retry_db_op`；
- `_persist_export_cache_row` 分两段闭包：`_insert_and_commit`（主段）与 `_prune_and_commit`（裁剪段）各自接重试。**主段**耗尽 → rollback + WARNING「交付不受影响」（缓存行丢失只损失下次导出加速）；**裁剪段**耗尽 → rollback + WARNING「旧缓存行将由下次导出自愈」——两段均 fail-soft，绝不让缓存卫生问题 500 掉已完成的交付物。

### 2.5 FIX-P0-4 AI 配置保存（`provider_factory.save_ai_config`）
- 生产实证：批量生成写锁窗口内保存配置偶发 500（首条 UPDATE/INSERT 抛 locked 直通）。
- 整事务体提取为 `_save_tx_once` 闭包接 `retry_db_op(4, 0.1, 0.05)`：`write_tx_conn` 每次进入获取独立池连接、异常统一回滚，locked 抛出时必未提交 → **整事务重放安全**（INSERT 用函数外生成的固定 cid，重放不双写）。
- 闭包内 `prio` 局部变量承接外层 `raw_priority` 读取，规避「闭包赋值使外层名字判为局部」的 UnboundLocalError 陷阱。

## 三、P1-1 提示词缓存重载风暴（表级水印）

**根因**（R107 实证）：`_db_newer_than_cache()` 用**整库文件 mtime** 判新旧——WAL 下任务进度、审计流水、导出缓存任何一张表写入都 bump mtime → 批量生成期间热路径每次 `get_prompt()` 判「库变新→全量重载」，`loaded=504/reloaded=500` ≈1004 条 INFO（占全日志 7%，最大单一噪音源），且每次重载多烧一次全表 SELECT。

**修法**（`services/ai/prompts/_cache.py`，三层递进）：
1. **表级水印**：加载时同连接记 `(COUNT(*), MAX(updated_at))` of prompt_templates；mtime 判「库变新」后加第二道闸 `_needs_reload_by_watermark`——水印未变 = 他表写入，只推进 `_loaded_db_mtime` 不重载。**记录点与探测点逐字同计算式**（绝不 `len(cache)` 另写一套，两式不等价会造成每次探测都误判变更）。
2. **节流**：探测最小间隔 `_WATERMARK_PROBE_MIN_INTERVAL=1.0s`（`time.monotonic`），窗口内他表高频 bump 不重复开连接；外部进程真实改提示词的可见延迟 ≤1s（人尺度操作，可接受）。
3. **回退语义**：水印无法记录（极旧库缺列/查询失败 → None）→ 逐字维持旧「mtime 变新即重载」行为；探测失败 → True 保守重载（fail-soft：宁可多烧一次不可漏更新）。
- `reload_prompt_cache` 显式失效时**四全局**（含水印）一并失效，「显式失效」与「按需加载」状态机口径一致（2026-09-24 同源债的续）。

## 四、P1-2 审计缺列误诊 + P1-3 复核 + P1-4 死配置剔除

### 4.1 误诊分流（`provider_factory._flush_audit_rows_once`）
- 生产实证：`ai_audit_logs 缺 config_id/base_url 列（旧库未迁移）` 报错长期误诊——实测**列齐全**（19592 行），真实根因是批量生成写锁窗口 executemany 抛 locked 被宽 `except Exception` 归因成缺列；且锁败后降级写若碰巧成功，config_id/base_url 被静默裁掉（可靠性统计身份缺失）。
- 修法：`_is_missing_column_error(e)` 判据（SQLite 两种缺列文案 `"no column named"` / `"no such column"`）——**非缺列原样上抛**，交给 `_flush_audit_buffer` 既有 `retry_db_op` 整批重放（write_tx_conn 已回滚，无半写）；仅真缺列进 NO_IDENTITY→LEGACY 降级链。NO_IDENTITY 级同口径（缺列/行宽守卫 ValueError 才继续降级）。

### 4.2 中途抓获的行为回归（详见 §五）
分流判据首版把「行宽≠列数的 `ProgrammingError`」也上抛，误杀跨版本旧行宽的既有降级路径——补 `isinstance(e, sqlite3.ProgrammingError)` 例外。

### 4.3 P1-3 sensetime 思考吞噬：复核登记，不改
- R107 登记该形态为「长 output 思考型模型响应疑似被截断/吞没」。复核结论：正文链对思考型模型的**翻倍重试**（O3：max_tokens 不足判据命中 → 预算翻倍重试一次）早已落地且有既有护栏覆盖，生产日志该形态签名均在 O3 覆盖内收敛，无新增代码缺口。**本轮仅登记，不动代码**（避免对已闭合路径的行为放大）。

### 4.4 P1-4 确定性死配置连击剔除
