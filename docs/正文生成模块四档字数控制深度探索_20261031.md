## 1. 结论摘要（TL;DR）

「四档字数控制」是 R66（2026-10-11）引入、此后经 R70/R71/R119 持续加固的**正文目标字数分级体系**：

- **四档定义**：`brief 简短 800 / standard 标准 1200 / detailed 详细 2000 / ultra 超长 2500`，唯一事实源 `backend/app/services/content_utils.py:66` 的 `WORD_BUDGET_TIERS`；默认档 `standard=1200` 同时就是全项目默认预算 `DEFAULT_WORD_BUDGET`（:36）。
- **语义**：档位是「**每个叶子（三级目录）章节各自的目标字数**」，选中档位后逐叶落库 `UPDATE sections.word_budget` 并跳过旧的「按二级章节总量 AI 分配」链路——档位与自定义 `word_budget_override` **互斥**（都传时档位优先）。
- **300 字叶子下限**：`LEAF_MIN_WORD_BUDGET=300`（:70）贯穿三处——档位取值 `max(档值,300)`、自定义分配下限、续写触发线。
- **执行闭环共五道**（详见 §5）：提示词容差带承诺（0.9X~1.1X，硬上限 1.2X）→ 首稿输出 token 物理上限 → 字数不足自动续写（触发线 max(0.8X, 300 下限)，最多 2 轮）→ 超 1.3X 自动压缩（3 轮、只删不改、压缩禁区）→ 收尾透明警告（advisory，不阻断）。
- **可追溯闭环共四层**：逐章结构化日志 → `section_done` 事件偏差键 → checkpoint/completed 的 `word_audit` 汇总 → 审核预检规则 DLV-16（33 个偏差章聚合为恰好 1 条 finding）。
- **专项护栏现状（本轮实跑）**：`backend/tests/test_word_budget_tiers_r66_20261011.py` **85 passed / 1.68s**，全绿。
- ⚠️ **消歧**：代码库中还存在另一个「四档」——**表格密度四档**（`content_table_requirement: none/light/moderate/heavy`，`content_plan.py:164-184`），与字数无关，详见 §9。

## 2. 档位常量与解析（单一事实源）

### 2.1 常量定义 — `backend/app/services/content_utils.py`

| 常量 | 值 | 锚点 | 说明 |
|---|---|---|---|
| `WORD_BUDGET_TIERS` | `{"brief":800, "standard":1200, "detailed":2000, "ultra":2500}` | :66 | 四档真源；前端只展示不定义第二套判据（前端仅持一份**预估用**数值表，见 §7.3） |
| `WORD_BUDGET_DEFAULT_TIER` | `"standard"` | :67 | 默认档 |
| `DEFAULT_WORD_BUDGET` | `1200` | :36 | 未设预算时的默认目标字数，**值=标准档**；R66 前是散落 8 处的"事实默认 1500" |
| `LEAF_MIN_WORD_BUDGET` | `300` | :70 | 三级目录（叶子）正文下限：既是档位/分配的下限，也是续写触发的最低门槛 |

### 2.2 档位解析 — `resolve_word_budget_tier(raw)`（:73-100，纯函数）

- **接受**：档位名（大小写/空格宽容，`"Ultra "` 可解析）；档位数值本身（800/1200/2000/2500 直传也认，兼容脚本调用，:97-99）。
- **拒绝**：`None`/空串/bool/非法值 → 返回 `None`，含义是「不启用档位，沿用各章自身预算，行为与旧版逐字一致」——这是全链路加法式兼容的支点。
- **刻意不做区间吸附**（:97 注释）：`1000` 这类非档位数值**不算档位**，避免「用户随手传个数」被静默解释成最近档。
- 档位与另一条覆盖路径 `normalize_word_budget_override`（:233-271）同族但独立：后者接受**任意正整数**（自定义字数），脏值（"abc"、负数、bool、非有限浮点）一律归 `None` 绝不抛异常——2026-09-23 B4 修复的背景是字符串入参曾在提示词拼接处抛 `TypeError` 炸挂整批生成。

### 2.3 请求体接线 — `backend/app/routers/sse_handlers.py:5321-5327`

```
word_budget_override = normalize_word_budget_override(body.get("word_budget_override"))
word_budget_tier     = resolve_word_budget_tier(body.get("word_budget_tier"))
```

## 3. 三条预算路径的互斥关系（生成前分配）

`generate_content` 中按优先级**三选一**（`sse_handlers.py:5762-5893`）：

| 优先级 | 路径 | 请求参数 | 每叶目标字数 | 落库 |
|---|---|---|---|---|
| 1 | **四档档位**（R66 新增） | `word_budget_tier` | `max(档值, 300)`，全部叶子同值 | `executemany UPDATE sections.word_budget`（:5767-5770），失败仅 WARNING 不阻断（:5771-5772） |
| 2 | **自定义总量**（旧链路） | `word_budget_override` | 二级章节为预算单元，单元内各叶子由 **AI 智能分配**（一次调用处理全部单元，:5821+），失败降级**均分**；应用时逐叶 `max(分配值, 300)`（:5869-5872） | 同上 executemany（:5878-5883） |
| 3 | **目录默认**（都不传） | — | 每章自身 `word_budget`（DB 值）；经 `leaf_word_budget()`（content_utils.py:850-864）稳健读取，NULL/字符串/浮点/bool 脏值回退 `DEFAULT_WORD_BUDGET=1200` | 不改库 |

三个设计要点：

1. **档位语义是"每叶子定值"而非"总量分配"**——注释明言二者互斥（:5757-5761）：档位直接绑定叶子、不做单元分配。
2. **override 极小 + 叶子极多时，单元总预算可能被 300 下限撑破**——刻意取舍（:5865-5868）：「300 字要求优先于用户总量」，且 floor 放在 SSE 应用循环而非 `_apply_word_budget_allocations` 内部（后者被性能用例以 `total_budget=100` 直调并断言守恒，floor 入内会打挂既有契约）。
3. **前端互斥、后端优先级兜底**：前端 tier 与 custom 两态互斥不共存（§7.2）；脚本若同时传，`if tier is not None` 分支先命中，override 被忽略。

**目录侧预算来源**（路径 3 的数据基础）：

- 新建章节：`models.py:74-77` `SectionCreate.word_budget=1200`（Pydantic 默认）；`schema_sql.py:55-59` 列默认 `1200`——**仅影响新建库**，存量库列默认不变（零迁移），且应用侧 INSERT 均显式传值。
- 保存目录（save-outline）：`sections.py:1400-1410`——请求节点不带 `word_budget` 时**保留库中已有预算**（旧实现无条件回落 1500，会把用户已设预算全部重置，已修）；新节点无预算落 `DEFAULT_WORD_BUDGET`。
- ⚠️ 易混淆：`schemes.word_budget`（方案级，默认 30000）是**目录生成**的分档阈值（分步/一次生成目录的切换判据，`sse_handlers.py:4454-4461`），与正文四档**无关**。

## 4. 字数判定唯一口径

### 4.1 唯一执行尺子 — `text_word_count`（content_utils.py:274-314）

- 口径：**剔除代码围栏后的字符数**（CRLF 先归一为 LF，:313——否则 50 行章节多计 ~50 字 ≈3%，在 0.8X/1.3X 边界足以翻转 under/over 结论）。
- 围栏闭合判据唯一事实源是 `fence_common`（R76 收口，本模块只保留委托薄包装）；```markdown 家族围栏的内部正文**计入**字数（R119/TD-4——导出侧会把 markdown 围栏当真实正文渲染，字数若整段剔除即与成稿分叉，生产实测 3/258 章偏差 44%~52%）。
- **全项目所有字数判定**（`word_count` 落库、`word_status`、续写门槛、压缩门槛）唯一走本函数；生成侧与单章手工保存侧共用 `word_status_for`（:800-812），保证同一章"自动生成"与"手工保存"状态一致。

### 4.2 阈值组（与档位联动）

| 阈值 | 值 | 锚点 | 用途 |
|---|---|---|---|
| `WORD_UNDER_RATIO` | `0.8` | content_utils.py:37 | 低于预算 80% → `word_status='under'`，同时是续写触发线基数 |
| `WORD_OVER_RATIO` | `1.3` | `ai/prompts/_limits.py`（R47 上收单一事实源） | 超过预算 130% → `over`，同时是自动压缩触发线 |
| 容差带 `word_budget_tolerance` | `0.1`（settings，config.py:509） | 提示词承诺带 0.9X~1.1X、续写总上限系数 1.1X、DLV-16 判定带，**一处改全链动** |
| 叶子下限 | `300` | content_utils.py:70 | 分配 floor + 续写 floor + DLV-16 下限判定 |

### 4.3 刻意隔离的两个"第二读数"（都不参与判定）

- **可读字数** `readable_word_count`（R70，:398-421）：CJK 逐字 + 西文按词，剔标点/结构符/围栏/图片/URL。背景：字符口径把中文标点、`| - # * >`、URL、空白全计入，33 章真实语料实测 mean 偏差 136.9%（字符）vs 106.5%（可读）——R66 当年「系统性超写」论据有近三成是口径虚高。护栏 `test_word_caliber_diagnostic_r70` 以**反向 AST** 锁死判定路径引用即红。
- **收尾透明警告** `word_closeout_notice`（R71，:436-482）：收尾时字数仍在带外（续写/压缩都没拉回来）→ 报告 `report["word"]` 键写 advisory（`sse_handlers.py:6608-6624`），文案明确「系统不强行灌写 / 未强行裁剪——请人工核对」。**只提示、不阻断、不进修复链路**；入参必须是调用方用 `text_word_count` 算好的读数，本函数不自算（不造第三把尺子）。红线同源：「宁可超字数，不可损坏正文」。

## 5. 执行闭环：五道机制（生成一章的完整字数生命周期）

```
档位/override/默认 → 每叶 word_budget 落库
        ↓
① 提示词约束  _word_budget_hint（:705-733）→【目标字数】注入 user 上下文
        ↓
② 首稿物理上限 max_tokens_for_budget（:206-230）
        ↓ 生成
③ 不足 → 自动续写 should_continue_round（content_runtime.py:349-392）
        ↓ 仍不足 → continue_failed 透出（:1409-1440）
④ 超标 → 自动压缩 _should_auto_shrink（:736-750）→ shrink_content_rounds
        ↓
⑤ 收尾 → word_status 落库 + word_closeout_notice 透明警告 + word_audit 汇总
```

### ① 提示词约束 — `_word_budget_hint(word_budget)`（sse_handlers.py:705-733）

- 文案由 `settings.word_budget_tolerance` **实时计算**：`tol=0.1` 时产出「`N字（可接受 0.9~1.1 倍即 0.9N~1.1N 字；硬上限 1.2N 字，超出即视为不合格）`」，与 R66 前硬编码**逐字节一致**（护栏 B 组 7 个 budget 值参数化锁定）。
- 为什么必须写明区间+上限+后果：实测（运行库 96 章）不给约束时模型把目标当"下限"，平均写到 1.69X、最高 2.82X、72% 章节 over（:712-714）。
- 注入点：首稿 user 上下文 `【目标字数】：`（`content_runtime.build_chapter_user_context`）与续写消息共用同一函数产出，避免两处口径漂移。

### ② 首稿输出 token 物理上限 — `max_tokens_for_budget`（content_utils.py:206-230）

- 公式：`max(1536, 目标字数 × 1.25 × 0.8 token/字)`。背景（P1-2，2026-09-17）：此前不传 max_tokens 落配置值 32768，模型把目标当参考持续扩写，实测 62% 章节 over。
- `MAX_TOKENS_OVER_FACTOR=1.25` 比提示词硬上限 1.2X 留一档余量；`MAX_TOKENS_FLOOR=1536` 防短章节被截断。
- 续写轮独立折算：`continue_max_tokens`（content_runtime.py:395-410）按**剩余缺口** `max(1, 1.1×budget − wc)` 折算，上限随缺口收敛。

### ③ 不足方向：自动续写 — `should_continue_round`（content_runtime.py:349-392，唯一判定点）

- 触发条件：`wc < max(budget×0.8, min_floor_chars)`（或 `continue_count < min_passes`，续写本章模式传 1=强制补一轮），且 `continue_count < max_rounds`。
- **300 下限参与触发线**（R66）：`min_floor_chars` 由调用点钳制为 `min(300, budget)`（sse_handlers.py:7554）——预算极小的脏数据章（如 budget=100）不会出现「90 字就达标」；同时钉住不超过预算本身，否则触发线永远够不着 1.1X 总上限、白烧轮次（:7541-7544）。
- 轮次与退出：
  - `CONTENT_CONTINUE_MAX_ROUNDS = 2`（P1-1 收敛，续写失败**不重试**）；
  - **无进展退出**（2026-10-24 引入易标外部规则）：连续 3 轮字数零增长即停（`CONTENT_EXPAND_NO_PROGRESS_ROUNDS=3`），判定收口在 `should_continue_round`，计数维护在 `_continue_if_needed`（sse_handlers.py:7536-7562）；
  - 续写总上限：消息文案钉死「补充后总字数不得超过 1.1×budget 字」（`build_continuation_messages(total_cap_factor=1.0+tol)`，content_runtime.py:339/344）——R66 修复 P1-5「续写把超纲继续放大」。
- 失败透出：续写最终失败且字数仍 <80% → `continue_failed=True` 进 `section_done`（:1409-1440），让用户能区分「达标」与「欠字数且补写失败」。
- 续写产出经段落级去重拼接（`_dedup_continuation`，防弱模型把尾段原样重写）。

### ④ 超出方向：自动压缩 — `_should_auto_shrink`（sse_handlers.py:736-750）→ `content_shrink.shrink_content_rounds`

- 触发：`text_word_count(content) > budget × 1.3`（与 `word_status='over'` 同口径；只数正文，几百字符的 mermaid 图顶不过阈值）。
- **默认联动（R66）**：`auto_shrink_over` 未显式传时，**给了 tier 或 override 即默认开**（`_shrink_default`，:5359-5361）——「用户明确设定了全局字数标准，超写章节却从不纠偏」正是 R66 要修的缺陷；两者都没传维持旧默认关（逐章压缩调用有费用）。前端 UI 默认开（`useState(true)`，R66 起随请求显式下发）。
- 压缩实现（`content_shrink.py`，对齐 OpenBidKit）：
  - 操作模型：AI 只返回 `replace`/`delete` 两种**局部**操作（target_text 逐字唯一），严禁整篇重写；
  - **压缩禁区**：代码围栏（CommonMark 语义 `fence_spans`）、GFM 表格（连续行合并成块区间）、图片的字符区间任何操作不得触碰（`collect_protected_ranges`）；
  - **校验即拒绝**：target_text 不存在/出现多次/命中禁区 → 整轮拒绝（ValueError），不做部分应用；
  - `SHRINK_MAX_ROUNDS=3`、`SHRINK_SETTLE_RATIO=1.15`（降到 1.15 倍以内即收敛）；
  - 任何失败保留原正文（宁可超字数，不可损坏正文），只记日志（:7746-7752 附近）。
  - 自动压缩与手动「压缩本章」**共用同一实现**（同一提示词条目、同一保护区校验、同一轮次参数），无行为分叉。
  - 压缩调用也显式传 `max_tokens_for_budget(wb)`（:7720-7722），不回退 32768 大配置。

### ⑤ 收尾：状态落库 + 可追溯

- `word_status_for(wc, budget)` 三态落库（`_persist_section` 与 `sections.update_section:801-805` 同口径——后者在同时提交新预算时用**新预算**算状态）。
- 逐章结构化日志「字数校验|节=…|目标=…|实际=…|偏差=…|偏差率=…|判定=…」。
- `section_done` 事件附 `word_deviation / word_ratio / word_within_band`。
- 任务级汇总：`word_audit_summary`（content_utils.py:129-193，纯函数、脏行逐行宽容）写入 checkpoint（:5555）与 completed 载荷（:8830），键 `word_audit` 含 `{total, in_band, under_band, over, under, below_leaf_floor, mean_ratio, median_ratio, max_ratio, items}`——断线重挂与审核预检同读本键。

## 7. 前端消费面

### 7.1 选择器 — `ContentGenerationTab.tsx:84-95`

### 7.2 发送语义 — `SchemeWorkbenchPage.tsx:6003-6015` + `useContentGeneration.ts:77,139`（hook 同口径）

## 11. 已知边界、遗留与观察项（承 R66 §8，均维持原判定）

1. **存量 1500 行不迁移**：避免动历史字节契约；用户重选档位重新生成即被覆盖，此前 DLV-16 按 1500 如实判定（可能误报偏差——这是「不迁移」的既定代价）。
2. **模型遵循度分桶**：待库内出现多模型记录后把 `ai_audit_logs` 模型字段并入取证脚本即可，无需新代码。
3. **`WORD_BUDGET_MIN=50 < 300`**：刻意保留（显式预算赢过咨询下限）；若产品侧要全面钉死 300，改一处常量，护栏 D 组已锁钳制语义。
4. **字符口径 vs 可读口径**：R70 已把两个读数并列显示供决策；若要切换执行口径，800/1200/2000/2500 四档预算须同轮下调（÷1.285），否则真实目标被隐形放大近三成——**刻意不改**，四档数值与字符口径绑死是当前契约。
5. **档位持久化的部分覆盖面**：tier/override 只 UPDATE 本次选中叶子（`select_target_leaves` 的结果），未选中章节预算不动——重跑不同范围时同章预算可能被不同档位覆盖（最后一次生成为准，属预期语义）。
6. **档位与「目录默认」路径的先后**：档位落库后，后续不传档位的生成（路径 3）会沿用上次落库的档位预算——用户想回到"目录默认值"需手动改各章预算或重建目录（前端「使用目录默认值」= 不发 tier，而非清除已落库预算）。
