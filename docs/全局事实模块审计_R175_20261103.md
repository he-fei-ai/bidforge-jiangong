### 4.2 冲突未决时下游取哪个值

**结论：不取值，整条事实被排除。** 唯一注入门控：

```python
# facts_extractor.py:3151
_FACTS_INJECT_WHERE = "has_conflict=0 AND is_resolved=1 AND is_simulated=0 AND is_stale=0"
```

目录、正文、导出均复用 `build_injectable_facts_query`（`:3284`），因此未裁决冲突事实**不会**以“旧值/高置信值/最新值”任一形式进入正文。人工裁决 `resolve-conflict` 才写回选定值并清 `has_conflict/is_stale`（`global_facts.py:2219-2312`）。

### 4.3 “最新 vs 最可信”的依据

| 场景 | 胜出规则 | 证据 |
|---|---|---|
| 同一批次多来源同名同键 | 非模拟优先，其次 `confidence` 高，再按稳定顺序 | `facts_extractor.py:1746-1761` |
| 同一批次多来源同名不同键 | 不自动择一，全部保留并标记冲突 | `facts_extractor.py:1782-1797` |
| 跨批次重提取，旧行未确认 | 新批次覆盖（删除未保护旧行后插入新行） | `facts_extractor.py:2915-2924` |
| 跨批次重提取，旧行已确认/手填 | 旧行受保护，新证据只回写 `has_conflict/is_stale`，不降级 | `facts_extractor.py:2664-2687/2829-2862` |
| 自动确认开关 | `auto_resolve_extracted_facts=True` 时才自动 `is_resolved=1`，且冲突/模拟不自动确认 | `config.py:117`、`facts_extractor.py:2874-2875` |

### 4.4 可能导致“正文用了错误事实”的路径

1. **默认配置下无路径**：未确认、冲突、模拟、过期四类全部被 `:3151` 排除；`resolve` 端点还显式拒绝模拟值（`global_facts.py:1999-2052`）。
2. **条件风险（需同时满足两个开关）**：`auto_resolve_extracted_facts=True` 且 `run_cross_validations` 抛异常被吞（`:2250-2254`）。此时 SAME-NAME/NUM-UNIT/MACH-SCHED 新冲突不会被标记，但仍会被自动确认并注入。默认 `auto_resolve=False`，属非默认路径风险。
3. **陈旧正文**：事实更新后 `sections` 只打 `facts_stale` 标记（`sections.py:135-142`），正文不会自动重生；导出仍可输出旧正文 + 新事实附录，形成“正文与事实不一致”，但不是注入了错误值。
4. **冲突清单可见性不闭环**：`result.cross_conflicts` 只随 SSE/检查点下发，不落库；刷新页面后跨维冲突清单消失。底层 `has_conflict/conflict_values` 仍在 DB，单条事实仍可见，但缺少“为什么冲突/建议怎么裁”的持久化记录。

## 5. 抽取完整性分析

### 5.1 分段、并发、重试

- 块大小 8000、重叠 500（`facts_extractor.py:54-55`）；先按标题切，表格整表保护（`:1023-1140`）。
- 最大 60 段（`:62`）；超出时按优先级截断并写 warning（`:1949-1968`），不是静默丢弃。
- 并发上限取 `settings.max_concurrency` 默认 5（`:68`、`:2027`）。
- 单段重试 `FACTS_CHUNK_RETRIES=2`（共 3 次），退避 5s/20s 指数（`:70-73/1317-1325`）。
- 单段异常不阻断整批（`gather(return_exceptions=True)`、`:2063-2066/2107`）。

### 5.2 部分失败落库（关键缺陷）

- `chunk_hashes_run` 定义为“本轮实际重跑段”，**包含失败段**（`:1992-1995`）。
- 落库删除条件使用 `run_hashes`（`:2918-2923`），且只保护 `is_resolved=1/手动录入` 行（`:2664-2687`）。
- 结果：某段 AI 失败、其余段成功时，该失败段的**未确认旧事实被删除**，本轮又不会重建；只有下次重跑成功才恢复。若一直失败，属不可逆丢失。
- SSE 层只在“总事实为 0”时拦截落库（`sse_handlers.py:5540`），部分成功不拦截。

### 5.3 模型声明失败段（`segment_failed`）

- 代码注释已承认：该段指纹仍写入 `chunk_hashes_ok`，下次增量**永久跳过**，只有 force 重提取才能恢复（`facts_extractor.py:355-363`）。
- 实现确实 `ok_idx.add(idx)`（`:2100`），`save_extracted_chunks` 以 `chunk_hashes_ok` 写入进度（`:3001-3045`）。
- 叠加 5.2 的删除范围，声明失败段的未确认旧事实也会被删。属“文档化的设计取舍 + 数据损失未闭环”。

### 5.4 结构性不会被抽取的字段

| 字段 | 结论 | 证据 |
|---|---|---|
| `zone_type`（条目级） | 模型输出 Schema 无此字段；分段 `zone_type` 只用于提示词，从未回写条目 | `facts_extractor.py` 抽取解析仅取 `f.get("zone_type","")`；`prompts/analysis.py` 输出 Schema 无 `zone_type` |
| `norm_group` | 生产代码无任何赋值点；`to_db_row` 只写 `self.norm_group or ""` | `facts_extractor.py:225` |
| `page_ref` | Schema 要求“无页码填 null”；正文是纯 markdown，无页码锚点 | `prompts/analysis.py` 字段说明 |
| `key` | Schema 不产出；由名称/类别派生 | `facts_extractor.py:1415-1467` |
| `value`（DB 列） | 表本身无 `value` 列，列表接口从 `content` 反解 | `facts_extractor.py:268-292`、`global_facts.py:775` |

> 结论：`zone_type`、`norm_group` 是死字段；`page_ref` 基本恒空。不属“抽取漏项”，而是 Schema/落库列长期未收敛，建议删除或补齐。

### 5.5 其他完整性边界

- 单条值空白：`_parse_fact_dict` 只拦 `None/""/[]`，**纯空格**能进入 `FactItem`（`facts_extractor.py:1415-1430`）；`_norm_value` 归一为空后，合并分支会在 `unique[0]` 抛 `IndexError`（`:1627-1629/1752-1797`）。
- 文档级 400k 字符截断：用户已定稿行为，超长尾部不参与抽取，有 warning；不报为缺陷。
- 多源：`source` 区分文件；同一事实跨文件靠名称/键合并，无独立“来源投票”权重。

## 6. 跨模块传递链路还原（标断点）

```
文档 raw_text(≤400k)
  → split_into_chunks(8000/500, ≤60段)
  → extract_from_single_chunk(AI, 并发≤5, 重试2)
  → merge_and_deduplicate(confidence/模拟优先, 冲突候选)
  → run_cross_validations(5类规则, 异常吞掉)
  → persist_extraction(保护已确认/手填, 删除未保护旧行)
  → global_facts 表(has_conflict/is_resolved/is_simulated/is_stale)
  → injectable 查询(四重门控)
      ├─ 目录一级: build_facts_text(max 3000) + dd(≤1600) + 知识库 → 外部截 1500

      ├─ 正文: core 6000 + chapter 6000; content_plan 选中 → full_titles

```

### “4000 字预算”核实

## 7. 缺口清单

1. 无按批次回滚/版本历史：只有 `POST /clear` 全清与重提取，无法回到上一版事实（`global_facts.py:2315`；全仓无 facts history 表）。
2. 跨维冲突不持久化：`cross_conflicts` 仅 SSE/检查点，DB 只存单条 `has_conflict/conflict_values`，无 severity/hint/rule_id 长期记录。
3. 无事实变更审计日志：`updated_at` 有，但谁改、改前值、裁决理由未落库。
4. 无失败段恢复入口：前端只显示 `failed_details`，`declared_failed` 未进 `FactsSegmentStats`（前端本地类型丢弃该字段），也没有“只重跑失败段”的按钮。
5. 无预算丢弃可视化：目录侧 `build_facts_text` 不接 `audit_out`，被 1500 截掉的事实不可见；正文侧有 `budget_dropped`，但组标题分支漏记。
6. 无契约测试：`types/facts.ts` 与后端响应无自动对齐机制，靠人工漂移。
7. 无分页 clamp：后端对越界 offset 返回空组（`global_facts.py:812`），前端无回退（BUG-06）。
8. 正文与目录事实格式不统一（dd 仅目录、预算口径不同），无单一渲染出口。
9. 无“事实→章节”覆盖率监控指标，仅事后 `/chapters`。
10. 无并发提取同方案的显式互斥（只有 SSE 同型 pre-guard；R166 已补注册期跨型，但事实写入仍可与手工编辑交错）。

## 9. 确定 BUG 清单（13 项）

> 计数口径：仅收录“当前代码可直接证实行为错误”的项；设计取舍/可见性缺口放入第 7 节。并发修改文件上的结论已标注，修复前需复核。

### P1（3 项）

**BUG-01｜部分抽取失败会删除该段未确认旧事实**
- 证据：`facts_extractor.py:1992-1995`（`chunk_hashes_run` 含失败段）、`:2918-2923`（删除条件命中 `run_hashes`）、`:2664-2687`（只保护已确认/手填）。
- 触发：≥2 段，部分段 AI 失败且其他段成功；失败段存在未确认旧事实。
- 影响：失败段旧事实被删且本轮不重建；持续失败则不可逆丢失。
- 修复方向：删除范围改为 `run_hashes ∩ ok_hashes`（失败段保留旧事实），或落库前按段事务化。

**BUG-02｜模型 `segment_failed` 段被记为已完成，默认增量永久跳过**
- 证据：`facts_extractor.py:355-363`（注释承认永久跳过）、`:2100`（`ok_idx.add`）、`:3001-3045`（以 `chunk_hashes_ok` 写进度）。
- 触发：模型返回 `segment_failed=true` 且无条目；其他段成功。
- 影响：该段下次增量不重跑，叠加 BUG-01 旧事实被删，只能 force 恢复。
- 修复方向：`segment_failed` 段不得进入 `ok_idx`；或单独建“待重试段”表，并在前端提供“只重跑失败段”。

**BUG-03｜数据字典挤占目录事实预算，二三级事实可全量丢失**
- 证据：`content_data_contract.py:170`（dd ≤1600）、`facts_builder.py:765-771`（`budget=max(0,1000-len(dd)-1)`）、`sse_handlers.py:1332-1335`；一级 `sse_handlers.py:911-912/1252`（3000 构建后外部 1500）。
- 触发：`content_data_dictionary=True`（默认）且 dd 长度 ≥1000；一级 dd ≥1500。
- 影响：二三级章节看不到任何事实；一级事实被腰斩/全部挤出，目录生成失去项目参数。
- 修复方向：先算 dd 并按比例限额（如 ≤预算 20%），再把剩余预算传事实渲染；一级去掉 3000→1500 的二次截断，或把 1500 作为唯一预算并让 dd 计入其中。

## 附：本轮结论摘要

- **是否会出现“正文用了错误事实”**：默认配置下不会。四重门控（`facts_extractor.py:3151`）把未确认、冲突、模拟、过期事实全部排除；人工裁决是唯一写回路径。条件风险仅存在于“`auto_resolve=True` + 交叉校验异常被吞”。
- **冲突判定是否闭环**：DB 标记层闭环（未决即排除，不取默认值）；可见性层不闭环（`cross_conflicts` 不落库、刷新丢失、无 rule_id/hint 持久化）。
- **真正的主要风险**：不是错误事实，而是**关键事实被预算与失败策略静默丢弃**（BUG-01/02/03），导致目录/正文覆盖不足。
- **最该修的 3 项**：BUG-01/02（失败段事实丢失）、BUG-03（dd 挤占目录事实预算）、BUG-04/05/06（前端契约与分页使审核链不可用）。
- **确定 BUG 数量**：13 项（P1×3、P2×7、P3×3）。
