## 4. 深度探查结果与修复项清单

### D1（P1 · 数据损坏级，已实测确认）— 编号剥离「第三份分叉副本」过度剥离

- **文件**：`backend/app/services/outline_reorganize.py` L111-122（修复前）
- **现象**：`_NUM_RE` 是继 `numbering.py`、`export.py/content_blocks.py` 之后的**第三份独立编号剥离正则**，其中「中文编号」「点分编号」两个分支过于激进。实测（脚本对拍）：

  | 输入 | 旧 `_strip_number` | 规范 `strip_outline_numbering` |
  |---|---|---|
  | `十二层平面布置` | `层平面布置` ❌ | `十二层平面布置` ✅ |
  | `三层梁板施工` | `层梁板施工` ❌ | `三层梁板施工` ✅ |
  | `十个人` | `个人` ❌ | `十个人` ✅ |
  | `1.2.3钢筋工程` | `3钢筋工程` ❌ | `钢筋工程` ✅ |

- **根因**：`[（(]?[一二三四五六七八九十]+[）)]?[、．]?\s*` 全部量词可选 → 裸中文数字被剥；点分分支回退成「更短前缀 + 点当分隔符」。
- **影响链**：`_strip_tree`（L130）把剥离结果写入 `nn["title"]`，`reorganize_to_standard` 经 `_loose_titles` 写入 description（"（含：…）"）与补充/附录章节标题 → 随 `outline_json` 落库，**用户可见的标题损坏**。
- **修复方案**：删除本地 `_NUM_RE`，`_strip_number` 委托 `numbering.strip_outline_numbering`（编号剥离唯一实现）。
- **关键函数**：`_strip_number`、`_strip_tree`。
- **回归用例**：`backend/tests/test_outline_reorganize.py::test_strip_number_not_destructive`、`::test_strip_number_matches_canonical`。

### D2（P2 · 潜在，已实测确认）— 目录库导入 fallback id 跨父级冲突

- **文件**：`frontend/src/components/OutlineLibraryEditModal.tsx` L501-512（修复前）
- **现象**：`importToTree` fallback id 为 `import_${Date.now()}_${i}`，`i` 仅为**同父内序号**。整棵树在同一毫秒构造完时，「第 1 章的第 1 个子节」与「第 2 章的第 1 个子节」得到**完全相同的 id**。
- **根因**：与方案工作台已修的 BUG-15 同类（`upload_${Date.now()}_${i}`）—— 时间戳 + 局部序号不保证全局唯一。
- **影响**：该 id 被 `collectAllKeys` / `findNode` / `moveFlags` / `removeNode` / `insertIntoNode` / `updateNode` 消费 → 展开态、选中、改名、删除、上移下移作用到错误节点（选中第二个节点，编辑面板显示第一个节点内容）。
- **修复方案**：改用**位置路径**（`1` / `1.1` / `1.1.2` …）生成 `import_${posId}`，全局唯一且稳定。
- **关键函数**：`importToTree`。
- **回归用例**：`frontend/src/tests/OutlineLibraryEditModal.test.tsx`（新增 D2 describe）—— **已实测：旧代码该用例失败（`expected undefined to be truthy`），修复后通过**。

### D3（P2 · 潜在）— 目录深度上限「第二份常量副本」

- **文件**：`backend/app/services/outline_reorganize.py` L27（修复前）
- **现象**：本地重新定义 `MAX_OUTLINE_DEPTH = 3`，与唯一事实源 `services/outline_utils.MAX_OUTLINE_DEPTH` 形成第二份副本。
- **影响**：一旦目录上限调整为 4，本模块仍按 3 裁剪（`_reorg_children` 归位结果被静默截断），与本仓「目录深度唯一事实源」约定矛盾。
- **修复方案**：改为 `from app.services.outline_utils import MAX_OUTLINE_DEPTH`。
- **回归用例**：`test_outline_reorganize.py::test_max_outline_depth_is_canonical`。

### D4（P2 · 分叉收口 + 死副本清理）— 标题编号剥离的最后一份活动分叉 + T-2 残留死常量

- **文件**：`backend/app/services/content_blocks.py`、`backend/app/routers/export.py`
- **现象 1（活动分叉）**：`content_blocks._strip_title_number` 自带 `_TITLE_NUM_STRIP_RES`（5 条正则），实测比规范实现**更差**：`1.2.3钢筋工程 → 3钢筋工程`（点分未吃满整条路径）、`1.1 → 1`（纯编号标题被误剥半截）。
- **现象 2（死副本）**：`export.py` 在 T-2 下沉后残留 **7 个零引用**的本地副本常量（`_ORDERED_MARKER_RES` / `_TABLE_CAPTION_RE` / `_IMAGE_LINE_RE` / `_MERMAID_TITLE_RES` / `_LEAD_IN_TAIL_RE` / `_HEADING_NUM_PREFIX_RES` / `_TITLE_NUM_STRIP_RES`），以及一份与 content_blocks 逐字相同的活动副本 `_LEAD_IN_HINT_RE`。
- **修复方案**：
  1. `_strip_title_number` 委托 `numbering.strip_outline_numbering`（唯一实现）+ **有界循环**（兼容 `第1章 1.1 工程概况` 多重前缀），删除 `_TITLE_NUM_STRIP_RES`；
  2. 删除 export.py 的 7 个死副本；`_LEAD_IN_HINT_RE` 改为从 `content_blocks` 导入（`is` 同源）。
- **关键函数**：`content_blocks._strip_title_number`、模块级常量。
- **回归用例**：`backend/tests/test_numbering_fork_cleanup_20261005.py`（6 用例：行为正确 + 不动点 parity + 死副本缺席 + 引导语同源）。

### D5（P2 · 潜在）— 前端目录层级上限「双份常量」

- **文件**：`frontend/src/pages/SchemeWorkbenchPage.tsx`、`frontend/src/components/OutlineLibraryEditModal.tsx`
- **现象**：两处各自内联 `MAX_OUTLINE_DEPTH = 3`，可独立漂移 → 三个入口对目录层级的拦截口径可能不一致。
- **修复方案**：提取唯一前端事实源 `frontend/src/utils/outlineConstants.ts`，两组件统一导入（沿用 `utils/uploadAccept.ts` 的领域常量模块惯例）。
- **验证**：`tsc --noEmit` 通过；workbench / 目录库 / 弹窗组件测试全通过。
