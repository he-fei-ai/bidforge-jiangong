## 1. 本轮结论摘要

这批改动的主线不是加功能，而是把**会静默失效的地方全部变成会响**：

1. **硬截断留痕**——进模型请求、进审计、进落库的每一处 `text[:N]` 要么改成带账面/带模型可见说明的裁剪，要么被棘轮锁死并写进白名单，裸切片零新增。
2. **失败不折成 0**——扫描失败不再输出「0 条问题」，指纹缺失不再冒充「本次成功」，检测器崩溃不再当作「未发现问题」，配额未回退不再当作「没发生」。
3. **护栏自身可被验证**——棘轮、守恒探针、AST 源码护栏都带注入自检：把违规代码注入真实源码的内存副本，护栏必须变红；删掉被保护的分支，护栏必须变红。
4. **关闭期任务有确定终态**——`shutdown_inflight()` 在 `close_db()` 之前把在途任务落 `failed`，池的获取/探活/归还三个窗口在取消时精确回退配额，8 次泄漏即永久阻塞的故障模式被测试锁死。

一句话：**这一轮买到的主要不是新能力，而是「出错时能被看见、被定位、被复现」的确定性。**

## 4. 关键技术裁决

### 4.1 三个裁剪原语的边界

| 原语 | 位置 | 谁用 | 为什么不混用 |
|---|---|---|---|
| `clip_text` | `prompt_material_guard.py:267` | 旧调用点 / 非进模型路径 | **只留痕不告知**。模型收到半截文本却以为拿到全文，是最危险的静默错误，因此**禁止**出现在进模型请求路径（棘轮 `:266` 强制）。 |
| `clip_text_logged` | `prompt_material_guard.py:325` | 关键词匹配、启发式兜底等**内部判定** | 往用于匹配/正则的字符串里插「已截断」说明会改变判定结果，等于用可观测性换另一种静默错误。返回值必须与旧 `text[:limit]` **逐字节一致**，只新增日志账目。 |
| `clip_text_notice` | `prompt_material_guard.py:423`（账面版 `:387`） | 所有进模型请求 | 模型必须知道「后面还有内容被省略」：追加 `[……{label}已截断：原文 N 字，此处保留前 K 字，已省略 M 字]`，并按段落/句子/词边界收刀（边界离上限不足 60% 才硬切，`:303`）。 |

判断规则一句话：**文本会进模型 → notice；文本只用于程序判定 → logged；两者都不是 → 不应调用任何裁剪函数。**

### 4.2 为什么删掉 `SENSITIVE_MATERIAL_LABELS`

它是 `MATERIAL_LABELS` 的真子集（按前缀语义「项目资料摘要」已被「项目资料」命中），且**全仓零消费**。它声称的「按标签限定脱敏」语义从未实现——`redact_sensitive` 对整段文本无条件脱敏，围栏也由 `MATERIAL_LABELS` 统一判定。保留的唯一效果是两套集合随产品演化漂移。若未来真需要「只脱敏不围栏」的差异语义，应在 `govern_text` 里按标签分支实现，而不是再挂一个没人读的常量。

### 4.3 为什么 `get_prompt` 未注册 key 仍返回空串、只升日志级别

- 返回空串是 `fail-soft` 的既定契约：文案配置错误不应升级成 500，让整条生成链路直接不可用。
- 但「空系统提示词 + 任务照跑」属于高危静默，所以日志从 `warning` 升到 `error`（`_cache.py:378`），并计入 `render_errors`（`:383`），保证能在 ERROR 级别检索到、也能在指标里看见「谁在反复读不存在的模板」。
- 取舍：**不改变行为，只改变可见性**。真正修配置需要在提示词管理页补 key，而不是让运行时抛错。

### 4.4 为什么审计写入方分三类而不是全部收进漏斗

| 类别 | 写入方 | 语义 |
|---|---|---|
| `ai_call` | `provider_factory.py` | 一次模型调用的遥测：厂商/模型/token/耗时/尝试序列。**漏斗 SQL 唯一自持方**。 |
| `ai_batch` | `compliance.py` | 批次遥测：复用同一组 SQL 常量，但一条记录代表一批调用。 |
| `state_transition` | `state_machine.py` | 任务/阶段**迁移流水**：不填 provider/model、不计 token/耗时、`attempt_count` 恒 1；`success` 列恒 1 只表示「迁移动作已落库」，**不表示调用成功**。 |

全部收进漏斗会直接把「整表聚合」类指标打歪——这正是 `73d891c` 修掉的故障（`tokens_today` 被 `agent_*` 行污染）。因此做法是：**按类别登记 + 按 action 过滤聚合**，而不是消灭第二类写入方。护栏锁死三件事：未登记写入方红（`:187`）、除 provider_factory 外不得自抄 INSERT（`:221`）、state_machine 单写入口 + `agent_` 前缀（`:228-232`）。

### 4.5 为什么 `_LazySseHandlers` 用属性代理，而不是把符号下沉

环的两条边：`_sse_outline_review` 顶层 `import sse_handlers`，而 `sse_handlers` 文件末尾又把 40 个符号转发自 `_sse_outline_review`。先导入前者时，后者转发会向**半初始化**的前者取 `_DANGEROUS_REQUIRED_KEYWORDS`（定义在文件更靠后）→ `ImportError: partially initialized module`。

- 下沉共享符号：那 40 个符号里多数是 `_sse_outline_review` 自身定义的函数，下沉等于整体搬迁，改动面远大于收益。
- 函数内局部 import：只是把失败点往后挪，环仍在。
- 属性代理（`_sse_outline_review.py:12-38`）：只在属性访问时导入真模块，读走 `getattr`、写走 `setattr`，`monkeypatch.setattr(sse_handlers, ...)` 的 facade 语义完全不变。

## 5. 两条连接池 P1

### 5.1 故障模型

`_db_pool_total`（写池，`db.py:1626`）与 `_read_pool_total`（读池，`db.py:1896`）是**获取闸门**：只有 `total < 8` 才允许新建连接，池空时等待 `Condition`。计数只在「连接真正关闭」时递减。

`CancelledError` 继承 `BaseException`，旧的 `except Exception` 接不住。取消发生在「容量已预留、连接尚未纳入任何容器」的窗口时：

- 配额永久 +1（`close_db()` 只按池内/在途容器递减，容器里没有这条连接，减不回来）；
- 重复 8 次后 `total == 8`，`total < MAX` 永假；
- 池空、在途集合空、没有连接会再归还 → `wait()` 永久睡死。

### 5.2 写池三个窗口

| 窗口 | 位置 | 状态 | 修复 |
|---|---|---|---|
| ① 预留后建连 | `db.py:1759-1773` | `total += 1` 已执行，`connect/setup/probe` 任一 await 被取消 | `except BaseException` → `total -= 1` + `notify()` + `close()` + `raise` |
| ② 出池后探活 | `db.py:1696-1706` | 连接已 `pop`（仍在 `total` 中）、未进在途集合 | 同上 |
| ③ 归还窗口 | `db.py:1813-1826` | 已从在途集合 `discard`，探活/入池期间被取消 → 既不在池也不在在途 | 同上 |

### 5.3 读池三个窗口

`db.py:2035-2052`（建连）、`:1973-1983`（探活）、`:2089-2102`（归还），形态与写池逐字同构。

### 5.4 读池与写池的实质差异

1. **探活语句不同**：写池 `PRAGMA wal_checkpoint`；读池连接是 `query_only=ON`，checkpoint 的写路径会被拒，必须用 `PRAGMA wal_checkpoint(NOOP)`（`db.py:1902-1915`）。
2. **新建路径多一个 await 窗口**：读池在建连后还要执行 `_setup_connection` **和** `PRAGMA query_only=ON`（`db.py:2007`）再做探活；取消可落在其中任一 await 上。写池没有 `query_only` 这一步。
3. 正因如此，`1569dfb` 才需要把读池三个窗口单独补一遍，而不是「写池修了读池自然好」——两套计数、两套容器、两套探活。

### 5.5 证明方式

- 运行时：六个取消用例断言 `total == 0`、`pool == []`、不在 `borrowed`、`_is_dead_conn(conn)`、`task.cancelled()`（`test_db_shutdown_inflight_20261107.py:242-520`）。
- 源码：AST 护栏要求每个函数**恰好** N 个 `BaseException` 回退且以 `raise` 收尾（`:535-600`）。
- 守恒：autouse 探针逐用例校验 `total == 池内 + 在途`。
- 红→绿：修复前 4 failed（`assert 1 == 0`），修复后 10940 passed。

## 6. 关闭语义

### 6.1 顺序（`backend/app/main.py:504-524`）

1. uvicorn 停止接收新连接，等待在途请求，**上限 30s**（`--timeout-graceful-shutdown 30`）；
2. 停周期任务（审计 flush、回收任务），关 AI HTTP 连接池；
3. `shutdown_inflight(reason="服务关闭，任务中断", cancel_timeout=2.0)`，外层 `asyncio.wait_for(..., 3.0)`：取消在途子任务与游离后台任务，把 `running/paused` 落 `failed`；
4. 最后 `close_db()`：归还/关闭全局连接、读写池（含借出未归还）与完整性巡检任务；
5. 清理临时脚本 / 锁文件。

### 6.2 为什么 `--timeout-graceful-shutdown 30` 是必须的

uvicorn 是「先等在途请求任务、再走 lifespan」。不设该参数时对请求任务**无上限等待**：只要有一条 SSE 长连接（正文/目录生成、事实抽取）挂着，`lifespan.shutdown()` 永远进不去，关闭永久挂住。本机实测（uvicorn 0.49，一个永不结束的 SSE 长连接）：设 30 → 30.2s 正常关闭；不设 → **超过 40s 仍未关闭**。

### 6.3 反直觉约束：终态必须写进库再关连接

`shutdown_inflight()` 必须在 `close_db()` **之前**执行，且**不得依赖**「关闭后 `get_conn()` 再重建连接写一行」：

- 重建连接会留下非守护 aiosqlite 线程（进程退不掉）；
- 让「关闭即失败」退化成「关完又偷偷连回来写一行」，关闭语义不再确定；
- 关闭后再发起的 DB 操作仍可重建连接，这本身是已知 P3 遗留（见 7.6）。

### 6.4 关闭期任务语义

关闭时在跑的任务会被中断，库内终态写 `failed` / `服务关闭，任务中断`，不会停留在 `running`。前端重启后看到明确失败终态，可直接重新发起，不会出现「永远转圈」的僵尸任务。

## 7. 诚实边界（不许弱化）

### 7.1 全量回归的覆盖面

默认配置下的**全量**回归（10945 passed）只能证明「治理开关关闭时行为逐字节不变」，**不能证明开启后的行为**。四开关打开态只有 **364 条定向子集**覆盖（见 2.3）。也就是说：开关开启时的整链路（尤其预算分配器 + 章节注入 + 定向子集未覆盖的分支）没有全量证据。

### 7.2 前端与 SSE 的验证深度

- 前端布局与暗色是 **jsdom + mock fixture 下的浏览器实测**，不是真实业务链路（真实数据量、真实长列表、真实弱网未覆盖）。
- SSE 只验证了「端点不可达」的重连态，**没有验证「流中途断 TCP」**——Vite 代理会把截断流归一成 EOF，测试环境构造不出「半截流」，因此该场景在本轮仍属未验证。

### 7.3 esbuild 跨语言 parity 用例

该用例在非 Windows 上**永远 skip**。进 CI 必须改成按平台解析（否则 Linux CI 上它是「永远绿的空壳」，不提供任何保护）。

### 7.4 `_diag/` 未核对

`_diag/` 因 NTFS ACL 拒绝访问，内容**始终未核对**。本轮对其不持任何结论。

### 7.5 远端默认分支

远端默认分支仍是 `master`，需在 GitHub 仓库设置里改；`git` 命令无权修改默认分支。

### 7.6 已知残留（本轮不修）

1. 读池**取锁瞬间**被取消的极窄窗口（`await cv.wait()` 自身被取消，尚未进入任何预留状态）——当前按「未持有配额」处理，理论上仍存在竞态，但未构造出可复现路径。
2. `close_db()` 在 `await c.close()` 阶段被取消——连接可能已半关闭，配额回收依赖后续流程，未做专门加固。
3. `close_db()` 之后新发起的 DB 操作仍可重建连接（P3）——关闭语义的「最后一道门」是约定，不是强制。
