- `sse_handlers.generate_outline` 分步链：暂停闸门（`wait_resume`）排在并发信号量之前（R223 SSE-2 已固），`_partial_holder` 承接已生成成果。
- `_sse_outline_review._finish_stopped_with_partial`（:307）：目录生成「用户停止」的唯一收尾出口，**先落 checkpoint → 再置终态 → 最后 yield**（顺序契约 R188）。
- **DAT-6′**：取消/断线兜底若落在 **completed checkpoint 已落库之后**（任务已 `finish_task("completed")` 并 pop），`_finish_stopped_with_partial` 仍会：① 再写 partial checkpoint **覆盖** completed 成果；② 再调 `finish_task("stopped")` 把正确终态**覆写成 stopped**。

## 4. 修复与增强（步骤 4/5 · 落地 1 项 + 护栏 3 条）

### 4.1 DAT-6′ 修复：`_finish_stopped_with_partial` 终态重入守卫

**文件**：`backend/app/routers/_sse_outline_review.py:342-361`

**修法**：写 checkpoint 前读任务 DB 行状态，**终态 `completed`/`degraded` 时跳过覆盖与 `finish_task`**，直接返回裸 stopped SSE 事件（零副作用）。

```python
# ✅ R226（DAT-6′ · P2 · R223 遗留 #1）：任务已进入终态后重入（迟到取消/断线
#    兜底落在 completed checkpoint 落库之后）。_write_task_checkpoint_db 是
#    无条件 UPDATE（sse_checkpoint.py:97 `WHERE id=?`），partial checkpoint 会
#    覆盖 completed 成果；finish_task 的 _write_task_terminal_db 有
#    `WHERE status IN running/paused` 守卫（不覆写终态），但 checkpoint 无守卫。
#    守卫读 DB 行状态：终态 completed/degraded 时跳过覆盖与 finish_task，
#    保留正确终态（R223 §10 登记：任务 completed 但重挂提示部分成果）。
#    读失败时保守放行（旧行为），finish_task 自身的 WHERE 守卫仍能阻止终态被
#    覆写；payload 此时尚未带 outline（仅 event=stopped），前端已收到过
#    completed 事件与完整成果，裸 stopped 恰是正确信号。
try:
    _db_status = await _sh._load_task_db_status(task_id)
except Exception:
    _db_status = None
if _db_status in ("completed", "degraded"):
    _sh.logger.info(
        "迟到停止请求被忽略（task=%s · 目录生成 · 任务已进入终态 %s，保留正确终态）",
        task_id, _db_status,
    )
    return "data: " + json.dumps(payload, ensure_ascii=False) + "\n\n"
```

**判据选择**：采用 **DB 行状态**（而非 `has_active_task` 内存态）。理由：① 与 R223 §10 登记规格「读任务行状态、终态 completed/degraded 时跳过覆盖」逐字一致；② 不击穿既有护栏——`test_stopped_carries_outline_and_saves_checkpoint` 等仅 seed DB 行（status="running"）不注册内存 `_tasks`，若用 `has_active_task` 恒 False 会误伤（`has_active_task` 依赖 `task_id in _tasks`，测试桩未注册任务即恒假）；③ 比 `has_active_task` 更稳健——连 `finish_task` 广播窗口（DB 行已 completed、任务尚未 pop）的窄竞态也捕获。

**新增辅助函数**：`sse_checkpoint._load_task_db_status(task_id) -> str | None`（读 `task_registry.status`，无行返回 None），经 `sse_handlers.py` 导入块暴露（`_sh._load_task_db_status` 可达）。

**Fail-open 语义**：读状态失败（连接异常）时保守放行（走旧收尾），`finish_task` 自身的 `WHERE status IN running/paused` 守卫仍能阻止终态被覆写——行为回退仅限「读不到状态」的极端场景，不扩大风险。

## 8. 教训归档

1. **守卫判据必须与被测/既有契约同源（DAT-6′ 落地过程中的方向修正）**：首版用 `has_active_task`（内存态），被既有护栏 `test_stopped_carries_outline_and_saves_checkpoint` 当场抓红——该测试仅 seed DB 行（status="running"）不注册内存 `_tasks`，`has_active_task` 恒 False 会误伤合法停止。改读 **DB 行状态**（R223 登记规格逐字一致）后 12p 全绿。教训：**修复判据优先选既有护栏可观测的量**，避免「内存态 vs 测试桩」口径分叉（R223 教训 6 的再应用）。
2. **「无条件 UPDATE」vs「带守卫 UPDATE」的不对称是 DAT-6′ 的根因形态**：`_write_task_checkpoint_db` 无 status 守卫、`_write_task_terminal_db` 有——同一终态收口的两条写路径守卫不对称，partial 覆盖 completed 的唯一漏洞就在无守卫那条。教训：**收口路径的每条 DB 写语句都应审视 status 守卫**，守卫缺失处即潜在覆写点。
3. **「同族第 N 处」持续发现模式在状态机面同样成立**：`_finish_stopped_with_partial` 的终态重入守卫与 facts 链 `finally` 的 `has_active_task` 兜底（sse_handlers.py:8271）是**同一族**「终态防覆写」判据——本次用 DB 行状态实现，facts 链仍用内存态；下次收口 facts 链同类问题时**必须 grep 全族调用点**（R223 教训 3 的再应用）。
