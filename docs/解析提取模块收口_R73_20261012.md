## 2. 功能架构与现状分析

1. **上传**：`upload_documents` 三重配额（单文件 30MB / 累计 200MB / 数量 20，全部可配并经 `/system/upload-limits` 下发前端）、流式分块落盘（防 OOM）、失败回滚已落盘文件、同名替换（commit 后 purge 四层产物）、文件头签名预检（16 字节）、累计触顶文件名独立上报 `quota_files`。前端 `partitionUploadFiles + splitByUploadTotalQuota + splitByUploadFileCount` 三项预检与后端逐字同语义（B8/B10 已收口）。

3. **内容解析**：14 格式分派 → Markdown 结构化（表格竖线归一、页标记 `<!-- page:N -->`、PDF 双引擎表格合并、Excel/CSV 表头识别、图片 OCR 多帧/多引擎、旧版 Word 转换链、归档膨胀三道闸门）。
4. **信息保存**：`parsed_markdown` 落库（`MAX_PARSED_CHARS=400000` 截断 + `parse_truncated` 双口径持久化）+ 四层存储（`doc_chunks` 全删全插幂等、块级指纹 diff、时效列回写）+ meta/index/semantic 三文件（写失败 fail-soft 不丢 DB 主结果）。
5. **错误处理**：`ParseError` 契约（不可恢复失败只抛 ParseError）；路由层 ParseError→400 原样展示、泛化 Exception→400 无细节日志；`parse_status` 状态机 pending/success/failed 全程维护 + 存量自愈 `_reconcile_parse_status`。
6. **工作流程**：6 步工作流之「上传解析（import）」= 上传 → 解析（单据/批量）→ 预览/分类 → 下一步（提取项目子 Tab）。`UploadParseTab` 受控组件 + `computeDocStats` 统计口径。
7. **AI 调用**：解析阶段零 AI（纯程序）；AI 面在「提取」（generate-facts SSE / bid-analysis 18 项）与「目录识别 AI 兜底」（outline_recognition scene 已登记）。
8. **数据链与存储**：project_documents → doc_chunks/doc_extractions（四层）→ global_facts/bid_analysis_items → sections/export。删除/强重解析均接 `_mark_project_facts_stale + _invalidate_project_export_caches`；R32 级联登记表补全。
9. **路由与接口**：见 §1 全部端点；`main.py` 挂载 `global_facts_docs` 路由（2026-10-09 拆分；前端 9 个文档 API 方法签名/字段逐项一致，本轮已比对）。

## 3. 体检方法与已核实非缺陷（防止重复排查）

### 3.1 探测手段
- **18 组畸形/截断/改名输入 fuzz** `parse_file_content_ex`（PDF 截断、伪造 ZIP、OLE 垃圾、图片截断、GBK/Big5/UTF-16、空文件等），每例独立子进程 12s 超时；
- **热/冷进程对比**（判断是否生产缺陷）；
- **前后端契约逐项比对**（前端 api 层 9 个文档方法 ↦ 后端签名/响应字段）；
- **路由/调用链 grep**（`docPipelineApi` 消费点、handler 接线、API 封装与页面调用）；
- 配额/常量单一事实源核查（`MAX_PARSED_CHARS` 别名、`/system/upload-limits` 下发、`uploadAccept` 兜底）。

### 3.2 已核实非缺陷（附证据，后人勿重复排查）
1. **截断图片解析「挂死」**：fuzz 中 `png/jpg/bmp/tiff` 截断到 12s 超时 —— 经热进程实测（引擎缓存后）**0.04s 抛 `ParseError("OCR 识别失败…rapidocr: cannot identify image file")`**。挂死根因 = 新起子进程冷加载 RapidOCR ONNX 模型（~12s+）；生产服务常驻后引擎缓存、仅首个请求多一个 worker 占用，**非缺陷**。
2. **`.doc` 空 OLE 转换慢**：LibreOffice 对损坏 OLE 转换 >12s，但 `legacy_office._run_process` 有 `timeout_s`（默认 120s，可配）且失败归入 attempts 继续下一后端 → 有界能降级，**非缺陷**（登记观察项）。
3. **`global_facts_docs` 顶部三个静态配额常量（30MB/20/200MB）与 `global_facts` 动态值不一致**：静态值是「模块级占位」，上传路径动态读 `gf` 命名空间，无生产代码把 docs 侧静态值当权威 —— 维护性债务，**非活跃缺陷**。
4. **R72-C 前端测试「不存在」**：R72 测试 docstring 声称覆盖项在 `outlineLibraryImport.test.ts`，实际落地于 `OutlineLibraryEditModal.test.tsx`（381 行起「导入空结果不覆盖当前树（R72·C）」2 例）—— **文档引用名失实**，测试本身在位。
5. **`CompDocError` 逃逸不会导致 500**：修复前两条上传路由均有泛化 `except Exception` 兜底（`global_facts_docs:1108-1114` / `upload_outline:226-228`）—— 只是「坏文件被记成 ERROR 级全堆栈 + 用户提示无差别」，不构成崩溃（这正是 §6 修复动机：契约 + 观感 + 日志降噪）。

## 6. 修复项清单（§5 对应 · G1）

### 6.1 根因实证（fuzz 探针）
| 输入 | 修复前异常 | 逃逸类型 |
|---|---|---|
| OLE 头合法但结构损坏的 `.xls` | `xlrd.compdoc.CompDocError: Expected "little-endian" marker...` | 非 ParseError |
| 把 `.docx` 改名成 `.xlsx` | `openpyxl` → `KeyError: There is no item named '[Content_Types].xml'` | 非 ParseError |
| xlsx sheet XML 损坏 | `openpyxl` → `OSError: File contains no valid workbook part` | 非 ParseError |
| 把 `.xlsx` 改名成 `.xls` | `xlrd` → `KeyError: 'xl/_rels/workbook.xml.rels'` | 非 ParseError |

### 6.2 修复方案（`backend/app/services/file_parser.py` · `parse_file_content_ex` 格式分派区）
在 14 格式分派块外套 `try/except`：
- `except ParseError: raise` —— **原样透传**（压缩炸弹/加密/缺依赖/OCR 无引擎等既有语义与文案一字不改）；
- `except Exception as _e` —— 统一转换为 `ParseError(f"{LABEL} 文件已损坏或不是有效的文件，请确认真实格式后重新上传")`，WARNING 单行日志（不带 exc_info；原因串已含库错误，够定位）；
- 闸门前置保持：`_reject_binary_text_ext` / `_guard_zip_archive` 在 try 之外，各自 ParseError 不经归一（文案保持）。

### 6.3 向后兼容
纯加法归一：合法文件解析结果 `(text, diag)` 逐字不变；ParseError 类失败文案逐字不变；仅新增「库异常→ParseError」映射。两条上传路由修复前后均 400，但文案更具体、日志不再刷 ERROR 堆栈。

### 6.4 护栏（`backend/tests/test_import_parse_contract_r73_20261012.py`，10 例 / 4 组）
- **A 契约归一**：3 条真实逃逸字节（损坏 OLE .xls / docx 改名 xlsx / sheet XML 损坏）→ `pytest.raises(ParseError)` 且文案含格式名、不含底层细节；无 xlrd/openpyxl 环境 importorskip（不红不误报）。
- **B 透传**：monkeypatch `_guard_zip_archive`/`_parse_image_ocr` 抛 ParseError → 原样透传（文案不被包装改写）。
- **C 防御纵深**：monkeypatch 任意解析器抛 RuntimeError → ParseError；合法 CSV/GB18030 正常解析（回归控制）。
- **D 静态接线锁**：`inspect.getsource` 断言分派区存在 `except ParseError:`/归一文案，且归一 except 位于 `_parse_image_ocr` 调用之后（防包装只罩前半段）。

### 6.5 A/B 反向验证（`try/finally` 还原 + sha256 字节一致）
- 变异：`except Exception as _e:` → `except (ValueError, KeyError) as _e:`（CompDocError/OSError 恢复逃逸）；
- 结果：**2 failed, 1 passed**（护栏定向抓出两条逃逸；KeyError 一条仍被窄化为预期不红的对照组）；
- 还原：`restore_sha_match True`，3 passed。

### 12.3 G4 · 旧版 Word OLE 头结构预检（毫秒级早退）

**问题**：`convert_legacy_word_to_docx` 对损坏 / 被截断的 `.doc` 无任何结构预检，
要走完「`detect_office_backends` → LibreOffice 转换 → **120s 超时** → 第二后端重试」
≈ 4 分钟，且期间占住一个线程池 worker；最终用户拿到的仍只有「转换失败」。
§8 把它登记为「观察项」，本轮落地。

**设计红线（关键）**：预检**只判定「合法 CFB 文件的必要条件」**，
**绝不做内容语义解析**。这样它在结构上**不可能**把正常的老版 Word 误判成损坏 ——
误拒的代价（用户文件被拒、无法解析）远高于白等的代价。

**改动（`backend/app/services/legacy_office.py`，+98 行）**：

| 符号 | 职责 |
|---|---|
| `_CFB_HEADER_SIZE = 512` / `_CFB_RESERVED_SECTORS = 0xFFFFFFFB` | 常量（MS-CFB 2.2 / 2.1） |
| `validate_ole_compound_header(content) -> str \| None` | 纯函数判定；`None` = 合法**或不在职责内**（文件太短 / 非 CFB 容器） |
| `legacy_ole_preflight_enabled()` | 读 `settings.legacy_ole_preflight` |
| `ole_preflight_reason(content) -> str \| None` | **唯一出口**：开关 + fail-open 兜底 |

判据四条（全部可证伪的必要条件）：
1. **头字段值域**：小版本 `= 0x003E`、大版本 `∈ {3, 4}`、字节序 `= 0xFFFE`、
   扇区位移 `∈ [7, 12]`、迷你扇区位移 `= 6`；
2. **扇区算术（截断判据）**：头部声明的 `n_fat + n_dir + n_mini + n_difat`
   ≤ 文件实际扇区数 `(len - 512) / 2**sec_shift`；
3. **v4 才强制** FAT / 目录扇区数 ≥ 1；
4. **目录扇区索引**非保留值（`0xFFFFFFFB~0xFFFFFFFF`）且不越界。

接线在 `detect_office_backends` **之前**（连组件探测开销都省），命中即
`ParseError("旧版 Word 文件已损坏（<原因>）：请用 Word/WPS 重新打开并另存为标准 .docx 后重新上传")`。

**两个真实陷阱（本轮回退了两次）**：

| # | 首版错误 | 实测后果 | 修法 |
|---|---|---|---|
| 1 | 扇区计数偏移读错：从 `0x34` 连读 4 个计数 | `0x34~0x3C` 实为「事务签名 / 迷你扇区上限 / 首个迷你 FAT 扇区」而**不是**扇区计数 → 把一份 **1.23MB 真实 Excel 97 `.xls`（v3 · 512B 扇区 · 19 个 FAT 扇区 · 2408 扇区）误判成「已截断」** | 按 MS-CFB 2.2 严格取 `0x28 / 0x2C / 0x40 / 0x48` |
| 2 | 「v3 也要求 FAT / 目录扇区 ≥ 1」 | CFB **v3** 允许 FAT 内联在 DIFAT 数组（`num_fat=0`）且规范要求目录扇区数写 0，真实 Excel 97 `.xls` 正是此形态 → 误拒正常文件 | `if major == 4 and n_fat < 1` / `if major == 4 and n_dir < 1` **只对 v4 强制** |

第二条陷阱已被护栏 `test_v3_excel_shape_accepted` 用那份真实 `.xls` 的字段布局钉死。

**fail-open 红线**：`ole_preflight_reason` 包 `try/except` 记 WARNING 后返回 `None`
—— 预检自身任何异常都不得阻断原本可解析的老版 Word（预检只是加速用的辅助判定）。
两条护栏锁住：`test_preflight_reason_fail_open_on_own_exception`
（monkeypatch `validate_ole_compound_header` 抛 `RuntimeError` → 仍返回 `None`）
+ `test_switch_off_skips_validation_entirely`（开关关闭时**判定函数都不得被调用**）。

语义级兜底（§5.14「源码含字符串是假判据」同族）。

### 13.7 递延项硬化（item ① / item ④）

> §13.4 登记 item ①（非 CFB/ZIP 容器）与 item ④（真实 `.doc` 语料）刻意递延。
> 调查后确认两者**均无真实症状可修**，故最优方案是**硬化递延决策本身** ——
> 把「为何不做」的架构依据做成可执行护栏，防未来会话重新审视或「修复」
> 一个不存在的问题（本仓「no symptoms = 不加 speculative code +
> 加固递延决策」模式，同 R69 §6.2）。

**item ① 调查结论**：`LEGACY_WORD_EXTENSIONS = {"doc", "wps"}` 全是 OLE/CFB 容器；
ZIP 容器（`.docx`/`.xlsx`）走 `file_parser._parse_docx` 的 Python `zipfile` 快路径，
**不经过 LibreOffice 转换**，损坏 ZIP 由 `zipfile` 毫秒级抛错（并经 R73 G1 契约归一
收敛为 `ParseError`）。因此「损坏 ZIP 白等 120s」的症状**结构上不存在** ——
G4 对非 CFB 返回 `None` 交后端判定是正确行为，**不需要新增 ZIP 容器预检**。

**item ④ 调查结论**：`validate_ole_compound_header` 只看 CFB **容器头部**字段，
**不读任何流名**（Workbook/WordDocument/0Table/Data 等）。CFB 容器层 `.doc` 与
`.xls` 的唯一差异是内部流名，头部字段布局完全相同 —— 因此
`test_v3_excel_shape_accepted`（用真实 1.23MB Excel 97 `.xls` 字段布局钉死）
**结构性地覆盖**了 v3 Word `.doc` 的头形态。缺真实 `.doc` 语料时，
**不存在**「头级判据对 .doc 漏检」的风险。

**硬化护栏（`TestZipContainerNoPreflightNeeded` 3 例 + `TestHeaderCheckIsFormatAgnostic` 2 例）**：

| 护栏 | 锁定的不变量 | A/B 验证 |
|---|---|---|
| `test_legacy_word_extensions_are_cfb_only` | `LEGACY_WORD_EXTENSIONS` 不得含 ZIP 扩展名（docx/xlsx/zip...） | 塞 `docx` → 定向失败（`restore_ok: True`） |
| `test_docx_parser_catches_bad_zipfile` | 损坏 ZIP 作 `.docx` → `ParseError`（3 种损坏形态行为级验证） | — |
| `test_zip_container_returns_none_from_ole_preflight` | G4 预检对 ZIP 返回 `None`（交后端快路径） | — |
| `test_validate_does_not_read_stream_names` | 头预检源码不引用任何 CFB 流名（格式无关性硬锁） | — |
| `test_v3_excel_shape_structurally_covers_v3_doc` | 同一字段布局对 .doc/.xls 都合法（显式标注覆盖关系） | — |

**A/B 1/1 CAUGHT**：把 `docx` 塞进 `LEGACY_WORD_EXTENSIONS` →
`test_legacy_word_extensions_are_cfb_only` 定向失败（`restore_ok: True`）。

**为什么这是「最优方案」而非新增 ZIP 预检代码**：新增 `validate_zip_container()`
会是一个**无症状的 speculative 函数** —— 它要防的「损坏 ZIP 白等 LibreOffice」
症状在当前架构下不存在（ZIP 不走 LibreOffice）。而硬化递延护栏锁住的是
**架构依据本身**（ZIP 走快路径、头检查格式无关），一旦有人误改
`LEGACY_WORD_EXTENSIONS` 或往头预检加流名读取，护栏立即红 —— 这才是真正的
regression 防线。新增 speculative 代码只会增加误拒正常 ZIP 文件的风险
（与 G4「只判必要条件」红线冲突）。
