## 一、技术选型

### 1.1 结论：自研轻量 `SplitPane`（Pointer Events），零新增依赖

| 候选 | 评估 |
| --- | --- |
| **react-resizable-panels** | 只支持**百分比** min/max，无法表达「侧边栏 200–400px」这类 **px 级防坍塌约束**（本需求 sidebar 200–400px 是硬性 px 约束）；会接管 DOM 结构，嵌套需 panelGroup/panel 组件层级，与现有 antd Sider / Card 布局耦合度高 |
| **splitpanes** | 同为**百分比**模型；会接管 DOM；5 个区域全部是「两栏切分」，用它属于过度依赖 |
| **自研 SplitPane**（采用） | ① 5 个区域全部是**两栏切分**，一个两栏组件 + 一个通用手柄即可覆盖全部；② 可同时表达**比例持久化**（刷新后保持、随窗口缩放）与 **px 级 min/max 防坍塌**（侧边栏 200–400px）；③ 零新增依赖（无 `package.json` 变更）；④ 用 Pointer Events + `setPointerCapture`，鼠标/触摸统一 |

**选型依据**：需求明确「侧边栏 200–400px」px 级约束 + 「<1024px 降级」+ 「嵌套拖拽防冲突」+「重置布局」+「ResizeObserver 自适应」。自研实现可逐条精确满足且不引入第三方 DOM 接管。

### 1.2 核心设计决策

1. **持久化「比例」（0~1）而非 px**：窗口尺寸变化后按比例还原，再由 SplitPane 用 px 级 min/max 夹紧。避免「存 px 在窗口变小后溢出」。
2. **防坍塌双保险**：渲染用 CSS `flex-basis:%` + `min/max-width/height(px)` 夹紧；`ResizeObserver` 监听容器尺寸变化**再次夹紧**（窗口缩窄 / 上层拖拽联动时不坍塌、不溢出）。
3. **嵌套防冲突**：手柄 `pointerdown` 调 `e.stopPropagation()`，内外层 SplitPane 互不干扰。
4. **拖拽中全局态**：`body.bp-resize-dragging` 禁用文本选中 + 锁定 `col-resize`/`row-resize` 光标；卸载兜底 `cleanup` 摘全局类 + 补发持久化。
5. **窄屏降级**：`disabled=true` 渲染为单栏堆叠、不挂手柄、不读不写持久化。
6. **存储 fail-soft**：所有 localStorage 读写 `try/catch`，隐私模式/存储禁用时布局功能静默降级。

## 三、验证结果

### 3.1 功能护栏（`resizablePanelsR145.test.tsx`，11 passed）

| 组 | 覆盖 |
| --- | --- |
| A/B | 横向拖拽增量 → flex-basis 按新比例更新；拖拽结束写入 localStorage，重挂载按存储比例还原 |
| C/C2 | 防坍塌：拖过头被 `max` 夹紧、极限拖小被 `min` 夹紧（1000px 容器 max=450 → 45%；min=100 → 10%） |
| D | 窄屏降级：`disabled` 不渲染手柄、不读写持久化 |
| E | 重置布局：清空持久化 + 回默认比例 |
| F | 嵌套防冒泡：内层手柄拖拽不改变外层比例 |
| G | 手柄语义：`role="separator"` + `aria-orientation` + 轴类光标 |
| ResizeHandle 独立 | `onDelta` 上报增量、`onDragEnd` 回调；`disabled` 不响应拖拽 |
| 重置信号 | 初始挂载 `resetSignal=0` 不误重置（不读脏值） |

### 3.2 拖拽流畅度与自适应

- **拖拽**：Pointer Events + `setPointerCapture`，`pointermove` 计算增量 → `setRatio(clampRatio(...))`，实时更新 `flex-basis:%`；拖拽中 `body.bp-resize-dragging` 禁用文本选中、光标锁定，无选择污染。
- **持久化**：拖拽结束（`pointerup`/`pointercancel`/卸载兜底）写 `bp-rp:<key>`；刷新后按比例还原，再由 px min/max 夹紧。
- **ResizeObserver 自适应**：容器尺寸变化（窗口缩放/上层拖拽联动）时重新夹紧，内部 `bp-resize-pane` 用 `overflow:hidden` + `contain:layout style` 约束表格/图表/文本，不溢出、不变形。

## 四、R145 引入的回归与修复（R147 收口）

### 4.1 现象

R145 的 SplitPane 布局改造后，`schemeWorkbench.test.tsx` 出现 **12/28 确定性失败**（6 个工作流 Tab / 8 个树操作 + 4 个导出预检），失败点集中在 `gotoOutlineTab` 的「点击 Tab 后目录树不渲染」与 `runExportCheck` 的「预检按钮未找到」。

### 4.2 根因（A/B 决定性对照）

- 强制 `narrowWorkbench = true`（走无 SplitPane 降级分支）→ **28/28 passed**；恢复 SplitPane 宽分支 → 12 failed。**排除**「SplitPane 功能本身坏了」，定位为「SplitPane 结构改变了渲染时机」。
- 移除 `GenTaskListPanel`（替换为占位）→ 仍 12 failed。**排除**任务列表轮询是诱因。
- 加日志诊断：T1（冷模块）点击时 `tab.isConnected=true`、`handleWorkbenchTabChange` 被调用、切换成功；T2（热模块）点击时 **`tab.isConnected=false`**、handler **未被调用**。**确认根因是 R120 记录的 stale-node 点击**：`findByText` 捕获的 Tab DOM 引用在组件因数据加载（`load/loadFacts` 落定）再渲染时脱离文档树，React 事件委托（挂 root/document）对脱离节点不触发 `onChange` ⇒ 点击 Tab 静默无效。SplitPane 的额外渲染层只是**放大**了这一既有测试脆弱点，不是功能缺陷。

### 4.3 修复（R120 规程，测试基础设施）

- **`frontend/src/tests/schemeWorkbench.test.tsx`**：新增 `clickWorkflowTab(text)` 帮助函数 —— 先 `await screen.findByText(text)` 作为「就绪门」，再 `screen.getByText(text)` **重新查询当前挂载节点**，然后 `closest('[role="tab"]')` + `fireEvent.click`。将所有 `findByText(...) → closest → click` 的 Tab 点击路径（`gotoOutlineTab`、`runExportCheck`、`gotoExportTab`、`openPreview` 及各内联 `解析提取`/`导出文档`/`审核与预检` 点击）统一替换为 `await clickWorkflowTab(...)`。
- **断言逐字保留**：只换「怎么拿到 Tab 节点」，不换「断什么」（`工程概况` 出现、预检按钮存在、请求发起等断言未动），检测力不减。
- **生产代码零变更**：R145 实现（SplitPane/ResizeHandle/resizableLayout/GenTaskListPanel/5 区域接线/CSS）经复验保持原状；本会话对 `SchemeWorkbenchPage.tsx` 的猜测性改动（`userTabSelectedRef` 守卫 `pickInitialTab`）经诊断证伪后**全部回退**，`grep` 确认零残留。

### 4.4 修复验证

`schemeWorkbench.test.tsx`：**12 failed → 28 passed**（JSON reporter 复跑确认）；全量前端 86/87 files、1446/1447 tests（唯一失败为既有 `LogViewerPage` 并行会话项）。

## 七、判据教训归档

1. **「A/B 决定性对照」优先于猜测** —— 强制走无 SplitPane 分支立刻 28/28，定位 SplitPane 结构为诱因；移除 `GenTaskListPanel` 仍 12 failed，排除任务轮询；日志 `tab.isConnected=false` 一锤定音 stale-node。三步对照取代了「猜 `pickInitialTab` 竞态」的错误假设（该猜测性修复已回退）。
2. **R120 教训复证** —— `findByText`/`waitFor` 捕获的 DOM 引用可因数据落定再渲染而脱离文档树；规程是点击前重新查询当前挂载节点。R145 的额外渲染层放大此脆弱点，但根因是测试基建，不是功能缺陷。
3. **「移除组件验证」要选对嫌疑对象** —— 先移除 `GenTaskListPanel`（仍失败）排除轮询，再用 A/B 强制分支排除 SplitPane 结构本身，最后用日志定位 stale-node；逐层排除避免误判。
4. **猜测性修复必须可回退** —— `userTabSelectedRef` 守卫（假设 `pickInitialTab` 竞态）虽无害但无证据支撑，诊断证伪后全部回退，`grep` 零残留，避免留下无据变更。
