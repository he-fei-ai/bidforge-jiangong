# 审核与预检模块报告

> 模块定位：七步流水线第 6 步「质量门禁」（上传解析 → 提取项目 → 目录生成 → 全局事实 → 正文生成 → **审核预检** → 导出）。
> 报告生成日期：2026-10-01。基于 `backend/app/routers`、`backend/app/services`、`backend/app/schema_sql.py`、`backend/app/db.py` 与前端 `src/` 实际代码深度探索所得。

---

## 1. 模块边界与职责

本模块**不生成正文、不提取事实**，是「只读前序产物 + 写入结论 + 反馈失效」的守门层。由四路构成：

1. **程序化预检**（`preflight_engine`）：离线确定性规则，秒级、无 AI 调用。
2. **AI 语义判定**：合规检查（`/compliance/check`）、一致性审计（`/consistency-audit`）、专家论证（`/expert-review`）。
3. **人工审核工作流**（`review.py` 状态机 + `review_records` 留痕）。
4. **就绪度聚合**（`/overview` 六维加权评分 + 放行结论）—— 用户真正需要的「一个数字 + 一个结论」。

外加两条闭环修复链：

- **自动修复**（`review_autofix`）：按 `rule_id` 定位 → 改写 → 校验 → 落库 → 可回滚。
- **一致性修复**（`consistency_repair`）：扫描 → 仲裁 → 修复 → 确认/回滚。

三条「唯一事实源 / 约束」保证三态自洽：

- 规则注册表 = `audit_rules.py`（`RULE_VERSION` 管控跨版本可比性，当前 `1.7.0`）。
- 评分语义 = 仅由 `audit_scoring.py` 决定。
- 失效判据 = 仅由 `content_fingerprint`（`compliance.py:_content_fingerprint`）与 `review.reset_review_on_content_change` 决定。
- 分层约束 = services 不得 `import routers`（所有「写正文」动作返回 routers 层执行）。

## 4. 核心服务与调用关系

### 4.1 审核 `review.py`
- `_validate_transition`（L65）/ `_ALLOWED_TRANSITIONS`（L51）：状态机（含自流转幂等，9-21 四态自流转修复）。
- `_write_record`（L90）/ `_scheme_project_id`（L111）：`review_records` 留痕（G4/G5 补 `project_id`）。
- `reset_review_on_content_change`（L129，**关键**）：正文被改写后该章审核状态退回 `pending` 并留痕（G9）；被一致性修复、自动修复、正文生成复用。
- `submit_scheme_review`（L404）：方案级提交，含**预检门控**（L450-486：查 `blocked`/`released` + `content_fingerprint` 过期则 422）。顺序为「章节完整性 → 预检门控 → 状态机流转」（L421-426 修复），用户先得到最该处理的信息。
- `batch_review_sections`（L279）/ `review_section`（L362）：批量/单章流转。

### 4.2 预检 `preflight_engine.py`
- `run_preflight`（L679）：依次跑 7 个 checker —— `check_completeness`(CMP) / `check_standards`(STD) / `check_safety`(SAF) / `check_consistency`(CON) / `check_duplication`(CON-06) / `check_traceability`(TRC) / `check_deliverability`(DLV)，输出统一 finding 结构（L28-39 契约）。
- `_resolve_rule`（L153）→ `audit_rules._resolve_base_rule`：派生编号归一（如 `CON-05-1`，9-27 修复）。
- `compliance.py:_build_preflight_context`（L452）装配 `PreflightContext`；`readiness_overview`（L620）调用 `run_preflight` + `score_findings`。

### 4.3 合规检查 `compliance_check`
- `compliance_check`（L110）：一次 `/check` = 一个 `batch_id`（L187，根治批次截头 9-23）；`_normalize_ai_results`（L201）把 AI 自由编号归一到注册表。
- `_readiness_overview_compute`（L660，**聚合核心**）：程序化预检 + 导出预检（`collect_export_issues`/`export_issues_to_findings`，G1） + 最近一批 AI compliance（按 `batch_id` 取） + 最近一致性审计 + 未解决一致性扫描冲突 + 专家论证 → `review_autofix.capability_summary` 标注 → `score_findings` 评分。
- `_persist_run`（L846）：落 `preflight_runs`（G5 `project_id`、G3 `content_fingerprint`）。

### 4.4 一致性扫描 `consistency_scanner.py`（P0-1 增量缓存）
- `run_scan`（L559）：先 `_load_cached_rows`（L363）命中增量缓存 → 未命中章 `chunk_sections_for_scan`（L327）分批 + `asyncio.Semaphore` 并发（批失败按章回退） → `_save_cached_rows`（L401）upsert 缓存。
- `content_fingerprint`（L352）/ `context_fingerprint`（L356）：章节正文指纹 + 上下文（事实/资料/设计/规范）指纹；任一变即缓存失效。
- `persist_conflicts`（L536）：**upsert**（9-22 修复第二次扫描 C001 冲突仍保留已确认状态）。
- `consistency_repair.py:scan`（L74）调 `run_scan` + `arbiter.arbitrate_conflicts`；`repair`（L135）调 `repair_agent.run_repair` 后逐个 `reset_review_on_content_change`。

### 4.5 评分 `audit_scoring.py`
- `score_findings`（L105）：六维加权（block 40 / high 20 / medium 8 / low 2）；存在 block 时等级封顶 C 且 `released=False`（L150-163）。
- `merge_findings`（L197）：按 `rule_id` 去重。
- `ai_results_to_findings` / `expert_result_to_findings`：把 AI/专家结论转统一 finding。

## 7. 关键业务逻辑

### 7.1 审核状态机
- 四态：`pending` / `reviewing` / `approved` / `rejected`，由 `_ALLOWED_TRANSITIONS`（L51）+ `_validate_transition`（L65）约束，含自流转幂等（9-21 修复的四态自流转）。
- 方案级提交推进到 `approved` 时，严格要求「所有章节均 approved」（非状态非空），`reviewing`/`rejected` 不放行（L427-434）。

### 7.2 预检门控（提交前放行校验）
`submit_scheme_review`（L450-486）推进到 `approved` 时：
- `blocked` 为真 → 422「存在交付阻断项」。
- 无 `preflight_runs` → 422「尚未执行审核预检」。
- `content_fingerprint` 与实时指纹不一致 → 422「结论已过期，请重新运行一键总检」（旧库无指纹时回退 `sections.updated_at` 比对，L472-482）。
- `released=False` → 422「未达放行条件」（L483-486）。
- `released` 与 `content_fingerprint` 必须**同查**（只查其一会放过 C/D 级脏结论或漏判时间戳未变的脏数据，L451-452）。

### 7.3 内容指纹与失效闭环
- `_content_fingerprint`（`compliance.py`）：章节正文 + 图表 + 全局事实 + 字数预算 的统一版本锚点；事实确认/裁决/重解析后旧预检结论自动过期（`_run_is_stale`，L548）。
- `reset_review_on_content_change`（review.py:129）：正文变更（手动编辑/一致性修复/自动修复）→ 审核状态退回 `pending`。
- 自动修复/一致性修复改写正文后调用 `reset_review_on_content_change` + `invalidate_consistency_scan_cache`，使「改一章只重扫一章」。

### 7.4 一致性增量缓存（P0-1）
- 旧库无 `consistency_scan_cache` 表时退化为「每章必调 AI」（失效）。
- `content_hash` / `context_hash` 命中则跳过 AI，未命中章并发批扫；任一指纹变即缓存失效。

### 7.5 六维加权评分
- `score_findings`：block 40 / high 20 / medium 8 / low 2；存在 block → 等级封顶 C 且 `released=False`。
- 规则注册表 `audit_rules.py`（`RULE_VERSION=1.7.0`）是唯一事实源；与导出映射 `_EXPORT_ISSUE_RULE_MAP` 必须双向一致（漏登会让 finding 落兜底分支、dimension 塌陷、总分系统性偏移）。

## 9. 模块间依赖

- **← 前序（正文生成）**：`sse_handlers.py` 生成收尾自动置 `review_status='pending'` + 写 `review_records`（L6033-6080），并以 `auto_consistency_repair` 模式尾部触发 `run_scan`（L5896）+ 仲裁 + 修复。
- **← 前序（全局事实）**：`consistency_audit` 经 `_build_facts_text` 读 `global_facts`；`_content_fingerprint` 把 global_facts 状态纳入指纹 → 事实变更使旧预检过期。
- **→ 后序（导出）**：`export.collect_export_issues` 产出 `review_pending/review_rejected/review_missing` 等 issue → `export_issues_to_findings` 映射为 DLV-09/DLV-15 → 被 `/overview` 聚合进评分（G1 桥接）。导出预检消费一致性结论的路径是「经 readiness_overview 六维聚合」，而非导出直接读一致性表。
- **失效 → 重新生成/重审闭环**：`preflight_runs.content_fingerprint` 比对实时指纹 → `/submit` 门控拒绝过期结论；自动/一致性修复改写正文后强制审核退回 + 一致性缓存失效。

### 10.2 最易回归的三处

3. **`content_fingerprint` 过期判定三处必须同查**（compliance.py:895 注释：曾因 SELECT 漏列导致 `stale` 恒 False）。

### 10.3 分层约束
- services 不得 `import routers`（`review_autofix.py:724` 静态守护）。所有「写正文」动作返回 routers 层执行，并强制触发审核退回与一致性缓存失效，保证「生成→审核→导出」三态自洽。

## 12. 总结

审核与预检模块是专项方案「能否交付」的质量门禁，四路判定（程序化预检 / AI 语义 / 人工审核 / 就绪度聚合）共用同一规则注册表与同一套六维评分，辅以两条可回滚的闭环修复链（自动修复、一致性修复）。其健壮性高度依赖三条唯一事实源（规则注册表、评分引擎、`content_fingerprint`/审核退回判据）与 services 不反向依赖 routers 的分层约束。历史多轮（G1-G9、P0-1、批次截头、指纹过期）修复表明：模块最易回归的风险集中在「规则注册表与导出映射双向一致」「batch_id 取批」「指纹三列同查」三处，均已通过静态护栏 + 回归用例兜底。
